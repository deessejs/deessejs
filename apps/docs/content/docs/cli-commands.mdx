This page documents every command in the public CLI surface. The full surface stays small on purpose: four top-level commands plus a three-command `auth` group. Adding to either counts as a breaking change and goes through the release train.

Every command accepts `--json` for scripts. With this flag, the CLI skips prompts, spinners, and colour, then writes one JSON object to stdout. Errors use `{ ok: false, code, message, hint }`. The exit code follows the rules below, regardless of `--json`.

---

## `deessejs list`

Fetch the template registry and render it as a table.

```bash
deessejs list
```

### Flags

| Flag                | Effect                                                                              |
| ------------------- | ----------------------------------------------------------------------------------- |
| `--category <name>` | Filter to a single category. Unknown categories yield an empty list (not an error). |
| `--json`            | Emit `{ templates: TemplateV1[] }` instead of a table.                              |

### Output

A coloured table with one row per template: slug, owner/repo, short description, category. The footer prints the count and a hint about `--category` and `--json`.

### Exit codes

- `0`: success.
- `1`: `network_error` (registry unreachable after retries), `parse_error` (registry response didn't match the v1 contract), `internal`.

### Examples

```bash
deessejs list
deessejs list --category web
deessejs list --json | jq '.templates[].slug'
```

## `deessejs info <slug-or-github-url>`

Show validated fields from a template's `deesse-template.json`, then print the install command.

```bash
deessejs info next-app-starter
deessejs info https://github.com/owner/repository --ref main
```

### Arguments

| Argument               | Description                                                            |
| ---------------------- | ---------------------------------------------------------------------- |
| `<slug-or-github-url>` | Catalog template identifier, or HTTPS URL to a GitHub repository root. |

### Flags

| Flag             | Effect                                                                          |
| ---------------- | ------------------------------------------------------------------------------- |
| `--ref <branch>` | Inspect a branch or other Git ref. Defaults to the repository's default branch. |
| `--json`         | Emit `{ descriptor, source }` for either input form.                            |

### Output

A catalog slug and a direct GitHub URL show the same descriptor fields. The output includes the title, name, description, project type, version, optional author, license, category, labels, and source repository. JSON output includes the complete normalized descriptor.

Both input forms require a valid root `deesse-template.json`. For a catalog slug, the CLI uses a lightweight lookup instead of fetching the GitHub-enriched template listing. The `info` command reads the descriptor through GitHub's Contents API without downloading or inventorying the full repository. It checks the descriptor schema, declared repository, and include/exclude patterns. The command exits with an error if GitHub returns no descriptor or an invalid one. The `init` command resolves an immutable commit and checks any declared source ref before copying files.

The formatted view ends with the matching install command:

```
Install: deessejs init next-app-starter
Install: deessejs init https://github.com/owner/repository
```

### Exit codes

- `0`: success.
- `1`: `not_found` (slug doesn't exist in the registry. The error hints at the closest matches), `network_error`, `parse_error`, `template_invalid`, `internal`.

## `deessejs init <slug-or-github-url>`

Create a project from a template descriptor, detect the package manager, and install dependencies.

```bash
deessejs init next-app-starter
deessejs init https://github.com/owner/repository
```

### Arguments

| Argument               | Description                                                            |
| ---------------------- | ---------------------------------------------------------------------- |
| `<slug-or-github-url>` | Catalog template identifier, or HTTPS URL to a GitHub repository root. |

### Flags

| Flag             | Effect                                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------------- |
| `--pm <name>`    | Override detected package manager. One of `pnpm`, `npm`, `yarn`, `bun`.                                 |
| `--dir <path>`   | Target directory. Resolves relative to the current working directory. Default: `./<slug>`.              |
| `--ref <branch>` | Git ref to use. Default: the repository's default branch.                                               |
| `--no-install`   | Skip the install step. Useful for CI or pre-baked Docker images.                                        |
| `--force`        | Use an existing empty target directory. The CLI never removes existing files.                           |
| `--verbose`      | Show template resolution details and the package manager's full output during installation.             |
| `--json`         | Emit `{ ok, slug, dir, ref, installed }` on success or `{ ok: false, code, message, hint }` on failure. |

### Package manager detection

When you omit `--pm`, the CLI checks the generated project in this order:

1. The `packageManager` field in `package.json` (Corepack convention, such as `pnpm@9.0.0` or `bun@1.1.0`). The CLI uses the leading tool name and ignores the version.
2. lockfile presence: `pnpm-lock.yaml` → pnpm, `bun.lockb` → bun, `yarn.lock` → yarn, `package-lock.json` → npm.

If neither matches, the CLI aborts with `internal` and asks you to pass `--pm` explicitly.

### Behaviour

1. Resolve a catalog slug through the registry, or parse a GitHub repository URL directly.
2. Resolve the requested ref to an immutable GitHub commit and download its source archive.
3. Require `deesse-template.json`. Check its schema and use its include/exclude patterns to choose project files. Catalog slugs and direct URLs follow the same process. The CLI has no clone fallback.
4. Choose the target directory (`./<slug>` for catalog entries or `./<repository>` for direct URLs), unless you set `--dir`.
5. Copy the selected files into the target directory. If that directory already exists and you omit `--force`, the CLI aborts with `target_exists`.
6. Detect the package manager and run its install command. The CLI supports `pnpm install`, `npm install`, `yarn install`, and `bun install`. By default, it hides installer output. Pass `--verbose` to show it with the resolved source, ref, target path, commit, and selected file count. The CLI also reports these details when `--no-install` skips installation.

### Exit codes

- `0`: success (created + installed, or created only if `--no-install`).
- `1`: public codes (`not_found`, `network_error`, `parse_error`).
- `1`: internal codes (still exit 1, but with a different `code` field if you pass `--json`): `template_invalid`, `invalid_target`, `target_exists`, `target_not_empty`, `install_failed`, `internal`.

### Examples

```bash
# Default: scaffold into ./next-app-starter
deessejs init next-app-starter

# Custom directory
deessejs init next-app-starter --dir ./apps/web

# Force pnpm even if the template ships yarn.lock
deessejs init next-app-starter --pm pnpm

# Use a feature branch without installing
deessejs init next-app-starter --ref feat/new-thing --no-install

# CI usage
deessejs init next-app-starter --json --no-install | tee clone-result.json
```

## `deessejs auth`

Subcommand group for the device-flow sign-in. See [CLI: Authentication](/docs/cli-auth) for the full walkthrough including troubleshooting.

### `deessejs auth login`

Browser-based device-flow sign-in. Writes `~/.deessejs/auth.json` on success.

```bash
deessejs auth login
```

| Flag     | Effect                                                                                 |
| -------- | -------------------------------------------------------------------------------------- |
| `--json` | Emit `{ ok: true, user }` on success, `{ ok: false, code, message, hint }` on failure. |

Exit codes: `0` on success, `1` on any failure (`network_error`, `cli_device_denied`, `cli_device_expired`, `internal`).

### `deessejs auth status`

read-only diagnostic. Validates the cached bearer against the server and prints one of three terminal states (no session, valid, stale). Always exits `0`.

```bash
deessejs auth status
```

| Flag     | Effect                                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `--json` | Emit `{ ok, user?, fetchedAt? }`, `{ ok: false, reason: "no_session" }`, or `{ ok: false, reason: "session_invalid", stored }`. |

### `deessejs auth logout`

Invalidate the server-side session and delete the local token file. The CLI always deletes the local file, even if the server-side sign-out fails.

```bash
deessejs auth logout
```

| Flag     | Effect                                                                                             |
| -------- | -------------------------------------------------------------------------------------------------- |
| `--json` | Emit `{ ok: true }` on success, `{ ok: true, reason: "no_session" }` if nothing existed to revoke. |

Exit codes: always `0`. A non-2xx from the server's sign-out endpoint logs but doesn't change the exit code. Local cleanup remains the user-facing outcome.

## Error codes reference

The CLI returns only the error codes listed below. Treat this closed list as part of the public API. Adding a code counts as a breaking change. Use these values in your scripts:

| Code                 | Meaning                                                       | Remediation                                                            |
| -------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `not_found`          | A slug, template, or other identifier doesn't exist           | Check the spelling or run `deessejs list` to see available identifiers |
| `network_error`      | Network request failed after retries                          | Check connectivity and retry. The CLI already retries three times with jitter. |
| `parse_error`        | Server response didn't match the v1 contract                  | Likely a server-side regression. Open an issue.                        |
| `cli_outdated`       | Server requires a newer CLI                                    | Run `npm install -g @deessejs@latest`                                  |
| `cli_device_denied`  | You denied the device-flow request in the browser             | Re-run `deessejs auth login` and select Approve                        |
| `cli_device_expired` | The 30-minute device-code window elapsed                      | Re-run `deessejs auth login`                                           |

With `--json`, the CLI may also return internal codes (`template_invalid`, `invalid_target`, `target_exists`, `target_not_empty`, `install_failed`, `internal`). Treat these codes as implementation details. Their behavior may change without notice.

Every error response on `--json` carries a `hint` field with a human-readable remediation hint. Print it before exiting.

## Global flags

No global `--api-url` flag exists. The CLI always calls `https://app.deessejs.com/api/v1`. Integration tests can use custom base URLs. Production commands use the production host.
