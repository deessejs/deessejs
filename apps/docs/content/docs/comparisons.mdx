Most DeesseJS users arrive from one of three starting points: `create-t3-app`, the original `SaaS Template`, or a hand-rolled scaffold. This page calls out where DeesseJS converges and where it diverges.

## Comparing DeesseJS with create-t3-app

The `create-t3-app` CLI generates one Next.js app with the t3 stack: Prisma, NextAuth, and tRPC. DeesseJS offers a curated template registry through its CLI.

|         | `create-t3-app`                            | DeesseJS                                                         |
| ------- | ------------------------------------------ | ---------------------------------------------------------------- |
| Scope   | One Next.js app and stack                  | Multi-surface templates for web, mobile, edge, and AI.           |
| Stack   | t3 conventions (drizzle + tRPC + NextAuth) | drizzle + oRPC + Better Auth (similar shape, modernized choices).|
| Output  | A repo on disk                             | A repo on disk, plus a CLI you can re-run.                       |
| Auth    | NextAuth only                              | Better Auth + device-flow CLI login.                             |
| Updates | Re-run the CLI, accept new defaults        | `deessejs list` to see new templates, fork the new repo.         |
| Lock-in | Zero (no runtime service)                  | Zero (templates fork cleanly).                                   |

Choose `create-t3-app` for one Next.js app with the t3 stack. Choose DeesseJS for shared contracts across web, mobile, and AI apps. Its templates connect to one Better Auth instance.

## DeesseJS versus the original SaaS Template

DeesseJS forked from `deessejs/saas-template` in July 2026. The divergence map (`docs/engineering/plans/saas-template-divergence.md` in the source repo) records the changes and serves as the canonical reference.

What changed in the fork:

- **Identity**: copy, README wording, and the brand surface. The SaaS Template name disappears from DeesseJS-flavoured repos.
- **Contracts package layout**: auth, database, and email publish as workspace packages and version independently.
- **API surface**: Hono + oRPC mount at `/api/v1/`, with versioned Zod contracts in `@workspace/contracts/v1`. The original used ad-hoc route handlers.
- **Device-flow auth**: the CLI can authenticate with the web app without copying cookies.
- **CLI**: `@deessejs/cli` publishes to npm. The original offered no CLI. Users forked a template and edited it.

What stayed the same:

- Next.js App Router
- drizzle + Postgres
- Tailwind + shadcn/ui (now under `@workspace/ui`)
- Better Auth (the original used NextAuth. The DeesseJS team chose Better Auth for the device-flow plugin.)

## DeesseJS versus hand-rolled scaffolds

If you copy a previous project and tweak it, you have a hand-rolled scaffold. The trade-offs:

- **No audit trail.** When the original moves on, your fork drifts apart. DeesseJS templates version and re-list.
- **No shared contracts.** Your auth rules may differ from a partner's fork. DeesseJS templates share `@workspace/auth`, `@workspace/database`, and `@workspace/email` across the monorepo and each npm release.
- **No CLI surface.** A copy-pasted scaffold has no `deessejs list`, no `deessejs info`, no `deessejs auth login`. You either build those yourself or you don't have them.

Hand-roll a project when you need just one starter. Add a second surface or the CLI, and shared infrastructure starts to repay its cost.

## DeesseJS versus Vercel's `create-next-app`

`create-next-app` scaffolds a Next.js app with Vercel's defaults but no opinion on auth, database, or any cross-cutting concern. DeesseJS templates always include the contract stack. If you want a blank Next.js canvas, use `create-next-app`. If you want a working app with auth, database, and email already wired, use a DeesseJS template.

## Summary

DeesseJS combines opinionated starters and a CLI for teams shipping across web, mobile, edge, and AI. Shared contracts keep apps consistent. Teams adopt a single contract family and its infrastructure.
