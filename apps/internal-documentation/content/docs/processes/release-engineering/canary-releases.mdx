# Canary releases

The `@canary` channel publishes a bleeding-edge build of `@deessejs/cli` on every push to `staging`, without consuming changesets and without touching the `@latest` dist-tag. The canary job lives inside `release.yml` (the same workflow that handles `@latest` on `main`), gated on the source branch. There is no separate workflow file for canary.

## When this process applies

- A feature PR has been merged to `staging`.
- Anyone (maintainer, contributor, consumer) wants an installable bleeding-edge build of the staged work.

There is no on-demand trigger for the canary path anymore. The previous manual `workflow_dispatch` with `canary: true` is preserved for emergency dogfooding from a non-`staging` branch.

## Prerequisites

- Branch `staging` carries the work to ship.
- The Trusted Publisher for `@deessejs/cli` is configured against `.github/workflows/release.yml` on `https://www.npmjs.com/package/@deessejs/cli/access`. No second publisher entry is needed because there is no second workflow.
- A contributor has merged a PR touching CLI-relevant paths to `staging`, including a changeset (enforced by `changesets-check.yml`, see [ADR-026](../../decisions/ADR-026-changesets-merge-gate.mdx)).

## Procedure

### 1. The push to staging triggers the workflow

A merge (or direct push) to `staging` triggers `release.yml`. The workflow determines the channel by inspecting `github.ref`:

```yaml
on:
  push:
    branches: [main, staging]
```

The `if:` gate on the release job exempts the staging path from the `.changeset` filter that applies on the `main` path:

```yaml
if: |
  github.event_name == 'workflow_dispatch' ||
  github.ref == 'refs/heads/staging' ||
  contains(github.event.head_commit.message, '.changeset')
```

### 2. release.yml computes a synthetic version

The `Determine release channel` step inspects the source branch:

```bash
if [ "${{ github.event_name }}" = "workflow_dispatch" ] && [ "${{ inputs.canary }}" = "true" ]; then
  echo "dist_tag=canary"          >> "$GITHUB_OUTPUT"
  echo "release_type=prerelease"  >> "$GITHUB_OUTPUT"
  echo "version_source=synthetic" >> "$GITHUB_OUTPUT"
elif [ "${{ github.ref }}" = "refs/heads/staging" ]; then
  echo "dist_tag=canary"          >> "$GITHUB_OUTPUT"
  echo "release_type=prerelease"  >> "$GITHUB_OUTPUT"
  echo "version_source=synthetic" >> "$GITHUB_OUTPUT"
else
  echo "dist_tag=latest"        >> "$GITHUB_OUTPUT"
  echo "release_type=stable"    >> "$GITHUB_OUTPUT"
  echo "version_source=changeset" >> "$GITHUB_OUTPUT"
fi
```

The synthetic canary version `<base>-canary.<UTC-timestamp>.<short-sha>` is computed and written back to `apps/cli/package.json` via `jq`. Changesets are **not** consumed at this step; they stay available for the eventual `@latest` publish on `main`.

### 3. release.yml validates the base version

Before publishing, the workflow checks that `apps/cli/package.json#version` is a clean `X.Y.Z` semver (no pre-release suffix). The check reads from the committed tree (`git show HEAD:apps/cli/package.json`), not from the working tree, so a polluted value from a previous canary run cannot poison the check.

```bash
BASE=$(git show HEAD:apps/cli/package.json | jq -r '.version')
if ! echo "$BASE" | grep -Eq '^[0-9]+\.[0-9]+\.[0-9]+$'; then
  echo "::error::apps/cli/package.json#version is '$BASE', expected X.Y.Z."
  exit 1
fi
```

If a previous run left the file dirty (e.g. `2.1.0-canary.x.y.z`), this step fails the job with a clear message instead of publishing a chained version. See [ADR-025](../../decisions/ADR-025-auto-canary-on-staging.mdx#base-version-guards) for the rationale.

### 4. release.yml publishes under the canary dist-tag

```bash
npm publish --tag canary --provenance --no-git-checks
```

Provenance is attached. `--no-git-checks` prevents the publish from failing on the dirty working tree.

### 5. release.yml re-pins @latest defensively

After the canary publish completes, the workflow re-pins `@latest` to its previous value (reads it from `npm view @deessejs/cli@latest version`). This guards against any accidental tag move in step 4.

### 6. release.yml restores the package.json version

The canary rewrite in step 2 leaves `apps/cli/package.json` set to the synthetic version. After the publish succeeds, the workflow rewrites the file back to the committed base version:

```bash
BASE=$(git show HEAD:apps/cli/package.json | jq -r '.version')
CURRENT=$(node -e "console.log(require('./package.json').version)")
if [ "$CURRENT" != "$BASE" ]; then
  jq --arg v "$BASE" '.version = $v' package.json > package.json.tmp
  mv package.json.tmp package.json
fi
```

The published tarball is already on npm; only the next canary run sees the clean base. Without this restore, the next run would compute `<synthetic>-canary.<new-timestamp>.<new-sha>`, producing a suffix chain that grows without bound.

### 7. release.yml reads the version for tagging

The `Read new version` step reads from `steps.canary-version.outputs.canary_version` (the synthetic value computed in step 2), not from `package.json`. Reading from the file would yield the base (because step 6 has just reset it) and the tag would name the wrong release.

### 8. release.yml creates a GitHub Release

```bash
gh release create release/v<canary-version> --prerelease
```

The release is marked `prerelease: true`. The tag format matches the `@latest` flow for tooling consistency.

## Manual on-demand (deprecated)

The previous on-demand path — `workflow_dispatch` on `release.yml` with `canary: true` — still works. It triggers the same canary implementation but on whatever commit the dispatch references, not on the latest `staging` push. Use it for emergency dogfooding on a non-`staging` branch (for example, a feature branch that you want to test without merging).

## Artefacts

- A `@deessejs/cli@canary` version on npm, with provenance, that does not consume changesets.
- A `release/v<canary-version>` git tag on the merge commit.
- A GitHub Release marked `prerelease: true`.
- `apps/cli/package.json#version` is rewritten in place during the workflow and reset to the prior value when the workflow completes.

## Retention

Canary builds accumulate on npm until manually deprecated. There is no automatic cleanup. To prune:

```bash
npm deprecate @deessejs/cli@<canary-version> "Superseded by @deessejs/cli@<latest-version>"
```

Within 72 hours of publish, `npm unpublish @deessejs/cli@<canary-version>` is also available. After 72 hours, deprecate instead.

With the auto-trigger, the rate of accumulation increases. Expect several canarys per week. A periodic cleanup is recommended: run `npm deprecate` on canarys older than 14 days, or build a small GitHub Action that does it on a cron.

## Recovery

**Trusted publisher does not accept the new staging trigger:** the publisher is keyed on the workflow file path, not on the branch. If `release.yml` is the configured publisher, both staging and main pushes publish successfully. If the publish fails, verify the OIDC configuration on `https://www.npmjs.com/package/@deessejs/cli/access`.

**Canary version collides with an existing dist-tag:** the `npm publish` step rejects the duplicate. Bump the UTC timestamp suffix by pushing a new commit.

**`@latest` dist-tag was accidentally moved during step 3:** the defensive re-pin in step 4 catches this in the same workflow run. If the workflow aborts before step 4, manually re-pin:

```bash
npm dist-tag add @deessejs/cli@<previous-latest-version> latest
```

**A push to staging does not trigger the canary:** the `if:` filter exempts staging from the `.changeset` gate, so this should not happen. If it does, verify that `release.yml` is enabled in the Actions tab and that no other workflow file shadows it.
