# Release engineering

This process covers shipping `@deessejs/cli` from a merged PR on `staging` to a tagged release on `main`, plus the two auxiliary channels (`@canary` and per-PR previews) that give contributors and consumers installable builds before the next `@latest` lands.

## When this process applies

- A PR touching `apps/cli/**` has been merged to `staging` and the maintainer is ready to promote a release.
- A reviewer or consumer needs an installable preview of a PR before approval.
- A maintainer needs to publish a `@canary` build for dogfooding.
- A bad version on npm has to be yanked or deprecated.

## Prerequisites

- Branch `staging` is up to date with the work to ship.
- The contributor added a `.changeset/<slug>.md` file if their PR changed the CLI's public surface (the `changesets-check.yml` workflow enforces this).
- The maintainer has `gh` CLI authenticated and write access to the repository.
- The npm Trusted Publisher is configured for `@deessejs/cli` on `https://www.npmjs.com/package/@deessejs/cli/access`.
- `NPM_CONFIG_PROVENANCE=true` is available to GitHub Actions via OIDC.

## Procedure

### 1. Promote staging to main

After the PR is approved and CI is green on `staging`, a human creates the promotion PR or runs the merge:

```bash
gh pr create --base main --head staging --title "chore: promote staging to main" --body "Promotes the latest staging work to main for release."
```

The PR review confirms no `staging`-only commits are missing from `main`, then merges. This step is **human-owned** per `AGENTS.md`; agents do not run it.

### 2. Verify the release workflow runs

`.github/workflows/release.yml` triggers on push to `main` when the commit message contains `.changeset`. The job does, in order:

```bash
pnpm install --frozen-lockfile
pnpm changeset version           # bumps apps/cli/package.json#version, regenerates CHANGELOG.md, deletes consumed .changeset/*.md
pnpm changeset publish --provenance --access public
git tag -f release/v{VERSION}
gh release create release/v{VERSION} --generate-notes
```

`{VERSION}` is read from `apps/cli/package.json#version` after step 2.

### 3. Verify artefacts

After the workflow completes:

- `npm view @deessejs/cli@latest version` returns the new version.
- The `release/v{VERSION}` tag is present on the merge commit.
- A GitHub Release exists with autogenerated notes.
- `apps/cli/CHANGELOG.md` lists the new entry at the top.

### 4. Publish a canary build (on demand)

When a maintainer needs a bleeding-edge build for dogfooding:

1. Open the Actions tab → `release.yml` → **Run workflow** → check ☑ `canary`.
2. The workflow computes `<base>-canary.<UTC-timestamp>.<short-sha>`, rewrites `apps/cli/package.json#version` in place via `jq`, and publishes with `--tag canary --provenance --no-git-checks`.
3. The workflow defensively re-pins `@latest` to its previous value after canary publish.
4. A GitHub Release tagged `release/v<canary-version>` is created with `prerelease: true`.

Canarys accumulate on npm until manually deprecated. There is no automatic cleanup.

### 5. Per-PR previews (automatic)

`.github/workflows/cli-preview.yml` triggers on every `pull_request` against `staging` or `main`, but only when the PR touches one of the following paths:

```yaml
paths:
  - "apps/cli/**"
  - "packages/contracts/**"
  - "packages/api/**"
  - ".github/workflows/cli-preview.yml"
  - "pnpm-lock.yaml"
```

The `pnpm-lock.yaml` entry matters: a catalog bump that changes effective CLI output must trigger a new preview even when no source file under `apps/cli/**` changed.

The job uses a concurrency group keyed on the PR number with `cancel-in-progress: true`. A new push to the PR cancels the previous preview build and replaces it. Previews are therefore idempotent per PR: only the latest commit is reflected in the install address.

Build scope is the CLI and its transitive workspace deps, in topological order:

```bash
pnpm turbo build --filter=@deessejs/cli
```

Tests and lint are deliberately not run here. They are covered by `ci.yml`, and the publish path runs `cli-publish-verify.yml` separately on PRs that touch release-config files.

The workflow then uploads the tarball:

```bash
pnpm exec pkg-pr-new publish ./apps/cli --pnpm --compact --bin --comment=off --json output.json
```

Flags rationale:

- `--pnpm` is required because the workspace uses pnpm catalogs.
- `--compact` shortens the install URL.
- `--bin` renders `npx ...` form in the PR comment instead of `npm i ...`.
- `--comment=off` disables pkg-pr.new's default sticky comment so this workflow can post its own richer one (four package managers, link to commit, stable marker).
- `--json output.json` feeds the comment-posting step.

After upload, the workflow posts or updates a sticky PR comment with the marker `<!-- pkg-pr.new -->`. The marker lets the workflow detect a prior comment from an earlier push on the same PR and edit it in place instead of creating a new one. The body contains install instructions for `pnpm` (open by default), `npm`, `yarn`, `bun`, plus a link to the commit.

Security: the workflow runs with `contents: read` and `pull-requests: write`. It does **not** request `id-token: write`. pkg.pr.new authenticates via its own GitHub App, separate from npm Trusted Publishing. A compromise of this workflow's secrets cannot affect the `@latest` or `@canary` release paths.

Previews live on pkg.pr.new's infrastructure (Cloudflare R2), not on npm. Retention is best-effort: roughly one month without a download, or six months of age, whichever comes first.

## Artefacts

From the `@latest` flow:

- A new `@deessejs/cli` version on npm with provenance attestation.
- A `release/v{VERSION}` git tag on the merge commit.
- A GitHub Release with autogenerated notes.
- An updated `apps/cli/CHANGELOG.md`.

From the `@canary` flow:

- A `@deessejs/cli@canary` version on npm, with provenance, that no-op consumes changesets (the `@latest` line stays intact).
- A `release/v<canary-version>` git tag.
- A GitHub Release marked `prerelease: true`.

From the per-PR preview flow:

- A tarball uploaded to pkg.pr.new (Cloudflare R2), addressed by commit SHA.
- A sticky PR comment with install instructions for `pnpm`, `npm`, `yarn`, `bun`.

## Recovery

**Provenance rejected (403 from npm):** the Trusted Publisher is not configured. Open `https://www.npmjs.com/package/@deessejs/cli/access` and complete the OIDC configuration, then re-run the workflow.

**Lockfile drift:** `pnpm install --frozen-lockfile` fails. Run `pnpm install` locally, commit the lockfile change, and re-trigger the workflow.

**`apps/cli/package.json#private: true` left in place:** changesets refuses to publish. Verify the field is `false` before re-running.

**Workflow misbehaves and a release must still go out today:** use the [manual fallback](../../../../documents/internal/process/release-engineering.md#manual-fallback) — publish from a maintainer machine, accept the loss of provenance for that one release, and file an issue to repair `release.yml`.

**Within 72 hours of a bad publish:** `npm unpublish @deessejs/cli@x.y.z` removes the version entirely.

**After 72 hours:** `npm unpublish` is no longer allowed. Use `npm deprecate @deessejs/cli@x.y.z "Critical bug: see <link> — upgrade to x.y.z+1"` and record the yank in the next release notes.

**Stale preview comment on a PR:** the comment was not updated after the latest push. The most likely cause is a `<!-- pkg-pr.new -->` comment that was authored by a fork contributor (the bot does not run with `pull-requests: write` on forks). Close and re-open the PR, or have a maintainer push a follow-up commit to retrigger the workflow.

**Preview workflow fails on pkg.pr.new unreachable:** pkg.pr.new's infrastructure is third-party. The CLI release path is unaffected (no shared auth, no shared secret). Retry once, and if it persists, document the gap in the PR review and rely on `ci.yml` + `cli-publish-verify.yml` for the gate.
