---
title: middleware composition
description: Group or not, and when each is right.
---

A study of the patterns for grouping middleware in a Hono
app. Built on the upstream Hono docs and the Hono source,
specifically `src/middleware/combine/` and the `compose`
machinery. The upstream page is the source of truth when the
lib changes; this entry exists to show when to group the
middleware chain and when to leave it separate.

## The question

Given a chain of middleware applied to every request:

```ts
api.use("*", requestId())
api.use("*", secureHeaders())
api.use("*", cors({ origin: serverEnv.ALLOWED_ORIGINS, credentials: true }))
api.use("*", honoLogger())
api.use("*", session())
```

Should the codebase wrap this in a single `app.use("*", compose(...))`,
or use a helper that groups the five middleware, or leave it as-is?

## The short answer

**Leave them as separate `app.use` calls.** The composition
cost happens once per request when `compose()` walks the
matched middleware array, regardless of whether the array has
five entries or one. Grouping offers no runtime savings.

The PR [Hono PR #495](https://github.com/honojs/hono/pull/495) shows that
Hono has even **removed** an internal `await` on the composed
function to avoid the per-request cost. The takeaway:
Hono's composition runs cheaply already, and adding an extra
`compose(...)` layer on top is a no-op for performance.

## When to group

Three real reasons exist to group middleware, and none of
them concern performance.

### 1. Conditional branching, `hono/combine`

The `some`, `every`, and `except` helpers serve **conditional
composition** (try A or B, run A and B together, or run A
unless X). They don't serve grouping a fixed chain.

```ts
import { some, every } from 'hono/combine'
import { bearerAuth } from 'hono/bearer-auth'
import { myRateLimit } from '@/rate-limit'

app.use(
  '/api/*',
  some(
    myCheckLocalNetwork(),
    every(bearerAuth({ token }), myRateLimit({ limit: 100 })),
  ),
)
```

Use `some` / `every` / `except` when the composition is
**conditional**. Don't use them to merge a fixed chain, since
they add an `await` and a try/catch with no functional gain.

### 2. Logical grouping, application-level helper

If the chain has a clear **name** (a layer of concerns), a
helper factory is the right shape:

```ts
// In packages/api/src/http/middleware/index.ts (or a compose helper)
export const requestPipeline = () =>
  sequence(
    requestId(),
    secureHeaders(),
    cors({ origin: serverEnv.ALLOWED_ORIGINS, credentials: true }),
    honoLogger(),
    session(),
  )

// In packages/api/src/index.ts
api.use("*", requestPipeline())
```

This isn't about performance; it's about giving the chain
a name and a single edit point. The cost is the same five
`compose()` walks per request. The gain is a meaningful
`requestPipeline` symbol in the composer.

Use a helper when the chain is **named, repeated, or
mutated as a unit**. A one-off chain of five middleware in
the composer doesn't need a helper.

### 3. Domain-scoped middleware, `app.use(path, mw)`

Path-scoped middleware is a different operation, not a
grouping. The dispatcher **excludes** non-matching routes
from the match result, which reduces per-request composition
work. Use it when a middleware applies only to a subset of
routes (for example `/api/*` for rate limiting, `/auth/*` for
session).

## What the cost is

Per the Hono source (`src/compose.ts`), the dispatcher:

1. Walks the matched middleware array recursively.
2. Updates `context.req.routeIndex` at each step.
3. Awaits each middleware's `next()` and unwinds the stack.

For five middleware on every route, all five match on
every request. The cost is five `await next()` awaits
and five function calls. This runs cheaply; the per-request
cost stems from the handler itself, not from the
middleware count.

The risk of **adding** a `compose(...)` layer is that the
indirection makes the chain harder to read with no measurable
gain. The inline note in `compose.ts` mentions that the dispatch
path runs optimised already.

## Recommended shape for the API

The current `packages/api/src/index.ts` shape is correct:

```ts
api.use("*", requestId())
api.use("*", secureHeaders())
api.use(
  "*",
  cors({ origin: serverEnv.ALLOWED_ORIGINS, credentials: true }),
)
api.use("*", honoLogger())
api.use("*", session())
```

Each line is **what it does**, not **how it composes**. A
reader can scan the chain at a glance. The dispatcher
optimises the cost.

If the chain grows to 10+ middleware or the same chain
appears in many places, **then** extract a helper:

```ts
// http/middleware/pipeline.ts
export const securityPipeline = () =>
  sequence(
    requestId(),
    secureHeaders(),
    cors({ origin: serverEnv.ALLOWED_ORIGINS, credentials: true }),
    honoLogger(),
    session(),
  )
```

Still, the threshold is "duplicated or named," not "more
than five." Five middleware in a row is fine.

## What this entry isn't

This is a knowledge-base entry, not an ADR. The decision to
keep the chain separate is a **discipline**, not a
load-bearing invariant. If a future contributor wants to
extract a helper, the extraction runs as a refactor and isn't
architecturally significant. The structural decision lives
in ADR-004; the operational pattern lives here.
