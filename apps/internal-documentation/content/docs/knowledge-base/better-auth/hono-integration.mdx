# Better Auth + Hono integration

A study of how Better-Auth mounts inside a Hono app. Built
on the upstream Better-Auth docs, this entry exists to show
the shape of the integration, the conventions the codebase
follows, and the divergences that a contributor needs to
know about.

## Mount the handler

`auth.handler` runs on every request under `/auth/*` and
handles the Better-Auth HTTP surface (login, signup, session,
etc.).

```ts
api.on(["POST", "GET"], "/auth/*", (c) => auth.handler(c.req.raw))
```

The route mounts at the API's base path. A catch-all in
the host app forwards the request to the Hono app, which
dispatches to the Better-Auth handler.

## Cross-origin resource sharing

CORS configures at the Hono level, not the Better-Auth
level. Better-Auth expects cross-origin requests to get
authorization at the framework layer.

```ts
api.use(
  "*",
  cors({ origin: serverEnv.ALLOWED_ORIGINS, credentials: true }),
)
```

The allowed origins get validated at the env-package
boundary. CORS registers **before** the auth routes,
per the Better-Auth timing contract: the framework must
approve the cross-origin headers before the Better-Auth
handler reads the request.

## middleware, populate `c.var.user` and `c.var.session`

The session middleware runs once per request and populates
the typed context variables, so downstream middleware and
procedures can read them without re-issuing
`auth.api.getSession({ headers })`.

```ts
export const session = (): MiddlewareHandler => async (c, next) => {
  const data = await auth.api.getSession({ headers: c.req.raw.headers })
  c.set("user", data?.user ?? null)
  c.set("session", data?.session ?? null)
  await next()
}
```

`user` and `session` are `null` (not `undefined`) when the
request lacks authentication, giving consumers a predictable
shape. The `?? null` form works better than an explicit
early return because it makes the unconditional `await
next()` at the end stand out, with no hidden exit path.

## Typing the Hono environment

The codebase follows the official Better-Auth pattern, derived from the
auth instance config:

```ts
import type { AuthInstance } from "@workspace/auth"

export type ApiEnv = {
  Variables: {
    requestId: string
    user: AuthInstance["$Infer"]["Session"]["user"] | null
    session: AuthInstance["$Infer"]["Session"]["session"] | null
  }
}
```

`AuthInstance["$Infer"]["Session"]` is the type Better-Auth
derives from the auth config. A change in the session
schema flows through automatically, with no manual edit
here.

**Don't augment Hono's `ContextVariableMap` globally.** The
per-app `Variables` generic on `new Hono<ApiEnv>()` is enough.
Global augmentation is explicitly discouraged by the Hono
docs: it adds types to every context, even where the
setting middleware never ran, hiding runtime `undefined`
behind a typed contract. See [Hono Context API](https://hono.dev/docs/api/context).

The `?? "unknown"` fallbacks in the error handler and rate
limiter are honest , the global error handler runs before
the request-id middleware, so the request-ID variable is
genuinely `undefined` at that point.

[ADR-003](../../decisions/ADR-003-hono-env-typing.md) codifies the decision.

## Consuming the typed values in routes

A procedure downstream reads the typed context:

```ts
// oRPC procedure
export const getProfile = base.handler(async ({ context }) => {
  return context.user
})
```

The user field types as
`AuthInstance["$Infer"]["Session"]["user"] | null`. A
non-null assertion requires going through a guard middleware
that narrows the type and throws on unauthenticated access.

## Client-side configuration

The web app and the CLI build their oRPC client via
`<app>/src/lib/orpc.ts`. No special Hono-client setup
applies: the typed client (`@orpc/client`) handles cookie
forwarding automatically because the auth session is a
Better-Auth cookie managed by `auth.handler`.

## Cross-domain cookies

By default, Better-Auth sets `SameSite=Lax`. For
cross-subdomain setups (for example `app.deessejs.com`
calling `api.deessejs.com`), set
`crossSubDomainCookies.enabled` in the auth config; see
the upstream docs. This is a Better-Auth config change,
not a Hono change.

## What this entry isn't

This is a knowledge-base entry, not an ADR. It documents how
Better-Auth and Hono work in the current version of the
lib, and the shape of the integration. The **decisions**
(which patterns this entry covers and why) live in
`docs/engineering/architecture/decisions/`. When a future
change conflicts with this entry, the entry is wrong, not
the code.
