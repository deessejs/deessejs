# Better Auth test-utils

A study of the `testUtils()` plugin from Better-Auth. Built
on the upstream docs, this entry exists to show the shape
of the integration and the discipline that keeps the plugin
out of production.

## What `testUtils()` offers

The plugin doesn't register HTTP routes. It adds
privileged server-side helpers on `ctx.test`:

- **Factories**. `createUser`, `createOrganization`, build
  objects with sensible defaults, no DB write.
- **Database helpers**. `saveUser`, `deleteUser`,
  `addMember`, persist and remove records.
- **Auth helpers**. `login`, `getAuthHeaders`, `getCookies`,
  create authenticated sessions and return the headers
  needed to hit a protected route.
- **OTP capture**. `captureOTP: true` (the codebase doesn't
  use this; see "What the codebase uses" below).

## Where it lives in this repo

The plugin isn't in the production auth config. A separate
test-only auth instance wires it in, alongside its own
database connection. Keeping the plugin in a separate file
preserves type inference for `ctx.test` without adding
the plugin to the production auth config.

```ts
import { betterAuth } from "better-auth"
import { testUtils } from "better-auth/plugins"

export const auth = betterAuth({
  // ... same config as prod ...
  plugins: [testUtils()],
})
```

Tests import the `auth` from the test setup, not from the
production auth; the production auth doesn't expose
`ctx.test`, by design. The TypeScript inference stays intact
because `testUtils()` lives in a statically defined
`plugins` array (no conditional spread), per the upstream
caveat about inference.

## What the codebase uses

The auth-package tests exercise the helpers:

```ts
const ctx = await auth.$context
expect(ctx.test.createUser).toBeTypeOf("function")
expect(ctx.test.saveUser).toBeTypeOf("function")
expect(ctx.test.deleteUser).toBeTypeOf("function")
expect(ctx.test.login).toBeTypeOf("function")
expect(ctx.test.getAuthHeaders).toBeTypeOf("function")
```

```ts
const user = ctx.test.createUser({ email: "reset@example.com" })
await ctx.test.saveUser(user)
// ... exercise the forgot-password flow ...
await ctx.test.deleteUser(user.id)
```

The factories return defaults that match the schema, so
`createUser()` without arguments yields a verified user
with a generated email, enough for any test that doesn't
care about the values.

## What the codebase skips on purpose

- **No `captureOTP: true`**, the email-sending path in the
  test config runs as a fire-and-forget stub. Capturing OTPs
  in memory wouldn't change the assertions the codebase
  makes today, so the codebase doesn't pay the
  verification-hook complexity.
- **No `createOrganization` / `addMember`**, this repo runs
  as a single-tenant app. The organization plugin isn't
  installed, so these helpers aren't available and aren't
  needed.
- **No sharing the test auth with the production auth**, the
  upstream recommendation is explicit: keep `testUtils()`
  in a separate file so it doesn't ship with the prod
  server. The codebase follows this rule.

## What isn't yet written

The pattern works for testing the **auth package** itself.
It doesn't yet work for testing **API procedures that read
user/session**, the procedures that need
`await test.login(...)` to mint a real session and then
read `auth.api.getSession({ headers })` inside the
procedure.

The blocking work is twofold:

1. The API package's tests don't yet have any test that
   goes through the typed oRPC client.
2. The test database and the test setup wire into the
   auth package. A test in the API package that wants a
   real user would either need its own setup (duplication)
   or a shared test-helper package. Neither exists yet.

The intended approach, when the codebase gets there, is:

```ts
// (sketch, not yet written)
import { call } from "@orpc/server"
import { router } from "@workspace/api/router"

it("returns the templates list to an authenticated caller", async () => {
  const user = await testAuth.$context.then((c) => c.test.createUser())
  const { headers } = await testAuth.$context.then((c) =>
    c.test.login({ userId: user.id }),
  )

  const result = await call(router.templates.list, undefined, {
    context: {
      headers: new Headers(headers),
      user: null,
      session: null,
      requestId: "test",
    },
  })

  expect(result.templates).toBeInstanceOf(Array)
})
```

## What this entry isn't

This is a knowledge-base entry, not an ADR. It documents how
`testUtils()` works in the current version of the lib, and
the shape of the integration. The **decisions** (which
patterns this entry covers and why) live in
`docs/engineering/architecture/decisions/` and
`docs/engineering/architecture/rules/`. When a future
change conflicts with this entry, the entry is wrong, not
the code.
