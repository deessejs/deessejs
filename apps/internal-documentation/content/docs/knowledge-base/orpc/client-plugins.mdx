# oRPC client plugins

A study of the official client plugins oRPC publishes for
transport-layer concerns. Built on the upstream oRPC docs,
this entry exists to document the plugin surface and the
gap between what the plugins cover and what the CLI's
custom fetch hook ([KB entry](./fetch-hook)) does today.

## Plugin shape

`RPCLink` accepts the plugins via the `plugins` array. Each
plugin is a class with configuration options; the same link
can compose many.

{/* vale off: Vale.Terms, code block uses lowercase @orpc package name */}
```ts
import { RPCLink } from "@orpc/client/fetch"
import { ClientRetryPlugin } from "@orpc/client/plugins"

const link = new RPCLink({
  url: "https://api.example.com/rpc",
  plugins: [
    new ClientRetryPlugin({
      default: { retry: 2, retryDelay: 1000 },
    }),
  ],
})
```
{/* vale on */}

A plugin's `default` block sets the fallback for every
procedure; the typed client call's `context` argument
accepts per-call overrides.

## ClientRetryPlugin

The general-purpose retry plugin. Configurable per
procedure or globally. Documented at
[orpc.dev/docs/plugins/client-retry](https://orpc.dev/docs/plugins/client-retry).

```ts
import {
  ClientRetryPlugin,
  ClientRetryPluginContext,
} from "@orpc/client/plugins"

interface ORPCClientContext extends ClientRetryPluginContext {}

const link = new RPCLink<ORPCClientContext>({
  url: "https://api.example.com/rpc",
  plugins: [
    new ClientRetryPlugin({
      default: {
        retry: ({ path }) =>
          path.join(".") === "planet.list" ? 2 : 0,
      },
    }),
  ],
})
```

Options:

| Option | Default | Purpose |
|---|---|---|
| `retry` | `0` | Cap on retry attempts before throwing. |
| `retryDelay` | `(o) => o.lastEventRetry ?? 2000` | Delay between retries in ms. |
| `shouldRetry` | `true` | Filter to decide which failures retry. |

`shouldRetry` is the lever for status-code filtering.
Default retry-all-failures is rarely what you want; the
CLI would set:

```ts
shouldRetry: ({ failure }) =>
  failure.status >= 500 ||
  failure.status === 429
```

The plugin does **not** read HTTP headers to compute the
delay. It uses the static `retryDelay` function. For
custom rate-limit headers (`X-RateLimit-Reset`, vendor
extensions), the plugin isn't enough.

## RetryAfterPlugin

Specialized for rate-limit responses. Documented at
[orpc.dev/docs/plugins/retry-after](https://orpc.dev/docs/plugins/retry-after).

```ts
import { RetryAfterPlugin } from "@orpc/client/plugins"

const link = new RPCLink({
  url: "https://api.example.com/rpc",
  plugins: [
    new RetryAfterPlugin({
      condition: (response) =>
        response.status === 429 || response.status === 503,
      maxAttempts: 5,
      timeout: 5 * 60 * 1000,
    }),
  ],
})
```

Defaults:

| Option | Default | Purpose |
|---|---|---|
| `condition` | `status === 429 \|\| status === 503` | Which status codes trigger a retry. |
| `maxAttempts` | `3` | Cap on retry attempts. |
| `timeout` | `5 * 60 * 1000` | Cap on total time spent retrying. |

The plugin reads the standard `Retry-After` header
(RFC 7231 §7.1.3) to compute the delay. It doesn't
read `X-RateLimit-Reset` or any vendor-specific header;
if the server uses those, the plugin uses its own delay
logic.

## Coverage vs the CLI's custom fetch

The CLI's `apps/cli/src/api/retry.ts` and
`apps/cli/src/api/client.ts` together do the following:

| Capability | Where it lives today | Covered by plugins? |
|---|---|---|
| Retry on `5xx` | `fetchWithRetry` (lines 86-89) | Yes, via `ClientRetryPlugin.shouldRetry`. |
| Retry on `429` | `fetchWithRetry` (lines 72-84) | Yes, via `RetryAfterPlugin.condition` (default). |
| Read `Retry-After` (seconds) | Not implemented today | Yes, `RetryAfterPlugin` reads it. |
| Read `X-RateLimit-Reset` | `fetchWithRetry` (lines 75-79) | **No.** Plugins read `Retry-After`, not custom headers. |
| `User-Agent` header | `fetchWithRetry` (line 48) | Partial. The `RequestHeaders` plugin (see sidebar) injects static headers but doesn't interpolate the installed CLI version. |
| Jitter on retry delay | `fetchWithRetry` (lines 18, 23-24) | No. Plugin delay is a constant or a function of `lastEventRetry`. |
| Cap retry delay at 30s | `fetchWithRetry` (line 78) | No. Plugin timeout is total, not per-attempt. |
| Atomic retry + cache fallback | `apps/cli/src/cache/index.ts` + `fetchTemplates` | Out of scope for plugins; the cache is application-layer, above the fetch hook. |

**About 70% of the wrapper's behavior matches what the
official plugins cover.** The remaining 30% is what
justifies keeping the custom hook:

- `X-RateLimit-Reset` is the header the CLI's server
  actually sends. The plugin reads the standard
  `Retry-After` instead. Switching to the plugin would
  mean either changing the server to send `Retry-After`,
  or adding a custom condition callback that derives the
  delay from the response headers.
- Jitter and per-attempt caps protect against thundering
  herd when many `CLIs` retry the same endpoint at once.
  The plugin's `retryDelay` is a constant or a function;
  it doesn't cap per-attempt or jitter.
- The `User-Agent` header carries the installed CLI
  version (read at runtime from the bundled package).
  The plugin layer injects static headers, not
  per-process values without an interceptor.

## When to migrate to the plugins

A migration makes sense when the upstream server sends
standard `Retry-After` headers (not `X-RateLimit-Reset`)
and the deployment doesn't need jitter. Until then,
keeping the custom hook is the lower-risk choice.

If a future contributor migrates, the migration looks
like:

1. Replace `apps/cli/src/api/retry.ts` (delete the file).
2. Replace `apps/cli/src/api/client.ts` with a thin
   `RPCLink` constructor that adds `ClientRetryPlugin`
   and `RetryAfterPlugin`.
3. Keep `apps/cli/src/api/self-version.ts` (the runtime
   `User-Agent` source) and feed its value into the
   `RequestHeaders` plugin via a closure.
4. Update `apps/cli/test/http/fetch-templates.test.ts`
   to mock the plugins instead of `fetchWithRetry`.

The migration is a one-PR change once the server contract
moves to `Retry-After`.

## What this entry isn't

This is a knowledge-base entry, not an ADR. It documents
the official oRPC plugins in the current version of the
lib, and the gap between the plugins and the CLI's
custom implementation. The **decisions** (which approach
this entry covers today and when to migrate) live in
`docs/engineering/architecture/decisions/`. When a future
change conflicts with this entry, the entry is wrong, not
the code.
