# oRPC fetch hook

A study of the `RPCLink.fetch` option, the hook oRPC exposes
for transport-layer concerns. Built on
{/* vale off: Vale.Terms, URL contains lowercase orpc */}
[orpc.dev/docs/client/rpc-link](https://orpc.dev/docs/client/rpc-link)
{/* vale on */}
, the upstream page is the source of truth when the lib
changes; this entry exists to surface the parts of the API
that bite contributors and to document the wrapper shape
the CLI uses.

## What the hook is for

`RPCLink` builds the request URL, serializes the procedure
input, parses the wire envelope, and decodes the typed
response. The `fetch` option is the single injection point
for everything that happens **on the wire**: HTTP headers,
auth tokens, retries, rate-limit handling, telemetry,
observability.

Without a custom fetch, `RPCLink` falls back to
`globalThis.fetch`. That works for happy-path calls. For
anything that needs to be resilient or observed on the
wire, the hook is where the work goes.

## The signature

The hook isn't `(request, init) => Response`. It's
five arguments, taken straight from
`@orpc/client/adapters/fetch/index.d.ts`:

```ts
fetch?: (
  request: Request,
  init: { redirect?: Request["redirect"] },
  options: ClientOptions<T>,
  path: readonly string[],
  input: unknown
) => Promise<Response>
```

| Argument | Purpose |
|---|---|
| `request` | The outgoing `Request` oRPC built (URL + headers + body). |
| `init` | The `RequestInit` shape oRPC will pass to `fetch`. Used by `RPCLink` for `redirect` overrides. |
| `options` | Per-call oRPC context (headers, interceptors, plugins). Surfaced for plugin and interceptor use; the CLI ignores it. |
| `path` | The procedure path segments as an array (for example `["templates," "list"]`). Surfaced for plugin and interceptor use; the CLI ignores it. |
| `input` | The serialized input for the procedure. Surfaced for plugin and interceptor use; the CLI ignores it. |

The last three arguments exist to let interceptors and
plugins read per-call state without re-parsing the request.
A wrapper that doesn't need them should accept them with
`_` prefixes (TypeScript convention) and ignore them.

## The hidden pitfall

A wrapper typed `(request, init) => Response` won't
match the hook signature. The compile-time error is easy
to silence:

```ts
// DANGER: silences the signature mismatch.
const orpcFetch: typeof fetch = async (request, init) => {
  return globalThis.fetch(request, init)
}
```

The runtime behavior breaks: oRPC calls the hook with
five arguments; the wrapper accepts two; the extra
arguments get discarded. For most calls this works
because JavaScript doesn't enforce argument arity. But
when oRPC later changes the contract (a new option, an
extra metadata argument), the wrapper drops the
new value and the behavior diverges from what the typed
client expects.

The CLI learned this the hard way: commit
`9b003da wip(cli,web): migrate to @orpc/client + RPCLink
(broken, see issue)` shipped a wrapper with the wrong
signature masked by a cast. The plan
`docs/engineering/plans/orpc-client-migration.md` Phase 1.4
documents the lesson as: **the wrapper signature comes
from `@orpc/client` directly, no re-declaration**.

## The CLI wrapper

`apps/cli/src/api/client.ts` exports `orpcFetch`, the
adapter the CLI uses. Its responsibilities are limited to
the wire boundary:

1. Normalize the request shape. `RPCLink` may pass either
   a `string` URL or a `Request` instance, depending on the
   call site. The wrapper accepts both and builds a single
   `Request` shape.
2. Read the request body once. The `Request.body` is a
   stream that nothing can consume twice. The wrapper
   reads it via `req.text()` and passes the string to the
   inner retry helper. A second read throws.
3. Delegate to `fetchWithRetry`. The retry helper owns
   the actual HTTP resilience: retry on 5xx, retry on 429
   honoring `X-RateLimit-Reset`, jitter, and the
   `User-Agent` header.
4. Reconstruct the `Response`. The wrapper returns a
   `Response` object with `content-type: application/json`
   so the typed client can parse the body. Without the
   explicit content-type, oRPC throws a parse error.

The wrapper is the **only** place in the CLI that talks to
the network. The retry helper (`apps/cli/src/api/retry.ts`)
is the only place that knows about HTTP status codes. The
contract decoding is the only place that knows about the
wire envelope. The split keeps each concern testable and
replaceable.

## What the hook isn't for

- **Business-logic middleware.** Things like auth headers
  derived from a token store, tracing spans, or per-tenant
  rate limits belong to oRPC's client middleware
  (`client.use(...)`), not to the fetch hook. The hook
  runs at the transport layer; client middleware runs at
  the procedure layer.
- **Contract decoding.** oRPC handles the wire envelope
  inside `RPCLink` after the hook returns. The hook should
  not parse JSON, check shapes, or throw typed errors.
- **Caching.** The CLI's disk cache (`apps/cli/src/cache/`)
  sits **above** the hook in the call stack: the cache
  returns a cached payload before the hook is invoked. The
  hook isn't the right layer for cache reads or writes.

## Common question, should the team replace the hook with a
plugin?

oRPC publishes two official plugins that cover most of
what the wrapper does: `ClientRetryPlugin` and
`RetryAfterPlugin`. The companion KB entry
[oRPC client plugins](./client-plugins) covers them. The short answer
is that the plugins cover about 70% of the wrapper's
behavior. The remaining 30% (custom rate-limit header,
User-Agent injection, jitter) justifies keeping
the hook as the implementation layer. A future migration
to the plugins is possible once oRPC exposes hooks for
custom rate-limit headers; until then, the custom hook is
the right choice.

## What this entry isn't

This is a knowledge-base entry, not an ADR. It documents
how `RPCLink.fetch` works in the current version of the
lib, and the shape of the integration the CLI uses. The
**decisions** (which patterns the team picked and why) live in
`docs/engineering/architecture/decisions/`. When a future
change conflicts with this entry, the entry is wrong, not
the code.
