# Tokens

The design system has one token layer: CSS variables declared in `packages/ui/src/styles/globals.css`, mapped to Tailwind v4 utility classes via `@theme inline`. Components consume utility classes only. They never reference token values directly. See [ADR-020](./decisions/ADR-020-design-system) §2 for the lock.

The page organises tokens by family. Each family lists the variables in the source file and the rule of use. The intent is "do not invent a new token; pick the one that fits" — not "read every variable once".

## Color

`oklch()` everywhere. The lightness channel drives contrast; chroma and hue are for identity. Two semantically distinct families are layered:

| Family | Variable shape | Used for |
|---|---|---|
| Solid neutral + state | `--background`, `--foreground`, `--primary`, `--destructive`, ... | Page surface, text fills, icons. |
| Subdued neutral | `--secondary`, `--muted`, `--accent`, ... | Sub-surfaces, hovered rows, description text. |

A neutral palette is the base. State colors are first-class siblings of `--destructive`, not bolt-ons. The set:

| Token | Role |
|---|---|
| `--destructive` | Error and confirm-destructive action. |
| `--success` | Confirmed-positive state, success toast, valid badge. |
| `--info` | Informational state, info toast, neutral notice. |
| `--warning` | Cautionary state, warning toast, attention callout. |

Each pairs with a `-foreground` token. The naming follows the existing `--primary`/`--primary-foreground` pattern; the `Sidebar` family at the bottom of `globals.css:86-153` follows the same shape for sidebar-internal surfaces.

Two rules compose:

1. Components never reference hardcoded values. `bg-[#fff]`, `text-zinc-900`, `rgb(0 0 0 / 0.04)` in a primitive — review-reject.
2. App-level CSS may extend the cascade (MDX-prose scope, font import, brand logo) but may not redeclare a semantic token in a different unit. `apps/app/app/globals.css` is the named exception to forbid (see [ADR-020](./decisions/ADR-020) §5a).

Contrast guidance lives in [`DESIGN.md`](../../../../../DESIGN.md) §2.3 (oklch lightness gap, APCA Lc thresholds, WCAG AA / AAA). Light bg → foreground L ≤ 0.45; dark bg → foreground L ≥ 0.75; verify with a contrast calculator before merge.

## Typography

Geist Sans for UI and prose, Geist Mono for code and tabular data. No serif. The typeface is loaded by the consuming app (`apps/web/src/app/layout.tsx` ships the reference wiring via `next/font`) and wired through `font-sans` / `font-mono` Tailwind classes generated by `@theme inline`.

Four voices define the scale. Each voice has a role; the role dictates when it applies.

| Voice | Role | Sizes |
|---|---|---|
| Heading | Page and section titles. Tracking tightens as size grows. | 14, 16, 20, 24, 32, 40, 48, 56, 64, 72 |
| Label | Single-line scannable text. Pairs with icons. | 12, 13, 14, 16, 18, 20 |
| Copy | Multi-line body text. Taller line-height than Label. | 13, 14, 16, 18, 20, 24 |
| Button | Button labels only. | 12, 14, 16 |

The classes are `text-heading-N`, `text-label-N`, `text-copy-N`, `text-button-N` (and `-mono` variants on Label and Copy). The `-mono` variants are paired with their sans counterpart (`label-14-mono` pairs with `label-14`). The sans variants carry a "Subtle" or "Strong" suffix in the spec when relevant.

Three rules apply to every voice:

1. `copy-14` and `label-14` cover ~80% of all text. Deviating from these is a deliberate design choice, not a default.
2. Never set `font-size`, `font-weight`, or `line-height` by hand. Always use a token class.
3. Use `<strong>` inside copy or label for a "Strong" modifier — the Geist pattern.

App-level density is allowed inside the voice system: `apps/web` marketing may use `text-heading-72` for its hero and `text-heading-48` for section titles; `apps/app` dashboard tops out at `text-heading-24` or `text-heading-20`. Both choices stay in the voice system. The two apps have **same tokens, distinct densities**. See the consumer map on [the index page](./index).

Tabular Mono. There is no design-system rule pinning when to pick a `-mono` variant. The contract is the `-mono` variants exist as Label-13-mono, Label-14-mono, Label-12-mono, Copy-13-mono; an app that wants tabular figures in a column uses them. Anything beyond that is an app-level decision. The asymmetry is a known limit of the spec: `DESIGN.md` §2.5 claims "always use Geist Mono" for tabular figures, but the design system does not ship a way to enforce that claim — call it out in [pitfalls](./pitfalls) §"Tabular figures are a typing discipline, not an enforced rule".

## Geometry

### Spacing

Four-pixel base. The scale is `4, 8, 12, 16, 24, 32, 40, 64, 96` mapped to `gap-*`, `p-*`, `m-*`, `space-*` Tailwind classes. The rhythm is **8 inside a group, 16 between groups, 32 to 40 between sections**. Container max-width is 1200 px, centered, with side padding growing at wide breakpoints.

### Radius

`--radius: 0.625rem` is the single base; Tailwind v4 generates the scale (`rounded-xs` through `rounded-4xl`) from it via `@theme inline`. The contract is **"consume the Tailwind classes Tailwind gives you"**, not "pick from a hand-curated table". The Geist-named tiers in `DESIGN.md` §2.6 are the spec's intent; the code contract is Tailwind's auto-derivation.

One app-wide rule: one radius family per view. Do not mix `rounded-xs` and `rounded-2xl` inside a single screen.

### Elevation

Three shadow tokens. Hierarchy comes from tonal surfaces + borders first; shadows are the lightest layer on top.

| Token | Use |
|---|---|
| `shadow-card` | Raised cards (`0 2px 2px rgb(0 0 0 / 0.04)` light). |
| `shadow-popover` | Popovers, menus, dropdowns. |
| `shadow-dialog` | Modals, dialogs. |

Pair each elevation with its matching radius — `shadow-card` + `rounded-sm`, `shadow-popover` + `rounded-md`, `shadow-dialog` + `rounded-lg`.

## Motion

Two token surfaces.

| Token | Value | Use |
|---|---|---|
| `--ease-geist` | `cubic-bezier(0.175, 0.885, 0.32, 1.1)` | All functional transitions. Slight overshoot, never spring physics. |
| `0ms` (default), `150`, `200`, `300`, `400+ms` | Durations | State changes vs. fades vs. reveals vs. page transitions. |

Tailwind v4 ships `animate-spin`, `animate-ping`, `animate-pulse`, `animate-bounce` natively; custom animations declared in `@theme` generate matching utilities. `tw-animate-css` provides the `data-state=open` / `data-state=closed` keyframe utilities that Radix-based primitives consume (`accordion`, `dialog`, `popover`, `sheet`).

For interactive motion — spring physics, drag, layout animations, choreography — reach for `motion` (the npm package). The DS does not own Motion as a dependency; apps that need it add it locally and consume its APIs (`whileHover`, `whileTap`, `AnimatePresence`, `LayoutGroup`, `useScroll`). See `DESIGN.md` §3.5.

**Reduced motion** is the fourth token, in a sense. Wrap state-changing animation classes in `motion-safe:` (apply when the user does not prefer reduced motion) or `motion-reduce:` (apply when they do). The `prefers-reduced-motion` media query is honoured by Tailwind's variant.

## Chart palette

`--chart-1` through `--chart-5` are declared in `globals.css` as semantic colors. No chart component ships today. The palette is kept because the day an app needs a chart, the colors are already aligned with the rest of the surface. Documented here so future contributors do not strip them as dead weight.

## Where the tokens live

| Concern | File |
|---|---|
| Color tokens (light + dark) | `packages/ui/src/styles/globals.css:86-153` |
| Tailwind utility mapping | `packages/ui/src/styles/globals.css:10-84` (the `@theme inline` block) |
| Sidebar family | same file, last block of `:root` and `.dark` |
| Typography scale | `packages/ui/src/styles/globals.css:12-43` (in `@theme inline`) |
| Easing | declared in the consuming app's `@theme inline` if needed; default Tailwind easing otherwise |
| Spacing, radius, shadows | Tailwind v4 defaults + `@theme inline` overrides |

A PR that adds a new semantic token edits the file at the path above and the corresponding row in the tables on this page in the same PR.
