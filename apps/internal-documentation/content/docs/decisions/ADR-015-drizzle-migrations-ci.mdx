# ADR-015: Drizzle migrations in CI

## Status

Proposed (2026-08).

## Context

`packages/database/` is the load-bearing boundary for every table the
monorepo reads and writes. The schema covers two sources: the
first-party tables defined in `packages/database/src/schema/` and the
Better Auth tables generated by `npx @better-auth/cli generate` and
merged into the same schema. Both feed the same Drizzle journal at
`packages/database/drizzle/`.

The migration scripts exist locally: `db:generate` produces SQL, and
`db:migrate` applies it. The integration job
(`.github/workflows/ci.yml#test-integration`) boots an ephemeral
Postgres, runs both, and exercises the auth and API packages. This
proves that migrations apply cleanly on a fresh database. It does not
prove anything about the production database.

Three concrete failure modes the current setup misses:

1. **Schema drift on a PR.** A contributor edits
   `packages/database/src/schema/auth.ts` (or any other schema file),
   commits the schema, and forgets `db:generate`. The integration
   job in CI starts from a fresh database; it regenerates against the
   just-edited schema, so the missing migration never surfaces. The
   schema and the journal are out of sync by the time the PR merges.
   The first place this breaks is production.

2. **Migration collisions across branches.** Two contributors each
   run `db:generate` from the same parent commit. Each generates a
   new SQL file in a different folder. Git merges cleanly because
   the files have distinct paths. The resulting journal depends on
   apply order, and the database state at the end of the merge is
   not the database state any of the two branches produced in
   isolation. The integration job does not catch this; the journal
   is consistent by construction in any single-branch context.

3. **Migrations applied manually, drift between local and
   production.** Today, applying migrations to staging or production
   is a manual local step. A contributor applies the migration
   locally against a personal database, commits the SQL, but the
   staging database is never updated until a human remembers. The
   staging app then starts against an older schema and fails. There
   is no signal in CI that staging is behind.

The repo's staging-first workflow (`AGENTS.md`) requires that staging
be the integration branch and that production be promoted from it
manually. The migration story has to fit inside this flow. The
current implementation does not.

## Decision

Three changes land together. They are gated so each one is useful on
its own; together they close the loop.

### 1. A drift check on every PR

A new workflow
(`.github/workflows/drizzle-check.yml`) runs on every
`pull_request` against `main` or `staging`. The workflow installs
dependencies, runs `drizzle-kit check`, then runs `drizzle-kit
generate` a second time and asserts the working tree stays clean.

```yaml
on:
  pull_request:
    branches: [main, staging]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: pnpm/action-setup@v6
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      # Validates the migration journal for commutativity and ordering.
      - run: pnpm --filter @workspace/database db:check
      # Re-runs generate against the committed schema. If the schema
      # changed without a matching migration, generate produces new
      # files and git diff --exit-code fails the step.
      - run: pnpm --filter @workspace/database db:generate
      - run: git diff --exit-code packages/database/drizzle
```

The check has two layers because each catches a different class of
bug. `db:check` validates the existing journal for commutativity
and ordering issues between migrations already on disk. The second
layer detects the case the first cannot: a schema change that did
not produce a matching migration. The PR is blocked either way.

The second layer uses `git diff --exit-code` on the whole
`packages/database/drizzle` directory. It deliberately does not
exclude `_journal.json` or any snapshot: if `db:generate` rewrites
them on a fresh run, that rewrite is the signal. Drizzle's
default prefix is `index`, so snapshots are numbered
`0000_snapshot.json`, `0001_snapshot.json`, etc. There is no safe
static allowlist of snapshot filenames to skip.

#### TTY risk during `db:generate`

`drizzle-kit generate` can prompt interactively when it detects a
column rename ("is this a rename or a new column?"). On a
non-interactive CI runner the prompt blocks until the job times
out or the process crashes on EOF. `drizzle-kit generate` does not
expose a documented `--no-prompt` or `--yes` flag.

The mitigation is contributor discipline, not CI config: the
contributor who edits a schema file must run `pnpm db:generate`
locally before pushing, answer the prompt, and commit the SQL.
The drift gate then re-runs `db:generate` against the committed
schema; if the schema is already in sync with the committed
migrations, no prompt fires because there is no diff.

The workflow is added to the required checks for both `main` and
`staging` in branch protection.

### 2. Auto-apply migrations on push to staging

A second workflow
(`.github/workflows/db-migrate-staging.yml`) runs on every push to
`staging`. The workflow installs dependencies, prints the SQL of
the migrations added in this push for audit, then runs
`drizzle-kit migrate` against the staging database.

```yaml
on:
  push:
    branches: [staging]
concurrency:
  group: db-migrate-staging-${{ github.ref }}
  cancel-in-progress: false
jobs:
  migrate:
    runs-on: ubuntu-latest
    env:
      DATABASE_URL: ${{ secrets.STAGING_DATABASE_URL }}
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: pnpm/action-setup@v6
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter @workspace/database build
      # Audit: print only the SQL files added by THIS push.
      # If the push touches no migration files, log a clear empty
      # line and skip the audit block.
      - name: Audit pending migrations
        run: |
          NEW=$(git diff --name-only "${{ github.event.before }}" "${{ github.sha }}" \
            -- 'packages/database/drizzle/*.sql')
          if [ -n "$NEW" ]; then
            echo "=== Migrations applied by this push ==="
            for f in $NEW; do
              echo "--- $f ---"
              cat "$f"
            done
          else
            echo "No new migrations in this push."
          fi
      - run: pnpm --filter @workspace/database db:migrate
```

The audit step uses `git diff --name-only` between the previous
and current commit on `staging`. It only prints SQL files that
were actually added by this push, so:

- A push that bundles multiple migrations prints all of them, in
  the order they were added. No more `tail -1` hiding batch
  migrations.
- A push that touches no migration prints a clear
  "No new migrations in this push." line. No more stale SQL from
  three weeks ago polluting the audit trail.

The `cat` of each migration is the audit trail. Every CI run
prints the SQL that was about to be applied, so the GitHub Actions
log captures the intent. If a migration lands that the reviewer
did not see in the PR, the log shows it.

The workflow is gated on `staging` only. A push to `main` does not
apply migrations; production migrations remain a manual step until
the team is comfortable with the staging auto-apply. The staging
auto-apply is the lower-risk half of the loop. Promotion to a
production auto-apply is a separate decision.

#### Network prerequisite

The workflow requires the GitHub-hosted runner to reach the
staging database. If staging runs on AWS RDS, GCP Cloud SQL, or
any provider inside a private VPC with no public IP, a standard
`ubuntu-latest` runner cannot connect. Two valid resolutions:

- Expose the database through a tunnel (Tailscale, Cloudflare
  Tunnel) that the runner reaches via a known hostname.
- Use a self-hosted runner inside the same VPC.

The `STAGING_DATABASE_URL` secret is provisioned at implementation
time, alongside one of the two resolutions above.

#### Ordering with the app deploy

The staging auto-apply workflow runs migrations only. The
application deploy is a separate workflow (today, manual; in the
future, possibly automated). For the expand-and-contract pattern
to work, the order must be:

1. Migrations apply to the staging database.
2. The new app version starts against the updated schema.

A migration that adds a nullable column is backward-compatible
with the old app version, so the order can be relaxed. A
migration that drops a column is NOT backward-compatible; the old
app must be retired before the drop migration runs. This is the
core of expand-and-contract, documented in the dedicated section
below.

### 3. Destructive-SQL lint on PRs

The third change is a static-analysis gate against destructive
SQL in the migration files. It does NOT live in `drizzle.config.ts`.

The earlier draft proposed `strict: true` as a guard against
destructive migrations. That proposal was incorrect. To clarify
what `strict` actually does:

- In `drizzle-kit` v0.31 (the version pinned in this repo's
  `pnpm-workspace.yaml` catalog), `strict` is a config field for
  `drizzle-kit push`. It causes push to prompt for confirmation
  before applying statements that would sync the schema with the
  database. It has no effect on `drizzle-kit migrate`.
- `drizzle-kit migrate` does not inspect the AST of the SQL
  files. It runs them in order. A `DROP TABLE` or `DROP COLUMN`
  inside a committed `.sql` file is applied silently.
- In `drizzle-kit` v1.0 beta, `strict` in config is silently
  ignored, and via CLI it throws a deprecation error. It is not a
  stable protection mechanism.

The right gate is a SQL linter that runs against the files in
`packages/database/drizzle/*.sql` on every PR. Two proven
candidates:

- **Squawk** (`squawkhq/squawk`): Postgres-aware linter that flags
  `DROP TABLE`, `DROP COLUMN`, `ALTER TABLE … DROP NOT NULL`,
  missing `IF EXISTS`, lock-taking operations, and similar
  patterns. Has a GitHub Action. Free, MIT.
- **Atlas migrate lint**: a more general migration linter; heavier
  to integrate.

The implementation picks Squawk. The workflow adds a step after
the drift check:

```yaml
      - uses: squawkhq/squawk-action@v1
        with:
          # Fail the PR on any warning, not just errors.
          fail-on: any
```

Squawk is configured per-project via `squawk.toml` at the repo
root. The configuration starts strict and is loosened only by an
explicit ADR (typical exceptions: `DROP TABLE` on tables the
team has marked as ephemeral, like `_drizzle_migrations` itself).

### What this rule forbids

Three things are out of scope for this ADR:

- **A production auto-apply.** The staging auto-apply is the
  proposal. Production stays a manual step until the team has
  observed the staging auto-apply for at least one month and has
  validated that the audit step, the Squawk gate, and the PR drift
  gate together catch the failure modes the team cares about. The
  follow-up ADR is filed in the "Future work" section.
- **A preview database per PR.** Neon branching and Supabase
  branching both offer a database-per-PR pattern. They are the
  right answer when the team needs to exercise the app against
  schema changes that cannot be applied to a shared staging
  database (destructive migrations, data backfills). The cost is
  roughly a developer-week per provider integration plus a monthly
  hosting line item. The staging auto-apply covers the schema-drift
  and collision cases; the preview-DB pattern covers the destructive
  migration case. The two are complementary; this ADR is the first
  half.
- **Removing the manual local apply.** Local development still uses
  `pnpm db:generate && pnpm db:migrate` against the developer's
  personal database. The CI workflows do not replace the local
  workflow; they gate the local workflow's output.

## Consequences

- **Every PR that touches `packages/database/src/schema/**` is
  blocked at the drift gate if the schema changed without a
  matching migration**. The gate catches failure mode 1 before
  merge. False positives are possible (a contributor edits the
  schema and re-generates the migration in the same commit); the
  signal in that case is no signal, which is the desired behavior.
- **Every PR that adds destructive SQL to a migration file is
  blocked by Squawk**. The gate catches failure mode 2's
  destructive variant at PR time. The reviewer can override
  Squawk with an explicit `squawk-allow` comment plus a follow-up
  issue, but the override is visible in the PR conversation.
- **Every push to `staging` applies pending migrations against the
  staging database**. Failure mode 3 disappears for staging. The
  audit step (`git diff` of added SQL files) puts every applied
  migration in the CI log, scoped to the push that introduced
  them.
- **The integration job remains the contract test for the migration
  path on a fresh database**. The new workflows do not replace it.
  The new workflows assert the production-shaped path: existing
  journal, new SQL, apply against an external Postgres.
- **`drizzle.config.ts` is unchanged**. The earlier draft proposed
  `strict: true`; that proposal was incorrect and has been
  retracted. No Drizzle config field protects `migrate` against
  destructive SQL. The protection lives in Squawk, outside Drizzle.
- **The Better Auth table changes go through the same gate**.
  `npx @better-auth/cli generate` writes to the same schema
  directory and the same Drizzle journal. A contributor who updates
  the Better Auth config without regenerating hits the same drift
  failure as a schema edit without regeneration.
- **Destructive migrations must follow the expand-and-contract
  pattern**. With Squawk on, a single-commit column drop fails
  CI. The contributor is forced to split: add nullable, ship the
  app change, then backfill, then drop. The pattern is documented
  in the ADR for posterity.

## Expand-and-contract for destructive changes

Two changes in particular must always land as multiple PRs:

1. **Renaming a column.** First PR adds the new column nullable,
   ships the app writing to both columns, backfills data in a
   separate batch. Second PR sets the new column to `NOT NULL`
   (after a `NOT VALID` + `VALIDATE CONSTRAINT` for large tables)
   and drops the old column. Both PRs pass the drift gate, the
   Squawk lint, and the staging auto-apply.

2. **Adding a `NOT NULL` constraint on a populated table.** First
   PR adds the column nullable and backfills. Second PR runs
   `ADD CONSTRAINT ... NOT VALID` followed by `VALIDATE CONSTRAINT`
   on a separate statement. Third PR (if needed) sets the
   column-level `NOT NULL`. Each PR's SQL is reviewed independently.

This is the same pattern documented in Drizzle's production guides.
The CI gate enforces it because Squawk is on.

## Cost

The drift-gate workflow runs in roughly one minute on a clean PR.
The staging auto-apply runs in roughly 90 seconds including
checkout and install. Both are cheap enough to run on every PR and
every staging push respectively.

The implementation is roughly:

- 30 minutes for `drizzle-check.yml` plus the branch protection
  update.
- 30 minutes for `db-migrate-staging.yml` plus the
  `STAGING_DATABASE_URL` secret and the network prerequisite.
- 30 minutes for the Squawk action plus `squawk.toml` at the repo
  root.
- 30 minutes for the documentation update (`packages/database/README`
  if it exists, or the schema file's leading comment).

Total: under two hours. The first run on a real PR surfaces any
false-positive risk; the second run is a confirmation.

## Future work

Three extensions are out of scope here but worth flagging:

1. **Production auto-apply.** A symmetric workflow that runs on
   push to `main` and applies against `secrets.PRODUCTION_DATABASE_URL`.
   The gate is the team's confidence in the staging auto-apply
   after one month of observed runs.
2. **Preview database per PR.** A Neon or Supabase integration
   that provisions a database per PR, applies migrations against it,
   and tears it down on close. Necessary for destructive migration
   PRs that cannot be safely applied to a shared staging database.
   The cost is the provider integration plus the monthly hosting
   line item.
3. **A `drizzle-migration-guard` GitHub Action.** The community
   project (`saudademjj/drizzle-migration-guard`) does a deeper
   cross-branch collision check than `drizzle-kit check`. It is
   worth adopting once it stabilizes; today it is single-maintainer
   and the API surface is small enough to read. Tracked here so
   the next iteration picks it up without re-justifying.

## How to verify

After the three changes land:

1. Open a PR that edits a schema file but does not regenerate a
   migration. The drift-gate workflow fails the PR with a clear
   diff in the log.
2. Open a PR that edits a schema file and regenerates a migration in
   the same commit. The drift-gate workflow passes; the
   integration job applies the migration against its ephemeral
   Postgres; the staging auto-apply runs on merge to staging and
   applies against the staging database.
3. Open a PR that adds a `DROP TABLE foo;` line to a migration
   file. The Squawk action fails the PR with a clear warning.
   The contributor splits the change into an additive migration
   plus a follow-up contract migration after the app retires
   `foo`.
4. Push to `staging` that bundles three migrations. The audit log
   shows all three SQL files, in order. Push to `staging` that
   touches no migration files. The audit log shows
   "No new migrations in this push."
5. `pnpm db:check` continues to pass locally. The check is the
   first line of defense for commutativity bugs; the CI gate is
   the second.
