# ADR-015, drizzle migrations in continuous integration

## Status

Proposed (2026-08).

## Context

`packages/database/` is the load-bearing boundary for every table the
monorepo reads and writes. The schema covers two sources: the
first-party tables defined in `packages/database/src/schema/` and the
Better Auth tables generated by `npx @better-auth/cli generate` and
merged into the same schema. Both feed the same drizzle journal at
`packages/database/drizzle/`.

The migration scripts exist locally: `db:generate` produces SQL, and
`db:migrate` applies it. The integration job
(`.github/workflows/ci.yml#test-integration`) boots an ephemeral
Postgres, runs both, and exercises the auth and API packages. This
proves that migrations apply cleanly on a fresh database. It doesn't
prove anything about the production database.

Three concrete failure modes the current setup misses:

1. **Schema drift on a PR.** A contributor edits
   `packages/database/src/schema/auth.ts` (or any other schema file),
   commits the schema, and forgets `db:generate`. The integration
   job in CI starts from a fresh database; it regenerates against the
   just-edited schema, so the missing migration never surfaces. The
   schema and the journal are out of sync by the time the PR merges.
   The first place this breaks is production.

2. **Migration collisions across branches.** Two contributors each
   run `db:generate` from the same parent commit. Each generates a
   new SQL file in a different folder. Git merges cleanly because
   the files have distinct paths. The resulting journal depends on
   apply order, and the database state at the end of the merge is
   not the database state any of the two branches produced in
   isolation. The integration job doesn't catch this; the journal
   is consistent by construction in any single-branch context.

3. **Migrations applied manually, drift between local and
   production.** Today, applying migrations to staging or production
   is a manual local step. A contributor applies the migration
   locally against a personal database, commits the SQL, but the
   staging database is never updated until a human remembers. The
   staging app then starts against an older schema and fails. There
   is no signal in CI that staging is behind.

The repo's staging-first workflow (`AGENTS.md`) requires that staging
serve as the integration branch and that the team promote production
from staging manually. The migration story has to fit inside this flow. The
current implementation doesn't.

## Decision

Three changes land together. The gating keeps each one useful on
its own; together they close the loop.

### 1. A drift check on every pull request

A new workflow
(`.github/workflows/drizzle-check.yml`) runs on every
`pull_request` against `main` or `staging`. The workflow installs
dependencies, runs `drizzle-kit check`, then runs `drizzle-kit
generate` a second time and asserts the working tree stays clean.

```yaml
on:
  pull_request:
    branches: [main, staging]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: pnpm/action-setup@v6
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      # Validates the migration journal for commutativity and ordering.
      - run: pnpm --filter @workspace/database db:check
      # Re-runs generate against the committed schema. Bounded
      # timeout because a missed db:generate on a column rename
      # makes generate prompt on stdin, which would otherwise block
      # until the job-level 360-minute timeout fires.
      - name: Detect schema drift
        timeout-minutes: 2
        run: |
          pnpm --filter @workspace/database db:generate
          if [ -n "$(git status --porcelain packages/database/drizzle)" ]; then
            echo "Schema drift detected: uncommitted migrations or snapshots."
            git status --porcelain packages/database/drizzle
            exit 1
          fi
```

The check has two layers because each catches a different class of
bug. `db:check` validates the existing journal for commutativity
and ordering issues between migrations already on disk. The second
layer detects the case the first can't: a schema change that did
not produce a matching migration. The CI blocks the PR either way.

The second layer uses `git status --porcelain` on
`packages/database/drizzle`. This catches modifications AND
newly added files (a freshly created `0004_*.sql` and
`meta/0004_snapshot.json` show up as `??`). It does
not exclude `_journal.json` or any snapshot: if `db:generate`
rewrites them on a fresh run, that rewrite is the signal. drizzle's
default prefix is `index`, so snapshots accumulate as
`0000_snapshot.json`, `0001_snapshot.json`, etc. No safe
skip-list of snapshot filenames to skip exists, and the snapshot
list grows with every migration, so nobody can maintain it by
hand.

`git diff --exit-code` isn't a substitute: it only inspects
already-tracked files, so a brand-new migration file would slip
past.

#### Teletype risk during `db:generate`

`drizzle-kit generate` can prompt interactively when it detects a
column rename ("is this a rename or a new column?"). On a
non-interactive CI runner the prompt blocks until the job-level
default timeout (360 minutes) fires, wasting a slot of CI quota.
`drizzle-kit generate` doesn't expose a documented `--no-prompt`
or `--yes` flag.

The CI defense is a 2-minute `timeout-minutes` on the drift step
itself. The contributor-level mitigation is to run
`pnpm db:generate` locally before pushing, answer the prompt, and
commit the SQL. The drift gate then re-runs `db:generate` against
the committed schema; if the schema is already in sync with the
committed migrations, no prompt fires because there is no diff.

The branch protection settings add this workflow to the required checks for both `main` and
`staging`.

### 2. Autoapply migrations on push to staging

A second workflow
(`.github/workflows/db-migrate-staging.yml`) runs on every push to
`staging`. The workflow installs dependencies, prints the SQL of
the migrations added in this push for audit, then runs
`drizzle-kit migrate` against the staging database.

```yaml
on:
  push:
    branches: [staging]
concurrency:
  group: db-migrate-staging-${{ github.ref }}
  cancel-in-progress: false
jobs:
  migrate:
    runs-on: ubuntu-latest
    env:
      DATABASE_URL: ${{ secrets.STAGING_DATABASE_URL }}
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: pnpm/action-setup@v6
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter @workspace/database build
      # Audit: print only the SQL files added by THIS push.
      # If the push touches no migration files, log a clear empty
      # line and skip the audit block.
      - name: Audit pending migrations
        run: |
          # GitHub sets github.event.before to forty zeros on the
          # first push to a new branch, and to a no-longer-existing
          # commit on a force push. Both cases make `git diff`
          # refuse to run ("fatal: bad object"), so this script falls back to
          # HEAD~1, which exists on every non-initial commit.
          BEFORE="${{ github.event.before }}"
          if [ -z "$BEFORE" ] || [ "$BEFORE" = "0000000000000000000000000000000000000000" ]; then
            BEFORE="HEAD~1"
          fi
          NEW=$(git diff --name-only "$BEFORE" "${{ github.sha }}" \
            -- 'packages/database/drizzle/*.sql')
          if [ -n "$NEW" ]; then
            echo "=== Migrations applied by this push ==="
            for f in $NEW; do
              echo "--- $f ---"
              cat "$f"
            done
          else
            echo "No new migrations in this push."
          fi
      - run: pnpm --filter @workspace/database db:migrate
```

The audit step uses `git diff --name-only` between the previous
and current commit on `staging`. It only prints SQL files that
were actually added by this push, so:

- A push that bundles many migrations prints each one, in
  the order they appear in the journal. No more `tail -1` hiding
  batch migrations.
- A push that touches no migration prints a clear
  "No new migrations in this push." line. No more stale SQL from
  three weeks ago polluting the audit trail.

The `cat` of each migration is the audit trail. Every CI run
prints the SQL that the workflow is about to apply, so the GitHub Actions
log captures the intent. If a migration lands that the reviewer
didn't see in the PR, the log shows it.

The workflow only runs on `staging`. A push to `main` doesn't
apply migrations; production migrations remain a manual step until
the team is comfortable with the staging autoapply. The staging
autoapply is the lower-risk half of the loop. Promotion to a
production autoapply is a separate decision.

#### Network prerequisite

The workflow requires the GitHub-hosted runner to reach the
staging database. If staging runs on AWS RDS, GCP Cloud SQL, or
any provider inside a private VPC with no public IP, a standard
`ubuntu-latest` runner can't connect. Two valid resolutions:

- Expose the database through a tunnel that the runner reaches via a
  stable host name.
- Use a self-hosted runner inside the same VPC.

The implementation provisions the `STAGING_DATABASE_URL` secret,
alongside one of the two resolutions above.

#### Ordering with the app deploy

The staging autoapply workflow runs migrations only. The
application deploy is a separate workflow (today, manual; in the
future, possibly automated). For the expand-and-contract pattern
to work, the order must be:

1. Migrations apply to the staging database.
2. The new app version starts against the updated schema.

A migration that adds a column without a `NOT NULL` constraint is backward-compatible
with the old app version, so the order can relax. A
migration that drops a column isn't backward-compatible; the old
app must retire before the drop migration runs. This is the
core of expand-and-contract, documented in the dedicated section
below.

### 3. Destructive-SQL lint on pull requests

The third change is a static-analysis gate against destructive
SQL in the migration files. It doesn't live in `drizzle.config.ts`.

The earlier draft proposed `strict: true` as a guard against
destructive migrations. That proposal was incorrect. To clarify
what `strict` actually does:

- In `drizzle-kit` v0.31 (the version pinned in this repo's
  `pnpm-workspace.yaml` catalog), `strict` is a config field for
  `drizzle-kit push`. It causes push to prompt for confirmation
  before applying statements that would sync the schema with the
  database. It has no effect on `drizzle-kit migrate`.
- `drizzle-kit migrate` doesn't inspect the AST of the SQL
  files. It runs them in order. A `DROP TABLE` or `DROP COLUMN`
  inside a committed `.sql` file goes through with no warning.
- In `drizzle-kit` v1.0 beta, `strict` in config stays ignored,
  and via CLI it throws a deprecation error. It's not a
  stable protection mechanism.

The right gate is a SQL linter that runs against the new SQL
files a PR introduces. Two proven candidates:

- **Squawk** (`sbdchd/squawk`): Postgres-aware linter. Free, MIT.
- **Atlas migrate lint**: a more general migration linter;
  heavier to integrate.

The implementation picks Squawk. The workflow lints only the
SQL files this PR changes, `git diff --name-only` between
the base and the head, never the whole `packages/database/drizzle`
folder. This scope exists because the bootstrap migration
(`0000_*.sql`, generated by `db:generate` on the initial schema)
triggers dozens of valid Squawk warnings that lie outside this
gate, and fixing them retroactively is
a separate piece of work. The per-PR scope makes the gate
focused on the SQL a contributor is actually adding.

#### Squawk targets drizzle's perimeter, not all rules

Squawk has no warning-vs-error exit-code distinction today
(issue sbdchd/squawk#348 is open with no resolution), so each
rule is either active (fails CI) or excluded. The configuration
in `.squawk.toml` lists the rules the team wants enforced, with all others excluded by name and
with a one-line justification per exclusion.

Two classes of Squawk rules get excluded because of their
*structural* incompatibility with `drizzle-kit migrate`:

- **`require-concurrent-index-creation` /
  `require-concurrent-index-deletion`**: `drizzle-kit` wraps
  every migration in a single transaction, and Postgres rejects
  `CREATE INDEX CONCURRENTLY` inside a transaction block
  (drizzle-team/drizzle-orm#860 has been open since 2022). The
  fix is per-migration opt-out from the wrapping transaction,
  which the migrator doesn't yet expose. Until it does,
  Squawk's warning on every `CREATE INDEX` is a false positive.
  Workaround when a non-blocking index is genuinely needed:
  hand-write the SQL as a separate raw migration run outside
  the migrator.

- **`adding-foreign-key-constraint` /
  `constraint-missing-not-valid`**: the senior pattern is
  `ADD CONSTRAINT … NOT VALID` in one transaction, then
  `VALIDATE CONSTRAINT` in a second. `drizzle-kit migrate`
  generates a single transaction per migration file. The
  workaround is the same as for concurrent indexes: split
  across two raw SQL migrations or accept the brief scan on
  the existing rows.

Two further rules get excluded because the patterns they flag
don't apply to migrations in this repo:

- **`prefer-robust-stmts`** (missing `IF NOT EXISTS` /
  `IF EXISTS`): relevant for hand-written SQL that may be
  re-run, less so for generated migrations that the drizzle
  journal already guards against re-application.
- **`require-timeout-settings`** (explicit `lock_timeout`
  / `statement_timeout`): the per-migration connection runs
  under a deployment-controlled DDL session; the project doesn't
  use live-traffic DDL tools.

The rules kept active cover destructive and rename operations,
which `drizzle-kit generate` does emit correctly and
which an expand-and-contract gate must catch: `ban-drop-column`,
`ban-drop-table`, `ban-drop-database`, `ban-drop-not-null`,
`ban-truncate-cascade`, `renaming-column`, `renaming-table`,
`changing-column-type`.

Each `excluded_rules` entry has a one-line justification in the
TOML so a future contributor can challenge the exclusion with
the original reasoning in hand. Only a follow-up ADR can
reverse an exclusion. The pattern comes from the
`longterm-wiki` project's `.squawk.toml`, which documents its
drizzle-specific exclusions the same way.

#### The squawk-action tag is `@v1`; the workflow doesn't use it

`sbdchd/squawk-action` has no tagged release past `@v1`. The
`@v1` action only exposes three inputs (`access_token`,
`version`, `pattern`) and would warn-and-fail on the inputs
this ADR originally listed (`fail-on-violations`,
`upload-to-github`). The `@main` branch has these inputs but
is a moving target. The workflow invokes `squawk-cli` directly
via `npm install -g squawk-cli`, which exits non-zero on
violation by design (verified in
`crates/squawk/src/reporter.rs`). This is what lives in
`.github/workflows/drizzle-check.yml`; earlier revisions of
this ADR pointed at the GitHub Action and the team retracted them.

### What this rule forbids

Three things are out of scope for this ADR:

- **A production autoapply.** The staging autoapply is the
  proposal. Production stays a manual step until the team has
  observed the staging autoapply for at least one month and has
  validated that the audit step, the Squawk gate, and the PR drift
  gate together catch the failure modes the team cares about. The
  follow-up ADR lives in the "Future work" section.
- **A preview database per PR.** Neon branching and hosted
  Postgres providers both offer a database-per-PR pattern. They're
  the right answer when the team needs to exercise the app against
  schema changes that can't go through on a shared staging
  database (destructive migrations, filling historical rows). The
  cost is
  about a developer-week per provider integration plus a monthly
  hosting line item. The staging autoapply covers the schema-drift
  and collision cases; the preview-DB pattern covers the destructive
  migration case. The two are complementary; this ADR is the first
  half.
- **Removing the manual local apply.** Local development still uses
  `pnpm db:generate && pnpm db:migrate` against the developer's
  personal database. The CI workflows don't replace the local
  workflow; they gate the local workflow's output.

## Consequences

- **Every PR that touches `packages/database/src/schema/**` is
  blocked at the drift gate if the schema changed without a
  matching migration**. The gate catches failure mode 1 before
  merge. False positives are possible (a contributor edits the
  schema and re-generates the migration in the same commit); the
  signal in that case is no signal, which is the desired behavior.
- **Every PR that adds destructive SQL to a migration file is
  blocked by Squawk**. The gate catches failure mode 2's
  destructive variant at PR time. The reviewer can override
  Squawk with an explicit `squawk-allow` comment plus a follow-up
  issue, but the override is visible in the PR conversation.
- **Every push to `staging` applies pending migrations against the
  staging database**. Failure mode 3 disappears for staging. The
  audit step (`git diff` of added SQL files) puts every applied
  migration in the CI log, scoped to the push that introduced
  them.
- **The integration job remains the contract test for the migration
  path on a fresh database**. The new workflows don't replace it.
  The new workflows assert the production-shaped path: existing
  journal, new SQL, apply against an external Postgres.
- **`drizzle.config.ts` stays unchanged**. The earlier draft proposed
  `strict: true`; that proposal was incorrect and the team retracted it.
  No drizzle config field protects `migrate` against
  destructive SQL. The protection lives in Squawk, outside drizzle.
- **The Better Auth table changes go through the same gate**.
  `npx @better-auth/cli generate` writes to the same schema
  directory and the same drizzle journal. A contributor who updates
  the Better Auth config without regenerating hits the same drift
  failure as a schema edit without regeneration.
- **Destructive migrations must follow the expand-and-contract
  pattern**. With Squawk on, a single-commit column drop fails
  CI. Squawk forces the contributor to split: add the column without a
  `NOT NULL` constraint, ship the app change, then copy the data, then
  drop. The ADR documents the pattern for posterity.

## Expand-and-contract for destructive changes

Two changes in particular must always land as separate PRs:

1. **Renaming a column.** First PR adds the new column without a
   `NOT NULL` constraint, ships the app writing to both columns,
   and copies data from the old column to the new one
   in a separate batch. Second PR sets the new column to `NOT NULL`
   (after a `NOT VALID` + `VALIDATE CONSTRAINT` for large tables)
   and drops the old column. Both PRs pass the drift gate, the
   Squawk lint, and the staging autoapply.

2. **Adding a `NOT NULL` constraint on a populated table.** First
   PR adds the column without a `NOT NULL` constraint and populates it.
   Second PR runs `ADD CONSTRAINT ... NOT VALID` followed by
   `VALIDATE CONSTRAINT` on a separate statement. Third PR (if needed)
   sets the column-level `NOT NULL`. A reviewer reviews each pull
   request SQL independently.

This is the same pattern documented in drizzle's production guides.
The CI gate enforces it because Squawk is on.

## Cost

The drift-gate workflow runs in about one minute on a clean PR.
The staging autoapply runs in about 90 seconds including
checkout and install. Both are cheap enough to run on every PR and
every staging push respectively.

The implementation is about:

- 30 minutes for `drizzle-check.yml` plus the branch protection
  update.
- 30 minutes for `db-migrate-staging.yml` plus the
  `STAGING_DATABASE_URL` secret and the network prerequisite.
- 30 minutes for the Squawk action plus `squawk.toml` at the repo
  root.
- 30 minutes for the documentation update (`packages/database/README`
  if it exists, or the schema file's leading comment).

Total: under two hours. The first run on a real PR surfaces any
false-positive risk; the second run confirms.

## Future work

Three extensions are out of scope here but worth flagging:

1. **Production autoapply.** A symmetric workflow that runs on
   push to `main` and applies against `secrets.PRODUCTION_DATABASE_URL`.
   The gate is the team's confidence in the staging autoapply
   after one month of observed runs.
2. **Preview database per PR.** A Neon or hosted-Postgres provider
   integration that provisions a database per PR, applies migrations
   against it, and tears it down on close. Necessary for destructive
   migration PRs that can't go through on a shared staging database.
   The cost is the provider integration plus the monthly hosting
   line item.
3. **A `drizzle-migration-guard` GitHub Action.** The community
   project (`saudademjj/drizzle-migration-guard`) does a deeper
   cross-branch collision check than `drizzle-kit check`. It's
   worth adopting once it stabilizes; today it's single-maintainer
   and the API surface is small enough to read. Tracked here so
   the next iteration picks it up without re-justifying.

## Expected file structure

The three changes above land as five concrete files. Two files
get added, one file gets created at the repo root, two stay
unchanged but get called out for completeness.

```
deessejs/
├── .github/
│   └── workflows/
│       ├── drizzle-check.yml              # NEW: PR drift + Squawk gate
│       └── db-migrate-staging.yml         # NEW: push-to-staging auto-apply
├── packages/
│   └── database/
│       └── drizzle.config.ts              # UNCHANGED
├── .squawk.toml                           # NEW: Squawk config at repo root
└── apps/
    └── internal-documentation/
        └── content/
            └── docs/
                └── decisions/
                    └── ADR-015-drizzle-migrations-ci.mdx  # THIS FILE
```

The list above names `packages/database/drizzle.config.ts`
for completeness only. Earlier revisions of this ADR proposed a `strict: true`
edit there; the team retracted that proposal. The current shape
leaves drizzle's config untouched. CI workflows, not the config,
catch drift or destructive SQL.

`.squawk.toml` (note the leading dot) lives at the repo root
because Squawk's CLI looks for it there by default. The
file holds an `excluded_rules` list keyed by Squawk rule name
with a one-line justification per entry, and a `pg_version`.
No `[upload_to_github]` table exists, because only the GitHub
Action reads that block, and the team doesn't use the action
(see the section above). This ADR commits the actual TOML content
alongside itself and treats it as the source of truth, not a copy
in this document.

If a future contributor removes a rule from `excluded_rules`
in the TOML, the corresponding change goes through a follow-up
ADR; the inline comment per row in the TOML is the entry point for
that discussion.

## How to verify

After the three changes land:

1. Open a PR that edits a schema file but doesn't regenerate a
   migration. The drift-gate workflow fails the PR with a clear
   diff in the log.
2. Open a PR that edits a schema file and regenerates a migration in
   the same commit. The drift-gate workflow passes; the
   integration job applies the migration against its ephemeral
   Postgres; the staging autoapply runs on merge to staging and
   applies against the staging database.
3. Open a PR that adds a `DROP TABLE foo;` line to a migration
   file. The Squawk action fails the PR with a clear warning.
   The contributor splits the change into an additive migration
   plus a follow-up contract migration after the app retires
   `foo`.
4. Push to `staging` that bundles three migrations. The audit log
   shows all three SQL files, in order. Push to `staging` that
   touches no migration files. The audit log shows
   "No new migrations in this push."
5. `pnpm db:check` continues to pass locally. The check is the
   first line of defense for commutativity bugs; the CI gate is
   the second.
