# ADR-020, apps/web browser end-to-end tests

## Status

Accepted (2026-08). Implementation may begin.

## Context

`apps/web` is the marketing site. Its user-visible surface is the
  RSC tree under `apps/web/src/app/(product)/templates/`, the
  related navigation (`apps/web/src/components/headers/nav-sections.tsx`,
  `apps/web/src/components/footers/app-footer.tsx`), and the
  upstream call into `packages/api` via `orpc.templates.list`
  (`apps/web/src/lib/orpc.ts`, `packages/api/src/orpc/routes/templates.ts`).
Every unit and integration test in this monorepo today exercises
  one layer in isolation: Vitest at the helper layer (ADR-009)
  for the `buildFetchIsrInit` translation contract, the API
  surface in-process via `api.request()` (ADR-016) for the
  Hono mount, and the CLI tarball in-process via the
  `run()` helper (ADR-014) for the binary.
**No test currently exercises the marketing site as a black
  box the way a user does.** The gap is the failure mode the
  user actually sees: the rendered DOM, the network round-trip
  to `/api/v1/rpc/templates/list`, and the Next.js Data Cache
  behavior for the `templates:live` tag introduced in PR #85.

Three concrete failure modes the existing layer-cake doesn't catch:

1. **The issue #81 cache-poisoning regression.** PR #85
   introduced `templates:live` (`revalidate: 0`) and a runtime
   re-throw at the three call-sites. The fix passes at
   the unit level (`apps/web/test/unit/orpc.test.ts`) and
   the API-side unit level (`packages/api/tests/integration/rpc/templates.test.ts`).
   Nothing exercises it as a user: a real browser hitting
   the marketing site, where `/templates` renders a populated
   grid then an empty `/templates` re-throws through to the
   segment's `error.tsx`, with the response header
   `x-nextjs-cache` reflecting the new `revalidate: 0`
   directive. A regression that re-poisons the cache is
   invisible to every existing test.
2. **The wire-code `TEMPLATES_FETCH_FAILED` (502).** The new
   error contract in `packages/api/src/orpc/routes/templates.ts:58-62`
   runs at the unit layer but no client observes it: the typed client should branch on
   `err instanceof ORPCError && err.code === "TEMPLATES_FETCH_FAILED"`
   and the marketing site's `error.tsx` should render the
   "Couldn't load templates" copy. No test pins that chain.
3. **The new home-page -> detail links.** The marketing home
   (`apps/web/src/app/(marketing)/page.tsx`) hard-codes three
   featured slugs in `FEATURED_TEMPLATES` (lines 30-57). Only
   `saas-starter` registers server-side
   (`packages/api/src/templates.ts:30-43`). Selecting the other
   two links today lands on `not-found.tsx`. The asymmetry is
   correct but unobservable; a regression that breaks even
   the `saas-starter` link isn't caught.

Three patterns the existing test surface already provides, and
  that this ADR reuses rather than re-implements:

- **Vitest unit seam (ADR-009).** The translation contract
  `buildFetchIsrInit` lives at `apps/web/test/unit/orpc.test.ts`
  (8 tests). It pins the translation contract that the
  browser-level test depends on. Alone, this isn't enough
  because the failure modes above need a real browser to be
  observable.
- **Hono `api.request()` integration (ADR-016).** The
  `packages/api/tests/integration/rpc/templates.test.ts` block
  exercises the Hono mount end-to-end without booting
  Next.js. The right shape for the Hono surface; the wrong
  shape for a UI test that needs RSC, the Data
  Cache, and the segment `error.tsx` to be live.
- **CLI `run()` e2e (ADR-014).** The published-artifact
  smoke suite under `apps/cli/test/e2e/` runs the tarball
  against a mock HTTP server. The shape (`{ stdout, stderr,
  exitCode }`; helper `run()`; mode-based mock server)
  informs how this ADR shapes the browser harness, but the
  surface is different (no CLI binary, no git fixture).

## Decision

Add a dedicated Playwright suite under `apps/web/tests/e2e/`
  that exercises the deployed marketing site. The suite is one
  file per surface (`templates-index`,
  `templates-detail`, `templates-cache`, `navigation`), plus a
  helpers folder for the page-object selectors and the
  Vercel preview URL resolution. The suite has **no network
  interception helper**; the tests observe the rendered
  DOM, not the outbound API traffic (see Decision #5).

The suite runs in CI against the Vercel preview deployment
  for the PR. Failure modes that are too slow, flaky, or
  expensive for PR gating run in a deeper nightly workflow.

### What this rule decides

Four concrete decisions.

**1. Framework: Playwright.** Next's own testing guide lists
  Playwright and Cypress as peer-supported
  ([nextjs.org/docs/app/guides/testing](https://nextjs.org/docs/app/guides/testing),
  v16.3.1, last updated 2026-02-03). Next doesn't recommend one
  over the other; both are equally listed. The choice for
  Playwright rests on three technical grounds and one
  ergonomic ground: {/* vale fix: Vale.Spelling */}

  - **First-class multi-browser support.** Playwright ships
    Chromium, Firefox, and WebKit drivers in one binary
    ([Playwright.dev/docs/browsers](https://playwright.dev/docs/browsers)). {/* vale fix: Vale.Terms */}
    The repo will need real Firefox and WebKit coverage at
    some point; Cypress uses a remote-control architecture
    that requires Sauce Labs for non-Chromium browsers.
  - **`page.setExtraHTTPHeaders()` first-class support.**
    The chosen e2e strategy (see Decision #5) injects the
    Vercel Protection Bypass secret via Playwright's
    canonical `extraHTTPHeaders` API
    (`page.setExtraHTTPHeaders({
      'x-vercel-protection-bypass':
        process.env.VERCEL_AUTOMATION_BYPASS_SECRET,
      'x-vercel-set-bypass-cookie': 'true'
    })`),
    plus a per-test `x-e2e-force-fail: '1'` (or `'2'`)
    header that the oRPC handler reads via Next's
    `headers()` to gate the failure path. The Playwright
    API is a first-class method on `Page`; Cypress exposes
    the same function via `cy.intercept()` with a request
    callback, but the Playwright ergonomics compose
    cleanly with the
    TypeScript page-object style the team will adopt.
  - **Native parallel mode and sharding.** The PR gate runs
    in less than two minutes on three browsers; nightly can
    shard. Cypress parallel execution requires a paid
    Dashboard.
  - **Ergonomics: the canonical Next example uses it.** Vercel
    maintains the official `with-playwright` example
    in the Next.js canary branch. Reviewers can read the official example and
    find the team's config next to it; the cognitive cost of going
    against the example is higher than the cost of either
    framework's quirks.

Three grounds reject Cypress: no first-class
  Firefox/WebKit, parallel mode requires the paid Dashboard,
  and the test suite would deviate from the canonical Next
  example.

**2. Target: Vercel preview deployment, not a local Next dev
  server.** The CI workflow uses the
  `on: repository_dispatch` trigger with the
  `client_payload.url` from the Vercel payload as
  `BASE_URL`. Two reasons:

  - **The `x-nextjs-cache` header is a production-only
    signal.** Next.js emits `HIT | STALE | MISS | REVALIDATED`
    for ISR-rendered routes
    ([nextjs.org/docs/app/guides/incremental-static-regeneration](https://nextjs.org/docs/app/getting-started/revalidating);
    v16.3.1). The production runtime populates the header; `next dev` doesn't exercise it. The issue #81
    regression test is meaningless against `next dev`.
  - **The `revalidate: 0` directive on `liveCache` is a
    production-only semantic.** Per the Next.js docs, `0`
    means *« Prevent the resource from being cached. »*
    ([nextjs.org/docs/app/API-reference/functions/fetch](https://nextjs.org/docs/app/api-reference/functions/fetch); {/* vale fix: Vale.Terms */}
    v16.3.1). In dev mode, the directive is short-circuited
    when the request carries `cache-control: no-cache`,
    which DevTools sends. Production assertions on this
    directive fail against `next start` too,
    because the production app isn't on the test machine;
    the Vercel preview URL is the only environment where
    the production code path runs at a stable URL.

Local development runs against `pnpm dev` instead, using a
  separate config preset (`baseURL: http://localhost:3000`,
  `webServer` block from the Playwright docs). Local runs
  exercise the same test code without asserting the cache
  directive headers. The CI workflow doesn't use this
  preset.

  **Why `repository_dispatch`, not `deployment_status`.**
    Vercel documents `repository_dispatch` with
    `event_type: "vercel.deployment.success"` as the
    alternative path in their Knowledge Base for e2e-after-preview
    (see the Vercel Knowledge Base entry on e2e-after-preview). {/* vale fix: Vale.Terms */}
    Earlier drafts of this ADR used `on: deployment_status`,
    but the documentation path carries the deployment URL
    directly in `client_payload.url`, while
    `deployment_status` requires reading `environment_url`
    (or `target_url`) and is one indirection further. The
    `repository_dispatch` payload is also documented and
    trusted by Vercel in their own example workflows.

    **Note on the comparison.** The Vercel KB doesn't
    formally recommend one trigger over the other; it
    documents both paths. The "one indirection closer"
    framing is the ADR's editorial choice, justified by
    the simpler field path on the GitHub Actions side.
    The Playwright CI docs themselves use
    `deployment_status` in their canonical example.

  **Fork-PR posture.** Per the Vercel for GitHub docs
    (see the Vercel for GitHub integration page): {/* vale fix: Vale.Terms */}
    *"If you receive a pull request from a fork of your
    repository, Vercel will require authorization from you
    or a team member to deploy the pull request."* This
    means fork PRs don't produce a Vercel deployment by
    default, and no `repository_dispatch` event
    fires for them until a maintainer approves the deploy.
    Once approved, the workflow runs the same way as for
    an internal PR. The repo is internal-only today (no
    fork-PR workflows exist); the ADR doesn't engineer
    fork support into v1 but flags it as a known gap for
    the day the repo opens to external contributors.
    The alternative (`on: pull_request_target` for
    permission-rich runs) gets rejected because e2e
    inherently executes the pull-request code, which would create
    a pwn-request path that exposes secrets to risky
    code. {/* vale fix: Vale.Spelling */}

**3. Test placement: `apps/web/tests/e2e/`, deviating from
  Next's example project.** The canonical Next example
  uses `e2e/` at the project root
  (see the official Next.js Playwright example). {/* vale fix: Vale.Terms */}
  The deessejs convention from ADR-009 (§87-89) is
  `tests/` (plural) for packages and `test/` (singular)
  for apps. This ADR adopts **`tests/` (plural)** for
  `apps/web` and places the Playwright suite under
  `apps/web/tests/e2e/`. Three reasons:

  - **Consistency with the existing Vitest unit tests at
    `apps/web/test/unit/orpc.test.ts` (PR #85).** Co-locating
    `test/` (Vitest) and `tests/e2e/` (Playwright) under
    the same `apps/web/` root means a future contributor
    finds all tests by descending one directory. The
    Vitest `include` glob extends (see below).
  - **Findability over Next-example parity.** The {/* vale fix: Vale.Spelling */}
    divergence from Next's `e2e/` naming is small (a
    trailing `s`) but the upside is real: the
    convention becomes self-documenting for anyone reading
    the repo without external context.
  - **No collision with Vitest config.** Vitest's `include`
    pattern is `["test/**/*.test.ts," "tests/**/*.test.ts"]`
    (both globs). The Playwright `testDir` is
    `apps/web/tests/e2e/` and the test files use
    `.spec.ts`. The two config files use disjoint file globs {/* vale fix: Vale.Spelling */}
    (`.test.ts` vs `.spec.ts`) so the inclusion of
    `tests/**` in the Vitest `include` doesn't pick up
    Playwright suites.

  **Vitest config update (companion change to this ADR).**
  `apps/web/vitest.config.ts` currently sets
  `include: ["test/**/*.test.ts"]` (the Vitest preset
  default). The implementation PR for this ADR extends it
  to `["test/**/*.test.ts," "tests/**/*.test.ts"]`. The
  Playwright files (`.spec.ts`) aren't picked up by the
  Vitest `include` glob because the `.test.ts` extension
  filter excludes them.

The `e2e.config.ts` and `playwright.config.ts` are two
  presets of the same config: `playwright.config.ts` is the
  CI preset (deployed preview, `workers: 1`); `e2e.config.ts`
  is the local dev preset (hot reload, `next dev`). Playwright
  loads the config passed via `--config`, so both presets
  share one config file with a default export and a named
  export for the other.

**4. Stable selectors: a `data-testid` strategy, with a
  fallback chain.** The audit at the end of this ADR
  identifies 8 surfaces where today's selectors rely on copy
  and would gain from explicit `data-testid` attributes.
  The strategy is:

  - **Add `data-testid` on the four surfaces the load-bearing
    P0 tests depend on.** The grid container, each card,
    the sidebar groups, and the search input. Total: 8
    `data-testid` attributes on 4 surfaces. The attributes
    cost zero runtime overhead and zero CSS specificity
    (Tailwind doesn't see them).
  - **For surfaces the audit called out as P1/P2/P3, keep
    the existing selectors.** The role/name/aria selectors
    work for "Try again," "Search templates," the breadcrumb,
    etc. Mixing test-ids in P0 and role-based selectors
    elsewhere keeps the diff small.
  - **Never depend on text content for assertions.** The
    `error.tsx` suppresses `error.message` by design
    (`apps/web/src/app/(product)/templates/error.tsx:7-11`),
    so backend errors can't leak to tests even by accident.

The implementation lands the `data-testid` attributes in the
  same PR as the test files. Two PRs would let a UI change
  drift from a test expectation; one PR makes the coupling
  visible at review time.

**5. Test-only HTTP header injection, not `page.route()`
  and not env-var mutation.** Two rejected approaches,
  one chosen.

  **Why not `page.route()`.** Playwright's `page.route()`
  (and `browserContext.route()`) intercepts *"Any requests
  that a page does, including XHRs and fetch requests"*
  ([Playwright.dev/docs/network](https://playwright.dev/docs/network);
  v1.5x, fetched 2026-08-20, introduction section). The
  same page states the in-browser scope explicitly: *"Any
  requests that a page does … can be tracked, modified and
  handled."* The API reference page
  (`playwright.dev/docs/api/class-page#page-route`) provides
  the method signature and the Service Worker caveat; the
  phrase *"requests that a page does"* doesn't appear there.
  Out-of-browser traffic, anything running in Node, sits
  **out of scope** by design (issue #23705 on
  `microsoft/playwright` is the most-cited demonstration;
  confirmed by the primary doc above).
  `playwright.dev/docs/network`).

  For the setup specifically, the oRPC `POST
  /api/v1/rpc/templates/list` call inside
  `apps/web/src/app/(product)/templates/page.tsx:87` is an
  async RSC. The Next.js server runtime executes the fetch
  during SSR/RSC rendering (per the `fetch` API ref
  in the bundled docs, `apps/web/node_modules/next/dist/
  docs/01-app/03-api-reference/04-functions/fetch.md:8-10`:
  *"In the browser, the `cache` option indicates how a
  fetch request will interact with the browser's HTTP
  cache. With this extension, `cache` indicates how a
  server-side fetch request will interact with the
  framework's persistent cache. You can call fetch with
  async and await directly within Server Components."*).
  The browser never sees a `POST /api/v1/rpc/*` request on
  initial paint; the result interleaves in the HTTP
  response stream alongside the RSC payload.

  As a result, `page.route('**/api/v1/rpc/**')` would {/* vale fix: write-good.So */}
  pass through: the request never reaches the browser, the
  handler never gets invoked, the test would return a false
  green against the real (or test) upstream API.

  **Why not a mutated `process.env` on the Vercel preview.**
  An earlier draft proposed setting
  `TEMPLATES_E2E_FORCE_FAIL=1` directly on the Vercel
  preview environment via the env-var mutation API. The
  review correctly identified this as a load-bearing
  implementation bug, for two reasons:

  1. Vercel preview deployments are **immutable mid-run**.
     The Vercel REST API for env vars (`/v9/projects/:id/env`)
     writes into a deployment-time snapshot that new
     containers pick up at cold start; it doesn't mutate
     running instances. Setting the env var requires either
     a new deployment or a multi-second wait for a cold
     start on an existing instance.
  2. **Concurrency scale.** Even if it worked, mutating the
     preview env for each test (and clearing after) would
     destroy the parallelism of the PR gate. Two tests
     concurrently setting the flag to different values
     race; the matrix scenarios stack. The 3-minute budget
     dies.

  **The chosen pattern: Vercel Protection Bypass for
  Automation, single Vercel-managed secret for both jobs.**
  Pattern:

  * **Activation.** The Vercel project has **Deployment
    Protection enabled** (Password Protection or Vercel
    Authentication, either is fine; the choice is
    operational). A dedicated bypass secret named
    *"Playwright tests"* gets created in the project's
    *Deployment Protection → Bypass for Automation*
    settings. Vercel automatically injects that secret
    value into the deployed runtime as
    `process.env.VERCEL_AUTOMATION_BYPASS_SECRET`
    ([Vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation); {/* vale fix: Vale.Terms */}
    lastUpdated 2026-04-30, fetched 2026-08-20). {/* vale fix: Vale.Spelling */} The
    preview URL becomes inaccessible without the
    secret; the secret is the gate.

  * **One secret, two jobs.** The same secret that
    Vercel-managed-system-injects as
    `VERCEL_AUTOMATION_BYPASS_SECRET` is also read by the
    oRPC handler at
    `packages/api/src/orpc/routes/templates.ts:list` to
    gate the test-only failure path. The project holds a single secret, {/* vale fix: write-good.ThereIs */}
    on the project, exposed in two places (the deployment
    runtime + the oRPC handler); the secret's value
    never leaves the trusted path (Vercel injects it as a
    system env var; CI receives it as a GitHub Actions
    repository secret). The same `extraHTTPHeaders` set
    that bypasses the Vercel edge is also the one the
    handler reads to enable the test-only code path.

  * **Playwright configuration.** Per Vercel's
    documentation, the canonical Playwright config for
    this exact scenario is:

    ```ts
    // apps/web/playwright.config.ts (excerpt)
    if (!process.env.VERCEL_AUTOMATION_BYPASS_SECRET) {
      throw new Error(
        "VERCEL_AUTOMATION_BYPASS_SECRET is required " +
        "to run tests against protected deployments",
      )
    }
    export default defineConfig({
      use: {
        extraHTTPHeaders: {
          "x-vercel-protection-bypass":
            process.env.VERCEL_AUTOMATION_BYPASS_SECRET,
          // Required so follow-up navigations (next/link
          // client transitions) inherit the bypass.
          // The first response sets a Set-Cookie header
          // on the preview domain; subsequent navigations {/* vale fix: Vale.Spelling */}
          // carry the cookie automatically.
          "x-vercel-set-bypass-cookie": "true",
        },
      },
    })
    ```

    The two headers are the exact pattern Vercel
    documents for "in-browser testing"
    ([Vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation#examples](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation#examples);
    verbatim *"to bypass authorization on follow-up
    requests (for example for **in-browser testing**) you can set
    an extra header or query parameter named
    `x-vercel-set-bypass-cookie` with the value `true`.
    This will set the authorization bypass as a cookie
    using a redirect with a `Set-Cookie` header."*).
    Without `x-vercel-set-bypass-cookie`, the first SSR
    paint works but the next client-side navigation
    (for example the `Try again` recovery in P0-3) loses the
    header; the issue #81 regression test would fail
    spuriously on the second navigation.

  * **Per-test guard inside Playwright tests.** On top of
    the static `extraHTTPHeaders` set, individual tests
    set the **second** test-only header that drives the
    oRPC handler's failure path:

    ```ts
    await page.setExtraHTTPHeaders({
      "x-e2e-force-fail": "1",
    })
    ```

    The two headers travel together: `x-vercel-protection-bypass`
    authenticates the request past the Vercel edge; `x-e2e-force-fail`
    selects the test branch inside the handler. Both
    scope per browser context, so two tests in
    parallel don't race.

  * **Server-side guard.** The oRPC handler reads both
    headers via Next's `headers()` async API at
    `packages/api/src/orpc/routes/templates.ts:list`:

    ```ts
    const h = await headers()
    const bypassAllowed =
      process.env.NODE_ENV !== "production" &&
      h.get("x-vercel-protection-bypass") ===
        process.env.VERCEL_AUTOMATION_BYPASS_SECRET
    if (bypassAllowed) {
      if (h.get("x-e2e-force-fail") === "1") {
        throw new ORPCError("TEMPLATES_FETCH_FAILED", {
          status: 502,
        })
      }
      if (h.get("x-e2e-force-fail") === "2") {
        return { templates: [] }
      }
    }
    ```

  * **`process.env.NODE_ENV !== "production"` is the
    load-bearing guard against accidental production
    behaviour.** A future contributor who adds the
    test-only code path can't enable it in production
    by forwarding the bypass header from a public client
    (production has no `VERCEL_AUTOMATION_BYPASS_SECRET`
    set); the server-side NODE_ENV check blocks it
    regardless of header content.

  * **Contract pinning.** The values (`"1"` for failure,
    `"2"` for empty catalog) are part of the wire
    contract between the test runner and the handler and
    pin here so a future refactor can't introduce
    a typo that falls back to the happy path.

  Implications for the issue #81 regression test (P0-6):
  the test sets `x-vercel-protection-bypass` (via
  `extraHTTPHeaders` in the global config) and
  `x-e2e-force-fail: 1` (per-test), navigates, asserts
  on the rendered DOM
  (`role=heading[name="Couldn't load templates"]` and
  `role=button[name="Try again"]`), then asserts the
  `x-nextjs-cache` header on the **document response**
  (the Next.js HTML/RSC stream, which **is**
  browser-visible) for the cache-poisoning regression
  signal. Selecting "Try again" issues a client-side
  navigation; the bypass cookie set by the first
  response sends automatically. The oRPC POST itself
  isn't observable; the test asserts on the consequence in
  the rendered tree and in the response cache header.

  **Why this is the correct senior-grade pattern, not a
  novelty.** The Vercel docs page for Protection Bypass
  for Automation includes a verbatim Playwright
  example for exactly this scenario, naming the
  `extraHTTPHeaders` + `x-vercel-set-bypass-cookie`
  pattern. Combining the bypass header with the
  in-handler guard reuses Vercel's documented secret
  management; a separate `E2E_TEST_SECRET` (the v2 of
  this ADR) was a duplicate secret surface that this v3
  eliminates.

### What this rule allows

- **A `playwright.config.ts` at `apps/web/playwright.config.ts`**
  with one canonical preset, a `dev` preset (for local
  `pnpm dev` runs), and a `BASE_URL` env var that flips
  between them. The CI workflow always sets `BASE_URL` to
  the Vercel preview; the local preset omits `BASE_URL` and
  uses Playwright's `webServer` block.
- **DOM-only assertions via Playwright's browser
  primitives** (`page.goto`, `page.locator`,
  `expect(...).toBeVisible`). The test surface is the
  rendered HTML, the same boundary a user observes. Tests
  do **not** intercept any `/api/v1/rpc/*` traffic because
  `page.route()` can't intercept server-side fetches
  executed inside React Server Components during SSR/RSC
  rendering (see Decision #5 for the reasons).
- **Vercel Protection Bypass for Automation as the
  canonical secret surface.** The single
  `VERCEL_AUTOMATION_BYPASS_SECRET` is Vercel-managed
  (created in the project's *Deployment Protection →
  Bypass for Automation* settings; Vercel injects it as
  a system env var into the deployed runtime). The CI
  workflow reads it from a GitHub Actions repository
  secret and feeds it to Playwright via
  `extraHTTPHeaders`. The same secret is the one the
  oRPC handler reads via the `x-vercel-protection-bypass`
  request header. The exact scheme is in Decision #5.
- **Header values are an enum (`"1"` for forced failure,
  `"2"` for empty catalog)** so a typo in the test
  no-ops rather than finding the happy path.
- **One suite per surface, named after the route family.**
  The convention follows ADR-016's `tests/integration/`
  rule: the file name mirrors the route, not the verb.
  `templates-index.spec.ts` exercises `/templates`;
  `templates-detail.spec.ts` exercises `/templates/[slug]`.
- **Two CI workflows** (one PR-blocking, one nightly),
  exactly the structure from ADR-014. The PR-blocking
  workflow runs in under three minutes on Chromium only;
  the nightly runs the multi-browser matrix.
- **A `test:e2e` script in `apps/web/package.json`** that
  runs `playwright test --config playwright.config.ts` for
  the CI preset and `playwright test --config e2e.config.ts`
  for the local preset. The convention matches ADR-014's
  `apps/cli/package.json:33` (`"test:e2e": .".."`) so the
  two apps are addressable the same way from CI (`pnpm
  --filter web test:e2e`). The Vitest `test` script
  (`apps/web/package.json`) stays unaffected, as Vitest and
  Playwright have independent runners.
- **The `tests/` shape from ADR-009 continues to apply at
  the helper layer.** A `page-objects/` directory inside
  `apps/web/tests/e2e/helpers/` isn't a Vitest test
  directory; it's a Playwright fixture. The ADR-009 shape
  applies to Vitest unit tests only.

### What this rule forbids

- **Booting `next dev` or `next start` in the PR-blocking
  workflow.** The PR workflow hits the Vercel preview
  directly. Local booting gets permitted only in the dev preset {/* vale fix: write-good.Passive */}
  and only on a developer machine, never in CI.
- **A `vitest.config.ts` change for the Playwright suite.**
  Playwright and Vitest are independent runners. Adding the
  `e2e/` directory to the Vitest `include` glob would fail
  the Vitest parse step.
- **Test-ids on the empty / not-found / error states that
  duplicate role-based selectors.** Role-based
  (`role=heading`, `role=button`) is more semantic. Contributors add test-ids {/* vale fix: write-good.Passive */}
  only where role-based selectors require copy that
  may change with i18n.
- **Spying on `process.exit` or stubbing `globalThis.fetch`
  in the e2e suite.** The Playwright abstraction is the
  browser; the page is the test surface.
- **A dependency on `playwright/test` fixture composition
  from `@playwright/test` outside of this folder.** The
  fixture surface is local; cross-test sharing happens via
  the helpers folder, not via test-runner-level fixtures.

### Why not the alternatives

Four patterns got considered and rejected.

- **Cypress.** No first-class Firefox/WebKit, parallel mode
  requires the paid Dashboard, deviates from the canonical
  Next example. The orthogonal benefit of a friendlier UI
  is moot for CI-driven smoke.
- **A snapshot-only smoke test that hits `apps/app` directly
  with curl.** Inspecting the HTML with grep pins the bytes
  but misses the JS-driven DOM, the ISR cache, the segment
  `error.tsx`, and the `data-testid` strategy. The failure
  modes above need a real browser.
- **Booting `next start` in CI via Docker and hitting
  localhost.** ADR-016 rejects this pattern for API
  integration tests (boot cost, port collisions, double
  surface). The argument applies a fortiori to a UI test {/* vale fix: Vale.Spelling */}
  that needs RSC *and* Hono *and* ISR *and* Vercel edge
  cache headers. The Vercel preview URL is the production
  surface; localhost isn't.
- **`chromium-only` smoke tests for the PR gate, Playwright
  multi-browser for nightly.** The P0 assertions are
  reproducible across browsers because they target
  semantics the specification defines (HTTP 200 on `/templates`, a
  `data-testid` present in the DOM, an `x-nextjs-cache`
  value). Browser-specific bugs land in the matrix, not in
  the gate. Skipping the browser matrix isn't the issue
  here; the issue is whether the gate is fast enough.

### CI workflow shape

Two workflows, named `apps-web-e2e.yml` and
  `apps-web-e2e-extended.yml`. The shape inherits from the
  CLI e2e workflows in ADR-014: PR-blocking and nightly,
  no tarball (browser tests against the deployed app), one
  pack step that is a no-op.

**`apps-web-e2e.yml` (PR blocking).**
```yaml
name: apps/web e2e
on:
  repository_dispatch:
    types: [vercel.deployment.success]
jobs:
  e2e:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: 'pnpm' }
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter web exec playwright install --with-deps
      - name: Run Playwright
        env:
          BASE_URL: ${{ github.event.client_payload.url }}
          VERCEL_AUTOMATION_BYPASS_SECRET: ${{ secrets.VERCEL_AUTOMATION_BYPASS_SECRET }}
          CI: 1
        run: pnpm --filter web exec playwright test
      - if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: apps/web/playwright-report/
          retention-days: 7
```

The `on: repository_dispatch` trigger with
  `vercel.deployment.success` is the pattern Vercel
  recommends in their own KB for e2e-after-preview
  ([Vercel.com/kb/guide/how-can-i-run-end-to-end-tests-after-my-vercel-preview-deployment](https://vercel.com/kb/guide/how-can-i-run-end-to-end-tests-after-my-vercel-preview-deployment)).
  The `client_payload.url` is the preview URL with the
  authoritative `&lt;project&gt;-&lt;hash&gt;-&lt;scope&gt;.vercel.app`
  format. The earlier draft of this ADR used
  `on: deployment_status` with `target_url`; that path
  remains valid. **Caveat on the comparison.** The Playwright
  CI docs themselves use `deployment_status` + `target_url`
  as their canonical example for *"Services like Vercel use
  this pattern so you can run their end-to-end tests on
  their deployed environment"* ([Playwright.dev/docs/ci](https://playwright.dev/docs/ci));
  Playwright doesn't endorse `repository_dispatch` over
  `deployment_status`; the editorial preference in this
  ADR comes from Vercel's own KB on e2e-after-preview,
  which documents `repository_dispatch` with
  `vercel.deployment.success` and `client_payload.url` as
  the alternative path. The two patterns coexist; the
  ADR chose `repository_dispatch` because
  `github.event.client_payload.url` is one indirection
  closer to the call site than
  `github.event.deployment_status.target_url`.

**`apps-web-e2e-extended.yml` (nightly non-blocking).**
  Schedule: `cron: "0 3 * * *"`. Runs a wider matrix:

  | Dimension | Scenarios | Notes |
  |---|---|---|
  | Browser | Desktop Chrome, Desktop Firefox, Desktop Safari (WebKit), Mobile Chrome (Pixel 5), Mobile Safari (iPhone 12) | PR gate runs Chromium only; nightly covers the multi-browser matrix per the canonical Playwright config |
  | Network | `real-network` (the Vercel preview hit by the PR gate); `forced-cache-poison` (a forced-handler failure path that re-runs the issue #81 regression against `x-e2e-force-fail: 1`); `slow-network` (e2e.config.ts only, local preset that delays the upstream); `flaky-network` (force the header to fail intermittently to test the `Try again` button) | Each scenario is a separate `matrix:` entry with its own header preset. **Note:** `page.route()` can't simulate slow or flaky behaviour at the RSC layer; see Decision #5. The matrix exercises handler behaviour, not network behaviour. |
  | Fixture | `populated-catalog` (the V1 single template); `empty-catalog` (`x-e2e-force-fail: 2`); `large-catalog` (custom registry fixture mounted at `apps/web/tests/fixtures/large-catalog.ts`, 100 templates, slow path, asserts the grid scroll + filter performance) | Cloned from the `large-fixture` / `unicode` / `real-pm` pattern in ADR-014:322-356 |

  Failures in any nightly scenario post a GitHub issue
  with the workflow run URL, the scenario, and the
  captured stdout/stderr. Same pattern as ADR-014's
  nightly workflow.

  **The `forced-cache-poison` scenario is the one that
  directly mirrors the issue #81 regression.** It runs
  P0-6 against a Vercel preview where the test sets the
  `x-e2e-force-fail: 1` request header (with the bypass
  cookie already set by the first navigation via
  `x-vercel-set-bypass-cookie: true`). The handler throws
  `ORPCError("TEMPLATES_FETCH_FAILED," { status: 502 })`
  on the first `/templates` request. The scenario asserts:
    1. The `error.tsx` boundary renders the documented
       copy.
    2. The `role=button[name="Try again"]` recovers to a
       fresh populated state (the test clears the
       `x-e2e-force-fail` header before selecting, so the
       next navigation reaches the real handler).
    3. The `x-nextjs-cache` header is **not** `HIT` after
       the recovery.

  If a contributor reintroduces the cache-poisoning bug,
  the same re-throw path, the same page-side error
  swallow, this scenario catches it on the same day. It
  is the load-bearing nightly assertion.

### Test seams and conventions

Three implementation details pinned here so a future
  contributor doesn't re-derive them.

**`expect.toPass()` for retry-aware assertions on the
  DOM.** When the test sets the env flag and then asserts
  on the rendered `error.tsx` copy, the Vercel preview
  edge cache can race the assertion (the preview may
  serve a cached success body for the first ~100ms after
  the env flag flip). `expect.toPass()`
  ([Playwright.dev/docs/test-assertions](https://playwright.dev/docs/test-assertions#expecttopass))
  is the canonical retry primitive. The default polling
  is fine; the test doesn't need to tune `intervals`.

**`page.on('response')` listeners clean up per-test.** {/* vale fix: write-good.Passive */}
  The `x-nextjs-cache` header assertion in P0-6 subscribes
  via `page.on('response')`. Without cleanup, the listeners
  accumulate across tests and the regression guard reports
  headers from previous tests. The convention: every test
  that subscribes removes the subscriber in a `finally`
  block.

**Local-preset reuse of the CI preset.** The dev preset
  (`apps/web/e2e.config.ts`) extends the CI preset with
  three lines: `webServer: { command: 'pnpm dev', port: 3000,
  reuseExistingServer: !process.env.CI }`, `use.baseURL:
  'http://localhost:3000'`. No test file gets duplicated. The
  `playwright.config.ts` and `e2e.config.ts` files together
  total under 80 lines.

**Note on the oRPC handler guard.** The
  `x-e2e-force-fail` guard lives in
  `packages/api/src/orpc/routes/templates.ts:list` (next to
  the `TEMPLATES_FETCH_FAILED` wire-code from PR #85).
  The handler reads the request headers via Next's
  `headers()` async API (Next 16 makes the request headers
  available to RSCs {/* vale fix: Vale.Spelling */} through this primitive; cited in
  [nextjs.org/docs/API-reference/functions/headers](https://nextjs.org/docs/api-reference/functions/headers)
  fetched 2026-08-20) and gates on the Vercel
  Automation Bypass secret:

  ```ts
  const h = await headers()
  const bypassAllowed =
    process.env.NODE_ENV !== "production" &&
    h.get("x-vercel-protection-bypass") ===
      process.env.VERCEL_AUTOMATION_BYPASS_SECRET
  if (bypassAllowed) {
    if (h.get("x-e2e-force-fail") === "1") {
      throw new ORPCError("TEMPLATES_FETCH_FAILED", { status: 502 })
    }
    if (h.get("x-e2e-force-fail") === "2") {
      return { templates: [] }
    }
  }
  ```

  Three unit tests pin the contract:

  1. **Closed by default.** When
     `process.env.VERCEL_AUTOMATION_BYPASS_SECRET` is unset
     **or** when the
     `x-vercel-protection-bypass` header value doesn't
     match, `bypassAllowed` is false and the guard is a
     no-op; the handler proceeds to the real `enrich()`
     path. **This is the load-bearing test against a
     forgotten secret rotation**: if the Vercel dashboard
     secret gets revoked but the deployed runtime still
     carries the old value, the handler proceeds without
     enabling the test path (the handler reads from the
     process env, not the header, for comparison).
  2. **Production-impervious.** When `NODE_ENV ===
     "production"`, the guard is a no-op regardless of
     header content. A future contributor who enables
     the code path can't fire it by accident from
     production traffic; the server-side env check
     blocks it.
  3. **Header mismatch.** A test pins that a
     `x-vercel-protection-bypass` value different from
     `VERCEL_AUTOMATION_BYPASS_SECRET` doesn't enable the
     path. This rules out a future refactor that
     switches to a truthy-coercion
     comparison (`if (h.get(...))`) by accident
     and would expose the
     test path to anyone able to send a header.

  These three tests are part of
  `packages/api/tests/integration/rpc/templates.test.ts`
  (next to the existing `enrich()` failure block from
  PR #85). They run on every PR.

### What this rule doesn't change

- **`apps/web/test/unit/orpc.test.ts` (8 tests, PR #85
  addition).** Stays. The unit tests pin the translation
  contract; the e2e tests pin the user-visible behavior.
  Removing the unit tests would weaken the regression net
  by an order of size.
- **`packages/api/tests/integration/rpc/templates.test.ts`.**
  Stays. The Hono-mount integration tests are the right
  shape for Hono; the e2e tests are the right shape for the
  rendered UI. Both stay needed.
- **The Vercel preview deployment surface.** The
  `apps/app/app/api/[[...route]]/route.ts` and the existing
  CI workflows for Vercel deployments stay. The new
  workflows add a `repository_dispatch` listener; they
  leave existing workflows alone.
- **Deployment Protection is now required on the Vercel
  project.** The implementation PR for this ADR activates
  Deployment Protection (Password Protection or Vercel
  Authentication, either is acceptable) on the deessejs
  Vercel project, with a dedicated bypass secret named
  *"Playwright tests"*. The runtime receives the secret
  as `VERCEL_AUTOMATION_BYPASS_SECRET` (Vercel-managed);
  CI receives the same value as a GitHub Actions
  repository secret (named the same, by convention). A
  future contributor can rotate the secret from the
  Vercel dashboard; doing so invalidates the running
  preview, which requires a redeploy to pick up the new
  value. The rotation policy gets documented in the
  implementation runbook; ADR-020 doesn't formalize
  the rotation schedule (out of scope).

### Consequences

- **CI costs ~3 minutes per PR (3 browsers, ~1 minute each
  in parallel under `workers: 1`).** The PR-blocking budget
  matches ADR-014's pattern. The nightly runs ~12 minutes.
- **PR #85's unit test for `buildFetchIsrInit` becomes a
  regression net for the helper, but the e2e test is the
  primary signal for the user-visible behavior.** A
  contributor who breaks the translation contract fails
  locally on the unit test; a contributor who changes the
  page structure in a way that hides the bug fails CI on
  the e2e test.
- **A regression that reintroduces the cache-poisoning bug
  fails CI before merge.** This is the load-bearing
  consequence of the ADR.
- **This is the first `e2e/` test tier materialised in the
  monorepo.** ADR-009 (Accepted, line 87-89) defines three
  Vitest tiers (`unit/`, `integration/`, `contract/`) for
  packages and the singular `test/` tier for apps. ADR-014
  (Accepted, line 150) calls for an `apps/cli/test/e2e/`
  fourth tier but nobody has implemented it yet. {/* vale fix: write-good.Passive */} ADR-020 ships
  the first materialised `e2e/` tier under `apps/web/tests/`.
  Naming: the Vitest `include` glob extends (see
  Decision #3 companion change) to
  `["test/**/*.test.ts," "tests/**/*.test.ts"]`; Playwright
  files use `.spec.ts` and live under `tests/e2e/`, so the
  Vitest glob doesn't pick them up. The two directories
  coexist under `apps/web/` because their `*.test.ts` vs
  `*.spec.ts` extensions keep the runners disjoint.
- **Vercel preview URLs are publicly accessible by default**
  ([Vercel.com/docs/deployments/generated-urls](https://vercel.com/docs/deployments/generated-urls); {/* vale fix: Vale.Terms */}
  lastUpdated 2025-09-24). {/* vale fix: Vale.Spelling */} The e2e tests run against the
  preview; a misconfigured preview env that exposes
  real-user data fails the e2e tests because the assertions
  include a populated catalog and a non-2xx upstream
  failure. **Deployment Protection** on the Vercel project
  **No contradiction with Deployment Protection.** This
  ADR explicitly enables Deployment Protection on the
  Vercel project (see Decision #5 and Consequences §5);
  the e2e tests authenticate past the protection via the
  `x-vercel-protection-bypass` header. The bypass secret
  is **not** embedded in `target_url`; it travels as a
  request header (or query parameter). Public-by-default
  refers to the *unauthenticated* default for
  human visitors; the e2e test runner isn't a human
  visitor and uses the documented bypass mechanism.

Three extensions are out of scope for this ADR but worth

1. **A second Playwright suite under `apps/app/` for the

2. **Pixel-level visual regression on the populated grid.**

3. **Closing the `vitestConfig` signature drift.** ADR-009

   `package` key. This ADR doesn't use `vitestConfig`,
   so it doesn't trip the drift, but a follow-up should
   align ADR-009's example with the implementation before
   the next consumer gets misled.

All three sit on the list so the next iteration of this ADR {/* vale fix: write-good.Passive */}

## Decision log

- **2026-08-20**: investigated browser E2E options for

  DOM-assertion primitives, and canonical-presentation

- **2026-08-20**: inventoried the existing test surface in
  the repo. Confirmed that ADR-009 (unit/integration/contract
  Vitest) and ADR-016 (Hono `api.request()`) cover the
  helper layer and the API layer but not the rendered UI.
  ADR-014 (CLI tarball) is the closest analogue in spirit
  but doesn't cover the browser surface.
- **2026-08-20**: drafted the test scope (P0-P3) by auditing
  the rendered templates tree. Pinned 8 `data-testid`
  attributes on 4 surfaces; the remaining 17+ assertions
  reuse role/name selectors.
- **2026-08-20**: chose `tests/e2e/` (under `apps/web/`,
  with the Vitest `include` glob extended to
  `["test/**/*.test.ts," "tests/**/*.test.ts"]`) to align
  with the repo convention (ADR-009:87-89) while keeping
  Playwright (`.spec.ts`) and Vitest (`.test.ts`) on
  disjoint file extensions. Earlier drafts used `e2e/`
  (matching Next's canonical example) and then
  `test/e2e/` (matching the singular `apps/cli/test/`
  convention); the final placement preserves both
  conventions by using the plural `tests/` for the app
  and the singular `test/` for the existing Vitest
  unit suite at `apps/web/test/unit/orpc.test.ts`
  (PR #85).
- **2026-08-20**: chose Vercel preview URL over `next
  start` for the same reason ADR-016 rejects the latter:
  the production cache headers are observable only in the
  production environment. Explicit override of ADR-016's
  rejection rationale for the narrow case of a UI smoke
  test that needs the production cache behavior.
- **2026-08-20 (v3)**: replaced the bespoke `E2E_TEST_SECRET`
  with Vercel's documented
  [Protection Bypass for Automation](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation).
  Earlier drafts proposed either a separate e2e-only
  secret (v2 of this ADR) or a runtime-mutated env flag
  (v1). Vercel exposes the Vercel-managed bypass secret as {/* vale fix: write-good.Passive */}
  `VERCEL_AUTOMATION_BYPASS_SECRET` system env var, serves
  as the gate that unlocks the preview URL, AND is the
  single secret the oRPC handler reads to enable the
  test-only failure path. The duplicate-secret surface
  drops out; the Playwright config snippet adapts
  verbatim from Vercel's canonical example. Added the
  `x-vercel-set-bypass-cookie: true` follow-up header so
  client-side navigations (the issue #81 recovery
  scenario in P0-3) inherit the bypass automatically via
  `Set-Cookie`. Deployment Protection is now required
  on the Vercel project; the activation is in scope of
  this ADR.
