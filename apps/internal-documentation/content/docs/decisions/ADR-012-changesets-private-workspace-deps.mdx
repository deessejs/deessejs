# ADR-012: Changesets versioning for private workspace deps

## Status

Accepted (2026-08). Non-negotiable.

## Context

`@deessejs/cli` is the only published package in the monorepo.
The other sixteen workspace packages (`@workspace/api`,
`@workspace/contracts`, `@workspace/auth`, `@workspace/database`,
`@workspace/ui`, plus all apps except `@deessejs/cli`) carry
`"private": true` and are never published to npm.

Since the oRPC migration, the CLI depends on two of those
private packages at the source level:

- `@workspace/api` provides `appRouter` (type-only) and the
  routing path constants (`API_BASE_PATH`, `API_RPC_PATH`).
  The lowercase `api` segment is the npm package name; the
  constant prefixes use the canonical casing.
- `@workspace/contracts` provides the Zod-derived type
  `TemplatesListResponseV1` (type-only at the CLI side).

The dependency is real at the TypeScript level. The CLI imports
from the API package's router module and from contracts v1 to
let `tsc` infer `RouterClient<typeof appRouter>` and
`TemplatesListResponseV1`. At runtime, tsup bundles the code via
`noExternal: [/^@workspace\//]`, so the published bundle doesn't
require these packages to ship with the bundle.

The `.changeset/config.json` currently declares
`"privatePackages": { "version": false, "tag": false }`. This
setting suppresses versioning for every private package. When
the release workflow reaches `pnpm changeset version`, Changesets
runs a dependency-graph consistency check and refuses to bump a
versioned package that depends on a skipped one. The CLI's two
private workspace deps trigger this check. The release fails at
the `Bump versions` step with this message:

~~~
The package "@deessejs/cli" depends on the skipped package
"@workspace/api", but "@deessejs/cli" is not being skipped.
Please add "@deessejs/cli" to the `ignore` option.
~~~

The fix targets the config rather than the CLI itself.

The original config came from
`docs/engineering/reports/versioning/06-implementation-specs.md`
section 6.1 with the rationale: *"Suppresses cosmetic version
bumps on private packages."* That assumption was correct in
July 2026, when the CLI had no workspace dependencies. It became
stale after the oRPC migration added two. The release workflow
hasn't produced a successful `@deessejs/cli` release since the
2.0.0 bump, even though `apps/cli/package.json` carries `2.0.0`.

## Decision

`.changeset/config.json` carries
`"privatePackages": { "version": true, "tag": false }`. Changesets
versions private workspace packages whenever other packages they
sit beneath (directly or transitively) ship a release. The
private packages don't get tagged or pushed to npm.

### Why this and not the alternatives

The four patterns that would resolve the ValidationError each
have a load-bearing flaw:

1. **Add the CLI to `ignore`.** This decouples the only
   published package from the release pipeline. The CLI must be
   bumped, tagged, published, and release-noted by Changesets.
   Adding it to `ignore` would force every CLI release to be
   manual, which is the opposite of the senior pattern locked in
   by `docs/engineering/reports/versioning/07-decisions.md`.
2. **Bundle the deps via `bundledDependencies`.** The code is
   already in the bundle via tsup's `noExternal`. The npm
   protocol `bundledDependencies` would require removing the
   imports from `dependencies` and adjusting `tsup.config.ts`.
   This reopens the 1.1.1 hotfix (the one that introduced
   `noExternal` to stop npm install from 404'ing) for no
   observable gain.
3. **A `prepublishOnly` script that rewrites `workspace:*` to
   real versions.** This solves a different problem (the
   `EUNSUPPORTEDPROTOCOL` error at `npm install`) and doesn't
   address Changesets' graph check, which runs before publish.
4. **Extracting the path constants into a new
   `@workspace/api-paths` package.** Conceptually cleaner, but
   the path constants are a side concern. The load-bearing
   dep is `@workspace/contracts`, which no one can move. A
   new package would resolve only the path constants and leave
   the contracts dep behind, which forces a follow-up ADR.

The
[Changesets `privatePackages` configuration](https://changesets.dev/guide/config)
documents `{ version: true, tag: false }` as the canonical
pattern for a monorepo where exactly one package ships to npm
and the others stay private workspace deps. Changesets passes
the graph check because it knows each private package has a
graph check because Changesets knows each private package has a
version, even though no tag or publish happens for them.

### Cost

Every release bumps the version field of all sixteen private
workspace packages and regenerates their `CHANGELOG.md`. The
churn is cosmetic. The packages never ship to npm, never get tagged,
never imported from npm. The CHANGELOG noise is the price of
keeping the CLI on the senior release pattern.

### What this ADR doesn't change

- `@workspace/contracts` remains `private: true`. It's never
  published to npm. The hotfix in CLI 1.1.1 stands.
- The CLI's `package.json` keeps the `workspace:*` entry for
  `@workspace/api`. The dependency serves two roles: type-only
  imports (`appRouter`) and string constants (`API_BASE_PATH`,
  `API_RPC_PATH`). The runtime side is inlined by tsup via
  `noExternal: [/^@workspace\//]`, so the published bundle is
  self-contained. Restructuring this dep (moving to
  `devDependencies`, splitting the path constants into a
  dedicated package, or switching to `peerDependencies`) is a
  separate refactor that crosses the ADR-005 boundary on path
  co-location. Out of scope here.
- The `privatePackages: { tag: false }` half stays. No git
  tags for private packages; only the CLI gets
  `release/v{VERSION}` tags.

## Consequences

- `pnpm changeset version` succeeds at every release. The
  release workflow unblocks.
- The CLI ships `2.0.1` (or whatever the current bump lands
  on) on the next workflow run after this ADR lands on
  `staging` and reaches `main`.
- Private package `CHANGELOG.md` files gain entries on every
  release. The entries are real (the version did move) but
  carry no consumer-facing meaning. A noise filter at
  consumption time isn't worth the complexity.
- The versioning report (`docs/engineering/reports/versioning/
  01-current-state.md`) needs an update to reflect that the
  assumption *"@deessejs/cli has no workspace deps"* (line 27
  of `06-implementation-specs.md`) no longer holds. Tracking
  happens in a separate issue; the report's recommendation is
  superseded by this ADR.
- `apps/cli/package.json` no longer carries the duplicate
  `@workspace/contracts` entry (it stays in `devDependencies`
  for typecheck). The package is still consumed at build time
  via tsup `noExternal`, and via TypeScript's compiler under `devDependencies`.
  No runtime behavior change.
