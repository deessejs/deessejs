# ADR-017: Templates integration test hits the real GitHub API

## Status

Accepted (2026-08). Non-negotiable.

## Context

The current `packages/api/tests/integration/rpc/templates.test.ts`
mocks `enrich()` at the module boundary (per the round-2 pin
in ADR-016):

```ts
vi.mock(import("../../../src/core/templates/index.js"), () => ({
  enrich: vi.fn(async () => [
    { slug: "saas-starter", ... },
  ]),
}))
```

The mock is fast, deterministic, and free. It also hides every
class of bug that lives between the `enrich()` boundary and
the real GitHub REST API:

- A typo in `packages/api/src/core/github/client.ts` (wrong
  endpoint, wrong header, missing auth) never caught here.
- A regression in `fetchRepo` / `fetchReadme` payload parsing
  (for example, the base64-with-newlines handling at
  `client.ts:60-61`) never caught here.
- A contract change on GitHub's side (for example, a rename
  of `stargazers_count` or `pushed_at`) never caught here.
- A timeout, rate-limit, or 5xx from GitHub never caught
  here. The mock returns instantly.

The pre-existing `packages/api/tests/contract/templates-list.test.ts`
already exercises the procedure logic via `call()` with a mock.
The `enrich()` boundary itself is the only place where code
consumes the real GitHub wire; mocking it shifts every
contract regression from "test fails" to "production
breaks."

The user's stance in 2026-08 was: "if the test fails because
of a real GH error, that's a real problem to test and fix
if it becomes recurrent." The current test hides that
category of failure entirely.

## Decision

Drop the `vi.mock(import("..."))` for `enrich` in the
integration test. The test hits the real
`https://api.github.com/repos/{owner}/{repo}` and
`.../readme` endpoints through the real
`packages/api/src/core/github/client.ts` module.

The fixture (one entry in `packages/api/src/templates.ts`)
stays. The test continues to call `POST /api/v1/rpc/templates/list`
with no input. The procedure calls `enrich(TEMPLATES)`,
which calls `fetchRepo("deessejs", "saas-template")` and
`fetchReadme("deessejs", "saas-template")` against
`api.github.com`.

### What this catches that the mock doesn't

- GitHub response shape drift (for example, a field removed
  or renamed).
- Auth header bug (`Bearer` prefix, `X-GitHub-Api-Version`
  pinning, `User-Agent`).
- Base64 README decoding (the `Buffer.from(content, "base64")`
  call at `client.ts:61` is easy to break with whitespace or
  encoding changes).
- Rate-limit / 5xx handling: the route currently returns
  503 on any failure. A real test confirms the 503 path is
  wired (the route catches, the envelope is correct).
- The `GITHUB_TOKEN` plumbing: `serverEnv.GITHUB_TOKEN` is
  read by `enrich.ts:27`. Without a real test, a regression
  in the env resolution is invisible.

### What this risks

- **Rate limits.** Anonymous: 60 req/h per IP. With a
  `GITHUB_TOKEN`: 5000 req/h. CI runners share an IP. The
  test runs once per CI run on `push`/`pull_request` and
  once on nightly + verify workflows. Each test invocation
  fires 2 GitHub requests (`repos/{owner}/{repo}` +
  `repos/{owner}/{repo}/readme`). With ~30 CI runs/day, the
  anonymous budget exhausts in minutes. **A `GITHUB_TOKEN`
  is mandatory.**
- **Latency.** GitHub's REST API averages 200-500ms. The
  test currently runs in 92ms (mock). Real-GitHub latency
  is 400ms-1s for the two parallel requests in
  `enrich.ts:29-54`. The Vitest hook timeout is 10s
  (set in `packages/vitest-config/src/index.ts:17`); the
  test fits with margin.
- **Flakiness.** Any GitHub outage or rate-limit failure
  becomes a CI failure. ADR-016 round 3 added a loud-skip
  pattern for Postgres (`postgres:ready`). GitHub deserves
  the same approach: skip with a clear signal when
  rate-limited, fail with a clear signal when the response
  shape drifts.
- **Network in CI.** Most CI providers allow outbound
  HTTPS. GitHub works everywhere. No exception needed in
  `.github/workflows/ci.yml`.

### What the change adds

Three concrete changes. They land in the same PR as the test
update; together they make the test stable on real network.

#### 1. Rate-limit-aware skip in the test

Same pattern as the `postgres:ready` flag. The test reads
`inject('github:ready')` at file load. The global setup does
a low-cost GitHub `GET /rate_limit` probe. If the response
shows remaining quota below a threshold, skip the test with
a clear signal (test name carries `[skip-github]`, global
setup emits a WARN).

The skip is **conditional**, not silent. A CI job that
loses network or quota shows the skip in the test name and
in the log aggregator. A CI job with full quota runs the
test and asserts the real response.

The threshold is 10 remaining requests (anonymous quota
resets hourly; a token grants 5000/h so the threshold is
irrelevant there). Below 10, the test skips.

#### 2. `GITHUB_TOKEN` as a Continuous Integration secret

The repo already references `GITHUB_TOKEN` for release and
changesets workflows (per
`docs/internal/learnings/changesets/README.md:110`). The
integration job at `.github/workflows/ci.yml:119-126`
needs the same secret injected into the env:

```yaml
env:
  GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

The token is the standard GitHub Actions token (`secrets.GITHUB_TOKEN`).
Its scope is the workflow run, its rate-limit budget is
1000 req/min, which is enough for hundreds of CI runs per
day. The token doesn't need any specific permissions for
`GET /repos/...` and `GET /repos/.../readme` on a public
repo.

#### 3. Test-classification, real-network vs pure

ADR-016's test seams include a fixture convention that
fixtures must derive from the Zod schemas
(`@workspace/contracts/src/vN/`). That convention holds.

ADR-017 adds a second convention: tests that hit the real
network must declare it. Concretely:

- File-level annotation at the top of
  `rpc/templates.test.ts`:

  ```ts
  /**
   * @testClass integration
   * @network github (real)
   * @rateLimitAware true
   */
  ```

- The CI workflow annotation tags the integration job
  with the same fields. A future contributor running a
  subset of tests locally can skip network-touching tests
  via `vitest --testNamePattern="network:"` (negative
  filter) or similar.

This is documentation, not enforcement. The alternative is a
custom Vitest reporter that reads file annotations, which
is overkill for two tests today.

### The four failure modes and how each scenario lands

| Failure mode | Symptom | Test behaviour | CI signal |
|---|---|---|---|
| GitHub 200 OK with correct shape | 200 + valid wire envelope | ✅ pass | green |
| GitHub 200 OK with shape drift | 200 + unexpected body | ❌ fail | loud red |
| GitHub 401/403/429 | route catches → 503 + not-ready | ✅ pass (envelope pinned) | green, but flagged by observability |
| GitHub network timeout / DNS failure | `fetchRepo` throws → 503 + not-ready | ✅ pass (envelope pinned) | green, but flagged by observability |

The two middle rows are why the test stays in CI even when
the happy path is intermittent: every failure mode exercises
the route's failure envelope. The mock hid these.

### Why a separate ADR, not an ADR-016 revision

ADR-016 is about the harness structure (in-process
`api.request()`, schema-derived fixtures, loud Postgres skip).
ADR-017 is about a single test's mocking strategy and the
operational cost (rate limits, latency, CI secret). Mixing
them obscures the decision. A separate ADR also lets the
PR that adds the real-network test land independently of
the rest of ADR-016's surface. The change is a 3-line diff
in the test file plus a CI secret wiring.

## Consequences

- The `templates.list` integration test exercises the real
  GitHub wire. A contract regression on GitHub's side
  fails CI within one run, not in production.
- The CI workflow needs `GITHUB_TOKEN` injected as an env
  var on the integration job. The token already exists in
  repo secrets.
- The global setup adds a GitHub rate-limit probe. The
  probe adds 1 GitHub request per CI run; well within the
  5000/h budget with a token.
- A local developer running the test without `GITHUB_TOKEN`
  falls back to anonymous quota (60/h). The skip threshold
  of 10 makes the test stable on the first few runs of the
  hour and skips for the rest. A developer who runs the
  test continuously exhausts the budget fast; they get
  skips, not failures. This is the correct trade-off.
- A future contributor who adds another oRPC procedure
  that hits a real network should follow the same pattern:
  declare `@network <provider>` in the file header, add a
  rate-limit-aware skip, gate on a global-setup flag.

## Out of scope

- Real-network tests for the Better Auth `/api/v1/auth/get-session`
  smoke test (it already hits the auth library in-process,
  not a network endpoint).
- A custom Vitest reporter for the `@network` annotation.
  ADR-017 keeps the annotation as documentation only.
- Rate-limit budget tracking across CI runs. The threshold
  is local to the test; cumulative usage isn't tracked.

## Decision log

- **2026-08-18**: discussed with the user. The current
  mock hides GitHub contract regressions; the user wants
  the real network in CI, with rate-limit-aware skip for
  flakiness. Drafted this ADR.
- **2026-08-18**: chose the three changes (rate-limit skip,
  CI secret, file annotation) as the smallest viable set.
  Rejected alternatives: dedicated `octokit` dependency
  (overkill for two endpoints), per-test mock with golden
  snapshots (defeats the purpose), nightly only real-network
  test (delays detection by 24h, defeats the user's
  stated goal).
