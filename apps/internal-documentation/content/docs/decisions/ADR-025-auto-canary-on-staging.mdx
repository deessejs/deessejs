# ADR-025: Auto-canary on staging

## Status

Proposed (2026-09). Awaiting review.

## Context

Today, the `@canary` channel for `@deessejs/cli` is published via a manual `workflow_dispatch` run on `release.yml` with `canary: true`. A maintainer must open the Actions tab, select the workflow, check the input, and click **Run workflow**. The channel exists but the friction is high enough that canarys are rare.

Three concrete consequences:

1. **Dogfooding is gated on a maintainer.** A contributor who wants to test a feature on staging before it lands on `@latest` cannot trigger a canary on their own. They ask a maintainer, who may or may not be around.
2. **Staging work is invisible to consumers.** A consumer who wants to test the next release against their integration cannot `npx @deessejs/cli@canary` until a maintainer publishes one. The work on staging does not flow to npm.
3. **The release pipeline has a hidden hole.** `release.yml` already does the canary work; it just requires a human to trigger it. The pipeline is 90% automatic and 10% manual. Closing the 10% removes the surprise.

This ADR moves the canary trigger from `workflow_dispatch` to `push: branches: [staging]`. Every merge to staging publishes a `@canary` build automatically.

## Decision

A new workflow `.github/workflows/staging-canary.yml` triggers on every push to `staging` and publishes `@canary`. The canary publish logic is extracted from `release.yml` into a reusable job and exposed via `workflow_call`, so both workflows share the same implementation.

### Why a new workflow and not a new trigger on `release.yml`

`release.yml` triggers on `push: branches: [main]` and on `workflow_dispatch`. Adding `push: branches: [staging]` would conflate two release tiers on the same workflow file, which conflicts with the "single canonical release workflow" property that ADR-021 records as the load-bearing design. Splitting the trigger into two workflows preserves that property.

The shared job inside `release.yml` is declared with `workflow_call` so `staging-canary.yml` can invoke it without duplicating the canary implementation. This is the only structural change to `release.yml`.

### What the new workflow does

`staging-canary.yml`:

```yaml
name: staging-canary

on:
  push:
    branches: [staging]

concurrency:
  group: staging-canary-${{ github.sha }}
  cancel-in-progress: false

permissions:
  contents: write
  id-token: write

jobs:
  canary:
    uses: ./.github/workflows/release.yml
    with:
      channel: canary
    secrets: inherit
```

The `secrets: inherit` is required because the canary publish needs `NPM_CONFIG_PROVENANCE` (inherited as an env var via OIDC) and no additional secrets. `permissions: id-token: write` is required because the called workflow requests OIDC for npm Trusted Publishing.

### Why the concurrency group is keyed on SHA

A push to staging that contains multiple commits (rare but possible, e.g. force-pushes) results in a single SHA at the end. The concurrency group `${{ github.sha }}` means a SHA in flight will not be re-published by a subsequent push that lands on the same SHA. If a force-push changes the SHA, the previous run completes (cancel-in-progress: false) and a new one starts.

`cancel-in-progress: false` is deliberate. A canary publish carries side effects (a tag, a GitHub Release, an npm publish). Canceling mid-publish would leave a partial artifact. We let the in-flight publish finish and discard any newer publishes that race with it.

### What changes in `release.yml`

Two changes:

1. The `release` job gains a `workflow_call` trigger and accepts a `channel` input:

```yaml
on:
  push:
    branches: [main]
  workflow_dispatch:
    inputs:
      canary:
        description: 'Publish a @canary build from the current commit (instead of @latest).'
        type: boolean
        required: true
        default: false
  workflow_call:
    inputs:
      channel:
        description: 'Pre-selected channel: latest or canary. Bypasses input detection.'
        type: string
        required: true
```

2. The `Determine release channel` step is updated to honor the `channel` input:

```yaml
- name: Determine release channel
  id: channel
  run: |
    if [ -n "${{ inputs.channel }}" ]; then
      case "${{ inputs.channel }}" in
        canary)
          echo "dist_tag=canary"          >> "$GITHUB_OUTPUT"
          echo "release_type=prerelease"  >> "$GITHUB_OUTPUT"
          echo "version_source=synthetic" >> "$GITHUB_OUTPUT"
          ;;
        latest)
          echo "dist_tag=latest"        >> "$GITHUB_OUTPUT"
          echo "release_type=stable"    >> "$GITHUB_OUTPUT"
          echo "version_source=changeset" >> "$GITHUB_OUTPUT"
          ;;
      esac
    elif [ "${{ github.event_name }}" = "workflow_dispatch" ] && [ "${{ inputs.canary }}" = "true" ]; then
      echo "dist_tag=canary"          >> "$GITHUB_OUTPUT"
      echo "release_type=prerelease"  >> "$GITHUB_OUTPUT"
      echo "version_source=synthetic" >> "$GITHUB_OUTPUT"
    else
      echo "dist_tag=latest"        >> "$GITHUB_OUTPUT"
      echo "release_type=stable"    >> "$GITHUB_OUTPUT"
      echo "version_source=changeset" >> "$GITHUB_OUTPUT"
    fi
```

When the workflow is called from `staging-canary.yml`, the `inputs.channel` is set and the step emits the canary outputs immediately. The detection logic for `workflow_dispatch` and `push: main` paths stays intact.

### Trusted publisher constraint

npm Trusted Publishing allows only one trusted publisher per package, keyed on the workflow file path. `release.yml` is already configured on `https://www.npmjs.com/package/@deessejs/cli/access`. Adding `staging-canary.yml` as a separate publisher would be rejected.

This is why the canary job is invoked via `workflow_call` from `release.yml`: npm sees the call site as a run of `release.yml`, the trusted publisher matches, and the publish succeeds. The `staging-canary.yml` file is a trigger wrapper, not a publisher.

The trust boundary is therefore the same as today: only `release.yml` has OIDC. `staging-canary.yml` inherits OIDC via `workflow_call`. If `staging-canary.yml` is compromised, the attacker still needs the trusted publisher to match, which is checked by GitHub Actions at the publish step. A `workflow_call` that surfaces a job from a compromised wrapper still runs the trusted workflow's steps; the wrapper cannot inject arbitrary publish commands.

## Consequences

**Wins:**

- Canaries are continuous. Every staging merge produces an installable canary.
- Consumers can `npx @deessejs/cli@canary` at any time after a staging merge.
- The release pipeline has zero human clicks for the canary path.

**Losses:**

- npm and the GitHub Releases feed accumulate more tags and releases. Canary retention was already best-effort (per the existing process page); the increased cadence makes the cleanup more important.
- A broken staging build produces a broken canary on every merge. The canary is no longer a curated artifact.

**What stays locked:**

- The canary job is unchanged in implementation. The synthetic version format (`<base>-canary.<UTC-timestamp>.<short-sha>`) stays.
- The `@latest` channel is unchanged. `release.yml` continues to publish `@latest` on push to `main` via the `changeset` path. See [ADR-024](./ADR-024-auto-publish-on-main.mdx) for the human-gate removal on that path.
- `cli-preview.yml` is unchanged. The per-PR preview channel still uses pkg.pr.new for ephemeral PR-feedback tarballs.

## How to verify

After the change:

1. Open a PR touching `apps/cli/**` with a changeset. Get approval. Merge to `staging`.
2. Observe `staging-canary.yml` triggers within ~30 seconds. The job calls `release.yml` with `channel: canary`.
3. The canary publishes under `@canary`. `npm view @deessejs/cli@canary version` returns the synthetic version.
4. A `release/v<canary-version>` tag exists on the merge commit. A GitHub Release marked `prerelease` exists.
5. The `@latest` dist-tag is unchanged (`npm view @deessejs/cli@latest version` returns the previous stable).

**Negative test:** push directly to `staging` without going through a PR. The workflow triggers anyway; this is intentional (force-pushes and emergency fixes need it). The canary publishes.

## Where this rule came from

The decision inverts the "manual canary" workflow that ADR-021 documented as on-demand. The reasoning is that canarys are now load-bearing for consumer dogfooding on a continuous release cadence, not a rare debug tool. The cost (npm tag accumulation) is offset by the value (anyone can `npx @deessejs/cli@canary` at any time).

The original ADR-021 reasoning for `workflow_dispatch` was risk-versus-payoff: changesets pre-release mode was operationally heavy and forced a separate branch. With the synthetic versioning scheme (which bypasses changesets pre-release mode entirely), the operational cost drops to near zero, and the on-demand trigger no longer earns its keep.
