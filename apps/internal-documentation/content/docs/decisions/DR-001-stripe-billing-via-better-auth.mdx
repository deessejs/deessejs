# DR-001: Stripe billing via better-auth

## Status

Proposed (2026-09). Awaiting review on `dr/stripe-billing-via-better-auth`.

## Context

The codebase ships zero runtime Stripe code. The
`packages/auth/` instance at `packages/auth/src/auth.ts` instantiates
`betterAuth({...})` with `emailAndPassword`, `emailVerification`,
`session`, and the three pinned plugins
(`deviceAuthorization({...})`, `bearer()`, `nextCookies()`). No
payment, subscription, or billing capability exists anywhere in
the monorepo. The Stripe SDK is not in `dependencies`. No
TypeScript file imports from `stripe`, `stripe-node`,
`@stripe/stripe-js`, or `better-auth/plugins/stripe`. No env var
starting with `STRIPE_` lives in `packages/env/src/schema.ts` or
in the repo-root `.env.example`. No webhook handler exists under
any `apps/**/app/api/`. No `/billing`, `/checkout`, or
`/subscription` route exists in `apps/app/`. The marketing site
`/pricing` page renders three static plans and routes payment
out-of-band via `mailto:support@deessejs.com`.

Stripe references in the tree are documentation only:
`documents/internal/architecture/01-stack/stripe.md` (the
canonical ADR-level design doc), the SVG logo at
`apps/web/public/logos/stripe.svg` (marketing asset), the FAQ
copy in `apps/web/src/lib/pricing.ts` (lists Stripe among the
covered stacks), and the `BillingWidgetMockup` decorative
component on the marketing landing page (`purely visual`,
`apps/web/src/app/(marketing)/_components/contracts-grid.tsx`).
The "Billing" and "Upgrade to Pro" items in
`apps/app/components/sidebars/nav-user.tsx` are static labels
with no handler.

The project is single-tenant by design (see
`docs/guides/better-auth/org.md`, marked "historical reference
only"). The organization plugin is intentionally absent from
`packages/auth/src/auth.ts`. The same constraint applies to a
Stripe integration: there is no organization table to bill to.
Every customer is a user; every subscription's `referenceId` is
a user id; `customerType` is `"user"` on every call.

The Stripe SDK is not pinned in `pnpm-workspace.yaml`. The
catalog blocks `stripe@*` (no version declared) and the
`@better-auth/stripe` package is not declared anywhere. The
better-auth version installed is `1.6.23` (per `pnpm-lock.yaml`);
the official Stripe plugin (`@better-auth/stripe@1.7.2` at the
time of writing) declares `better-auth ^1.7.2` and
`@better-auth/core ^1.7.2` as peer dependencies. The version
delta is the load-bearing constraint this DR resolves.

The plugin adds two schema changes that the rest of the
codebase does not yet anticipate. First, a `stripeCustomerId`
column on the `user` table (a string column, optional, written
when `createCustomerOnSignUp: true` is set and read by every
Stripe call thereafter). Second, a new `subscription` table with
sixteen columns (`plan`, `referenceId`, `stripeCustomerId`,
`stripeSubscriptionId`, `status`, `periodStart`, `periodEnd`,
`trialStart`, `trialEnd`, `cancelAtPeriodEnd`, `cancelAt`,
`canceledAt`, `endedAt`, `seats`, `billingInterval`,
`stripeScheduleId`). Both changes go through the existing
`pnpm auth:generate` script that writes
`packages/database/src/schema/auth.ts`, plus a Drizzle migration
generated by `pnpm db:generate`. No hand-edit to the schema file
(the file is owned by the auth CLI per the comment at its top).

The webhook endpoint is auto-mounted by the plugin at the
configured better-auth `basePath` plus `/stripe/webhook`. The
current `basePath` is `/api/v1/auth` (the local constant
`AUTH_BASE_PATH` in `packages/auth/src/auth.ts`). The full path
is therefore `/api/v1/auth/stripe/webhook`. The Hono catch-all
at `apps/app/app/api/[[...route]]/route.ts` already delegates
`/api/v1/auth/*` to `auth.handler(c.req.raw)` (the line at
`packages/api/src/http/routes/http.ts:57`), so no Hono route
edit is required. The Stripe signature verification uses
`stripeWebhookSecret` and the raw request bytes preserved by the
plugin's `disableBody: true` + `cloneRequest: true` setting.

The current `experimental.joins: true` flag in
`packages/auth/src/auth.ts:71` and the Drizzle adapter in
`packages/database/src/schema/auth.ts` (owned by `auth:generate`)
do not yet enable joins in the adapter (the gap is
`documents/internal/architecture/11-packages/auth/M0-deferred-work.md`
item 3). The Stripe plugin does not require joins; this DR does
not close the deferred gap.

`apps/app/proxy.ts` (the Next.js 16 proxy replacing
`middleware.ts`) gates `(protected)` routes on
`session.user.emailVerified`. Stripe's webhook never carries a
session cookie; the proxy must not block it. The proxy today
exempts a static list of paths; this DR adds one to that list
(`/api/v1/auth/stripe/webhook`).

The `secondaryStorage` option in better-auth is a no-op stub in
this repo (the M0-deferred-work item 2). Stripe's plugin does
not depend on `secondaryStorage`, but rate-limits on the new
endpoints (`/subscription/upgrade`, `/subscription/cancel`,
`/subscription/restore`, `/subscription/billing-portal`) remain
broken in production until Upstash Redis lands. This DR does
not close that gap; it scopes itself to Stripe wiring.

## Decision

Wire the official `@better-auth/stripe` plugin into
`packages/auth/` and surface the `subscription` client API in
the three client factories (`apps/app`, `apps/web`, `apps/cli`).
The scope of this DR is **server + clients only**. No new
surface in `apps/app/` (no `/billing` route, no settings page,
no sidebar wiring). No surface change in `apps/web/` (the
static `/pricing` page stays static). No CLI command surface.
The deliverable is the plugin wired end-to-end with hardcoded
plans and verified via a script-level smoke.

The plugin does not introduce a UI affordance the user can
reach. The smoke test exercises the endpoints with `curl` and
the Stripe CLI against the locally-forwarded webhook. UI work
is a follow-up DR.

### Server config

`packages/auth/src/auth.ts` adds `stripe(...)` to the existing
`plugins: [deviceAuthorization({...}), bearer(), nextCookies()]`
array. The new entry goes **before** `nextCookies()` (the rule
documented at `docs/guides/better-auth/hooks.md` §"Plugin order"
is that `nextCookies()` is last):

```ts
import Stripe from "stripe"
import { stripe } from "@better-auth/stripe"

const stripeClient = new Stripe(
  serverEnv.STRIPE_SECRET_KEY || "sk_test_placeholder",
  { apiVersion: "2024-12-18.acacia" },
)

plugins: [
  deviceAuthorization({ verificationUri: "/device" }),
  bearer(),
  stripe({
    stripeClient,
    stripeWebhookSecret: serverEnv.STRIPE_WEBHOOK_SECRET!,
    createCustomerOnSignUp: true,
    subscription: {
      enabled: true,
      plans: [
        {
          name: "starter",
          priceId: serverEnv.STRIPE_PRICE_STARTER!,
          limits: { projects: 1, storageMb: 512 },
        },
        {
          name: "pro",
          priceId: serverEnv.STRIPE_PRICE_PRO!,
          limits: { projects: 10, storageMb: 5120 },
        },
      ],
    },
  }),
  nextCookies(),
],
```

Three things to note:

1. `createCustomerOnSignUp: true` creates a Stripe customer on
   first sign-in (and attaches the customer id to the user's
   `stripeCustomerId` column). The default is `false`; opting
   in avoids a second round-trip on the first
   `authClient.subscription.upgrade()` call.
2. Plans are **hardcoded** in the auth config. No DB-backed
   `plans: async () => ...` indirection in this DR. Adding the
   indirection is a separate scope (it adds a `plan` table, an
   admin CRUD surface, and a new migration).
3. `organization` is **not** set. The project is single-tenant;
   no `customerType: "organization"` path is reachable. The
   plugin defaults `organization.enabled` to `false`, which is
   the desired state.

The `stripeClient` instance is built once at module load. The
SDK instance is re-used on every Stripe call; the plugin does
not require a per-request factory.

The plugin requires `stripe ^18` through `^22` as a peer dep. This DR
pins `stripe@^18` in the catalog (the lowest version still
under upstream support, matching the plugin's stated
compatibility range). The `apiVersion` literal
`"2024-12-18.acacia"` matches the SDK default for that range;
pinning it makes the contract auditable.

### Env contract

`packages/env/src/schema.ts` adds four server-only fields:

```ts
STRIPE_SECRET_KEY: z.string().min(1).optional(),
STRIPE_WEBHOOK_SECRET: z.string().min(1).optional(),
STRIPE_PRICE_STARTER: z.string().min(1).optional(),
STRIPE_PRICE_PRO: z.string().min(1).optional(),
```

All four are **optional**, matching the precedent of
`BETTER_AUTH_SECRET` (`schema.ts:20-23`) and `GITHUB_CLIENT_*`
(see ADR-028). Optional, not required, because the rest of the
test suite (Vitest, Drizzle migration tests, integration
suites that sign in via email/password) must continue to run
without Stripe credentials on disk. The plugin's
`stripeWebhookSecret: serverEnv.STRIPE_WEBHOOK_SECRET!` reads
`undefined` at request time if the env is unset; better-auth
fails loud (the same failure mode as a missing
`GITHUB_CLIENT_ID` per ADR-028 §"Server config"). The
`!`-assertion is acceptable per the same ADR.

`packages/env/src/server.ts` exposes the four keys through the
`materialised` literal block (the same shape as the `Resend*`
pair and the `GITHUB_CLIENT_*` pair added in ADR-028). The
proxy at `packages/env/src/server.ts:72-85` already iterates
the server-side list; the four keys are added in the same edit.

`.env.example` at the repo root gains the four keys, with a
comment block covering:

- The Stripe Dashboard click-path to obtain the secret key
  (Developers → API keys → Reveal live key).
- The Dashboard click-path to obtain the webhook signing secret
  (Developers → Webhooks → Add endpoint → URL
  `https://app.deessejs.com/api/v1/auth/stripe/webhook` → Reveal
  signing secret).
- The Dashboard click-path to obtain the price ids (Products →
  click product → copy price id from the pricing table).
- The webhook events to subscribe in the Dashboard. The
  plugin handles the four lifecycle events internally;
  six more events fall through to the `onEvent(event)` hook
  configured in `packages/auth/src/auth.ts`. The complete
  list (lifecycle plus operational):
  - `checkout.session.completed` (lifecycle).
  - `customer.subscription.created` (lifecycle).
  - `customer.subscription.updated` (lifecycle).
  - `customer.subscription.deleted` (lifecycle).
  - `invoice.payment_failed` (operational: card declined,
    funds insufficient, 3DS required; flips the local
    subscription to `past_due` and powers the
    `past_due` UI state in `billing-current-plan.tsx`).
  - `invoice.payment_action_required` (operational: off-session
    authentication required; the user is silently blocked
    from the service until they confirm).
  - `invoice.paid` (operational: recovery after a failed
    payment; flips `past_due` back to `active`).
  - `invoice.finalized` (operational: captures the latest
    invoice id for the billing history UI).
  - `checkout.session.expired` (lifecycle: cleans up rows
    left at `status: "incomplete"` when a Checkout session
    expires before completion).
  - `payment_method.attached` and `payment_method.detached`
    (operational: refreshes the payment-method cache that
    `billing-payment-method.tsx` reads).
  - `setup_intent.succeeded` (operational: billing-portal
    flow attaching a new card without a checkout session).

### Database schema

Two changes flow from `pnpm auth:generate`:

1. The `user` table gains an optional `stripeCustomerId`
   column.
2. A new `subscription` table lands with the sixteen columns
   documented above. The model name is `subscription` (the
   plugin default). No rename in this DR.

The change-set runs as follows:

```bash
pnpm --filter @workspace/auth auth:generate
pnpm --filter @workspace/database db:generate --name stripe_subscription
```

The second command emits a new SQL file under
`packages/database/drizzle/`. The migration is reviewed
locally before commit (the precedent is
`packages/database/drizzle/0000_boring_steel_serpent.sql` and
`0001_magenta_firebrand.sql`). The migration is **not** run
during `pnpm install` or during CI; staging and production
apply it via `pnpm db:migrate` after the PR merges (per
`ADR-015-drizzle-migrations-ci`).

The plugin's published schema declares zero indexes on the
`subscription` table. The project convention is to index
every column that is read by an authorization or webhook
backfill (see `packages/database/src/schema/auth.ts:33,57,73,116-117`
for the precedent). The implementation PR adds an index on
`subscription.referenceId` via the plugin's `schema:` option.
The override is additive: it preserves the table name and all
column names from the plugin default, and adds an index
block. The override does not rename the model or any column,
so the `What this rule forbids` §"Renaming the subscription
table" rule stays intact.

`stripeCustomerId` and `stripeSubscriptionId` carry implicit
unique indexes from the plugin's `unique()` constraint
(Postgres behavior), so lookups by those columns are fine
without an explicit index. `referenceId` has no such
constraint and would otherwise fall back to a sequential
scan once the table grows past a few hundred rows.

### Client wiring

Three client factories gain the `stripeClient` plugin.

**`apps/app/lib/auth-client.ts`** (the primary app client):

```ts
import { stripeClient } from "@better-auth/stripe/client"

plugins: [
  deviceAuthorizationClient(),
  stripeClient({ subscription: true }),
]
```

**`apps/web/src/lib/auth-client.ts`** (the marketing factory):

```ts
import { stripeClient } from "@better-auth/stripe/client"

plugins: [
  stripeClient({ subscription: true }),
]
```

The marketing site has no Stripe-aware surface today; the
plugin is wired for parity (the marketing header is
session-aware per ADR-023, and a future pricing CTA would call
`authClient.subscription.upgrade()`).

**`apps/cli/src/lib/auth/store/better-auth-client.ts`** (the
CLI client):

```ts
import { stripeClient } from "@better-auth/stripe/client"

plugins: [
  deviceAuthorizationClient(),
  stripeClient({ subscription: true }),
]
```

The CLI does not expose a subscription command today. The
plugin is wired for parity (the device-flow-based
authentication surface is the same shape, and a future
`subscribe` command would consume `authClient.subscription.*`
methods).

### Webhook mount

No Hono route is added. The plugin mounts its endpoint at
`{basePath}/stripe/webhook`, which resolves to
`/api/v1/auth/stripe/webhook` (the `basePath` constant at
`packages/auth/src/auth.ts`). The existing Hono catch-all
(`packages/api/src/http/routes/http.ts:57`) already delegates
`/api/v1/auth/*` to `auth.handler(c.req.raw)`. The new endpoint
flows through the same handler.

`apps/app/proxy.ts` adds `/api/v1/auth/stripe/webhook` to the
path allowlist that the email-verification gate skips (the gate
runs `auth.api.getSession({ headers })` and rejects requests
without a valid session; the Stripe webhook carries no session
cookie). The allowlist is the documented exception mechanism
per ADR-028 §"Route protection".

## Consequences

- **Entitlements (server-side limits enforcement) is out of
  scope for this DR.** The `limits` map returned by
  `authClient.subscription.list()` is consumed by the client
  UI (the `billing-current-plan.tsx` card shows the limit
  values; future copy like "1 of 1 projects created" can be
  derived from them). No oRPC procedure, no Hono middleware,
  and no server action in `packages/api/` reads the `limits`
  field today. A request to `/api/v1/templates/create` is not
  gated by the user's plan; nothing in the codebase enforces
  the limits yet. Server-side entitlement enforcement is a
  separate concern that lands in a future DR (it touches the
  templates router and the `oRPC` `base` middleware, both
  outside this DR's surface).
- The endpoints `POST /api/v1/auth/subscription/upgrade`,
  `GET /api/v1/auth/subscription/list`,
  `POST /api/v1/auth/subscription/cancel`,
  `POST /api/v1/auth/subscription/restore`, and
  `POST /api/v1/auth/subscription/billing-portal` respond to
  authenticated calls. The webhook endpoint at
  `POST /api/v1/auth/stripe/webhook` responds to Stripe's
  server-to-server calls with signature verification.
- The `user` table gains a `stripeCustomerId` column populated
  on first sign-in (because `createCustomerOnSignUp: true` is
  set). Existing users (no column today) get the column on the
  next sign-in after the migration lands; the column is
  optional, so existing rows survive the migration unchanged.
- The new `subscription` table is empty on first migration. A
  subscription row is written on the first webhook receipt
  (`customer.subscription.created` and
  `customer.subscription.updated`). The plugin's
  `status: "incomplete"` default applies to rows written
  before the first webhook lands (a transient state, not a
  load-bearing initial value).
- `apps/app/proxy.ts` continues to gate `(protected)` routes
  on `emailVerified`. The webhook path is exempted; no other
  gate change.
- `packages/auth/src/auth.ts` instantiates the Stripe SDK
  exactly once at module load. The SDK instance is reused on
  every Stripe call. The instance uses a `sk_test_placeholder`
  fallback when `STRIPE_SECRET_KEY` is unset, so the module
  can be imported in CI / Vitest without a real Stripe key on
  disk. Real API calls with the placeholder key fail at
  request time with `StripeAuthenticationError`; that is the
  intended failure mode for environments where Stripe is
  intentionally absent. See the *Server config* section above
  for the exact fallback expression.
- Three client factories (`apps/app`, `apps/web`, `apps/cli`)
  gain `authClient.subscription.{upgrade,list,cancel,restore,billingPortal}`
  methods. None of the methods is called from the codebase
  after this PR merges; the wiring is dormant until the UI
  follow-up lands.
- `pnpm env:check` passes with and without the four `STRIPE_*`
  keys set. The `min(1)` constraint rejects whitespace-only
  strings.
- `pnpm auth:generate` produces a non-byte-identical
  `packages/database/src/schema/auth.ts` (the new column and
  table land). `pnpm db:generate` emits a new SQL file under
  `packages/database/drizzle/`.
- The user-visible surface in `apps/app/` (the `/settings/billing`
  route, the six billing components, the `use-billing` hook,
  the sidebar and hub wiring, and the `BILLING_PLANS` source
  of truth) lands in a follow-up PR whose scope is locked in
  the `UI follow-up scope` section below. The follow-up PR
  does not renegotiate that section; it inherits it.

## What this rule allows

- Adding `stripe(...)` to the `plugins` array in
  `packages/auth/src/auth.ts` with `stripeClient`,
  `stripeWebhookSecret`, `createCustomerOnSignUp`, and a
  hardcoded `subscription.plans` list.
- Declaring `stripe@^18` and `@better-auth/stripe@^1.7.2` in
  `pnpm-workspace.yaml` `catalog:`.
- Adding `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`,
  `STRIPE_PRICE_STARTER`, and `STRIPE_PRICE_PRO` as optional,
  server-only fields in `packages/env/src/schema.ts`, and
  exposing all four in the `materialised` block of
  `packages/env/src/server.ts`.
- Running `pnpm --filter @workspace/auth auth:generate` to
  regenerate `packages/database/src/schema/auth.ts` (the file
  is owned by the auth CLI).
- Running `pnpm --filter @workspace/database db:generate` to
  produce the corresponding Drizzle migration, and committing
  the resulting SQL file.
- Adding `stripeClient({ subscription: true })` to the three
  client factories (`apps/app/lib/auth-client.ts`,
  `apps/web/src/lib/auth-client.ts`,
  `apps/cli/src/lib/auth/store/better-auth-client.ts`).
- Adding `/api/v1/auth/stripe/webhook` to the
  `apps/app/proxy.ts` allowlist.
- A smoke test that calls each new endpoint with mocked
  credentials and asserts the response shape, gated on the
  presence of `STRIPE_SECRET_KEY` at test-time.

## What this rule forbids

- Adding any UI surface in this PR (no `/billing` route in
  `apps/app`, no settings page edit, no sidebar wiring, no
  `/pricing` CTA in `apps/web`). UI work is locked in the
  `UI follow-up scope` section below and lands in a separate
  PR.
- Hardcoding Stripe price ids or webhook secrets anywhere in
  the monorepo outside server-env reads in
  `packages/auth/src/auth.ts`.
- Reading the Stripe secret, webhook secret, or any price id
  through raw `process.env`. The contract is `serverEnv.*`
  from `@workspace/env/server`.
- Hand-editing `packages/database/src/schema/auth.ts` to add
  the `stripeCustomerId` column or the `subscription` table.
  Both come from `pnpm auth:generate`.
- Hand-editing a Drizzle migration file to add the new column
  or table. Both come from `pnpm db:generate`.
- Renaming the `subscription` table or any of its columns via
  the plugin's `schema:` option. The default names match the
  plugin's public API; renaming introduces a translation
  layer that nothing else in this DR needs.
- Enabling `organization: { enabled: true }`. The project is
  single-tenant; the option is dead code.
- Setting `customerType: "organization"` anywhere. The option
  is unreachable by design.
- Adding a custom `BetterAuthPlugin` implementation of Stripe
  in lieu of `@better-auth/stripe`. The official plugin exists
  and is maintained upstream; a fork is a maintenance burden.
- Importing `stripe` (the server SDK) directly from
  `apps/app/components/`, `apps/web/components/`, or any
  client bundle. The boundary held by ADR-003 (server types
  via `$Infer.Session`) and ADR-004 (`@workspace/auth`
  imported only by `http/middleware/session.ts` and
  `http/routes/auth.ts`) stays intact. The Stripe SDK is
  server-only and is imported from `packages/auth/src/auth.ts`
  exclusively.
- Using `experimental.joins` as a justification to enable
  joins in the Drizzle adapter in this PR. The deferred work
  item 2 in `M0-deferred-work.md` stays deferred.

## What this rule does not change

- The `(protected)` route gate in `apps/app/proxy.ts`. Only
  the webhook path is exempted; every other `/api/v1/auth/*`
  endpoint still flows through the existing `emailVerified`
  check (the ones that require it).
- The `account.accountLinking` block in
  `packages/auth/src/auth.ts:67-71` (per ADR-028). Stripe does
  not interact with account linking.
- The `session.expiresIn` and `session.updateAge` settings.
  Stripe's webhook does not establish a session.
- The `experimental.joins: true` flag. The plugin does not
  require joins.
- The `secondaryStorage` no-op stub. The rate-limit gap on the
  new endpoints is unaddressed by this DR.
- The marketing `/pricing` page. The page remains static; the
  four hardcoded `STRIPE_PRICE_*` env vars are the
  implementation surface for a future `/pricing` CTA, not a
  content edit.
- The CLI's published surface. The CLI does not expose a
  `subscribe` or `billing` command in this DR.
- The `packages/auth/tests/` suite shape. No test is added in
  this DR; the verification is a manual smoke documented
  below.

## UI follow-up scope

This DR ships the server wiring and the client factory
extensions only. The user-visible surface in `apps/app/` lands
in a follow-up PR whose scope is locked here. The follow-up PR
inherits this section's contract; it does not negotiate it.

### Route

`apps/app/app/(protected)/settings/billing/page.tsx` is a new
Server Component. The shape is identical to the existing
`apps/app/app/(protected)/settings/sessions/page.tsx`: the
file imports `SettingsPage` and `SettingsCard` from
`@/components/settings` and wraps three `SettingsCard` slots
("Current plan", "Payment method", "Billing history"). No new
`layout.tsx`. No metadata export. The `(protected)` route gate
covers the path automatically because `"/settings"` is in
`PROTECTED_PREFIXES` (see `apps/app/proxy.ts`); no proxy edit
is needed. The Hono catch-all at
`apps/app/app/api/[[...route]]/route.ts` already delegates

## Marketing pricing follow-up scope

The implementation PR wires the Stripe plugin server-side and
the three client factories. The UI follow-up PR ships the
authenticated `/settings/billing` surface. Neither ships a
way for an **unauthenticated** marketing visitor to start a
subscription. This section locks the third follow-up PR that
closes that gap. The follow-up PR inherits this section; it
does not renegotiate it.

The chosen path is **option (a) deferred auth**: the visitor
clicks "Buy Pro" on the marketing `/pricing` page, completes
Stripe Checkout with an email the visitor owns, lands on a
post-checkout redirect into `apps/app/` where the codebase
provisions a `user` row from the email and links the
subscription to it. The path is the only one that respects
the "marketing-first, no friction" stance the `/pricing` page
already takes (the current Pro CTA is a `mailto:` link; the
replacement is the same one-click shape, just routed through
Stripe).

### Why option (a) and not option (b)

Option (b) would require the visitor to sign in (or sign up)
before checkout. That breaks the marketing flow: a visitor
who is not yet a customer is asked to create an account on
the SaaS before paying for the SaaS. The friction is the
exact reason the codebase has no top-level `/signup` →
"buy" flow today; the design separates marketing from the
authenticated product. Option (a) keeps the visitor out of
the auth wall until Stripe confirms the payment, then
provisions an account on the way back. The cost is one new
server-side provisioning step (the webhook handler).

### Page change in `apps/web`

`apps/web/src/app/(marketing)/pricing/page.tsx` is currently
a Server Component (no `"use client"`, no event handlers).
The change required by this follow-up PR is **data-only**:

1. In `apps/web/src/lib/pricing.ts`, the Pro `PricingLayer`'s

   The `external: true` flag stays (the destination is

   The Enterprise CTA is untouched (`/enterprise` stays a

   The Open Community CTA is untouched (`/templates`).
2. The Open Community and Enterprise cards stay as they are

### Server-side provisioning flow

The implementation PR's webhook handler at
`/api/v1/auth/stripe/webhook` is the canonical entry point for
Stripe events. The marketing follow-up PR adds a **second
handler** for the post-checkout redirect:

`apps/app/app/(marketing-onboarding)/checkout-success/page.tsx`
(new route) is what Stripe Checkout's `success_url` points
to. The page is a Server Component that:

1. Reads `searchParams.session_id` (the Stripe Checkout
   session id).
2. Calls `auth.api.getSession({ headers: await headers() })`
   (the standard better-auth session lookup).
3. If the visitor already has a session, redirects to
   `/settings/billing` (the in-app page from the
   `UI follow-up scope` section).
4. If the visitor is anonymous, redirects to
   `/signup?email=<stripe.email>&plan=pro&session_id=<id>`.
   The signup form reads the three query params and pre-fills
   them.

The Stripe webhook (`customer.subscription.created` /
`updated` events) is the source of truth for the subscription
row. The signup flow is the source of truth for the `user`
row. The two are joined by `subscription.referenceId =
user.id` once the signup completes. The plugin's webhook
handler writes the subscription row with
`referenceId = stripeCustomer.metadata.userId` (see the
`getCustomerCreateParams` option in the `Server config`
section above). The marketing follow-up PR sets
`getCustomerCreateParams` to write
`metadata.userId = session.userId` when a session exists, and
leaves it empty when it does not; the webhook handler
back-fills the empty case from the email after signup.

The new code in the marketing follow-up PR is concentrated in
one file:

`apps/app/app/(marketing-onboarding)/checkout-success/page.tsx`
(new) is the Server Component described above. Its
`success_url` value is
`${APP_URL}/checkout-success?session_id={CHECKOUT_SESSION_ID}`
(the Stripe template literal in the `getCheckoutSessionParams`
block of `packages/auth/src/auth.ts`).

### Marketing follow-up risks

### Risk 1: Stripe-collected email mismatch

The visitor may type a different email at checkout completion
than the one Stripe eventually sends in the webhook
(`receipt_email`). The follow-up PR rejects the signup when
the two emails differ. The error path is a "Something went
wrong, contact support" page rendered at
`/checkout-success?error=email-mismatch`. This risk is
accepted by the follow-up PR; the alternative (auto-creating
a user from an unverified email) is a security regression.

### Risk 2: webhook race with signup

The Stripe webhook (`customer.subscription.created`) may
fire before the visitor finishes signup. The
`subscription.referenceId` is empty until signup completes.
The follow-up PR handles this with a fire-and-forget
`databaseHooks.user.create.after` that re-queries Stripe for
the customer by email and back-fills `subscription.referenceId`.
The back-fill is idempotent (the unique key on
`subscription.stripeCustomerId` makes a duplicate
`UPDATE` a no-op).

### Risk 3: partial flow failure

The visitor may abandon the signup form mid-way. The Stripe
subscription exists; the `user` row does not. The follow-up PR
keeps the subscription row in `status: "incomplete"` until
the signup form completes, then flips it to `active` via the
back-fill. The Stripe customer is reusable: a follow-up
signup from the same email picks up the orphan subscription.

### Risk 4: `emailVerification.autoVerify` scope

The flag is set via a hook that detects the Stripe webhook
path. If the detection logic is wrong, the flag leaks to
email/password signups and bypasses email verification
globally. The follow-up PR uses
`request.url` matching as the gate (the Stripe webhook path
in `apps/app/app/api/[[...route]]/route.ts` is
`/api/v1/auth/stripe/webhook`; the hook matches
`request.url.endsWith("/stripe/webhook")`). This is a fragile
signal (a future Stripe route change would silently break the
match); the follow-up PR adds an integration test that
asserts the gate.

### Risk 5: anonymous `subscription.upgrade` is not supported

The plugin's `POST /subscription/upgrade` endpoint is
guarded by better-auth's `authenticated` middleware (the
plugin uses the standard `getSession()` guard on every
`subscription.*` route). An anonymous call from the
marketing `/pricing` page returns `401 Unauthorized` rather
than initiating a guest checkout. The flow described in
the *Server-side provisioning flow* section above assumes
the endpoint will accept the anonymous visitor; it will
not, without a code change.

Two resolutions are visible:

1. **Custom anonymous handler**. Add a Hono route at
   `packages/api/src/http/routes/checkout.ts` that accepts
   the anonymous POST, calls
   `stripe.checkout.sessions.create({ mode: "subscription",
   customer_email, line_items, success_url, cancel_url,
   metadata: { source: "marketing-pricing" } })` with the
   server-side Stripe SDK instance (the same one
   `packages/auth/src/auth.ts` constructs), and returns the
   Checkout URL to the browser. The handler does not
   require a session; the Stripe customer is created
   implicitly when the visitor completes Checkout. This is
   the resolution this DR locks. The Hono route is added to
   `mountHttp` per the existing ADR-011 pattern.
2. **Require sign-in first**. Redirect the anonymous visitor
   to `/signup?redirect=/pricing` before the Stripe
   checkout. This breaks the marketing flow and is rejected.

The custom anonymous handler is the chosen path. The
implementation lands in the marketing follow-up PR, not
in the implementation PR (the implementation PR has no
marketing-side wiring). The handler is consumed by the
Pro `PricingLayer.cta.href` update in
`apps/web/src/lib/pricing.ts`; the data-only edit points
at `/api/v1/auth/checkout/marketing?plan=pro` (the new
Hono route), not at the plugin's
`/subscription/upgrade` endpoint.

## Risks

### Risk 1: better-auth version delta

`@better-auth/stripe@1.7.2` requires `better-auth ^1.7.2`. The
installed version is `1.6.23`. Two resolutions are visible:

**(a) Bump the catalog to `better-auth@^1.7.2`.** The bump
requires auditing the breaking changes between 1.6.x and 1.7.x
(the `deviceAuthorization` plugin, the `bearer` plugin, and the
`nextCookies` plugin are the three pinned plugins; any breaking
change in their public surface is in scope). The audit is a
half-day of work. The bump ships the plugin in-tree without a
side-by-side install.

**(b) Install `@better-auth/stripe` at a 1.6-compatible version
if any exists.** The plugin repo does not publish such a
version per the npm registry. This option is rejected.

This DR resolves (a). The implementation PR bumps the catalog
to `better-auth@^1.7.2` (and `@better-auth/core@^1.7.2`,
`better-call@1.4.0` if the catalog pins them) in the same
commit as the plugin wire-up. A separate changeset entry
documents the version bump per ADR-012.

### Risk 2: schema migration on a populated production database

The migration adds a nullable column to `user` (zero-downtime
safe) and a new table (zero-downtime safe). Existing users
have no `stripeCustomerId`; the next sign-in after the
migration populates the column via `createCustomerOnSignUp`.
The first webhook receipt after the migration writes the first
row to `subscription`. No backfill is needed.

### Risk 3: webhook signature verification and Vercel proxy

The Stripe SDK's `constructEvent` (and `constructEventAsync`
on SDK ≥19) requires the **raw** request body, not a parsed
JSON object. The plugin sets `disableBody: true` and
`cloneRequest: true` on the endpoint to preserve the bytes.
Vercel's edge runtime buffers the request body before the
handler runs; the plugin's `cloneRequest` reads the buffered
bytes. There is no middleware in `apps/app/proxy.ts` that
parses the body before the webhook handler; the gate
allowlist keeps the body unparsed.

### Risk 4: `secondaryStorage` no-op rate limits

The new endpoints (`/subscription/upgrade`, `/subscription/cancel`,
`/subscription/restore`, `/subscription/billing-portal`) are
rate-limited by better-auth's default limits, which the project
overrides via `secondaryStorage` (currently a no-op stub). In
production, the limits are effectively unlimited until Upstash
Redis lands (the M0-deferred-work item 2). A malicious actor
could submit thousands of upgrade calls per minute. The blast
radius is bounded by Stripe's Checkout Session creation rate
limit (which Stripe enforces independently), but the local
guard is missing. This DR accepts the gap and notes it in
`M0-deferred-work.md`.

### Risk 5: `createCustomerOnSignUp` and existing-user data

The flag creates a Stripe customer on first sign-in. Existing
users (pre-migration) trigger a customer creation on their next
sign-in after the migration lands. The Stripe customer id lands
in `user.stripeCustomerId` immediately. The flag is the desired
default for a project without an existing customer base; it is
not the right default for a project migrating a large existing
user base (a manual backfill job would be required). This
project has no production users; the flag is safe.

### Risk 6: the plugin name in the package export

`@better-auth/stripe` exports the server entry from its root
(the `stripe()` function) and the client entry from
`@better-auth/stripe/client` (the `stripeClient()` function).
The import paths are documented in the plugin's `package.json`
and confirmed against the npm registry at the time of writing.

## Verification after merge

The implementation PR self-validates with these manual steps in
local dev:

1. With `STRIPE_SECRET_KEY` / `_WEBHOOK_SECRET` /

   dev server. The dev server boots because the SDK
   instantiation at `packages/auth/src/auth.ts` uses a
   `sk_test_placeholder` fallback when the env var is unset
   (per the *Server config* section). A smoke request that
   reaches Stripe (a `subscription.upgrade` call, a webhook
   receipt, or a `createCustomerOnSignUp` write) is the one
   that throws `StripeAuthenticationError` because the
   placeholder key is not a real Stripe key. This confirms
   the failure mode is request-time, not module-load, and
   that CI / Vitest can import `packages/auth/src/auth.ts`
   without a real Stripe key on disk.
2. With all four keys set, start the dev server. The server
   boots. `curl http://localhost:3001/api/v1/auth/get-session`
   returns the unauthenticated shape (no session cookie
   supplied). This confirms the Hono catch-all still routes
   to `auth.handler` and the plugin does not break the
   existing flow.
3. Sign up a test user via `POST /api/v1/auth/sign-up/email`.
   Inspect the `user` row in the local Postgres: the
   `stripeCustomerId` column is populated. This confirms
   `createCustomerOnSignUp: true` works.
4. Run `stripe listen --forward-to localhost:3001/api/v1/auth/stripe/webhook`
   in a separate terminal. Note the webhook signing secret
   the CLI prints; copy it into `.env` as
   `STRIPE_WEBHOOK_SECRET`. Restart the dev server.
5. From a browser, sign in as the test user and call
   `authClient.subscription.upgrade({ plan: "starter",
   successUrl: "/", cancelUrl: "/" })` from the browser
   console. The plugin returns a Stripe Checkout URL; opening
   the URL completes the test-mode checkout with the Stripe
   test card `4242 4242 4242 4242`.
6. The webhook fires; inspect the local Postgres: the
   `subscription` table has a row for the test user with
   `status: "active"`, `plan: "starter"`, and the
   `stripeSubscriptionId` populated. This confirms the
   webhook handler works end-to-end.
7. Call `authClient.subscription.list()` from the browser
   console. The response includes the active subscription
   and the `limits` map from the plan definition
   (`{ projects: 1, storageMb: 512 }`).
8. Call `authClient.subscription.cancel({ subscriptionId:
   <id> })` from the browser console. The webhook fires; the
   `subscription` row's `cancelAtPeriodEnd` column flips to
   `true`. The next webhook (the period roll-over, which the
   Stripe CLI does not simulate) would flip
   `status: "canceled"`.
9. `pnpm auth:generate` produces a non-byte-identical
   `packages/database/src/schema/auth.ts`. The diff adds the

10. `pnpm db:generate` emits a new SQL file under

    `NULL`-tolerant; the `CREATE TABLE` on `subscription`
    matches the plugin's expected shape.
11. `pnpm env:check` passes with and without the four
    `STRIPE_*` keys set.
12. `pnpm --filter @workspace/auth test` passes (the existing
    session, email, and providers tests; no test depends on
    the Stripe plugin in this DR).

The git context for this DR is the staging branch
`dr/stripe-billing-via-better-auth`, branched from
`staging` per the staging-first workflow
(`AGENTS.md`). The DR is the deliverable; the implementation
PR that follows it lands the five file changes documented in

## Implementation notes

These are non-blocking notes for the three follow-up PRs.
They are not part of the locked scope; they document
behaviors the implementer should preserve. They live here
rather than in a follow-up DR because they are small enough
to inline and do not change the file surface.

### Note 1: marketing follow-up, orphan subscriptions

The marketing flow described in the *Marketing pricing
follow-up scope* section assumes the visitor reaches
`/checkout-success?session_id=...` and submits the signup
form. If the visitor pays on Stripe Checkout and closes the
tab before submitting, the subscription exists in the
`subscription` table with `referenceId = null` (or, after
the `customer.subscription.created` webhook, with
`referenceId = stripeCustomer.metadata.userId` if a
`userId` was set in the metadata by the custom
`/api/v1/auth/checkout/marketing` Hono handler).

The marketing follow-up PR must handle two orphan paths:

1. **Webhook with no matching email**: the
   `customer.subscription.created` webhook fires before any
   `user` row exists. The `databaseHooks.user.create.after`
   back-fill described in *Risk 2* of the marketing section
   does not run, because no user is being created. The
   follow-up PR adds a server-side job (a cron, or a
   background queue) that queries for `subscription` rows
   with `referenceId = null` older than 30 minutes and
   sends a transactional email via
   `apps/app/components/auth/email-templates/finalize-account.tsx`
   (a new template) prompting the visitor to complete the
   signup. The email contains a magic-link token that
   resumes the signup flow on the same Stripe session.
2. **Customer with abandoned signup**, the visitor
   submitted `/signup` once, abandoned the password step,
   and never returned. The `user` row exists with
   `emailVerified = false`. The follow-up PR adds a daily
   job that re-sends the verification email (and a
   "you have an active subscription, finalize your
   account" copy variant) for `user` rows whose Stripe
   customer has an active subscription but whose
   `emailVerified = false` after 7 days.

Both jobs use the existing `sendAuthEmail` fire-and-forget
pattern (see `docs/guides/better-auth/hooks.md` and
`packages/auth/src/auth.ts:103-132`). The follow-up PR does
not introduce a new queue; it hooks into whatever the team
eventually picks for the M0-deferred-work item 2
(Upstash Redis). Until then, the jobs run on the same Vercel
cron the project uses for other maintenance tasks.

### Note 2: UI follow-up, downgrade behavior

The `billing-plan-picker-dialog.tsx` component in the
*UI follow-up scope* section calls
`authClient.subscription.upgrade({ plan })` for both upgrade
and downgrade directions. The same endpoint is used because
the better-auth Stripe plugin treats them symmetrically:
Stripe handles the proration automatically based on the
plan change.

The follow-up PR does not introduce a separate "downgrade"
button or a different confirmation copy. The picker dialog
shows the available plans with their `limits` map and the
monthly price. When the visitor picks a lower-tier plan than
their current one:

- The button label stays "Choose plan" (no "Downgrade" copy
  change in the DR's locked scope).
- The dialog footer adds a one-line informational note:
  "Proration is calculated automatically by Stripe and shown
  on the Checkout page." This copy is not in the locked
  scope but is a low-risk addition the implementer can ship
  without renegotiating the DR.

The follower must not pass `prorationBehavior: "none"` or
similar to bypass the default proration. The default
behavior is the user-facing one ("create_prorations").

### Note 3: UI follow-up, past-due and 3DS states

The `billing-current-plan.tsx` component in the
*UI follow-up scope* section renders a `Badge` for the
subscription status. The locked scope names the `Badge`
primitive but does not enumerate every Stripe status
variant. The follow-up PR must handle:

- `status: "active"` → green Badge, label "Active".
- `status: "trialing"` → outline Badge, label
  "Trial until <trialEnd>".
- `status: "past_due"` → destructive Badge, label
  "Payment failed" plus a secondary line
  "Update your payment method to restore access" and a
  Button "Manage in Stripe" that calls
  `authClient.subscription.billingPortal(...)`.
- `status: "unpaid"` → destructive Badge, label "Unpaid"
  plus a Button "Manage in Stripe" (same call).
- `status: "incomplete"` → muted Badge, label
  "Awaiting payment confirmation".
- `status: "incomplete_expired"` → muted Badge, label
  "Checkout expired" plus a Button "Choose plan" that
  reopens the picker dialog.
- `status: "canceled"` → muted Badge, label
  "Subscription ended" plus a Button "Choose plan" that
  reopens the picker dialog.

The `past_due` and `unpaid` Badges are the only ones that
trigger a direct user-visible alert. The `destructive`
variant of the shadcn `Badge` primitive
(`@workspace/ui/components/badge`) is the right tool; no
new primitive is needed in `packages/ui`.

The 3DS recovery path (the `invoice.payment_action_required`
webhook event) is a Stripe-side action, not a
`billing-current-plan.tsx` UI concern. The webhook updates
`status: "past_due"` locally; the Badge above surfaces the
"Payment failed" copy. The Stripe-hosted billing portal
(`authClient.subscription.billingPortal(...)`) is where the
user authenticates the 3DS challenge; the codebase does not
attempt to render 3DS itself.

does not negotiate that order; the team can interleave the

### What this section forbids

- Merging PR-2 before PR-1. PR-2's Hono handler calls the
  Stripe SDK directly; the SDK is wired in PR-1. The
  handler fails to import if PR-1 has not landed.
- Merging PR-3 before PR-2. PR-3's CTA points at the
  Hono handler from PR-2; the CTA leads to a 404 if
  PR-2 has not landed.
- Skipping the PR-1 catalog bump audit (the
  "half-day of work" gate in PR-1 step 10). The audit
  catches breaking changes in the three pinned plugins
  before the PR is opened.
- Using `useRouter()` for the external Stripe redirect in
  `billing-plan-picker-dialog.tsx`. The redirect is
  `window.location.href = data.url`.
- Adding a CI smoke that requires a real Stripe key. The
  smoke uses the `sk_test_placeholder` fallback; the
  `auth.api.getSession` and `subscription.list` calls
  fail at the Stripe boundary, but the test infrastructure

- [ADR-004: API package structure](./ADR-004-api-package-structure.md).
  The boundary that pins `@workspace/auth` as imported only
  by `http/middleware/session.ts` and `http/routes/auth.ts`.
  The Stripe SDK lives in `packages/auth/src/auth.ts`; no
  other workspace file imports it.
- [ADR-005: API is consumer-agnostic](./ADR-005-api-consumer-agnostic.md).
  The server-side counterpart. The Stripe plugin lives in
  `packages/auth/`; consumers (`apps/web`, `apps/app`,
  `apps/cli`, the API itself) talk to the catch-all handler
  in `apps/app/app/api/[[...route]]/route.ts`, not to
  better-auth directly.
- [ADR-011: Hono for system routes](./ADR-011-hono-for-system-routes.md).
  The Stripe webhook is a system route, mounted in `mountHttp`,
  delegated to Better Auth's `auth.handler`. This DR inherits
  the mount; it does not own it.
- [ADR-012: Changesets versioning for private workspace deps](./ADR-012-changesets-private-workspace-deps.md).
  The `packages/auth` bump that follows this DR inherits the
  rule that `packages/auth` is bumped even though it is
  private.
- [ADR-015: Drizzle migrations CI](./ADR-015-drizzle-migrations-ci.md).
  The migration workflow. The new SQL file generated by
  `pnpm db:generate` is committed in the implementation PR
  but not run; staging and production apply it via
  `pnpm db:migrate` after the PR merges.

  `packages/auth/src/auth.ts`, and the proxy allowlist in
