# ADR-020: Auth schema check

## Status

Proposed (2026-08).

## Context

The repo has two source-of-truth files for Better Auth:

- `packages/auth/src/auth.ts` — the `betterAuth({...})` config. Plugin
  list, email-and-password settings, session config, additional
  fields, all of it.
- `packages/database/src/schema/auth.ts` — the Drizzle tables
  (`user`, `session`, `account`, `verification`) and `relations()`
  declarations consumed by `drizzleAdapter` via the `schema` argument.

`schema/auth.ts` is **not** written by hand. It is generated by the
`auth:generate` script in `packages/auth/package.json`:

```
pnpm exec auth generate \
  --config ./src/auth.ts \
  --output ../database/src/schema/auth.ts \
  --yes
```

The generator reads `auth.ts`, infers the table shape Better Auth
expects, and writes the Drizzle schema. The repo commits the
generated file (verified: `git ls-files packages/database/src/schema/auth.ts`
returns the path). Committing it is intentional — every diff PR
shows the schema change alongside the auth config change that
caused it.

The Drift job in `.github/workflows/drizzle-check.yml` (ADR-015)
verifies one half of the consistency story: re-runs
`pnpm db:generate` against the committed `schema/*.ts` and asserts
the working tree stays clean. If the schema TS changes without a
matching SQL migration, the Drift job fails.

The Drift job does **not** verify the other half. A contributor
who edits `auth.ts` (adds a plugin, changes a session option,
introduces an `additionalField`) and forgets to run
`auth:generate` produces a PR that:

1. Includes the `auth.ts` change.
2. Has the **old** `schema/auth.ts` committed (because the dev
   did not regenerate).
3. Has no new SQL migration (because `db:generate` ran against
   the old schema TS).
4. Passes the Drift job (`db:generate` produces the same SQL as
   before, working tree clean).
5. Passes the Squawk job (no new SQL files).
6. Merges.
7. Staging apply runs `db:migrate` against the old schema TS —
   the staging DB ends up with the **old** table layout.
8. The app, configured by the **new** `auth.ts`, calls
   `auth.handler` and crashes on a missing column or an unknown
   table. The first login attempt fails.

Failure mode 8 is what this ADR catches. It is a real failure
mode that has happened in this repo: PR #66 (referenced here as
the trigger case) edited Better Auth config and shipped without
the regenerated schema TS, leaving staging inconsistent with
the app config until a human noticed.

### Three incident windows the auth-schema check closes

- **Local**: the contributor notices at the first
  `auth.handler` call. Debug takes 30 minutes, fix is
  trivial (run `auth:generate`, commit).
- **Staging**: the CI integration job applies the migration
  from the (stale) schema TS. Staging is aligned with the
  wrong schema. The app crashes at the first login device-flow.
  Incident touches a shared environment.
- **Production**: if release is automatic through changesets,
  the user sees the error before the human does. Rollback
  requires either a forward-fix migration or a manual revert,
  which means a double release in urgency.

At roughly 30 seconds of CI time per PR, the cost-benefit ratio
favors blocking.

## Decision

A new CI workflow, `.github/workflows/auth-check.yml`, runs on
every pull request against `main` or `staging`. The workflow
runs `pnpm auth:generate` and asserts the regenerated
`schema/auth.ts` is byte-identical to the committed version.

```yaml
on:
  pull_request:
    branches: [main, staging]

permissions:
  contents: read

jobs:
  auth-schema:
    name: Auth schema
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }

      - uses: pnpm/action-setup@v6
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: pnpm }

      - run: pnpm install --frozen-lockfile

      # Build @workspace/env first so drizzle-kit-adjacent
      # commands do not crash on missing dist files. Same pattern
      # as drizzle-check.yml and db-migrate-staging.yml.
      - run: pnpm turbo build --filter=@workspace/auth --force

      - name: Verify auth schema is in sync
        run: |
          pnpm --filter @workspace/auth auth:generate
          # git add -N marks untracked files as intent-to-add so
          # git diff sees them as "new" rather than "ignored".
          git add -N packages/database/src/schema/auth.ts
          if ! git diff --exit-code packages/database/src/schema/auth.ts; then
            echo "::error::packages/database/src/schema/auth.ts is out of sync with packages/auth/src/auth.ts"
            echo "::error::Run \`pnpm --filter @workspace/auth auth:generate\` and commit the result."
            git diff --stat packages/database/src/schema/auth.ts
            exit 1
          fi
```

The workflow runs as its own file rather than as a third job
inside `drizzle-check.yml`. The repo's CI is organized by
**domain of coherence**: `drizzle-check.yml` covers the Drizzle
journal and SQL generation, `cli-publish-verify.yml` covers the
CLI publish path, `changesets-check.yml` covers changesets.
Auth is its own domain. Future checks on Better Auth hooks
(`databaseHooks`), `additionalFields` shape, or the production
gating in `apps/app/proxy.ts` have a natural home here.

### Why this rule forbids informatif

We considered an informational variant (the workflow logs a
warning but does not block the PR). The reasoning for rejecting
it is the same as the reasoning for the Drift job's blocking
status in ADR-015: the cost of a missed check on the
shared-staging side is non-anonymous (an incident touching a
shared environment), and the cost of the check is one short
CI step. The "the contributor who touches `auth.ts` knows what
they are doing" argument cuts equally for `drizzle.config.ts`,
and the Drift job is already blocking there without complaint.

### Why the check uses `pnpm auth:generate` rather than parsing `auth.ts`

The Better Auth CLI is the only thing that knows how `auth.ts`
maps to Drizzle tables. We do not reverse-engineer that mapping
in CI — we run the same generator the contributor runs locally
and compare bytes. Two consequences:

- The check depends on the generator being deterministic for
  a given `auth.ts`. The repo pins `better-auth@^1.6.23` in
  the catalog. A future bump that introduces non-determinism
  in the generator (whitespace, reordered exports, etc.)
  surfaces as a CI failure here. That is the desired signal;
  the fix is a regeneration commit.
- The check runs on the contributor's local machine too. If
  the generator changes between the contributor's local run
  and CI (different `better-auth` version), the comparison
  fails. The fix is `pnpm install --frozen-lockfile` before
  the local `auth:generate`, which the existing CONTRIBUTING
  flow already requires.

## Consequences

- Every PR that edits `auth.ts` without regenerating
  `schema/auth.ts` is blocked at the gate. The error message
  tells the contributor exactly which file is stale and
  exactly which command to run. Debug time drops from
  "thirty minutes when staging breaks" to "fifteen seconds at
  PR review".
- The check is gated on `apps/auth/**` and
  `packages/database/src/schema/auth.ts` paths, same as the
  Drift job in ADR-015. A PR that touches unrelated paths
  does not pay the cost. (The trigger is `pull_request`
  without `paths`, so the cost is always paid — this is a
  future tightening if the CI minutes become a concern.)
- The gate runs as a required check on `main` and `staging`
  in branch protection. The gate does not modify the PR
  (no commits pushed from CI). The contributor must regenerate
  and commit manually.
- The check does not verify the SQL migration against the
  regenerated schema TS. That is the Drift job's job. The
  two checks together form a chain: this one verifies
  `auth.ts` → `schema/auth.ts`, the Drift job verifies
  `schema/auth.ts` → `drizzle/*.sql`. Both must pass.
- The Better Auth CLI is consumed via `pnpm exec auth ...`,
  which resolves through the lockfile. The version that
  runs in CI is the same that runs locally. Drift between
  local and CI versions surfaces as a non-matching diff and
  fails the gate.

## Out of scope

Three things this ADR does not cover:

- **Checks on `databaseHooks`.** The Better Auth docs
  recommend hooks for cross-cutting concerns (audit logging,
  analytics). When the repo wires its first hook, a
  contract-style test (input/output types match the schema)
  lands in `packages/auth/tests/hooks.test.ts` and the
  CI job here expands to cover the hook surface.
- **Checks on `additionalFields`.** The Better Auth docs
  describe user-defined fields (`additionalFields: { role:
  { type: "string" } }`). Each such field needs both a
  generator output (column in `user`) and a runtime handler.
  A contract test for the additional fields surface is a
  natural follow-up.
- **A pre-commit hook running `auth:generate`.** The CI check
  makes the failure visible at PR time. A pre-commit hook
  would catch the same case at commit time. The cost is
  adding `lefthook` (or `husky`) to the repo, which is a
  separate decision.

## How to verify

1. Open a PR that edits `packages/auth/src/auth.ts` (e.g.
   adds `magicLink()` to the plugins list) without running
   `auth:generate`. The auth-schema job fails with the
   error message naming the stale file and the command to
   run.
2. Run `pnpm --filter @workspace/auth auth:generate` locally,
   commit the resulting diff to `schema/auth.ts`, push. The
   auth-schema job passes. The Drift job also passes if the
   regenerated schema TS requires a new SQL migration and
   `db:generate` is run.
3. Open a PR that touches neither `auth.ts` nor
   `schema/auth.ts`. The auth-schema job runs, finds no
   diff, and exits 0 in roughly 30 seconds.

## Why this lands without a paired feature PR

The senior CI pattern is to ship a check job alongside the
first feature it would have caught. This ADR does not do that.
Reason: the first feature that exercises the check (the next
Better Auth plugin addition or session change) has not yet
been scoped, and waiting for it would leave the gate absent
during the interim. The ADR justifies the gate with the
concrete failure mode of PR #66, which is the kind of bug the
gate is designed to catch. A future ADR that adds a
Better Auth feature can cite this ADR as "the gate that
would have caught the PR #66 bug."
