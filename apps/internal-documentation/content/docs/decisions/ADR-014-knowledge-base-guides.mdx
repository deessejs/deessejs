# ADR-014: Knowledge Base guides

## Status

Accepted (2026-08). Non-negotiable.

## Context

The marketing site at `apps/web/` ships a knowledge base at
`/(content)/knowledge-base`. The surface is two levels deep:
a topic index at `/knowledge-base`, per-topic pages at
`/knowledge-base/[topic]`, and per-guide pages at
`/knowledge-base/guide/[slug]`.

[ADR-013](./ADR-013-knowledge-base-topics.md) is the
prerequisite for this ADR: it pins the `kbTopics`
collection and the topic pages. This ADR is the guides
half — it pins `kbGuides` and the guide pages.

Today, every byte of content on the guide side is
**hard-coded in TSX**:

- `app/(content)/knowledge-base/page.tsx` declares
  `FEATURED_GUIDES` and `ALL_GUIDES` — two inline
  constants that list the guides.
- `app/(content)/knowledge-base/guide/[slug]/page.tsx`
  declares `KNOWN_SLUGS` (the whitelist of valid slugs),
  `GUIDE_META` (the metadata for each guide: title,
  description, products), and a `generateMetadata` that
  reads `GUIDE_META` directly. The guide body itself is a
  placeholder — three generic numbered steps that are the
  same for every guide.

This shape has four costs:

1. **Editor friction.** Adding a guide means a TSX edit,
   a build, and a redeploy. The contributor who can write
   MDX cannot ship a guide without editing two files.
2. **Drift.** The guide-slug list is duplicated between
   `FEATURED_GUIDES`, `ALL_GUIDES`, and `KNOWN_SLUGS`. The
   mapping from topic to guide is duplicated a fourth
   time in `TOPIC_GUIDES` on the topic page. Rename a
   slug and four files must move in lockstep. Today, two
   guides (`background-jobs-queue`, `observability-logging`)
   have no topic assigned — a direct consequence of the
   duplication.
3. **No real guide body.** Guides are placeholders. The
   contributor who wants to write a real guide must
   first replace the placeholder JSX.
4. **No SSG.** There is no `generateStaticParams` on
   `guide/[slug]`. Each hit is a runtime lookup against
   `KNOWN_SLUGS`. The blog already pre-renders every post
   via `generateStaticParams` against
   `content-collections`; the guide side cannot.

The blog already solves all four problems with
`@content-collections/next`. The pipeline is wired in
`apps/web/next.config.ts` (`withContentCollections(nextConfig)`),
`pageExtensions` includes `mdx` (`next.config.ts:6`), and
shiki is in `serverExternalPackages` (`next.config.ts:7`).
The blog reads `allPosts` from `content-collections`
(`lib/blog/posts.ts:1`), renders MDX through
`components/blog/mdx-renderer.tsx`, styles prose via
`components/blog/prose.tsx`, and pre-renders with
`generateStaticParams`.

## Decision

The marketing-site knowledge base has a `kbGuides`
content-collection. The collection is declared in the
same `content-collections.config.ts` that already declares
`posts`, `releases`, `authors`, and (per ADR-013)
`kbTopics`. The collection reuses the existing rendering
stack unchanged.

### Content layout

```
apps/web/content/
  knowledge-base/
    guides/
      <guide-slug>.mdx
```

A guide is a file. The file's path (relative to the
collection directory) is the guide slug. The
`generateStaticParams` for `guide/[slug]/page.tsx` reads
the collection.

### Frontmatter

**Guide** (`content/knowledge-base/guides/<slug>.mdx`):

```mdx
---
title: Install the deessejs CLI
description: Set up the CLI, authenticate, and discover templates from the registry.
topic: getting-started
products: [cli, registry]
order: 0
draft: false
---
```

The body of the file is the guide's editorial content
rendered on the guide page between the header and the
"Need help?" footer.

The Zod schema is:

```ts
const kbGuides = defineCollection({
  name: "kbGuides",
  directory: "content/knowledge-base/guides",
  include: "**/*.mdx",
  schema: (z) => ({
    title: z.string(),
    description: z.string(),
    topic: z.string(),
    products: z.array(z.string()).default([]),
    order: z.number().default(0),
    draft: z.boolean().default(false),
  }),
  transform: async (doc, context) => {
    const body = await compileMDX(context, doc, {
      rehypePlugins: [rehypeShiki],
    })
    return {
      ...doc,
      body,
      slug: doc._meta.path,
      url: `/knowledge-base/guide/${doc._meta.path}`,
    }
  },
})
```

`topic` is **required** (`z.string()`, not
`.optional()`). A guide without a `topic:` field is a
schema error caught at build time. The topic must match
the slug of a file in
`content/knowledge-base/topics/`; the topic page itself
is owned by [ADR-013](./ADR-013-knowledge-base-topics.md).

`draft` defaults to `false` and is honoured in production
builds by filtering at the helper layer (the blog does
this for `posts`).

### Initial guide set

The migration seeds nine guide files. All nine are
1:1 translations of the existing inline constants in
`FEATURED_GUIDES` and `ALL_GUIDES`:

| Slug | Topic | Products |
|---|---|---|
| `install-deessejs-cli` | `cli` | cli, registry |
| `first-agent-stack` | `agents` | agents, ai-sdk |
| `deploy-to-vercel` | `deployment` | deploy |
| `nextjs-rag-template` | `agents` | templates, ai, postgres |
| `background-jobs-queue` | `queue` | queue |
| `observability-logging` | `observability` | observability |
| `postgres-migrations` | `databases` | database |
| `shadcn-theming` | `ui` | ui |
| `production-checklist` | `deployment` | deploy |

#### Orphaned guides

Two guides had no topic assigned in the inline-constant
era:

- `background-jobs-queue` — no matching topic existed.
- `observability-logging` — no matching topic existed.

[ADR-013](./ADR-013-knowledge-base-topics.md) closes this
gap by adding two new topics — `queue` and
`observability` — to the initial topic set. This ADR
points the two orphan guides at those new topics.

If the topic FK were enforced against `allKbTopics` at
build time (e.g. via a refinement), a guide pointing at a
non-existent topic would be a build error. Today the
schema only enforces that `topic` is a non-empty string;
the topic page itself reads
`allKbGuides.filter((g) => g.topic === slug)` and an
orphan guide silently disappears from the topic listing.
The next contributor who adds a refinement tightening
the FK lives in a future ADR.

### Page wiring

The guide side of the knowledge base reads from
`kbGuides`:

- `app/(content)/knowledge-base/page.tsx` —
  `FEATURED_GUIDES` and `ALL_GUIDES` constants removed;
  the page reads `allKbGuides` (sorted by `order`) for
  the Featured Guides and All Guides sections. `TAG_CLOUD`
  becomes
  `Array.from(new Set(allKbGuides.flatMap((g) => g.products))).sort()`
  — the same expression that exists today, lifted from a
  constant.
- `app/(content)/knowledge-base/guide/[slug]/page.tsx` —
  `KNOWN_SLUGS` and `GUIDE_META` removed; the page looks
  up the guide from `allKbGuides` by slug, renders the
  body via `MdxRenderer` wrapped in `Prose`, and exposes
  per-guide SEO via `generateMetadata` (which reads from
  the same collection and returns `title`, `description`,
  OG tags).

`generateStaticParams` is added on
`guide/[slug]/page.tsx`:

```ts
export function generateStaticParams(): Array<{ slug: string }> {
  return allKbGuides.map((g) => ({ slug: g.slug }))
}
```

### Sitemap

`app/sitemap.ts:86-90` currently emits a single static
entry for `/knowledge-base`. After this ADR it adds one
entry per guide:

```ts
{
  url: `${APP_URL}/knowledge-base`,
  lastModified: new Date(),
  changeFrequency: "monthly",
  priority: 0.5,
},
...allKbGuides.map((guide) => ({
  url: `${APP_URL}${guide.url}`,
  lastModified: new Date(),
  changeFrequency: "monthly" as const,
  priority: 0.4,
})),
```

The topic sitemap entries
(`/knowledge-base/<slug>`) land in
[ADR-013](./ADR-013-knowledge-base-topics.md). The shared
index entry above is mentioned in both ADRs to avoid
double-claiming it; the entry is added once, in
ADR-013's migration.

### Search

`lib/blog/search.ts` exports a `SearchItem` type with
`type: "post" | "release"`. After this ADR the union
extends to add `"kb-guide"`:

```ts
export type SearchItem = {
  title: string
  description: string
  url: string
  type: "post" | "release" | "kb-topic" | "kb-guide"
}
```

The new entries derived from `allKbGuides`:

```ts
...allKbGuides.map((guide) => ({
  title: guide.title,
  description: guide.description,
  url: guide.url,
  type: "kb-guide" as const,
})),
```

The `SearchDialog` component
(`components/blog/search-dialog.tsx`) renders the new
`kb-guide` type with the same tag-pill styling it uses
for `kb-topic` (added in ADR-013); the existing Fuse.js
keys (`title`, `description`) cover both.

### Rendering stack

The guide body is rendered through
`components/blog/mdx-renderer.tsx`, wrapped in
`components/blog/prose.tsx` for the same prose CSS used
by the blog. The `<Prose>` component is renamed to a
content-agnostic path only if a second consumer emerges;
for the v1 the import lives in `components/blog/prose.tsx`
and the knowledge base imports it from there. The cost of
leaving it under `components/blog/` is a misleading
directory name; the cost of moving it is a broken import
in the blog. The move is deferred until a second consumer
exists.

## What this rule allows

- **Adding a guide.** Drop a new `.mdx` in
  `content/knowledge-base/guides/`. The guide appears on
  the topic page for the value of `topic:` and on the
  index if its `order` is in the featured range.
- **Editing guide body content.** The MDX file is the
  body. No TSX edit, no rebuild of the guide surface.
- **Honouring `draft: true`.** A guide with `draft: true`
  is filtered out of production builds; it stays visible
  in dev. The blog already does this; the knowledge base
  follows.
- **Adding new frontmatter fields.** The collection is
  declared in one place; a new field is a Zod schema
  extension plus a read site in the relevant page.
- **Reordering guides.** `order: number` on each file
  controls sort. No file renames required.
- **Per-guide SEO.** `generateMetadata` reads from the
  guide; every guide gets its own `title`, `description`,
  OG card.

## What this rule forbids

- **Inline constants for guides on the knowledge-base
  pages.** `FEATURED_GUIDES`, `ALL_GUIDES`, `KNOWN_SLUGS`,
  `GUIDE_META`, and `TOPIC_GUIDES` (the topic-to-guide
  mapping on the topic page) are removed. The pages read
  from `allKbGuides`.
- **A guide without a `topic:` field.** `schema.topic` is
  `z.string()`, not `.optional()`. A guide without a
  topic is a schema error caught at build time.
- **A guide body in JSX instead of MDX.** The body is the
  MDX file.
- **A MDX render that bypasses `MdxRenderer`.** The
  guide page imports `MdxRenderer` and `Prose` the same
  way the blog does. A bespoke renderer would fork the
  shiki + rehype pipeline.
- **Hard-coded guide slugs anywhere on the guide side of
  the knowledge base.** A contributor who needs a guide
  slug reads `allKbGuides.map((g) => g.slug)`. There is
  no central enum of guide slugs; the filesystem is the
  source of truth.
- **A new `next.config.ts` editor.** The collection
  declaration is in `content-collections.config.ts`; the
  Next config is unchanged.

## What this rule does not change

- **The marketing-site nav, footer, and OG image for the
  knowledge base.** The surface stays
  `/(content)/knowledge-base`. The links in
  `components/headers/nav-sections.tsx:142-145` and
  `components/footers/app-footer.tsx:29` stay.
- **The `not-found.tsx` file on `guide/[slug]/`.** It
  delegates to `NotFoundPanel`; the panel is unchanged.
- **The `MdxRenderer` and `Prose` components.** They are
  reused verbatim.
- **The `rehypeShiki` plugin.** The blog uses it; the
  knowledge base uses it; the catalog pin stays where it
  is.
- **The `noindex, nofollow` robots directive on the
  knowledge-base index.** The page stays unindexed by
  search engines; the sitemap entries are for crawl
  discovery, not search ranking.
- **The Better-Auth and DB layers.** They do not interact
  with the knowledge base.

## Why this rule exists

The hard-coded guide surface is a placeholder. The
comment at `page.tsx:30-33` says it explicitly: "Data is
hard-coded in this file for V1. Once the editorial
pipeline stabilizes, swap these constants for a content
source under `apps/web/content/knowledge-base/`." The
pipeline stabilised when the blog shipped. The knowledge
base is the next consumer.

The temptation when extending the guide side is to add
another inline constant for the new content, framed as
"just one more list". Each new constant is a small loss:

- The slug drift compounds; the next rename of a guide
  is four files instead of three.
- The drift is silent. The TypeScript compiler does not
  flag a missing slug in `TOPIC_GUIDES` because the lists
  are typed `as const` arrays, not discriminated unions.
- The placeholder body stays. Every guide is three generic
  steps; the contributor who wants to write a real guide
  must first replace the placeholder component.
- The pipeline stays bespoke. The topic side and the
  guide side cannot share content; they cannot
  cross-reference by FK; they cannot reorder
  independently.

The cost of the rule is the migration of one page
(`guide/[slug]/page.tsx`), the rewrite of the index
page's guide sections, the addition of one collection,
and the writing of nine MDX files. The migration is
mechanical (edit, rename, write frontmatter). The two
orphan guides (`background-jobs-queue`,
`observability-logging`) get their `topic:` field set to
the new topics added by ADR-013.

## How to migrate

In one PR (split into three commits for review):

1. **Add `kbGuides` to `content-collections.config.ts`.**
   The config must declare the Zod schema, the directory,
   the include glob, and the `transform` that compiles
   MDX with `rehypeShiki`. The collection sits alongside
   `posts`, `releases`, `authors`, and `kbTopics`.
2. **Write the guide files.** Nine `.mdx` files land in
   `content/knowledge-base/guides/`. The slug of every
   file matches the slug that was in the TSX constant;
   the redirect surface stays stable. The `topic:` field
   on each guide points to a slug in
   `content/knowledge-base/topics/`.
3. **Rewrite the guide side of the pages.** Remove every
   inline constant. Add `generateStaticParams` on
   `guide/[slug]`. Add `MdxRenderer` and `Prose` to the
   guide page body. The index page reads `allKbGuides`
   for the Featured Guides and All Guides sections.
4. **Extend the sitemap and search.** Add the guide
   entries to `app/sitemap.ts`. Extend
   `lib/blog/search.ts` with `kb-guide` entries; the
   `SearchDialog` component renders them with the
   existing tag-pill logic.

The PR is medium-sized (one collection declaration,
nine new MDX files, one page rewrite, sitemap and search
edits). The diff is mostly mechanical; the review load is
the collection schema and the page rewrites.

## Consequences

- A PR that adds a hard-coded guide-slug list is
  rejected. The pages read from `allKbGuides`.
- A PR that adds a guide without a `topic:` field is
  rejected. The Zod schema enforces it at build time.
- A PR that adds a guide body in JSX instead of MDX is
  rejected. The body is the MDX file.
- A PR that bypasses `MdxRenderer` for guide bodies is
  rejected. The shiki + rehype pipeline is shared.
- A PR that hides `draft: true` guides in dev is rejected.
  The filter is build-time only; dev shows everything.

## Where this rule came from

The knowledge-base hard-coded surface was the seed
delivered when the marketing site launched. The seed
intentionally deferred the content pipeline: the comment
on `page.tsx:30-33` is explicit. The blog shipped first
and proved the pipeline; the changelog shipped next and
reused it. The knowledge base is the third consumer.

The first time the placeholder mattered was when the
editorial team asked to write a real guide. The
contributor who picked it up had to replace the
placeholder JSX, choose between topic assignments, and
keep four slug lists in sync. The cost was high enough
that the work stalled. The rule removes the stall: the
pipeline is the path; the constants are gone.

The decision to split this ADR from
[ADR-013](./ADR-013-knowledge-base-topics.md) was made
because topics are a prerequisite for guides. A guide
without a topic is a schema error; a topic page without
a list of guides is a partial surface. Topics land first
in the architectural narrative.
