# ADR-013: Device authorization for the CLI auth surface

## Status

Accepted (2026-08). Non-negotiable.

## Context

`apps/cli/` is the only published package in the monorepo
(`@deessejs/cli`, per ADR-010). Today its public surface is
three commands (`init`, `list`, `info`) that talk to the
upstream server exclusively through the typed oRPC client and
never carry an identity. The server's public routes
(`/api/v1/rpc/*`, `/api/v1/auth/*`) are reachable anonymously
for everything the CLI does today: listing templates, fetching
template metadata, cloning a repo. The CLI has no notion of
"who is running this command", and the server has no notion of
"this is an authenticated CLI".

This changes with the next feature surface. Two consumers
need to know who the caller is:

- A user running `deesse auth login` on a fresh machine
  needs to obtain a session token without typing a password
  into a terminal.
- The server, when it eventually exposes authenticated
  procedures (per the broader roadmap), needs a wire
  format that identifies the caller.

The CLI cannot store a long-lived password. The server
cannot ask the CLI for a password either. The shape that
fits both is **device authorization** (RFC 8628): the CLI
requests a code, the user approves the code in a browser,
the CLI polls for a token, and the token is a Better Auth
session token. Better Auth ships this as a first-class
plugin (`better-auth/plugins/device-authorization`), already
present in `node_modules/better-auth@1.6.23`.

The temptation when wiring device auth is to build a custom
flow: a parallel REST endpoint that returns a token, a CLI
subcommand that posts credentials directly, a webhook the
server calls back to. Each custom flow fragments the auth
surface, doubles the wire-format surface, and forces every
consumer to learn a new path. The cost compounds: the
custom endpoint becomes a public surface that future
contributors must understand, the parallel CLI subcommand
becomes a second way to authenticate, the callback becomes
a second wire format the server must validate.

The Better Auth device-authorization plugin is the
load-bearing shape. We do not work around it. We do not
reimplement it. We do not add a second auth surface.

## Decision

The CLI auth surface is driven by the Better Auth
device-authorization plugin. The plugin is wired once, on
the server, and the CLI consumes it through the same
`/api/v1/auth/*` mount that already serves Better Auth's
session endpoints. No new HTTP surface is added. No new
wire format is introduced.

### Server-side wiring

`packages/auth/src/auth.ts` adds the plugin to the existing
plugin array:

```ts
import { deviceAuthorization } from "better-auth/plugins"

plugins: [
  deviceAuthorization({
    verificationUri: "/device",
  }),
  nextCookies(), // must remain last
]
```

The plugin adds five endpoints under the existing
`/api/v1/auth/*` mount:

| Endpoint | Method | Purpose |
|---|---|---|
| `/api/v1/auth/device/code` | POST | CLI requests a device + user code |
| `/api/v1/auth/device/token` | POST | CLI polls for the access token |
| `/api/v1/auth/device` | GET | Web UI claims a code for the calling session |
| `/api/v1/auth/device/approve` | POST | Authenticated user approves a code |
| `/api/v1/auth/device/deny` | POST | Authenticated user denies a code |

No new mount. No new base path. No new wire envelope. The
five endpoints sit alongside `/sign-in/email`,
`/sign-up/email`, `/get-session`, and the rest of the
Better Auth surface that already lives under
`/api/v1/auth/*`.

The plugin adds one table (`deviceCode`) to the Better Auth
schema. The table is regenerated by `pnpm auth:generate`
and lands in `packages/database/src/schema/auth.ts`. The
generation step is already wired as `packages/auth`'s
`auth:generate` script; the new table follows the same
review process as every other schema change.

### Client-side wiring

`apps/app/lib/auth-client.ts` adds the client plugin to the
existing client:

```ts
import { deviceAuthorizationClient } from "better-auth/client/plugins"

export const authClient: ReturnType<typeof createAuthClient> =
  createAuthClient({
    baseURL: clientEnv.NEXT_PUBLIC_APP_URL,
    basePath: API_AUTH_PATH,
    plugins: [deviceAuthorizationClient()],
  })
```

The client plugin adds five methods (`device.code`,
`device.token`, `device`, `device.approve`, `device.deny`)
that map one-to-one to the server endpoints. The wire
shape is whatever Better Auth publishes; the typed client
does not invent a parallel shape.

### CLI commands

`apps/cli/src/commands/auth/` holds three new commands,
each in its own file, following ADR-010's command-file
invariants:

| Command | File | Purpose |
|---|---|---|
| `deesse auth login` | `login.ts` | Request codes, open browser, poll, persist token |
| `deesse auth status` | `status.ts` | Read token from disk, hit `/get-session`, show user |
| `deesse auth logout` | `logout.ts` | Hit server-side sign-out, delete token file |

The three commands are registered in `apps/cli/src/index.ts`
under the `auth` parent:

```ts
const authCommand = new Command("auth").description(
  "Authenticate this machine against the DeesseJS server",
)
authCommand.addCommand(loginCommand)
authCommand.addCommand(statusCommand)
authCommand.addCommand(logoutCommand)
program.addCommand(authCommand)
```

The new subcommand tree is reviewed against ADR-010 §1
(commands are siblings, not nested features). The `auth`
parent is a sibling of `init`, `list`, `info`; the three
children are siblings of each other.

### Token storage

The session token returned by `/device/token` is persisted
on disk at `~/.deessejs/auth.json`. The file lives in the
same `~/.deessejs/` directory that already hosts the
templates cache (`apps/cli/src/cache/location.ts`). The
file format:

```jsonc
{
  "access_token": "<session.token>",
  "user": { "id": "...", "email": "...", "name": "..." },
  "fetchedAt": "2026-08-17T..."
}
```

The file is owned by a new module
`apps/cli/src/auth-store/index.ts` (one concept per folder,
per ADR-002). The module exposes `readAuth`, `writeAuth`,
`clearAuth` — three pure file-IO helpers. The token file
is **opaque** to consumers: a tool that reads
`~/.deessejs/auth.json` directly is reading the cache, not
the contract. The format may change between CLI minor
versions without bumping the major, on the same opacity
rule that ADR-010 §4 pins for the templates cache.

The token file is **not encrypted at rest** in V1. The
threat model is "someone with shell access to my machine",
not "someone who steals my laptop's encrypted home
directory". If the threat model widens, encryption at rest
ships as a separate ADR.

### Wire format for the polling loop

The CLI does not invent a wire format for the polling
loop. The loop calls the typed Better Auth client method
`authClient.device.token({ grant_type, device_code,
client_id })` and decodes the response into the shape
Better Auth publishes. The error codes
(`authorization_pending`, `slow_down`, `expired_token`,
`access_denied`) are Better Auth's codes, not CLI codes.
The CLI maps them to behavior, not to user-facing labels.

The `interval` returned by `/device/code` is the minimum
polling interval. On `slow_down`, the CLI increases its
local interval by 5 seconds and continues. On
`expired_token` or `access_denied`, the CLI exits with a
distinct exit code mapped through `CliError`.

### Verification URI

The server-side plugin is configured with
`verificationUri: "/device"`. The path is a public route
on `apps/app/` (an `(unprotected)` route group), reachable
without a session — the page claims the code for the
calling session on `GET /api/v1/auth/device?user_code=...`,
which is the only call that requires a session.

The page lives at `apps/app/app/(unprotected)/device/page.tsx`
and follows the existing `(unprotected)` route convention:
the layout, the `AuthContainer` component (or its successor
in the design system), the `use-shadcn` discipline for any
form fields.

### Settings integration

The existing `/settings/sessions` page lists active sessions
via the Better Auth `session` table. The device-code flow
does not introduce a new settings entry: the verification
page is the user-facing surface, and the sessions page
already shows everything the user needs to manage
authenticated devices. A future ADR may add a "pending
device authorizations" panel; it does not belong in this
ADR.

## What this rule allows

- A new command under `apps/cli/src/commands/auth/`. Each
  command is a sibling file with its own flag list, output
  formatter, and exit-code mapping, per ADR-010 §1.
- A new module `apps/cli/src/auth-store/` with the three
  pure helpers (`readAuth`, `writeAuth`, `clearAuth`).
- Adding `deviceAuthorization(...)` to
  `packages/auth/src/auth.ts`'s plugin array. The plugin
  must sit before `nextCookies()` (which must remain
  last, per the Better Auth Next.js integration
  requirement).
- Adding `deviceAuthorizationClient()` to
  `apps/app/lib/auth-client.ts`'s plugin array.
- Regenerating `packages/database/src/schema/auth.ts` via
  `pnpm auth:generate` to add the `deviceCode` table.
- Reading the Better Auth docs and the plugin source to
  understand the polling protocol and the error codes.
  Reading is not bypassing.
- Mapping Better Auth's error codes to local CLI exit
  codes through the existing `CliError` machinery. The
  mapping is internal; the public error code list (per
  ADR-010 §2) does not gain new entries for the polling
  loop.

## What this rule forbids

- **A new HTTP route outside `/api/v1/auth/*` for the
  device flow.** The five endpoints live under the
  existing Better Auth mount. Adding
  `/api/v1/device/*`, `/api/v1/cli/*`, or any parallel
  mount is a regression.
- **A new wire envelope for the auth response.** The CLI
  decodes whatever Better Auth publishes; the CLI does
  not invent a parallel response shape.
- **A custom envelope alongside `ORPCError` for the
  polling loop.** ADR-001 forbids custom envelopes; this
  ADR reinforces the rule for the auth path. If a polling
  response cannot be decoded into the Better Auth shape,
  the error is a `network_error` or `parse_error` per
  ADR-010 §2, not a new code.
- **Storing the token outside `~/.deessejs/auth.json`.**
  The CLI does not read `~/.config/`, `~/.cache/`,
  environment variables, or the macOS Keychain for the
  session token in V1. The home-directory path is the
  contract.
- **Reading the session token from a non-CLI source.**
  The token is opaque; a tool that parses
  `~/.deessejs/auth.json` directly reads the cache at its
  own risk, on the same opacity rule as the templates
  cache (ADR-010 §4).
- **Storing the user's password on disk.** The device
  flow never sees the password; storing it would defeat
  the point of the flow.
- **Reimplementing the polling loop in the server.** The
  Better Auth plugin owns the polling protocol; the server
  exposes the five endpoints, the plugin enforces
  `interval` and `lastPolledAt` throttling, the CLI
  consumes them.
- **Adding `deviceAuthorization` to `packages/api/` or
  `packages/api/src/http/`.** The plugin lives in
  `packages/auth/`, which is the single source of truth
  per the better-auth guides (`docs/guides/better-auth/index.md`).
- **Bypassing `nextCookies()` to put `deviceAuthorization`
  last.** `nextCookies()` must be last in the plugin
  array; moving it is a Next.js integration regression.
- **Adding a settings page that duplicates the device
  verification page.** The verification page is the
  user-facing surface; `/settings/sessions` already
  covers device management.

## What this rule does not change

- **The single-tenant decision.** The
  device-authorization plugin does not introduce
  organization concepts; it adds a `deviceCode` table
  and five endpoints that operate on user identity, not
  on organization membership. The locked-in decisions in
  `docs/guides/better-auth/index.md` (no
  `organization(...)`, no `databaseHooks.session.create.before`,
  no `useActiveOrganization`) are unchanged.
- **The session cookie configuration.** The device flow
  creates a session with the existing
  `session.expiresIn: 7 days`, `updateAge: 1 day`
  configuration. The CLI token is a `session.token`;
  the cookie config is unrelated.
- **The CLI's public command set.** The three existing
  commands (`init`, `list`, `info`) and their flags are
  unchanged. The `auth` parent command is a new sibling,
  not a renamed or removed command.
- **The CLI's error code list.** The four codes
  (`network_error`, `parse_error`, `not_found`,
  `cli_outdated`) are unchanged. The polling loop maps
  Better Auth error codes to existing CLI codes through
  the `CliError` machinery; no new public code is added.
- **The CLI's HTTP wire format.** The CLI still talks to
  the upstream through the Better Auth client for the
  auth endpoints. The typed oRPC client (per ADR-001)
  remains the wire format for business procedures.
- **The CLI's cache opacity rule.** The token file
  inherits the same opacity rule as the templates cache
  (ADR-010 §4): the format may change between CLI minor
  versions without bumping the major.
- **The `trustedOrigins` configuration.** The device
  verification page lives on the same origin as the rest
  of `apps/app/`; no new origin is added to the
  allowlist.
- **The `apps/cli/` folder structure.** The new
  `commands/auth/` and `auth-store/` folders follow the
  one-folder-per-concept rule (ADR-002); no new file at
  the `apps/cli/` root.

## Consequences

- A PR that adds a device-auth endpoint outside
  `/api/v1/auth/*` is rejected. The contributor moves the
  endpoint under the Better Auth mount.
- A PR that adds a CLI command without a sibling file in
  `commands/auth/` is rejected. The contributor splits
  the command into one file per command.
- A PR that adds `deviceAuthorization` after
  `nextCookies()` in the plugin array is rejected. The
  plugin must sit before `nextCookies()`.
- A PR that introduces a custom auth wire format is
  rejected. The wire format is whatever Better Auth
  publishes.
- A PR that stores the token outside
  `~/.deessejs/auth.json` is rejected. The home-directory
  path is the contract.
- A PR that adds a new public CLI error code for the
  polling loop is rejected per ADR-010 §2. The
  contributor maps Better Auth codes to existing CLI
  codes or escalates the public-list change to a new ADR.
- A PR that adds `organization(...)` or
  `useActiveOrganization` in the same change as
  `deviceAuthorization(...)` is rejected. The
  device-auth plugin does not require the org plugin;
  the contributor splits the change.
- A PR that regenerates `schema/auth.ts` without
  reviewing the diff is rejected. The generator may
  overwrite custom field names or indexes (per
  `docs/guides/better-auth/setup.md`).
- A PR that ships a CLI binary with the auth commands
  without a changeset is rejected by the
  `check-changeset` CI job (per ADR-010 §6).

## Where this rule came from

The CLI shipped V1 (`@deessejs/cli@1.x`) without an auth
surface. The three commands that exist today
(`init`, `list`, `info`) are anonymous on the wire: the
server does not know who is calling, and the CLI does not
carry identity. The first feature that requires identity
on the CLI side — a roadmap item that surfaces a
"personal registry" experience for authenticated users —
forces the question: how does the CLI authenticate?

Three options were considered:

1. **Username and password in the CLI.** The user types
   credentials on every command (or stores them in the
   shell). The approach fails the threat model: shell
   history, copy-paste, screen sharing. It also fails
   the email-verification gate (per
   `docs/guides/better-auth/email.md`): a CLI that
   requires verified email cannot verify a user who has
   not yet logged in to the web app.
2. **A long-lived API key issued from the web app.** The
   user creates a key in `/settings/connections`, pastes
   it into the CLI on first run, the CLI stores it. The
   approach works, but the key-management surface
   (`/settings/connections` + a CLI storage path) is a
   second wire format that the CLI must learn.
3. **Device authorization.** The CLI requests a code, the
   user approves in the browser, the CLI polls for a
   token. The wire format is Better Auth's wire format;
   the token is a session token that the existing
   `/get-session` endpoint already knows how to decode;
   the verification page is the user-facing surface;
   no new key-management UI is needed.

Option 3 wins on three counts:

- **No new wire format.** The five endpoints live under
  the existing Better Auth mount.
- **No new user-facing key-management UI.** The
  verification page is a one-page surface, not a CRUD.
- **No new CLI storage path.** The session token lives
  in the same `~/.deessejs/` directory as the templates
  cache.

The risk of option 3 is the polling protocol: a CLI that
polls too aggressively could DDoS the server. Better Auth's
plugin enforces this: the `pollingInterval` field and the
`slow_down` error code prevent abuse. The CLI respects
the protocol; the server enforces it.
