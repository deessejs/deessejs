# ADR-033: GitHub integration v2 (webhooks, GitHub App, auto-deploy)

## Status

Proposed (2026-10). Companion ADR to `ADR-031` §5 (v1 list + select) and
`ADR-028` (OAuth GitHub sign-in). Ships no code.

This ADR is a long-term reference for the next iteration of the
GitHub integration. v2 is **not in the current milestone**: the v1
implementation lands in the `feat/github-import` PR per the
implementation roadmap in `ADR-031` and `ADR-032`. v2 lands in a
later milestone, after v1 is in production and after the team has
production data to size the v2 surfaces (webhook volume, rate-limit
pressure, build queue depth).

The decisions in this ADR are **proposed, not ratified**. They are
the team's best current thinking on how to extend the GitHub
integration; they will be challenged in review against the
production data that v1 produces. A future ADR (or a set of ADRs)
will ratify them when v2 enters a milestone.

## Context

The current GitHub integration is the v1 list-and-select flow scoped
in `ADR-031` §5 and implemented in the `feat/github-import` PR. v1
covers:

- OAuth sign-in via the GitHub OAuth App configured per `ADR-028`
  (the `socialProviders.github` block in `packages/auth/src/auth.ts`).
- Reading the user's GitHub `accessToken` from the `account` table
  (persisted by the OAuth flow).
- Calling `GET /user/repos` server-side, paginating, and rendering
  the list in the project-import screen.
- Recording a `project` row per selected repository, FK'd to the
  active organization, with the repo's `full_name` and
  `default_branch` as initial fields.
- **No webhook, no auto-sync, no auto-deploy.** v1 is a one-shot
  import.

v1 is enough to record a project's existence in the app. It is not
enough to keep the project's data fresh, to react to upstream
changes, or to deploy on push. v2 is the next iteration that fills
the gap.

Three forces drive the v2 design:

1. **Vercel-style reference.** The product roadmap anchors on
   Vercel. Vercel's GitHub integration combines (a) an OAuth App
   for sign-in, (b) a GitHub App for fine-grained permissions and
   webhooks, (c) per-repo installation of the GitHub App, and (d) a
   webhook endpoint that triggers builds on `push` and
   `pull_request` events. Picking the same shape matches the
   product reference and the user's mental model.
2. **The GitHub Apps model is the recommended path.** Per the
   GitHub Apps overview, "GitHub Apps are preferred over OAuth apps.
   GitHub Apps use fine-grained permissions, give the user more
   control over which repositories the app can access, and use
   short-lived tokens." Migrating the OAuth flow itself is out of
   scope (the OAuth App is in production per `ADR-028`); adding a
   GitHub App alongside the OAuth App is the path that respects the
   recommendation without breaking the existing flow.
3. **Webhook security is non-trivial.** The webhook endpoint
   receives unauthenticated POSTs from GitHub. Signature
   verification is mandatory: per the GitHub docs on validating
   webhook deliveries, the `X-Hub-Signature-256` header carries
   `sha256=` followed by the lowercase HMAC-SHA256 hex digest of
   the payload body, keyed with the shared secret, and the
   comparison must use a constant-time function
   (`crypto.timingSafeEqual` in Node.js) to mitigate timing
   attacks. A naive `===` comparison is a security bug.

## Decision

v2 is the addition of four surfaces on top of v1. Each surface is
proposed with a concrete shape; the implementation lands in a later
milestone.

### 1. A GitHub App alongside the OAuth App

The OAuth App (per `ADR-028`) continues to handle sign-in. A new
GitHub App is registered with the deessejs GitHub organization and
shipped to users as the integration target. The two are independent:

- The OAuth App's `clientId` / `clientSecret` are configured in
  `packages/auth/src/auth.ts` and are the source of truth for
  `socialProviders.github` (per `ADR-028`).
- The GitHub App's `appId`, `clientId`, `clientSecret`,
  `privateKey`, and `webhookSecret` are configured in
  `packages/env/src/server.ts` as new env vars. The `privateKey` is
  a multi-line PEM; the loader handles it via `z.string()` with
  `.transform((s) => s.replace(/\\n/g, "\n"))` to support
  Vercel's env-var inlining of multi-line strings.

The user flow on the project-import screen is unchanged for v1
(connect GitHub via OAuth, list repos, select). For v2, the user
is prompted to **install the GitHub App** on the GitHub
organization or user that owns the repos they want to integrate.
The install flow is the GitHub-standard "install on user/org"
redirect; the callback lands on a v2-only route
`/api/v1/github/install/callback` that records the installation
id on the `organization` row (new column `github_app_installation_id`).

#### Why this rule decides

- **OAuth App stays in place for sign-in.** Migrating the sign-in
  flow to a GitHub App is a separate effort (per `ADR-028` §"What
  this rule does not change" the OAuth flow is unchanged). v2 does
  not touch it.
- **GitHub App is the right primitive for webhooks and
  permissions.** OAuth Apps cannot subscribe to webhooks with
  fine-grained repository permissions. The GitHub App model is
  the only one that fits v2.
- **One installation per GitHub org/user, not per deessejs
  org.** The GitHub App is installed on the GitHub side
  (github.com/owner/settings/installations), not on the deessejs
  side. The mapping is one-to-many: one GitHub installation can
  serve many deessejs orgs that the same GitHub user belongs to.
  This is the Vercel shape.

#### Why not the alternatives

- **Replace the OAuth App with the GitHub App entirely.**
  Cleaner long-term, but requires migrating the sign-in flow and
  re-issuing tokens. Out of scope for v2.
- **Use the OAuth App's webhook capability.** OAuth Apps do not
  have a webhook subscription model; the alternative is polling,
  which the team's product reference (Vercel) does not use.
  Rejected.
- **One GitHub App per deessejs org.** The mapping is on the
  wrong axis. The GitHub App is installed on a GitHub user or org;
  the deessejs org is a downstream concept. Rejected.

#### What this rule allows

- A `GitHub App` registration flow that records the
  `appId`, `clientId`, `clientSecret`, `privateKey`, and
  `webhookSecret` in `packages/env/src/server.ts`. Optional
  fields, like the OAuth credentials in `ADR-028`; CI must run
  without them.
- A new `github_app_installation_id` column on the `organization`
  table, populated by the install callback.
- A `GET /api/v1/github/install` route that returns the GitHub
  install URL (a `https://github.com/apps/<app-slug>/installations/new`
  link with the deessejs `state` parameter for CSRF protection).
- A `GET /api/v1/github/install/callback` route that receives
  the install id, validates the `state`, and writes the
  installation id on the active `organization` row.

#### What this rule forbids

- Touching the OAuth App config in
  `packages/auth/src/auth.ts:159-164`. v2 does not change the
  sign-in flow.
- Storing the GitHub App's `privateKey` anywhere other than
  `packages/env/src/server.ts` (env-validated, server-only). The
  private key is read at request time when signing JWTs for the
  App's API calls; it is never persisted in the database and never
  sent to the client.
- A second `clientId` for the GitHub App in `auth.ts`. The App is
  not a `socialProviders` entry; it is a separate, server-side
  integration.

### 2. A webhook endpoint with signature verification

A new route `POST /api/v1/webhooks/github` is mounted in
`packages/api/src/http/routes/http.ts:21-58` (the existing direct
HTTP routes mount, per `ADR-011`). The route is a system route, not
an oRPC procedure, because the request body is the raw GitHub
webhook payload (JSON, signed).

The route handler:

1. Reads the raw request body (not the parsed JSON; the
   signature is computed over the raw bytes).
2. Reads the `X-Hub-Signature-256` header and the
   `X-GitHub-Event` header.
3. Looks up the webhook secret for the active installation (the
   GitHub App installation that fired the event). The secret is
   stored on the `organization` row that owns the
   `github_app_installation_id` (a new column
   `github_webhook_secret` is added; the secret is generated at
   install time and persisted encrypted, per `ADR-031`
   §"Out of scope" §"Token encryption" — the token-encryption
   ADR ships before the webhook secret is persisted).
4. Computes `sha256=` + HMAC-SHA256 hex digest of the raw body
   with the secret, and compares it to the header value using
   `crypto.timingSafeEqual` (per the GitHub docs on validating
   webhook deliveries, which explicitly warn against `==`).
5. Returns 403 if the signature does not match. Returns 200 if
   it does.
6. Dispatches the event to a per-event-type handler
   (`push`, `pull_request`) via an internal map; unknown events
   return 200 with no-op (GitHub requires 2xx to stop retrying).

The route is unauthenticated (no session cookie) — the
signature is the authentication. The proxy at
`apps/app/proxy.ts` excludes this path from the auth gates.

#### Why this rule decides

- **Signature verification is mandatory.** The GitHub docs are
  explicit: "Never use a plain `==` operator; instead use a
  constant-time comparison such as `secure_compare` or
  `crypto.timingSafeEqual` to mitigate timing attacks." A naive
  comparison is a security bug. The implementation uses
  `crypto.timingSafeEqual` from Node's `crypto` module.
- **Raw body, not parsed JSON.** The signature is computed over
  the raw bytes. Parsing the body to JSON and then re-serializing
  it can change whitespace and break the signature. The
  implementation uses `await c.req.raw.text()` (or
  `c.req.raw.arrayBuffer()`) to get the raw bytes.
- **Per-installation secret.** The GitHub App model supports one
  webhook secret per installation, not one per app. The secret is
  generated at install time and stored on the deessejs `organization`
  row that owns the installation. This is the GitHub-recommended
  shape.
- **System route, not oRPC procedure.** The request is an
  unauthenticated POST with a raw signed body; it is not a
  typed RPC call. The existing system route pattern in
  `packages/api/src/http/routes/http.ts:21-58` (per `ADR-011`)
  fits this surface.

#### Why not the alternatives

- **Verify the signature in middleware that wraps every API
  route.** Only the webhook route needs signature verification;
  middleware applied broadly is wasted work and complicates the
  route handlers that do not need it. The signature check is
  inline in the webhook handler.
- **Store the webhook secret in `packages/env` (server-wide).**
  The secret is per-installation, not server-wide. A single
  shared secret across all installations means revoking one
  installation's access requires rotating the secret for all.
  Per-installation storage is the GitHub-recommended shape.
- **Parse the body as JSON before verifying.** As noted above,
  this can break the signature. Rejected.

#### What this rule allows

- A new Hono route `POST /api/v1/webhooks/github` mounted in
  `mountHttp` (per `ADR-011`).
- A new `github_webhook_secret` column on the `organization`
  table (encrypted at rest, per the token-encryption ADR
  referenced above).
- A new `github_app_installation_id` column on the `organization`
  table (per §1).
- An event dispatcher in
  `packages/api/src/http/routes/webhooks-github.ts` (new file)
  that maps `X-GitHub-Event` to a per-event handler.
- The `push` and `pull_request` event handlers in v2; all other
  events return 200 with no-op.

#### What this rule forbids

- A plain `===` comparison of the signature. Per the GitHub
  docs, this is a security bug. The implementation must use
  `crypto.timingSafeEqual`.
- Parsing the body to JSON before verifying the signature. The
  signature is computed over the raw bytes.
- Re-using a single secret across installations. The secret is
  per-installation.
- Adding the webhook route to the oRPC router. The route is a
  system route, not an oRPC procedure (per `ADR-011`).

### 3. An auto-deploy pipeline triggered by `push`

A `push` event on the default branch of a repo linked to a
deessejs project triggers a build. The build is asynchronous: the
webhook handler enqueues a job and returns 200 immediately. The
actual build runs in a worker process that is **out of scope** for
this ADR (the worker is a separate project; the queue, the runner,
and the secret store are scoped in a follow-up ADR).

The v2 webhook handler's `push` event handler:

1. Validates the `repository.full_name` matches a `project` row
   (FK to the active `organization`).
2. Validates the `ref` is the project's `default_branch` (per
   `ADR-031` §5, the `default_branch` is recorded at import
   time).
3. Enqueues a build job (the queue is the follow-up ADR's scope;
   v2's enqueue call is a no-op stub in the implementation
   that the follow-up ADR fills in).
4. Returns 200.

The `pull_request` event handler is identical in shape but
operates on `pull_request.base.ref` instead of `ref`. The build
output is a preview deployment, scoped in the follow-up ADR.

#### Why this rule decides

- **Async enqueue, not sync build.** GitHub requires the webhook
  to return 2xx within a few seconds. A sync build would time
  out on slow builds. The enqueue is O(1) and returns 200
  immediately.
- **Default branch only for v2.** Pull-request previews are a
  v2.1 follow-up; the v2 webhook handles `push` to the default
  branch first, and `pull_request` is reserved for the v2.1
  follow-up. The dispatcher is structured to accept new event
  types without rewiring.
- **Queue and worker are out of scope.** The webhook handler
  enqueues a job; the queue and the worker are separate
  concerns with their own ADRs. Mixing them in this ADR would
  make the document unmanageable.

#### Why not the alternatives

- **Run the build synchronously in the webhook handler.** Ties
  the request lifecycle to the build duration; risks timeouts;
  consumes web worker capacity. Rejected.
- **Use GitHub Actions as the build runner.** Possible (the
  GitHub App can trigger a workflow via
  `POST /repos/{owner}/{repo}/actions/workflows/{id}/dispatches`)
  but locks the product into GitHub Actions. Out of scope for
  the SaaS template; revisit if the team adopts GitHub Actions
  as the build surface.
- **Handle `pull_request` in v2.** Doubles the v2 surface area
  and the v2 review. v2.1 follow-up.

#### What this rule allows

- A `push` event handler in
  `packages/api/src/http/routes/webhooks-github.ts` that validates
  the payload, looks up the matching `project` row, and enqueues
  a build job.
- A stub enqueue function in the implementation that the
  follow-up ADR fills in. The stub logs the job and returns
  immediately.
- A `pull_request` event handler stub that returns 200 with
  no-op, reserved for v2.1.

#### What this rule forbids

- A sync build in the webhook handler. The build is async.
- A `pull_request` build in v2. v2 handles `push` to the default
  branch only.
- A build queue implementation in this ADR's scope. The queue
  is a follow-up.

### 4. A rate-limit-aware GitHub API client

The v1 implementation reads the GitHub `accessToken` from the
`account` table and calls `GET /user/repos` per request. v1 does
not handle rate limits (the list call is per-user, per-import,
and the limit is unlikely to be hit in normal use). v2 adds a
rate-limit-aware client because v2 calls the API more
frequently (every webhook event triggers a follow-up API call
to fetch the commit details, the PR head, etc.).

The client wraps every GitHub REST API call and:

1. Reads the `x-ratelimit-*` headers on the response.
2. When `x-ratelimit-remaining` is below a threshold (proposed:
   10% of the limit), the client backs off exponentially and
   retries up to 3 times.
3. When the call hits a secondary rate limit (search, graphql,
   code_search), the client respects the
   `Retry-After` header and retries.
4. Surfaces a typed error to the caller when the limit is
   exhausted; the caller decides whether to fail the operation
   or queue it for later.

The rate-limit categories and headers are documented at the
GitHub REST API rate-limit reference. The primary limit is the
`core` resource (default for non-search REST API endpoints);
secondary limits cover `search`, `code_search`, `graphql`,
`integration_manifest`, `dependency_snapshots`,
`code_scanning_upload`, and `actions_runner_registration`.

#### Why this rule decides

- **v2 calls the API more than v1.** Every webhook event
  triggers at least one follow-up API call. The rate limit is
  5000 req/h per token for authenticated REST calls; v1 is
  unlikely to hit it, v2 might.
- **`x-ratelimit-*` headers are the source of truth.** Per the
  GitHub docs, the headers "reflect the counters that govern
  enforcement" and are "the authoritative source for the
  remaining allowance in the current window." The client reads
  them on every response and updates its internal state.
- **Constant-time back-off, not immediate retry.** A naive
  retry-on-429 floods the API and worsens the rate-limit
  pressure. The exponential back-off (1s, 2s, 4s) with jitter
  is the GitHub-recommended pattern.

#### Why not the alternatives

- **Polling the rate limit endpoint.** Wasteful; the
  `x-ratelimit-*` headers are on every response. Rejected.
- **Caching responses.** Possible for read-only endpoints
  (`GET /repos/{owner}/{repo}`) but not for the webhook
  follow-up calls. Out of scope for v2.
- **Using GraphQL to bypass the REST rate limit.** GraphQL has
  its own rate limit (calculated differently) and requires a
  separate client. Out of scope for v2.

#### What this rule allows

- A `GitHubClient` class in
  `packages/api/src/clients/github.ts` (new file) that wraps
  every GitHub REST API call with rate-limit handling.
- A typed `RateLimitError` that the caller can catch and
  decide how to handle (fail, queue, retry).
- The threshold (10% of the limit) and the back-off parameters
  (3 retries, 1s base, jitter) as configurable constants in
  `packages/api/src/clients/github.ts`.

#### What this rule forbids

- A naive retry on 429 without back-off. The client backs off
  exponentially.
- A retry that ignores the `Retry-After` header on secondary
  rate limits. The client respects the header.
- A bypass of the rate-limit client. Every GitHub REST call
  goes through `GitHubClient`; no direct `fetch` to
  `api.github.com` is allowed.

## Consequences

- **The OAuth App stays in place.** `ADR-028` is unchanged.
  v2 does not touch the sign-in flow.
- **The v1 list-and-select flow stays in place.** v2 is
  additive; v1 users do not need to migrate.
- **A GitHub App registration is required for v2 features.**
  The user installs the GitHub App on their GitHub org/user to
  enable webhooks. v1 works without the App; v2 features
  (webhooks, auto-deploy) require it.
- **A new column on `organization`.** The
  `github_app_installation_id` and `github_webhook_secret`
  columns are added by the v2 migration. The
  `github_webhook_secret` is encrypted at rest per the
  token-encryption ADR.
- **A new Hono route.** `POST /api/v1/webhooks/github` is
  added; the existing routes are unchanged.
- **A new client.** `packages/api/src/clients/github.ts`
  wraps every GitHub REST call with rate-limit handling. The
  v1 implementation refactors to use the client.
- **A Drizzle migration lands.** The migration is generated
  by Drizzle's introspection after the schema change, reviewed,
  and committed (per `ADR-015`).
- **The follow-up ADRs are not in this document.** The build
  queue, the worker, the secret store, the GitHub Actions
  integration, the v2.1 pull-request previews are each their
  own ADR.

## What this rule allows

- Adding the GitHub App env vars to
  `packages/env/src/server.ts`: `GITHUB_APP_ID`,
  `GITHUB_APP_CLIENT_ID`, `GITHUB_APP_CLIENT_SECRET`,
  `GITHUB_APP_PRIVATE_KEY`, `GITHUB_APP_WEBHOOK_SECRET`.
  Optional fields, like the OAuth credentials in `ADR-028`;
  CI runs without them.
- Adding the `github_app_installation_id` and
  `github_webhook_secret` columns to the `organization` table.
- The Drizzle migration that lands the schema change.
- The new Hono route `POST /api/v1/webhooks/github` mounted
  in `mountHttp` (per `ADR-011`).
- The `GitHubClient` class in
  `packages/api/src/clients/github.ts`.
- The `push` and `pull_request` event handlers in
  `packages/api/src/http/routes/webhooks-github.ts`.
- The proxy at `apps/app/proxy.ts` excluding
  `/api/v1/webhooks/github` from the auth gates (the route
  is unauthenticated; the signature is the auth).

## What this rule forbids

- Touching the OAuth App config in
  `packages/auth/src/auth.ts:159-164`. v2 does not change the
  sign-in flow.
- Storing the GitHub App's `privateKey` anywhere other than
  `packages/env/src/server.ts` (env-validated, server-only).
- A plain `===` comparison of the webhook signature. The
  implementation must use `crypto.timingSafeEqual`.
- Parsing the webhook body to JSON before verifying the
  signature. The signature is computed over the raw bytes.
- A sync build in the webhook handler. The build is async
  (the queue and the worker are out of scope).
- A direct `fetch` to `api.github.com` outside of
  `packages/api/src/clients/github.ts`. Every call goes
  through the rate-limit-aware client.
- A retry on 429 without back-off. The client backs off
  exponentially.

## What this rule does not change

- The OAuth App config in `packages/auth/src/auth.ts:159-164`
  (per `ADR-028`).
- The v1 list-and-select flow in `ADR-031` §5. v2 is
  additive.
- The Hono CORS allowlist (per `ADR-029`). The webhook route
  is server-to-server (GitHub calls the route); CORS does not
  apply.
- The proxy auth gates for `(protected)` routes (per
  `ADR-032`). The webhook route is excluded from the gates
  (signature-based auth, not session-based).

## Out of scope (deferred)

- **Build queue, worker, secret store, runner.** Each is a
  separate ADR. The v2 webhook handler's enqueue call is a
  stub in the implementation; the follow-up ADRs fill it in.
- **`pull_request` event handler.** v2 handles `push` only;
  v2.1 adds `pull_request` previews.
- **GitHub Actions integration.** Possible via
  `POST /repos/{owner}/{repo}/actions/workflows/{id}/dispatches`
  but locks the product into GitHub Actions. Out of scope for
  the SaaS template.
- **GitHub Marketplace listing.** A future consideration
  when the team wants third-party GitHub users to discover
  the integration.
- **OAuth App migration to GitHub App.** Out of scope for v2;
  the OAuth flow is in production and migrating it is its own
  effort.
- **Token encryption for the webhook secret.** The webhook
  secret is encrypted at rest per the token-encryption ADR
  referenced in §1; that ADR ships before the webhook secret
  is persisted.
- **Per-repo permissions UI.** The GitHub App's permissions
  are configured at install time on github.com; a deessejs-side
  UI to view or revoke them is a future ADR.

## Open questions

The decisions in this ADR are proposed, not ratified. The
following questions surface in review and will be resolved
when v2 enters a milestone:

1. **Threshold for the rate-limit back-off.** The 10% threshold
   is proposed; the team may prefer a different value (e.g.
   25% to be more conservative, 5% to be more aggressive).
2. **Retry budget for the rate-limit client.** The 3-retry
   budget is proposed; the team may prefer 5 retries with a
   longer total back-off.
3. **Webhook secret rotation.** The secret is generated at
   install time and stored on the `organization` row. Rotation
   is not in scope for v2; the team may want a rotation flow
   in v2.1.
4. **Per-org vs per-installation webhook secret.** v2 stores
   the secret per installation (per GitHub's recommended
   shape). The team may want to scope it per deessejs org
   instead, which is simpler but does not match the GitHub
   App's model.

## Where this rule came from

- The GitHub Apps overview (https://docs.github.com/en/apps/overview)
  documents the recommendation to prefer GitHub Apps over OAuth
  Apps: "GitHub Apps use fine-grained permissions, give the user
  more control over which repositories the app can access, and
  use short-lived tokens." v2 follows the recommendation by
  adding a GitHub App alongside the existing OAuth App.
- The GitHub webhook signature validation docs
  (https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)
  document the `X-Hub-Signature-256` header format
  (`sha256=` + HMAC-SHA256 hex digest of the raw body keyed
  with the secret), the recommendation to use
  `crypto.timingSafeEqual` (Node.js) for the constant-time
  comparison, and the test vector
  (`secret: "It's a Secret to Everybody"`,
  `payload: "Hello, World!"`,
  `expected: "sha256=757107ea0eb2509fc211221cce984b8a37570b6d7586c22c46f4379c8b043e17"`).
  v2 implements the verification exactly as documented.
- The GitHub REST API rate-limit reference
  (https://docs.github.com/en/rest/rate-limit/rate-limit)
  documents the `x-ratelimit-*` response headers as "the
  authoritative source for the remaining allowance in the
  current window" and the secondary rate limits for `search`,
  `code_search`, `graphql`, `integration_manifest`,
  `dependency_snapshots`, `code_scanning_upload`, and
  `actions_runner_registration`. v2 reads the headers on every
  response and backs off when the remaining is below the
  threshold.
- `ADR-028` (GitHub OAuth sign-in via better-auth) is the
  source of truth for the OAuth App config. v2 does not
  change it.
- `ADR-031` §5 (V1 scope of "Import a project from GitHub")
  is the source of truth for the v1 list-and-select flow. v2
  extends it without changing the v1 surface.
- `ADR-032` (First-organization onboarding implementation)
  scopes the org plugin enablement that v1 depends on. v2
  depends on the org plugin being in production.
- `ADR-011` (Hono for system routes) documents the
  `mountHttp` mount and the direct HTTP route pattern. The
  webhook route follows the same pattern.
- `ADR-015` (Drizzle migrations CI) documents the
  `auth:generate` workflow and the migration commit pattern.
  The v2 migration follows the same pattern.
