# ADR-032: First-organization onboarding implementation

## Status

Proposed (2026-10). Under review on
`chore/adr-031-organizations-and-github-import` (PR #205, the same PR
that amends ADR-031 and ships the documentation only — this ADR
itself ships no code).

The implementation PR that follows this ADR ships code. It is
intentionally not part of PR #205. PR #205 is the decision record; the
implementation lands in a follow-up PR that targets `staging`.

## Context

ADR-031 (as amended on this same branch) introduces a
first-organization gate: a user whose only organization is their
personal account is redirected to `/onboarding/first-organization` on
their next visit to a `(protected)` route, and the app does not render
until a real organization exists. ADR-031 §6 scopes the wizard in
three steps (name + slug, invite teammates, connect GitHub) with
per-step skips on steps 2 and 3, and no global skip.

ADR-031 is a decision record. It names the routes the implementation
must add (`/onboarding/first-organization`, the `check-slug` and
`create` Hono routes) but does not scope them. This ADR scopes them.

The implementation is non-trivial because four existing surfaces need
to move at once:

1. The proxy at `apps/app/proxy.ts` gains a third gate (after the
   "is signed in" and "is email-verified" gates) that resolves the
   session's `activeOrganizationId` and checks whether it points to
   the user's personal account. If so, and the request targets a
   `(protected)` route other than `/onboarding/*`, the proxy redirects
   to `/onboarding/first-organization`. The proxy today uses a pure
   HTTP self-fetch to `/api/v1/auth/get-session` to avoid bundling
   `better-auth` into the proxy (the comment at
   `apps/app/proxy.ts:32-43` documents why). The new gate reuses the
   same self-fetch path; it does not import `better-auth` directly.

2. The better-auth `organization` plugin must be enabled in
   `packages/auth/src/auth.ts`. The plugin is not in the `plugins`
   array today (the `plugins: [deviceAuthorization, bearer,
   nextCookies()]` block at line 175-200 of `packages/auth/src/auth.ts`
   does not include `organization()`). The schema in
   `packages/database/src/schema/auth.ts` (the source-of-truth file
   that the better-auth CLI's `auth:generate` rewrites) must gain the
   `organization`, `member`, and `invitation` tables the plugin
   expects. The CLI regeneration runs in this PR; the migration
   follows the same pattern as every other schema change (Drizzle
   migration committed alongside the schema, CI gate per `ADR-015`).

3. The wizard page at
   `apps/app/app/(onboarding)/first-organization/page.tsx` (new route
   group `(onboarding)`, parallel to `(protected)` and
   `(unprotected)`) renders the three steps as a single page with
   internal step state. The page is server-rendered for the initial
   state, with client components for the per-step interactivity
   (slug input, invite form, GitHub connect button). The page is
   outside the `(protected)` route group because the user has no real
   organization yet and therefore fails the proxy's
   `(protected)`-gate; putting it under `(protected)` would loop.

4. The `AGENTS.md` single-tenant guard ("ce repo est single-tenant
   — n'introduis pas ces patterns") must be lifted, and the
   `AGENTS.md` §"Better-Auth guides" table must gain a pointer to
   ADR-031 / ADR-032 for the multi-tenant shape. This is the last
   file that contradicts the new decision.

The implementation PR also ships the two follow-up ADRs that ADR-031
references: the `organization` plugin wiring (the `auth.ts` change
plus the schema regeneration) and the GitHub project-import screen.
Those two ADRs scope their own files; this ADR scopes only the
onboarding surfaces.

## Decision

The implementation PR ships the four surfaces above, in this order,
as separate commits on the implementation branch (not on PR #205):

1. `chore/org-plugin` — enable the `organization` plugin in
   `packages/auth/src/auth.ts`, regenerate
   `packages/database/src/schema/auth.ts`, commit the resulting
   Drizzle migration, update `AGENTS.md` to lift the single-tenant
   guard. No UI change.
2. `chore/onboarding-wizard` — add
   `apps/app/app/(onboarding)/first-organization/page.tsx`, the
   client components for the three steps, the two Hono routes
   (`check-slug`, `create`), and the proxy gate. This ADR scopes
   this commit in detail below.
3. `feat/github-import` — the GitHub project-import screen (the
   third follow-up ADR from the original ADR-031 PR). Out of scope
   here; the third follow-up ADR scopes it.

The implementation branch is created from `staging` after PR #205
merges. Until PR #205 merges, this ADR is documentation only and the
implementation branch does not exist.

### What this rule decides

#### 1. The proxy gains a third gate

`apps/app/proxy.ts` adds a third check after the
`isProtected && !session?.session` and
`isProtected && session?.session?.user && !session.session.user.emailVerified`
checks. The check:

- Only runs for `isProtected` requests.
- Reads the session's `activeOrganizationId` from the
  `get-session` response (the response shape is widened by the
  `organization` plugin; the existing `GetSessionResponse` interface
  in `apps/app/proxy.ts:45-47` gains a typed `activeOrganizationId`
  field).
- Resolves the active organization via a second self-fetch to a new
  Hono route `GET /api/v1/organization/active` (described below).
  The fetch is necessary because `get-session` returns the
  organization id, not the organization row; the gate needs the row
  to know whether the active organization is the user's personal
  account. The personal account has a known marker (its slug equals
  the user's username, or it carries a `personalAccount: true`
  column that the better-auth `organization` plugin sets). The fetch
  is cheap and uses the same self-fetch pattern the proxy already
  relies on.
- If the active organization is the personal account, the proxy
  redirects to `/onboarding/first-organization` (preserving the
  `?redirect=` query param so the user lands back on the page they
  were trying to reach after onboarding).

The check does not run for `isAuthPage` requests (the
`(unprotected)/(auth)/*` routes) and does not run for the
`/onboarding/*` route group itself. The `config.matcher` at
`apps/app/proxy.ts:18-30` gains the `/onboarding/:path*` entry but
the proxy body short-circuits for it.

#### 2. The wizard page lives under a new `(onboarding)` route group

`apps/app/app/(onboarding)/first-organization/page.tsx` is a
server-rendered page that mounts a client component
`OnboardingWizard` (new, at
`apps/app/components/onboarding/onboarding-wizard.tsx`). The page
reads the session server-side (via the better-auth `auth.api.getSession`
call the implementation already uses for `(protected)` pages) and
hands the session's `user.id` to the client component. The client
component owns the step state (`useState<1 | 2 | 3 | 4>(1)`), the
per-step form state, and the calls to the two Hono routes.

The page renders a minimal layout: a centered card with the
`APP_NAME` logo at the top, a step indicator (`1 — Personal slug`,
`2 — Org name and slug`, `3 — Invite`, `4 — GitHub`) with the
current step highlighted, the active step's form, and a "Skip this
step" button on steps 1, 3, and 4 (absent on step 2, per
ADR-031 §6). The card uses the same `Card`, `Input`, `Button`, and
`Field` primitives the rest of `apps/app` uses (the `use-shadcn`
rule applies — no raw HTML form controls).

The four step components live next to the wizard:

- `apps/app/components/onboarding/step-personal-slug.tsx`
- `apps/app/components/onboarding/step-name-slug.tsx`
- `apps/app/components/onboarding/step-invite.tsx`
- `apps/app/components/onboarding/step-github.tsx`

Each step is a controlled form with a single submit handler that
returns to the parent. The parent advances the step on success.

#### 3. Two Hono routes under `/api/v1/organization/*`

Both routes are direct HTTP routes in the `mountHttp` mount at
`packages/api/src/http/routes/http.ts:21-58`, not oRPC procedures.
The shape matches the existing system routes (`/auth/*`,
`/health`, `/ready`).

- `GET /api/v1/organization/check-slug?slug=<slug>` — validates
  the slug format (`^[a-z0-9-]+$`, length 3-32) and queries the
  `organization` table for an existing row with the same slug.
  Returns `{ available: true }` or
  `{ available: false, reason: "taken" | "invalid" | "format" }`.
  The route is rate-limited at the proxy layer (a new rate-limit
  bucket on `RATE_LIMIT_PER_MINUTE`, same as `/version`).
- `POST /api/v1/organization/create` — accepts
  `{ name: string, slug: string }`, calls the better-auth
  `auth.api.createOrganization` server-side (the route is exposed
  by the `organization` plugin), validates the response, and
  returns `{ organizationId: string, slug: string }`. The client
  then calls `authClient.organization.setActive({ organizationId })`
  to switch the session's active organization.

A third route, `GET /api/v1/organization/active`, is added to
support the proxy gate (see §1). It returns the active
organization's `id`, `slug`, and `personalAccount` boolean for
the session's user. The proxy is its only consumer.

The `invite` route (referenced in ADR-031 §6) is the
better-auth `auth.api.inviteMember` server-side call invoked
directly from the client via
`authClient.organization.inviteMember(...)` — the existing
better-auth handler at `/api/v1/auth/organization/invite-member`
serves it. No new Hono route is needed for the invite step; the
wizard uses the better-auth handler. The "no new Hono route" is
a deliberate scope cut.

#### 4. `AGENTS.md` amendment

`AGENTS.md` §"Better-Auth guides" gains two changes:

- The line "ce repo est single-tenant — n'introduis pas ces
  patterns" is deleted.
- A new row in the guides table pointing to ADR-031 (product
  shape) and ADR-032 (this ADR, implementation), with the
  description "Multi-tenant: every user has a personal account,
  the active organization gates `(protected)` routes, and the
  `organization` plugin is the source of truth."

No other section of `AGENTS.md` changes. The
"Staging-first workflow" and the "Fresh CLI" sections are
unaffected.

#### 5. Org lifecycle: rename, delete, personal-account immutability

> **Amendment (2026-10).** The wizard creates a real organization
> on top of the user's personal account (per `ADR-031` §1 and §2).
> Once the org exists, the user expects to be able to rename it
> (typo on the name, brand change) and, in the end, delete it
> (project cancelled, team dissolved). This sub-section scopes the
> org lifecycle surfaces in the implementation PR that follows.

**Rename.** The `name` and the `slug` of a real organization are
modifiable at any time from `/<org-slug>/settings` (the
organization settings page, owned by the per-org settings entry in
the sidebar). The action calls
`authClient.organization.update({ organizationId, name, slug })`.
The `slug` is the URL segment, so a change must propagate to every
in-app link to the org; the implementation uses the `app-config.ts`
`orgHome(orgSlug)` and `orgSettings(orgSlug)` helpers (per the
amended `ADR-030`) so the slug is never hardcoded. External links
to the old slug (search engines, bookmarks) are redirected to the
new slug via a 301 in `next.config.ts` rewrites. Per
`ADR-031` §2 §"Cycle of life permissions", both `owner` and
`admin` can rename.

**Delete.** The `name` and the `slug` of a real organization can
also be removed entirely, by hard delete. The action calls
`authClient.organization.delete({ organizationId })`. The
better-auth `organization` plugin's hard delete cascades to the
`member`, `invitation`, and `team` tables (the plugin's contract).
The `project` rows that FK the organization are also hard-deleted
(the schema's FK is `ON DELETE CASCADE` per the implementation
PR's Drizzle migration). The `user` rows and the `account` rows
(GitHub OAuth, per `ADR-028`) survive: the user still has their
identity, and the user can still re-link a GitHub account later.
Per `ADR-031` §2 §"Cycle of life permissions", only `owner` can
delete. The personal account is not deletable by anyone; see
`ADR-031` §1 §"What this rule forbids" and §"What this rule
allows".

**Session after delete.** If the user deletes the active
organization, the session's `activeOrganizationId` is reset to
the user's personal account (the always-available fallback). The
user is redirected to `/<personal-slug>/home` (the
personal-account dashboard) with a toast confirming the deletion.
The user is never left without an active organization.

**Redirect target.** The post-delete redirect is
`/<personal-slug>/home` because the route shape adopted by the
amended `ADR-030` is Vercel-style `/[org_slug]/*`; the personal
account's slug is the user's custom slug (default = username), per
`ADR-031` §6 step 1 and `ADR-032` §"Decision" §2. The
implementation looks up the personal-account slug at request time
from the `auth.api.getSession` response (the session carries the
active organization id; the personal-account slug is the user row's
`username` field or, if the user has run the wizard's step 1, the
personal-account organization's `slug`).

**The org settings page.** The page lives at
`apps/app/app/(protected)/[org_slug]/settings/page.tsx` (new
route, parallel to the `/<org-slug>/home` page). It is a
server-rendered page that mounts a client component
`OrgSettingsForm` (new, at
`apps/app/components/orgs/org-settings-form.tsx`) for the rename
form and a destructive-zone `DeleteOrgDialog` (new, at
`apps/app/components/orgs/delete-org-dialog.tsx`) for the delete
confirmation. The page reuses the `Card`, `Field`, `Input`,
`Button`, and `Dialog` primitives the rest of `apps/app` uses
(the `use-shadcn` rule applies).

**Server-side calls.** Rename and delete go through the
better-auth handlers at `/api/v1/auth/organization/update` and
`/api/v1/auth/organization/delete` (the plugin's built-in
routes; the implementation does not add a wrapper Hono route).
The `update` and `delete` handlers enforce role on the server
side; the client-side role check (hiding the delete button for
`admin`) is a UX nicety, not a security boundary.

### What this rule allows

- The proxy at `apps/app/proxy.ts` adding the
  `(protected)`-route-redirect-to-`/onboarding/first-organization`
  gate, with a `?redirect=<original-pathname>` query param
  preserved on the redirect.
- The new route group `(onboarding)` at
  `apps/app/app/(onboarding)/first-organization/page.tsx`, parallel
  to the existing `(protected)` and `(unprotected)` groups.
- The client component
  `apps/app/components/onboarding/onboarding-wizard.tsx` and the
  four step components.
- The three Hono routes
  (`GET /api/v1/organization/check-slug`,
  `POST /api/v1/organization/create`,
  `GET /api/v1/organization/active`) in
  `packages/api/src/http/routes/organization.ts` (new file) and
  wired in `packages/api/src/http/routes/http.ts:21-58` via a new
  `mountOrganization(api)` call.
- The Drizzle migration generated by
  `pnpm auth:generate` after the `organization` plugin is enabled,
  committed alongside the schema change.
- The `AGENTS.md` §"Better-Auth guides" amendment lifting the
  single-tenant guard and adding the ADR pointer.
- A toast on the Members page when an invite is sent from the
  wizard (the toast persists the `{ sent, failed }` count from
  the better-auth response). The toast is fired from the
  `step-invite` client component, not from the Members page
  itself.
- A `/<org-slug>/settings` page (per §"Decision" §5) with a
  `OrgSettingsForm` client component (rename) and a
  `DeleteOrgDialog` client component (destructive confirmation).
  The page reuses the layout chrome defined in the amended
  `ADR-030`.
- `next.config.ts` rewrites that 301-redirect the old slug to the
  new slug when an org is renamed (per §"Decision" §5). The
  rewrite list is the source of truth for "what URL was an
  org's old home"; the org's `slug` history is stored in a
  small `organization_slug_history` table (or a JSON column on
  the `organization` row — implementation choice in the
  implementation PR).
- A toast on the deletion confirmation that confirms the
  deletion, plus a redirect to `/<personal-slug>/home` after
  the session's `activeOrganizationId` resets to the personal
  account.

### What this rule forbids

- A `useActiveOrganization` import from the better-auth React
  client in any file outside the onboarding wizard and the
  `(protected)` layout's `NavUser` (the latter for the
  organization switcher, per ADR-031 §1 §"What this rule
  allows"). Other consumers read the active organization from
  the server-side `auth.api.getSession` call or from the
  `get-session` self-fetch the proxy already uses. The
  React-client hook is a footgun for SSR (the value can be
  stale on a server-rendered page) and the codebase has
  decided to read it server-side.
- A `useEffect`-driven redirect from the wizard's step
  components to the post-onboarding landing. The redirect is
  computed in the parent `OnboardingWizard` after the last
  step's submit resolves; per-step `useEffect` redirects are
  fragile and have been the source of past regressions in the
  auth flow.
- A re-implementation of the slug-validation logic in
  client-side code. The validation regex
  (`^[a-z0-9-]+$`, length 3-32) lives in the Hono route and is
  re-used by the client only for instant feedback (the
  `check-slug` call is the source of truth on availability).
- A global "Skip onboarding" button on the wizard. ADR-031 §6
  forbids it; the implementation must not reintroduce it under
  a different name ("Save and finish later", "I'll do this
  later", etc.).
- A second Hono route for the invite step. The better-auth
  handler at
  `/api/v1/auth/organization/invite-member` is the call; the
  client uses `authClient.organization.inviteMember(...)`
  directly. The implementation does not wrap it in an oRPC
  procedure or a Hono route.
- Deleting or renaming a personal-account organization (per
  `ADR-031` §1 §"What this rule forbids"). The UI hides rename
  and delete actions for personal accounts; the implementation
  must not surface them in any context (the `/<org-slug>/settings`
  page is only reachable for real organizations, and the
  `app-config.ts` helpers resolve the personal slug to the
  `account/settings` route, never to `/<org-slug>/settings`).
- Letting `admin` delete an organization. The destructive zone
  of the org settings page is `owner`-only; the client-side
  check is a UX nicety, but the better-auth `auth.api.deleteOrganization`
  server-side handler also enforces the role (per `ADR-031` §2
  §"Cycle of life permissions"). An implementation that bypasses
  the server-side check is a security bug, not a feature.
- A re-implementation of the rename or delete logic in
  client-side code. Both calls go through
  `authClient.organization.update(...)` and
  `authClient.organization.delete(...)`; the implementation
  does not reimplement role checks or cascade logic client-side.

### Why not the alternatives

- **A wizard that lives under `(protected)` with a special-case
  in the proxy to allow it.** The proxy's `config.matcher`
  already supports a list of allowed paths inside the
  `(protected)` group, but the cleaner shape is a separate
  `(onboarding)` group that the proxy explicitly does not
  redirect away from. The two-group split is more readable
  in the route tree and easier to reason about than a
  proxy-level exception.
- **A modal-based onboarding instead of a full page.** A
  modal would be harder to recover from (the user could close
  it by accident and lose the gate), and the gate is
  server-enforced, so the user would just be re-prompted on
  the next navigation. A dedicated page is the better
  affordance.
- **A wizard state persisted in the database (e.g. "the user
  has seen step 1").** ADR-031 §6 forbids progress persistence.
  Each wizard run is in-memory; if the user navigates away,
  they restart from step 1 on their next visit. The
  implementation must not store wizard state.
- **An oRPC procedure for `check-slug` and `create`.** Both
  routes are non-RPC: `check-slug` is a `GET` (not
  oRPC-shaped), and `create` is a system action that calls a
  better-auth server-side handler (the better-auth handler is
  already mounted at `/api/v1/auth/*` per ADR-011; layering an
  oRPC procedure on top adds nothing). The decision matches
  the existing `/auth/*` system route pattern.

### What this rule does not change

- The better-auth `socialProviders.github` block at
  `packages/auth/src/auth.ts:159-164` (per `ADR-028`). The
  GitHub OAuth flow is unchanged; the wizard's step 3 invokes
  it via `authClient.signIn.social(...)`.
- The `account` table schema (per `ADR-028` §"What this rule
  does not change"). The wizard reads the `accessToken` from
  the `account` row but does not modify the schema. Token
  encryption (deferred in `ADR-028` and again in `ADR-031`
  §"Out of scope") is not in scope here.
- The `apps/app/proxy.ts` matcher and the existing two gates
  (signed-in and email-verified). The new gate is a third
  check, layered on top of the existing two; the matcher
  gains `/onboarding/:path*` so the proxy runs the body for
  those requests, but the body short-circuits for them.
- The `apps/app/app/(protected)/layout.tsx` chrome (per
  `ADR-030`). The wizard has its own minimal layout; the
  protected chrome (header + left rail + main) is unchanged.
- The Hono CORS allowlist (per `ADR-029`). The new
  `/api/v1/organization/*` routes ride the same Hono catch-all
  in `apps/app/app/api/[[...route]]/route.ts`; no change to
  the host allowlist is required.
- The CLI (`apps/cli/`). The CLI is unchanged. The
  `apps/cli/src/lib/auth/flow/` device-flow does not interact
  with organizations.
- The `personalAccountEnabled: true` default. The
  configuration is added to `packages/auth/src/auth.ts` as
  part of the `organization` plugin enablement; it is the
  plugin's default, not a custom value.

## Consequences

- **The proxy gains a third gate.** A user whose only
  organization is their personal account is redirected to
  `/onboarding/first-organization` on their next visit to a
  `(protected)` route. The redirect carries a `?redirect=<path>`
  query param so the user lands back where they were trying to
  go after onboarding.
- **The wizard is reachable from the proxy's
  `config.matcher`.** The matcher gains
  `/onboarding/:path*`; the proxy body short-circuits for it
  (no gate runs, no redirect, the request flows through to
  the page). This is the only `(onboarding)` route in V1.
- **The better-auth `organization` plugin is enabled.** The
  plugin's routes (`/api/v1/auth/organization/*`) are
  available; the schema gains `organization`, `member`, and
  `invitation` tables; the session shape gains
  `activeOrganizationId`. The `AGENTS.md` single-tenant
  guard is lifted in the same commit.
- **A Drizzle migration lands.** The migration is generated
  by `pnpm auth:generate` after the `organization` plugin is
  enabled, reviewed, and committed. The migration follows
  the same shape as every other schema change in the repo
  (per `ADR-015`).
- **Three Hono routes ship.** `check-slug`, `create`, and
  `active`. The `check-slug` route is rate-limited at the
  proxy layer; the other two are session-authenticated (the
  better-auth middleware at `/api/v1/auth/*` covers them
  transitively via the session cookie).
- **The wizard page is server-rendered, client-interacted.**
  The initial state (current step, user session) is computed
  server-side; the step transitions and form submits are
  client-side. The page is reachable from the proxy's
  matcher; the proxy does not gate it.
- **No new env vars.** The wizard reuses
  `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` (per
  `ADR-028`) for the GitHub step; no new env vars are
  introduced. The `BETTER_AUTH_SECRET` is unchanged.
- **The wizard's post-onboarding landing.** This ADR scopes
  the landing to the new organization's dashboard at
  `/<org-slug>/home` (the Vercel-style `/[org_slug]/*` route
  shape scoped in the amended `ADR-030`). The
  `?redirect=<path>` query param is honored if it points to a
  route under `/<org-slug>/*`; otherwise the user lands on
  `/<org-slug>/home`. A future ADR can scope a richer
  per-organization dashboard (`/<org-slug>/projects` or
  equivalent) when the project-import screen is in scope.
- **The org lifecycle surfaces ship together with the
  onboarding.** The `/<org-slug>/settings` page (rename + delete)
  and the slug-rewrite 301 in `next.config.ts` land in the same
  implementation PR that ships the wizard. The personal account
  is immutable: the UI hides rename and delete actions, and the
  better-auth handlers reject personal-account ids. Deleting the
  active org resets the session to the personal account and
  redirects to `/<personal-slug>/home`.

## Out of scope (deferred)

- **GitHub project-import screen.** ADR-031 §5 scopes the
  shape (list + select, no webhook). The screen itself is
  scoped in the third follow-up ADR from the original
  ADR-031 PR, not here.
- **The `team` table.** Per ADR-031 §"Out of scope".
- **More than two roles.** Per ADR-031 §2.
- **Shareable-link invites.** Per ADR-031 §4.
- **Token encryption.** Per ADR-031 §"Out of scope". The
  `accessToken` is read in plaintext from the `account` row
  in step 3; encryption lands in its own ADR.
- **A `useActiveOrganization` React hook in
  consumer-agnostic positions.** Per ADR-031 §1 §"What this
  rule allows" (the hook is restricted to the wizard and
  the protected layout's `NavUser`).
- **A per-organization landing page.** The post-onboarding
  landing is `/home` (with the `?redirect` param honored);
  the per-org dashboard is a future ADR.
- **Email-template changes for the invite step.** The
  invite uses the better-auth default template; the
  `packages/email` package is not touched in this PR. A
  future ADR scopes branded invite emails.

## Known limitations in this version

### Limitation 1: post-onboarding landing is `/<org-slug>/home`, not a per-organization dashboard

The post-onboarding landing is `/<org-slug>/home` (per the
§"Consequences" note above, after the amendment to the route
shape in the amended `ADR-030`). A richer per-organization
dashboard (`/<org-slug>/projects` or equivalent) is a future
ADR. The user lands on a placeholder home page scoped to the
new organization; the org's content (members, projects, settings)
is reachable from the sidebar.

### Limitation 2: the proxy gate re-fetches the active organization

The proxy's third gate re-fetches
`GET /api/v1/organization/active` on every request to a
`(protected)` route. The fetch is cheap (one DB row) but
adds a roundtrip to every protected navigation. A future
optimization caches the `activeOrganizationId` on the
session or the better-auth response and skips the
re-fetch. The optimization is not in scope here; the V1
implementation always re-fetches.

### Limitation 3: the wizard does not persist partial state

If the user navigates away from the wizard mid-flow, the
in-memory step state is lost. On their next visit, the
wizard restarts from step 1. ADR-031 §6 forbids progress
persistence, so the limitation is by design. A user who
navigates away by accident loses a few seconds, not
data (no organization is created until step 1 submits).

### Limitation 4: the wizard does not survive a refresh on step 1

The `useState<1 | 2 | 3>(1)` initialization in the
`OnboardingWizard` resets on a full page refresh. A
user who has typed a name but not submitted, then
refreshes, loses the typed name. This is a known V1
limitation; partial-state persistence is the
mitigation, and ADR-031 §6 forbids it. The mitigation
in V1 is "type, then submit; do not refresh mid-form."

## Open questions

1. **Does the better-auth `organization` plugin's `update` action
   allow modifying the slug of a personal-account organization?**
   `ADR-031` §6 step 1 calls
   `authClient.organization.update({ organizationId: <personal>, slug })`
   to apply the custom slug the user picks. If the plugin rejects the
   update (or if personal accounts are not regular `organization` rows
   the plugin accepts `update` on), the step is a no-op that advances
   to step 2 with the username as the slug, and the customisation is
   deferred to a follow-up ADR. The implementation PR resolves this
   against the live plugin API; the fallback shape is documented
   here so the implementation is not blocked on the question.

## Where this rule came from

- ADR-031 §6 (as amended on the same branch) scopes the
  three-step wizard shape. This ADR is the implementation
  scoping ADR-031 §6 references.
- The better-auth `organization` plugin docs
  (https://www.better-auth.com/docs/plugins/organization)
  document the `personalAccountEnabled` configuration, the
  two-role default, the invitation lifecycle, the
  `setActive` session call, and the `createOrganization` /
  `inviteMember` server-side handlers. The Hono routes in
  this ADR wrap those handlers in the repo's existing
  direct-HTTP-route pattern.
- The proxy at `apps/app/proxy.ts:32-43` documents the
  self-fetch pattern for the session lookup. The third gate
  reuses the same pattern (the `get-session` response is
  widened with `activeOrganizationId`, the new
  `active` route is fetched via the same self-fetch).
- `ADR-015` (Drizzle migrations CI) documents the
  `auth:generate` workflow and the migration commit
  pattern. The schema change in the
  `chore/org-plugin` commit follows it.
- `ADR-028` (GitHub OAuth) documents the
  `socialProviders.github` block and the `accessToken`
  storage on the `account` row. The wizard's step 3
  invokes the OAuth flow via the same
  `authClient.signIn.social` call the rest of the app
  uses.
- `ADR-029` (Vercel preview URL wiring) documents the
  Hono CORS allowlist and the `host-allowlist.ts` shared
  module. The new Hono routes ride the same
  catch-all; no change to the allowlist is required.
- `ADR-030` (apps/app uses left rail nav) documents the
  `(protected)` chrome. The wizard has its own minimal
  layout; the protected chrome is unchanged.
