# ADR-016: API integration tests in CI use `api.request()` against the real Hono app

## Status

Accepted (2026-08). Non-negotiable.

## Context

The API surface is split across two layers:

- **Hono system routes** mounted by `mountHttp`
  (`packages/api/src/http/routes/http.ts`): `GET /api/v1/health`,
  `GET /api/v1/version`, `GET /api/v1/ready`, and `* /api/v1/auth/*`
  (Better Auth). These are the platform's view of the server:
  liveness, readiness, version, identity.
- **oRPC procedures** mounted by `mountRpc`
  (`packages/api/src/http/mount-rpc.ts`): the typed business
  surface. Today: `templates.list`. Tomorrow: any procedure
  added to `appRouter`.

In production both layers are served by the same Hono app,
which `apps/app` mounts via the catch-all at
`apps/app/app/api/[[...route]]/route.ts:22-23`:

```ts
import { handle } from "hono/vercel"
import { api } from "@workspace/api"

export const dynamic = "force-dynamic"
export const GET = handle(api)
export const POST = handle(api)
```

The current test surface covers some of this in isolation but
not the seam we actually care about:

- `packages/api/tests/unit/observability.test.ts` exercises
  the request-id middleware, secure headers, and the global
  `notFound` handler against the real `api` object via
  `api.request()`. This is the right shape — in-process, no
  listener, full middleware chain.
- `packages/api/tests/contract/templates-list.test.ts` calls
  the procedure directly via `call(appRouter.templates.list,
  ...)` from `@orpc/server`. It tests the procedure logic but
  bypasses the Hono mounting, the prefix, the wire format,
  and the error envelope.
- `packages/api/tests/integration/routes.test.ts` builds a
  throwaway Hono app per test and exercises patterns that
  look like the real routes. It does not exercise the real
  `api` and does not assert anything about the actual mount.
- `packages/auth` has its own Vitest suite. Better Auth's
  `/api/v1/auth/*` handler is wired into Hono via
  `mountHttp:57` but the Hono side of the mount is never
  tested; only the auth library itself is.

The gap is: nothing in the suite asserts that **the routes
Hono actually serves** — `GET /api/v1/health`, the
`templates.list` wire shape through the oRPC handler, the
prefixed URL convention, the `notFound` envelope, the
request-id round trip — all line up together. ADR-015 caught
exactly that class of bug: a Hono routing pattern that
worked for single-segment procedures silently returned 404
on the only two-segment procedure in the repo, and no test
surfaced it.

There is also a question of scope. `apps/app` is the real
host, but booting Next.js in CI just to test Hono is heavy:
the `test-integration` job already runs in ~2 minutes, and
adding a Next dev server, an `apps/app` build, and a network
fetch adds minutes and a class of flaky failures (port
collisions, cold starts, ISR cache states) unrelated to the
API surface we are testing.

## Decision

Run the API integration tests **in-process against the real
`api` Hono object** using Hono's `app.request()`. The
harness lives in `packages/api/tests/integration/`, splits
into one file per route family, and runs in the existing
`test-integration` CI job alongside the existing unit and
contract suites.

`Hono` ships `app.request()` for exactly this use case
([hono.dev/docs/guides/testing](https://hono.dev/docs/guides/testing)).
The method takes a `Request` and a `RequestInit`, runs the
full middleware chain in-process, and returns a `Response`.
It is the Web Fetch API equivalent of Fastify's
`fastify.inject()` and is the canonical pattern in 2026 for
testing Hono apps without binding a TCP port.

oRPC provides a complementary `call()` helper from
`@orpc/server` for testing procedures in isolation
([orpc.dev/docs/advanced/testing-mocking](https://orpc.dev/docs/advanced/testing-mocking)).
The two are not redundant: `call()` tests the procedure
logic, `api.request()` tests the Hono mounting. Both are
kept; this ADR only formalises the second.

### What the suite covers

One test file per route family. The minimum viable surface
is intentionally small; each file exists to catch a
specific class of regression.

| File | Routes | What it asserts |
|---|---|---|
| `system/health.test.ts` | `GET /api/v1/health`, `GET /api/v1/ready` | Liveness returns 200 with `{ status: "ok" }`. Readiness pings the DB and returns 200 or 503. No `force-dynamic` leakage, no auth required. |
| `system/version.test.ts` | `GET /api/v1/version` | Returns `{ version, minSupported }` matching the constants in `packages/api/src/constants/version.ts`. Cache-Control header is set. Rate-limit headers are set. |
| `system/auth.test.ts` | `GET /api/v1/auth/get-session` | Single happy-path call: an unauthenticated `GET` returns 200 with a `null` session. The point is to assert the Better Auth handler is mounted, not to retest Better Auth itself. |
| `rpc/templates.test.ts` | `POST /api/v1/rpc/templates/list` (URL with two path segments) | Asserts that the URL Hono serves matches the URL the `RPCLink` client sends. Asserts the wire envelope shape. Asserts the contract layer (`TemplatesListResponseV1`) round-trips end-to-end. Mocks `enrich()` to avoid GitHub network. |
| `routing/not-found.test.ts` | `GET /api/v1/does-not-exist` | Asserts the `notFound` envelope `{ defined: false, code: "NOT_FOUND", message, requestId }` and the 404 status. This is the test that would have caught ADR-015's bug if it had existed. |
| `routing/base-path.test.ts` | All routes | Each test must hit the full path including `/api/v1`. This pins the Hono `basePath("/api/v1")` decision in ADR-011 against a regression that would silently drop the prefix. |

GitHub network calls are mocked at the `enrich` boundary
(via `vi.mock`), not at the `fetch` boundary. This keeps the
test honest about what the procedure does and avoids
network flakiness in CI. The contract test
`templates-list.test.ts` already follows this pattern; the
new file reuses the same mock.

### What the suite does not cover

- **Real GitHub requests.** Out of scope; that is the
  `enrich` contract test's territory.
- **Cross-origin CORS handshakes from a real browser.** Out
  of scope; Hono's `cors` middleware is a third-party
  library tested by its authors.
- **`apps/app` rendering.** Out of scope; that is the
  existing Playwright-style test surface in `apps/app`,
  which this ADR does not touch.
- **Production deploy validation.** Out of scope; ADR-013
  covers the publish-verify path for the CLI. For the API,
  a smoke test in the `verify` workflow hits
  `app.deessejs.com/api/v1/health` and `/api/v1/ready`
  post-deploy; this ADR does not add that.

### Why not the alternatives

Three alternatives were considered:

- **Boot `apps/app` in CI and curl localhost.** Closer to
  production but pays the Next.js boot cost (10-30s),
  introduces port-management flakiness, requires a separate
  `apps/app` build step, and exercises two surfaces at once
  (Next.js routing + Hono routing). When a test fails, the
  cause is twice as hard to localise. Rejected.
- **Stand up a separate Vite dev server for the API.**
  `packages/api` is a library today; adding a Vite harness
  means declaring a `dev` script, a server entry, and a
  listener. None of that is needed for the test surface. The
  patterns cited in the search results (`vite dev` for
  Hono) target teams that *want* a dev server. We do not.
  Rejected.
- **Spin up a real Postgres per route file.** The CI
  service already provides Postgres. The non-DB routes
  (`health`, `version`, `not-found`, `auth` smoke,
  `templates.list` with the enrich mock) do not need it.
  Adding a per-file DB setup is busywork and a leak risk
  (the existing contract test does not use the DB either).
  The readiness probe test in `system/health.test.ts` is
  the only file that touches the DB; it gets its own
  beforeAll that asserts the service is up before running.
  Rejected.

The `api.request()` pattern is the cheapest option that
exercises the surface that breaks. Hono's tests docs, the
oRPC server-side client docs, and the comparison post at
[pkgpulse.com](https://www.pkgpulse.com/guides/supertest-vs-fastify-inject-vs-hono-testing-api-2026)
all converge on the same recommendation: use the
framework's native in-process injection over a real HTTP
listener for CI integration tests.

## Consequences

- The `test-integration` CI job picks up the new files
  automatically. No workflow change. The job already runs
  `pnpm turbo test --filter=@workspace/auth --filter=@workspace/api`
  against a Postgres service.
- `packages/api/vitest.config.ts` may need to add the
  `integration/` directory to its include glob if the
  existing pattern excludes it. The `coverage.include` glob
  is already `src/**/*.ts`; integration tests live under
  `tests/`, not `src/`, so they are not part of the coverage
  surface by design (integration tests assert behaviour,
  not line coverage).
- The auth smoke test (`system/auth.test.ts`) requires a
  `BETTER_AUTH_SECRET` in the env, which the CI job already
  sets. No new env requirement.
- The `templates.list` test mocks `enrich` to avoid GitHub
  network calls. The mock lives next to the test, not in
  `tests/contract/`, to make the seam explicit: the
  integration test is about the Hono mounting, and the
  `enrich` mock is the seam that keeps the test honest.
- A regression of the kind ADR-015 documents (Hono
  `*` matching one segment, oRPC paths being two segments)
  is caught by `rpc/templates.test.ts` with a 404 envelope
  assertion that is unique to the Hono `notFound` handler.
  This is the load-bearing assertion: it would have caught
  the original bug.
- Adding a new oRPC procedure or Hono route requires adding
  a test in the matching `*.test.ts` file. The convention
  is pinned in this ADR so a future contributor does not
  have to re-derive the rule.

## Decision log

- **2026-08-18**: investigated how to test the API in CI
  end-to-end. Confirmed via fresh CLI searches that
  Hono's `app.request()`, oRPC's `call()`, and Fastify's
  `inject()` are the three canonical patterns; selected
  Hono's as the primary because the API is Hono-direct.
- **2026-08-18**: inventoried the existing test surface.
  Found `unit/observability.test.ts` already uses
  `api.request()` and `contract/templates-list.test.ts`
  already uses `call(appRouter.templates.list, ...)`. The
  gap is the Hono mounting seam, which neither file
  exercises.
- **2026-08-18**: chose to formalise `api.request()` as
  the integration pattern and rejected three alternatives
  (apps/app boot, Vite dev server, per-file DB setup).
  Wrote the harness plan in this ADR.
