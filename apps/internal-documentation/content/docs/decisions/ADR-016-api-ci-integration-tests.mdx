# ADR-016: Application-programming-interface integration tests in continuous integration use `api.request()` against the real Hono app {/* vale fix: Microsoft.HeadingAcronyms */}

## Status

Accepted (2026-08). Non-negotiable.

## Context

The API surface spans two layers:

- **Hono system routes** mounted by `mountHttp`
  (`packages/api/src/http/routes/http.ts`): `GET /api/v1/health`,
  `GET /api/v1/version`, `GET /api/v1/ready`, and `* /api/v1/auth/*`
  (Better Auth). These are the platform's view of the server:
  liveness, readiness, version, identity.
- **oRPC procedures** mounted by `mountRpc`
  (`packages/api/src/http/mount-rpc.ts`): the typed business
  surface. Today: `templates.list`. Tomorrow: any procedure
  added to `appRouter`.

In production both layers share the same Hono app,
which `apps/app` mounts via the catch-all at
`apps/app/app/api/[[...route]]/route.ts:22-23`:

~~~ts
import { handle } from "hono/vercel"
import { api } from "@workspace/api"

export const dynamic = "force-dynamic"
export const GET = handle(api)
export const POST = handle(api)
~~~

The current test surface covers some of this in isolation but
not the seam that actually matters:

- `packages/api/tests/unit/observability.test.ts` exercises
  the request-id middleware, secure headers, and the global
  `notFound` handler against the real `api` object via
  `api.request()`. This is the right shape: in-process, no
  listener, full middleware chain.
- `packages/api/tests/contract/templates-list.test.ts` calls
  the procedure directly via `call(appRouter.templates.list,
  ...)` from `@orpc/server`. It tests the procedure logic but
  bypasses the Hono mounting, the prefix, the wire format,
  and the error envelope.
- `packages/api/tests/integration/routes.test.ts` builds a
  throwaway Hono app per test and exercises patterns that
  look like the real routes. It doesn't exercise the real
  `api` and doesn't assert anything about the actual mount.
- `packages/auth` has its own Vitest suite. Better Auth
  exposes `/api/v1/auth/*` through Hono via `mountHttp:57`
  but the Hono side of the mount goes untested; only the
  auth library itself gets coverage.

The gap: nothing in the suite asserts that **the routes
Hono actually serves**, including `GET /api/v1/health`,
the `templates.list` wire shape through the oRPC handler,
the prefixed URL convention, the `notFound` envelope, and
the request-id round trip, all line up together. ADR-015
caught exactly that class of bug: a Hono routing pattern
that worked for single-segment procedures returned 404 on
the only two-segment procedure in the repo, and no test
surfaced it.

A question of scope remains. `apps/app` is the real host,
but booting Next.js in CI just to test Hono is heavy: the
`test-integration` job already runs in ~2 minutes, and
adding a Next dev server, an `apps/app` build, and a
network fetch adds minutes and a class of flaky failures
(port collisions, cold starts, ISR cache states) unrelated
to the API surface under test.

## Decision

Run the API integration tests **in-process against the real
`api` Hono object** using Hono's `app.request()`. The
harness lives in `packages/api/tests/integration/`, splits
into one file per route family, and runs in the existing
`test-integration` CI job alongside the existing unit and
contract suites.

`Hono` ships `app.request()` for exactly this use case
(see the [Hono testing guide](https://hono.dev/docs/guides/testing)).
The method takes a `Request` and a `RequestInit`, runs the
full middleware chain in-process, and returns a `Response`.
It's the Web Fetch API counterpart of an
inject-pattern framework, the canonical 2026 choice for
testing Hono apps without binding a TCP port. {/* vale fix: Vale.Spelling */}

oRPC provides a complementary `call()` helper from
`@orpc/server` for testing procedures in isolation
([orpc.dev/docs/advanced/testing-mocking](https://orpc.dev/docs/advanced/testing-mocking)).
The two play distinct roles: `call()` tests the procedure
logic, the request helper tests the Hono mounting. Both stay;
this ADR only formalises the second.

### What the suite covers

One test file per route family. The viable surface stays
small on purpose; each file exists to catch a specific
class of regression.

| File | Routes | What it asserts |
|---|---|---|
| `system/health.test.ts` | `GET /api/v1/health`, `GET /api/v1/ready` | liveness returns 200 with `{ status: "ok" }`. Readiness pings the DB and returns 200 or 503. No `force-dynamic` leakage, no auth needed. |
| `system/version.test.ts` | `GET /api/v1/version` | Returns `{ version, minSupported }` matching the constants in `packages/api/src/constants/version.ts`. Cache-Control header sets. Rate-limit headers set. |
| `system/auth.test.ts` | `GET /api/v1/auth/get-session` | Single happy-path call: an unauthenticated `GET` returns 200 with a `null` session. The point: assert the Hono↔Better Auth boundary wires correctly (Hono reaches the handler, the handler returns the documented envelope). DB-gated via `inject('postgres:ready')`, see *Test seams and conventions* below. |
| `rpc/templates.test.ts` | `POST /api/v1/rpc/templates/list` (URL with two path segments) | Asserts that the URL Hono serves matches the URL the `RPCLink` client sends. Asserts the wire envelope shape. Asserts the contract layer (`TemplatesListResponseV1`) round-trips end-to-end. Mocks `enrich()` to avoid GitHub network. |
| `routing/not-found.test.ts` | `GET /api/v1/does-not-exist` | Asserts the `notFound` envelope `{ defined: false, code: "NOT_FOUND," message, requestId }` and the 404 status. This test would have caught ADR-015's bug if it had existed. |
| `routing/base-path.test.ts` | All routes | Each test must hit the full path including `/api/v1`. Pins the Hono `basePath("/api/v1")` decision in ADR-011 against a regression that would drop the prefix. |

GitHub network calls get mocked at the `enrich` boundary
(via `vi.mock`), not at the `fetch` boundary. This keeps the
test honest about what the procedure does and avoids
network flakiness in CI. The contract test
`templates-list.test.ts` already follows this pattern; the
new file reuses the same mock.

### Test seams and conventions

Three implementation details the test files should follow.
They're pinned here so a future contributor doesn't
re-derive them.

**`vi.mock` form.** Vitest's recommended mock form for
pnpm workspaces is the dynamic-import argument
(see Vitest issues 3105, 9259, 10145 for context):{/* vale fix: Vale.Terms */}

```ts
vi.mock(import("../../src/core/templates/index.js"), () => ({
  enrich: vi.fn(async () => [/* ... */]),
}))
```

The string-path form (`vi.mock("../../src/...," factory)`)
works in this repo today and is what the existing contract
test uses. The dynamic-import form is more robust across
pnpm hoist and tsconfig-paths setups and is what the new
test files should adopt. Both forms can coexist; this is
a forward-looking convention, not a forced migration.

**`globalSetup` for the DB-backed readiness test.** Only
`system/health.test.ts` touches Postgres. The CI job
already provides a Postgres service, but the test should
not retry the connection on every run. A `globalSetup`
file (configured in the Vitest config under `packages/api/`)
asserts the service is reachable before workers start and
passes a primitive flag down via
[`inject('postgres:ready')`](https://vitest.dev/config/globalsetup).
The readiness test skips itself when the flag is false.
**The skip is observable:** the test name carries a
`[skip-postgres]` annotation that surfaces in Vitest's
reporter output, and the `beforeAll` emits a `WARN` line
to standard error via the existing
`packages/api/src/constants/logger.ts` so the skipped test
stays visible in the log aggregator. A misconfigured CI
that should have provided Postgres surfaces in the
reporter. The non-DB tests ignore the flag and run
unaffected.

**Better Auth smoke shape.** The `/api/v1/auth/get-session`
handler mounts via `mountHttp:57`:

```ts
api.on(["POST", "GET"], "/auth/*", (c) => auth.handler(c.req.raw))
```

Per the [Better Auth Hono integration
docs](https://better-auth.com/docs/integrations/hono), the
handler returns a `Response` directly. The smoke test calls
`GET /api/v1/auth/get-session` with no cookies and asserts
a 200 with `{ session: null, user: null }`, the documented
shape for an unauthenticated request. The point: assert
the Hono↔Better Auth boundary wires correctly: the Hono
mount catches the URL, the handler returns the documented
envelope. Better Auth itself gets coverage in
`packages/auth`.

**The auth smoke test is DB-gated.** Unlike the other
non-DB routes in the table above, the auth handler reaches
into Postgres (via the session middleware and the
drizzle-backed user lookup). The smoke test reads
`inject('postgres:ready')` at file-load time and skips
itself with a loud annotation when the flag is false. Same
pattern as the readiness test. The annotation surfaces in
the reporter (the test name carries `[skip-postgres]` and
`globalSetup` emits a WARN). The test runs in the CI
`test-integration` job where Postgres is up; in the
`test-unit` job it skips. This stays acceptable because
the goal of the test is to assert the real Hono↔Better
Auth boundary in real conditions, not to re-test Better
Auth in isolation.

**Payload fixtures come from the contract schemas.** Test
files that send JSON payloads (the oRPC wire shape, the
auth request body, future procedure inputs) derive their
fixtures from the Zod schemas in
`@workspace/contracts/src/vN/`, not from hand-written
constants. The TypeScript shape of an inline fixture is
local; the contract schema is the source of truth shared
between the server, the typed client, and the tests. When
`TemplateV1` gains a required field, a hand-written
`{ slug: "saas-starter" }` fixture would drift and the
test would keep passing against an outdated shape. A
schema-derived fixture fails to compile at the production
type site (the procedure's input or output type) and the
test can't merge until the fixture gets updated. The
existing contract test already follows this pattern
(`vi.mock(import("../../src/core/templates/index.js"), ...)`)
returns an array that matches the schema; the new
integration tests extend the same convention to request
bodies.

### What the suite doesn't cover

- **Real GitHub requests.** Out of scope; that's the
  `enrich` contract test's territory.
- **Cross-origin CORS handshakes from a real browser.** Out
  of scope; Hono's `cors` middleware is a third-party
  library tested by its authors.
- **`apps/app` rendering.** Out of scope; that's the
  existing Playwright-style test surface in `apps/app`,
  which this ADR doesn't touch.
- **Production deploy validation.** Out of scope; ADR-013
  covers the publish-verify path for the CLI. For the API,
  a smoke test in the `verify` workflow hits
  `app.deessejs.com/api/v1/health` and `/api/v1/ready`
  post-deploy; this ADR doesn't add that.

**Layout rules, pinned by this ADR:**

- One test file per route family, grouped under a
  subdirectory that names the family (`system/`, `rpc/`,
  `routing/`). A future "future family" gets its own
  subdirectory, not a flat file at the root.
- Files start with the route family (`health.test.ts`,
  `templates.test.ts`), not with the verb (`get.test.ts`,
  `fetch.test.ts`). The route name is the public surface;
  the verb is incidental.
- `globalSetup.ts` lives at the root of `tests/`, not under
  `unit/` or `integration/`. It runs before workers start
  and stays outside the test graph.
- The existing `integration/routes.test.ts` stays put
  through the implementation PR. This file is a placeholder
  pattern that the new files replace; removal happens as
  a separate decision. The new files prove the real `api`
  works; the old file documents the baseline pattern a
  Hono test shouldn't follow.

### Why not the alternatives

Three alternatives came under review:

- **Boot `apps/app` in CI and curl localhost.** Closer to
  production but pays the Next.js boot cost (10-30s),
  introduces port-management flakiness, requires a separate
  `apps/app` build step, and exercises two surfaces at once
  (Next.js routing + Hono routing). When a test fails, the
  cause becomes twice as hard to localise. Rejected.
- **Stand up a separate JS dev server for the API.**{/* vale fix: Vale.Spelling */}
  `packages/api` is a library today; adding a JS bundler
  harness means declaring a `dev` script, a server entry,
  and a listener. None of that serves the test surface.
  The patterns cited in the search results (`vite dev`
  for Hono) target teams that *want* a dev server. The current
  setup doesn't. Rejected.
- **Spin up a real Postgres per route file.** The CI
  service already provides Postgres. The non-DB routes
  (`health`, `version`, `not-found`, `auth` smoke,
  `templates.list` with the enrich mock) don't need it.
  Adding a per-file DB setup is busywork and a leak risk
  (the existing contract test doesn't use the DB either).
  The readiness probe test in `system/health.test.ts` is
  the only file that touches the DB; it gets its own
  `beforeAll` that asserts the service is up before running.
  Rejected.
- **Use Hono's `testClient` for a typed test client.**
  `hono/testing` exposes `testClient(app)` which returns a
  type-safe client keyed off the app's route types
  ([Hono.dev/docs/helpers/testing](https://hono.dev/docs/helpers/testing)).
  The type inference **only works when routes chain
  directly on `new Hono()`**. `packages/api/src/index.ts:18-31`
  builds the app via `new Hono<ApiEnv>().basePath(...)`
  followed by separate `api.onError(...)`, `api.use(...)`,
  `mountHttp(api)`, `mountRpc(api)` calls, the exact
  pattern that strips `testClient` of its type
  information. Adopting `testClient` would require
  refactoring the Hono app construction to use chained
  method calls everywhere, a non-trivial change to a
  load-bearing file. The call to `api.request()` (which lacks the type narrowing of `testClient`) stays
  stays cheap, fast, and exercises the same surface; the
  type-safety gain doesn't justify the construction-site
  refactor. Rejected.

The `api.request()` pattern is the cheapest option that
exercises the surface that breaks. Hono's tests docs, the
oRPC server-side client docs, and the comparison post at
[pkgpulse.com](https://www.pkgpulse.com/guides/supertest-vs-fastify-inject-vs-hono-testing-api-2026)
all converge on the same recommendation: use the
framework's native in-process injection over a real HTTP
listener for CI integration tests.

## Consequences

- The `test-integration` CI job picks up the new files
  automatically. No workflow change. The job already runs
  `pnpm turbo test --filter=@workspace/auth --filter=@workspace/api`
  against a Postgres service.
- `packages/api/vitest.config.ts` may need to add the
  `integration/` directory to its include glob if the
  existing pattern excludes it. The `coverage.include` glob
  is already `src/**/*.ts`; integration tests live under
  `tests/`, not `src/`, so they're outside the coverage
  surface by design (integration tests assert behaviour,
  not line coverage). The Vitest config also picks up
  `packages/api/tests/globalSetup.ts` to seed the
  `postgres:ready` flag for the readiness test.
- The auth smoke test (`system/auth.test.ts`) requires a
  `BETTER_AUTH_SECRET` in the env, which the CI job already
  sets. No new env constraint.
- The `templates.list` test mocks `enrich` to avoid GitHub
  network calls. The mock lives next to the test, not in
  `tests/contract/`, to make the seam explicit: the
  integration test is about the Hono mounting, and the
  `enrich` mock is the seam that keeps the test honest.
- A regression of the kind ADR-015 documents (Hono
  `*` matching one segment, oRPC paths being two segments)
  gets caught by `rpc/templates.test.ts` with a 404 envelope
  assertion that's unique to the Hono `notFound` handler.
  This is the load-bearing assertion: it would have caught
  the original bug.
- Adding a new oRPC procedure or Hono route requires adding
  a test in the matching `*.test.ts` file. The convention
  pins here so a future contributor doesn't
  have to re-derive the rule.
