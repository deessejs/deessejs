# ADR-032: deesse-template.json registry item

## Status

Draft (2026-09). Awaiting review.

## Context

The DeesseJS template registry is the project's identity surface. The user has framed it on the marketing site as a registry that spans "packages, CLI, SaaS multi-tenant, mobile, desktop, AI agent, landing page" (per the locked homepage copy) — not a single-template repo. Today the registry is a single hand-curated TypeScript array exported from `packages/api/src/templates.ts`:

```ts
export const TEMPLATES: RegistryEntry[] = [
  {
    slug: "saas-starter",
    name: "SaaS Starter",
    description: "Production-ready Next.js + Better Auth + Postgres boilerplate for B2B SaaS.",
    owner: "deessejs",
    repo: "saas-template",
    license: "MIT",
    category: "saas",
    labels: ["nextjs", "saas", "auth", "postgres"],
    layer: "open-community",
  },
]
```

The wire contract `TemplateV1` (`packages/contracts/src/v1/template.ts`) carries thirteen flat fields. The CLI (`apps/cli/src/commands/init.ts`) consumes the same endpoint and shells out to `git clone --depth 1 --branch <ref>` plus `pnpm/npm install`. There is no manifest reading, no token replacement, no post-processing — the CLI is a glorified clone wrapper. Templates as files live in external GitHub repos; the registry only carries metadata.

Four structural gaps are the focus of this ADR (the fifth, no project-side config, is covered by [ADR-031](./ADR-031-deesse-json.mdx)):

### Gap 2: no item-side metadata beyond a flat shape

`TemplateV1` declares thirteen fields and nothing about dependencies, runtime requirements, post-install scripts, or transformations. The CLI therefore installs whatever package manager the user has on the machine without checking that the template requires `pnpm@9`, that it depends on `next@^15`, or that it ships an `.env.example` the user should rename to `.env`. The registry is content, not contract.

### Gap 3: no template composition

The roadmap mentions `packages-template`, `cli-template`, `mobile-template`, `desktop-template`, `ai-agent`, `landing-template` (six confirmed categories per `project-templates-roadmap`). None of them composes with another. A user who wants `saas-starter` + `ai-agent` runs two `init` calls into two directories and merges by hand. shadcn's `registryDependencies` (item names, namespaced `@acme/item`, GitHub `owner/repo#tag`, full URL, local path) solves this; the DeesseJS registry has no equivalent.

### Gap 4: no namespaces, no third-party registries

The CLI hardcodes `process.env.DEESSEJS_API_URL ?? "https://app.deessejs.com"` as the upstream. Every template ships from one org. The shadcn `components.json#registries{}` map (`"@v0": "https://v0.dev/chat/{name}"`) plus the GitHub-static-JSON convention (`registry.json` at a public repo root auto-discovered as a registry) lets the CLI install items from any author without a CLI release. The DeesseJS CLI has neither.

### Gap 5: no transform layer

`apps/cli/src/commands/init.ts:58-69` runs `git clone` and `pnpm install` and stops. The CLI cannot:

- rename `.env.example` to `.env` and interpolate `{{DATABASE_URL}}` from a project-level token map (resolved by [ADR-031](./ADR-031-deesse-json.mdx)'s `deesse.json#tokens`),
- remove files the user opted out of (e.g. a Storybook setup the user does not want),
- merge `AGENTS.md` fragments contributed by each template,
- run a `db:push` after `pnpm install`.

shadcn's `files[].target` placeholders (`@components/`, `@ui/`, `@lib/`, `@hooks/`, `~`) plus the `cssVars` / `envVars` / `css` fields cover the analogous surface for components; the DeesseJS registry has no parallel.

### Where these gaps come from

`apps/cli` is the only published package in the monorepo; its public surface is locked by ADR-010 §1 (three commands: `init`, `list`, `info`, plus the `auth {login,status,logout}` group). Adding a fourth command, renaming one, or changing a flag's meaning is a breaking change for downstream tooling. The CLI cannot grow new install semantics without a major bump.

The registry data is the other load-bearing piece. The memory file `.claude/agent-memory/tech-lead/project/templates-content-not-cli.md` pins the rule: adding a template entry is never a CLI change and never requires a CLI changeset; only `Template` schema-level changes can. ADR-001 names oRPC as the load-bearing core of the internal API and forbids parallel transports. ADR-005 names the API as consumer-agnostic. ADR-004 pins `packages/api`'s structure.

The four gaps above all require coordinated changes across `packages/api` (registry data + enrichment), `packages/contracts` (wire shape), and `apps/cli` (install behaviour). The change set is too large for an "obvious fix" PR; it needs an ADR before any code lands.

## Decision

### What this rule decides

Four concrete decisions. They ship together because shipping any one without the others leaves the registry shape half-declared and the CLI half-aware.

#### 1. The descriptor is `deesse-template.json`, co-located in each template repo

shadcn's `registry-item.json` lives next to the source files of each item. The DeesseJS descriptor lives at the root of each template repo (`deessejs/<slug>`):

```jsonc
{
  "$schema": "https://registry.deessejs.dev/schema/template.json",
  "name": "saas-starter",
  "title": "SaaS Starter",
  "description": "Production-ready Next.js + Better Auth + Postgres boilerplate for B2B SaaS.",
  "type": "template:app",
  "version": "1.4.0",
  "source": {
    "repo": "deessejs/saas-template",
    "ref": "v1.4.0",
    "cloneUrl": "https://github.com/deessejs/saas-template"
  },
  "requires": { "node": ">=20.0.0", "packageManager": "pnpm@9" },
  "dependencies": ["next@^15", "better-auth@^1"],
  "devDependencies": ["typescript@^5"],
  "templateDependencies": [],
  "files": [
    {
      "path": "apps/web/.env.example",
      "type": "template:env",
      "target": "apps/web/.env",
      "transform": "rename"
    }
  ],
  "prompts": [
    {
      "name": "database",
      "type": "select",
      "message": "Which database would you like to use?",
      "default": "postgresql",
      "choices": [
        { "label": "PostgreSQL", "value": "postgresql" },
        { "label": "MySQL", "value": "mysql" },
        { "label": "SQLite", "value": "sqlite" }
      ]
    },
    {
      "name": "databaseUrl",
      "type": "text",
      "message": "Database connection URL (optional):",
      "default": "",
      "when": "database != 'sqlite'"
    }
  ],
  "hooks": {
    "postInit": ["pnpm install"],
    "postInstall": ["pnpm db:push"]
  }
}
```

The file is owned by the template author, not by the registry or the project. The template repo's CI validates the JSON against the published schema (`registry.deessejs.dev/schema/template.json`). The CLI parse-validates the file at install time through a Zod schema (see Decision #2).

#### 2. The wire contract becomes `TemplateV2`

The current `TemplateV1` is extended (not replaced) into `TemplateV2`. Every field in `TemplateV1` stays in `TemplateV2` with the same type. New fields are appended:

- `version: string` (semver) — pins which version of the template shipped. Today's CLI does not know the version it installed.
- `source: { repo, ref, cloneUrl }` — replaces the implicit `https://github.com/${owner}/${repo}` fallback at `apps/cli/src/commands/init.ts:59`. `ref` is the git tag/branch/SHA the CLI clones. `cloneUrl` carries over from `TemplateV1`.
- `requires: { node?, packageManager? }` — runtime gate. The CLI refuses to install if the user's `node` is below the lower bound.
- `dependencies: string[]` — npm packages with optional `@version`. Mirrors shadcn's `dependencies[]`.
- `devDependencies: string[]` — dev-time packages.
- `templateDependencies: string[]` — slugs of other templates required by this one. Composable templates (the `packages-template` + `auth-addon` pattern).
- `type: "template:app" | "template:package" | "template:cli" | "template:mobile" | "template:desktop" | "template:agent" | "template:landing"` — discriminates whether the install clones an entire project (`template:app`) or overlays files onto an existing one (the other six types).
- `docs: string` (optional) — path to a Markdown doc inside the template repo, surfaced by `deessejs info <slug>`.
- `prompts: Prompt[]` (optional) — interactive questions at install time. Each prompt has `name`, `type` (`text`, `select`, `confirm`), `message`, `default`, optional `choices[]` (for `select`), optional `validate` (regex string), optional `when` (a simple DSL expression that gates the prompt against earlier answers — `"database != 'sqlite'"` skips the prompt when the database choice is SQLite).
- `hooks: { preInit?, postInit?, preInstall?, postInstall? }` (optional) — declarative lifecycle hooks. Each value is an ordered list of verb names from the runtime whitelist (`postinstall`). The hooks run at the named lifecycle stage; `postInit` fires after the clone + transforms, before the install step; `postInstall` fires after the package manager install. The block is parallel to `postinstall[]` and supersedes it for new templates: `hooks.postInit` is the canonical entry, `postinstall[]` is preserved as a back-compat alias.
- `postinstall: string[]` (optional) — whitelisted shell verbs. Kept as a back-compat alias for `hooks.postInit`; new templates use `hooks{}` instead.
- `files: FileSpec[]` (optional) — post-processing on the cloned tree. Each file has `path` (source in the template repo), `type` (`template:env`, `template:doc`, `template:config`, etc.), `target` (destination in the user's project, with `@components/`, `@lib/`, `@hooks/`, `@ui/`, `@apps/`, `@packages/` placeholders resolved against [ADR-031](./ADR-031-deesse-json.mdx)'s `deesse.json#aliases`), and `transform` (the verb: `rename`, `interpolate`, `remove`, `merge`).

The `TemplateV1` → `TemplateV2` migration is additive: `TemplateV2 = TemplateV1 & { new fields }`. No required fields are added. Existing CLIs that only know `TemplateV1` keep working because the upstream `packages/api` continues to publish the `TemplateV1`-shaped response for clients that haven't bumped.

The `@workspace/contracts` package gains a new export `TemplateV2` alongside `TemplateV1`. Both Zod schemas live in `packages/contracts/src/v1/`. The server's enrichment layer (`packages/api/src/core/templates/enrich.ts`) merges live GitHub data onto `TemplateV2` entries the same way it merges onto `TemplateV1` today. The server's `templates.list` oRPC procedure returns `TemplatesListResponseV2` (a parallel response shape); the V1 response is preserved for backward compatibility.

The `templates-content-not-cli` rule from `.claude/agent-memory/tech-lead/project/templates-content-not-cli.md` is preserved: a new template entry (one line added to `packages/api/src/templates.ts`) never triggers a CLI changeset, only `Template` schema-level changes can.

#### 3. CLI install flow is enriched by `deesse.json`

The CLI's `init <slug>` command gains the following sequence:

1. Read or create `deesse.json` at the project root (per [ADR-031](./ADR-031-deesse-json.mdx)).
2. Fetch `deesse-template.json` from the registry host (per Decision #4).
3. Validate against the `TemplateV2` Zod schema. Reject with `parse_error` on failure.
4. Resolve `templateDependencies` recursively (each dependency is fetched and validated the same way).
5. Run `prompts[]` in declaration order, applying `when` gates against prior answers. Skip with `--yes`; the documented `default` applies.
6. Run `hooks.preInit` (if present).
7. Clone the template repo at `source.ref` (or fall back to `main` / `master`).
8. Apply `files[]` transformations (rename, interpolate against `deesse.json#tokens`, remove, merge).
9. Run `hooks.postInit` (or `postinstall[]` for back-compat).
10. Run the package manager install (`pnpm/npm install`), detected from the lockfile.
11. Run `hooks.postInstall` (if present).
12. Update `deesse.json#templates["<slug>"]` with the installed `version` and `installedAt` timestamp.

Every step is idempotent (re-running the command on an installed project updates the entry but does not re-clone). Steps 6, 9, 11 are gated by the closed-list verb whitelist (see Consequences).

#### 4. The registry host is static-only

`registry.deessejs.dev` is a **static file host**. There is no API runtime, no Hono server, no oRPC endpoint behind it. The host serves two kinds of files over plain HTTPS `GET`:

- **JSON Schemas** — `/schema/project.json` and `/schema/template.json`. Generated from the Zod sources in `@workspace/contracts` (via `zod-to-json-schema` or equivalent) by a CI job in `packages/contracts` that runs on every release of that package. The JSON Schemas are versioned in lockstep with `@workspace/contracts`; a `@workspace/contracts@2.x` release bumps the JSON Schema URL to `/schema/v2/{project,template}.json` and keeps the unversioned URL redirecting to the latest.
- **Registry items** — `/r/<slug>.json`. One file per official template, generated by a CI job in `packages/api` from the `TEMPLATES` array in `packages/api/src/templates.ts`. Each item's JSON content is the merged `TemplateV2` shape (registry data + GitHub enrichment, the same shape the oRPC `templates.list` procedure returns today). The CI job writes the merged JSON to a `public/r/` directory inside `packages/api` and a deployment step publishes that directory to the static host.

Why static-only, three reasons that compound:

1. **No backend to operate.** A static host on Vercel (or any CDN) costs near-zero runtime RAM and never pages on-call. The CI jobs that publish files are short-lived build steps; they don't run between releases.
2. **Cache-friendly everywhere.** A CDN-cached JSON file is faster than a dynamic endpoint, and every CDN on earth knows how to cache `GET`s with `Cache-Control: public, max-age=...`. The CLI's existing ETag revalidation (per ADR-010 §4) keeps working unchanged against a static host — the file just becomes immutable between releases.
3. **No secret material.** The static host serves files that are public by definition (a registry is public data). There is no `GITHUB_TOKEN`, no per-user rate-limit concern, no auth header to manage. The static host's only configuration is the DNS record and the TLS cert.

What stays on `app.deessejs.com` (the existing oRPC host, per ADR-021):

- The `templates.list` oRPC procedure (returns the enriched `TemplateV2` array, the same shape as `/r/<slug>.json` but as a list).
- The `templates.get` procedure (returns one item, the same shape as `/r/<slug>.json`).
- All auth flows, all device-flow endpoints, all session-aware code paths.

The CLI may fetch from either source. The static host (`registry.deessejs.dev`) is the **primary source** for `init <slug>` (one item, immutable between releases). The oRPC endpoint (`app.deessejs.com`) is the **primary source** for `list` and `info` (live, possibly rate-limited, possibly enriched with non-public metadata later). Today both endpoints return the same shape; tomorrow the two sources may diverge if non-public fields land on the oRPC side (e.g. private templates behind auth).

Provisioning requirements (called out here so the implementation PR has a checklist):

- DNS: a CNAME `registry.deessejs.dev` → the static host's edge. One record.
- TLS: a wildcard cert covering `*.deessejs.dev` is not needed — a single-host cert for `registry.deessejs.dev` suffices. Let's Encrypt or Vercel's auto-issued cert, whichever the host provides.
- Vercel project: one new project named `registry-deessejs-dev` (or equivalent on the chosen CDN), root directory `packages/api/public` (where the CI job writes the published artifacts). The project has no `apps/<x>/vercel.json` linking it to sibling projects; it stands alone.
- CI: a new GitHub Actions workflow in `packages/contracts` (publishes JSON Schemas) and `packages/api` (publishes registry items). Both run on a tag push or release event for their respective packages.

This decision pins the role of `registry.deessejs.dev` for V2. A future ADR may revisit (e.g. adding `deessejs.dev/api/v1/items` for dynamic content, or splitting the registry host per-stack), but V2 ships static-only.

### What this rule allows

- A template author co-locates `deesse-template.json` in `deessejs/saas-template` at the repo root. The template repo's CI validates the JSON against the schema published at `https://registry.deessejs.dev/schema/template.json`. The validation step is opt-in for the author; the schema URL is the contract.
- A registry of registries: an org maintains a static JSON catalog at `https://example.com/r/registry.json` (shadcn's auto-discovery shape). The CLI fetches it, lists items, and installs from it. No CLI release required for a new third-party registry to be usable.
- A `template:package` item that overlays files into an existing monorepo's `packages/<name>/` directory. The CLI uses `deesse-template.json#files[].target` (with `@packages/` placeholder resolved via [ADR-031](./ADR-031-deesse-json.mdx)'s `deesse.json#aliases`) to know where to write.
- A `template:app` item that clones the entire repo (today's `init` behaviour) plus applies transforms on top of the clone. `template:app` keeps the existing `git clone` shape; the other six types are the new surface.
- `deessejs info <slug>` reads `deesse-template.json#docs` and renders it. Today's `info` command only prints the GitHub-enriched metadata; the docs field gives it a richer surface.
- A user pins the install at a specific version by adding `--ref v1.4.0` to `deessejs init`. The CLI uses `deesse-template.json#source.ref` instead of the upstream `main` / `master` fallback at `apps/cli/src/utils/git.ts`.
- A user runs `deessejs init` with `--yes` to skip `deesse-template.json#prompts[]`. The CLI applies the documented defaults instead. A prompt gated by `when: "database != 'sqlite'"` is skipped automatically when the prior `database` answer is `sqlite`; `--yes` short-circuits the gate and applies the default.
- A template author ships `deesse-template.json` from a third-party registry. The CLI parses it through the Zod schema exported from `@workspace/contracts` (`TemplateV2` + the embedded `Prompt` and `Hook` sub-schemas) and rejects a malformed payload with `parse_error`. The Zod schema is the canonical contract; the JSON Schema at `https://registry.deessejs.dev/schema/template.json` is its external description for editor tooling. The two stay in lockstep — a CI job regenerates the JSON Schema from the Zod source on every release of `@workspace/contracts`.

### What this rule forbids

- A template author publishing `deesse-template.json` outside the template repo (e.g. in a separate `deessejs/registry-data` repo). The co-location rule keeps the file's lifecycle tied to the template's lifecycle.
- `deesse-template.json` with a `postinstall` verb outside the whitelist. The CLI rejects unrecognised verbs at parse time. The whitelist is part of this ADR and lives in `apps/cli/src/commands/init.ts` as a closed-list constant.
- `deesse-template.json` `dependencies` that pin a non-npm registry (e.g. a private Git URL) without a `registries{}` entry in the user's `deesse.json` (per [ADR-031](./ADR-031-deesse-json.mdx)). The CLI refuses to install a private dependency that the user has not declared.
- Skipping `deessejs/templates-content-not-cli`. A new entry in `packages/api/src/templates.ts` still does not trigger a CLI changeset. The memory file's rule stays load-bearing.

### Why not the alternatives

Three patterns the team considered and rejected.

1. **One file `registry.json` colocated in `packages/api/src/`.** Mirrors what shadcn does in their monorepo. Rejected because the user explicitly framed the registry as a global, multi-stack surface (per `project-templates-roadmap`); centralising the registry data in one repo forces a CLI release every time a new template ships. The co-located `deesse-template.json` per repo keeps the registry content-driven.

2. **Build pipeline (`deessejs build`) generating `deesse-template.json` from TS source.** Mirrors `shadcn build` from sources like `registry/new-york/button.tsx`. Rejected for V2 because the build command would be a new public CLI command (breaking per ADR-010 §1) and the source files (`deesse-template.json` is data, not code) would be the schema itself. The V3 follow-up may revisit this once a real use case surfaces (e.g. multi-style templates where one repo ships several variants).

3. **`manifest.json` (the historic design from `documents/internal/architecture/12-apps/cli/template-conventions.md`).** The historical proposal describes a richer manifest with tokens, removal lists, demos, etc. Rejected as the V2 shape because the historical doc is design history, not shipped code (per the divergence plan at `docs/engineering/plans/saas-template-divergence.md`); the `deesse-template.json` in this ADR supersedes it. The historical file's content is preserved in the git history of `documents/internal/architecture/12-apps/cli/template-conventions.md` for reference.

### What this rule does not change

- The CLI's three commands (`init`, `list`, `info`) and the `auth` group stay the public surface per ADR-010 §1. This ADR adds no new public command.
- The CLI's typed oRPC client at `apps/cli/src/api/client.ts` stays the only outbound transport per ADR-001. `deesse-template.json` is fetched through the same client (`templates.list` returns it as part of the enrichment layer).
- The cache directory (`~/.deessejs/`) and the cache file shape stay as documented by ADR-010 §4. `deesse-template.json` responses share the cache; the cache format is opaque (per ADR-010 §4).
- The closed-list `CliErrorCode` per ADR-010 §2 stays closed. New install failures (post-install script fail, transform fail) map to `install_failed` (already on the internal list) or to `parse_error` for malformed `deesse-template.json`.
- The `engines.node >= 20.0.0` floor at `apps/cli/package.json` stays. The CLI continues to publish as `@deessejs/cli` per ADR-010 §6.
- The wire contract `@workspace/contracts` stays the canonical place for shared types. `TemplateV2` is added to `packages/contracts/src/v1/template.ts` next to `TemplateV1`. No contract moves outside the package.
- The `apps/cli/src/commands/init.ts` flags (`--pm`, `--dir`, `--ref`, `--no-install`, `--force`, `--json`) stay as the per-command flags per ADR-010 §1. `--ref` becomes load-bearing (it now overrides `deesse-template.json#source.ref`); the other flags keep their current meaning.
- The `--offline` global flag (per ADR-010 §1) keeps its "fall back to cache when the network is unreachable" semantics. Offline mode skips the `deesse-template.json` fetch if the cache hit is fresh; an item with a newer `source.ref` than the cached version refuses to install offline (logged at `cli_outdated`, not `install_failed`).

## Consequences

- **`packages/contracts` grows `TemplateV2`.** The new Zod schema lives in `packages/contracts/src/v1/template.ts` alongside `TemplateV1`. A barrel re-exports both. Server consumers that read `TemplateV1` continue to work; consumers that opt in read `TemplateV2`. The change is non-breaking for the wire because the server publishes both response shapes.
- **`packages/api/src/templates.ts` gains typed entries.** Each entry in the `TEMPLATES` array picks up the new `TemplateV2` fields (`version`, `source.ref`, `requires`, `dependencies`, etc.). The enrichment layer at `packages/api/src/core/templates/enrich.ts` extends to merge `deesse-template.json` data when the upstream returns one (a future `deesse-template.json` is co-located in `deessejs/<slug>`; the enrichment fetches it via the GitHub raw URL pattern, parallel to the existing `fetchRepo` + `fetchReadme` calls).
- **`apps/cli` learns to apply `files[]` transformations.** The init flow gains a transform step that walks `deesse-template.json#files[]`, substitutes `@components/`, `@lib/`, `@hooks/`, `@ui/`, `@apps/`, `@packages/` against `deesse.json#aliases` (per [ADR-031](./ADR-031-deesse-json.mdx)), and applies the `transform` verb (`rename`, `interpolate`, `remove`, `merge`). The verbs live in `apps/cli/src/transforms/` (new folder) — one file per verb, following the one-folder-per-concept rule from ADR-002 and the command-file invariant from ADR-010.
- **`packages/ui/src/deploy-button.tsx` and `packages/ui/src/demo-button.tsx` may consume `deesse-template.json#docs`.** Out of scope for this ADR; a follow-up can wire the gallery to surface docs. The `apps/web/src/app/(product)/templates/[template_slug]/page.tsx` page renders the existing enriched metadata; the docs field is an additive read.
- **The `postinstall` whitelist lives in `apps/cli/src/commands/init.ts` as a closed-list constant.** Initial whitelist: `["pnpm install", "pnpm add", "pnpm remove", "pnpm db:push", "pnpm db:migrate", "pnpm format", "pnpm typecheck", "npm install", "yarn install", "bun install", "git init"]`. Adding a verb is an internal change (not a new public error code, not a new flag).
- **A template author adds `deesse-template.json` to their repo's root, with the `$schema` URL pointing at `https://registry.deessejs.dev/schema/template.json`.** The schema is published from the registry host (a static file at `/schema/template.json`); the same pattern works for `deesse.json` at `/schema/project.json` (per [ADR-031](./ADR-031-deesse-json.mdx)). The schema URL is the contract.
- **A template repo's CI runs `ajv validate --spec https://registry.deessejs.dev/schema/template.json --strict < deesse-template.json`.** This is opt-in (the CLI does not require it), but recommended. The CLI's own internal validator at `apps/cli/src/commands/init.ts` uses the same schema via Zod's `parseAsync`, returning `parse_error` on failure. The Zod schema lives in `@workspace/contracts` and is exported as `TemplateV2`; the JSON Schema is generated from it (a CI job in `packages/contracts` regenerates the JSON Schema on every release).
- **`packages/contracts` gains a CI job that publishes JSON Schemas.** Triggered on every release of `@workspace/contracts`. The job runs `zod-to-json-schema` (or equivalent) over the `TemplateV2` and the embedded `Project` (the `deesse.json` root type per [ADR-031](./ADR-031-deesse-json.mdx)) Zod schemas, writes the result to `packages/contracts/dist/schema/{project,template}.json`, and deploys those two files to the static host at `/schema/{project,template}.json`. The job is non-breaking at the contract level (it produces files, it doesn't change types).
- **`packages/api` gains a CI job that publishes registry items.** Triggered on every release of `@workspace/contracts` (when the Zod shape changes) or every push that touches `packages/api/src/templates.ts` (when a new template lands). The job runs the existing enrichment pipeline (`packages/api/src/core/templates/enrich.ts`), serialises each enriched entry to JSON, writes them to `packages/api/public/r/<slug>.json`, and deploys the `public/r/` directory to the static host. The job is the implementation of the `templates-content-not-cli` invariant on the publication side: a new template entry never triggers a CLI release, only a registry publication.
- **`registry.deessejs.dev` is provisioned as a static-only Vercel project.** One new Vercel project (`registry-deessejs-dev` or equivalent), one CNAME record, one TLS cert (auto-issued by Vercel or Let's Encrypt). The project has no runtime, no environment variables beyond the deploy token, and no `apps/<x>/vercel.json` linking it to sibling projects. The implementation PR carries a runbook page at `documents/internal/runbooks/registry-deessejs-dev.md` documenting the provisioning checklist.
- **The `templates-content-not-cli` rule stays load-bearing.** A new entry in `packages/api/src/templates.ts` (the array that today has one entry, `saas-starter`) never triggers a CLI changeset. Only `Template` schema-level changes do. The new `packages/api` publication CI job is the operational implementation of the rule on the registry side.
- **The cache directory gains a sibling file.** `~/.deessejs/template-items/<slug>.json` caches the per-item response (today the cache is `templates.json` only). The cache shape change is internal per ADR-010 §4 (the cache file format is not part of the public surface); stale entries are discarded via the existing ETag-driven revalidation. The disk path stays under `~/.deessejs/` per ADR-010 §4's locked invariant; `template-items/` is a new sub-folder inside it.

## Open questions

Three design calls surfaced during review and remain open in this version of the ADR.

### Question 1: ship `deessejs add @namespace/slug` as a V2 feature?

shadcn's `add` is the headline command. DeesseJS's `init` is the headline today. Adding `add` requires either (a) bumping the CLI surface (breaking per ADR-010 §1) or (b) implementing `add` as an alias for `init <slug>` that reads `deesse.json#registries` (per [ADR-031](./ADR-031-deesse-json.mdx)) to resolve the namespace. Option (b) is non-breaking but blurs the meaning of `init` (today: clone a project; tomorrow: also overlay files). The team's preference: defer `add` to V3; keep `init` as the single install verb in V2. The strongest motivation for `add` in V3 is the `deesse.json#database` + `deesse.json#paths` blocks added by [ADR-031](./ADR-031-deesse-json.mdx): a user who wants to layer `crud` or `auth` onto an existing project needs a command that reads those blocks and writes into the right directories without re-running the full clone.

### Question 2: pin the `postinstall` whitelist at this size, or smaller?

The proposed whitelist is eleven verbs. shadcn's analogue is implicit (any `pnpm`/`npm` script). The team needs to decide whether the whitelist's verbosity is a feature (clear contract) or a liability (template authors hit the wall when they need `pnpm prisma generate`). The default this ADR proposes is the eleven-verb list; a smaller V1 whitelist (five verbs) is acceptable if reviewers prefer.

### Question 3: namespaces in V2 or V3?

The `deesse.json#registries` map is in [ADR-031](./ADR-031-deesse-json.mdx). Whether the CLI ships the auto-discovery behaviour (a public repo with a `registry.json` at its root is automatically a registry) in V2 or V3 is open. V2 ships the explicit `registries{}` map; V3 may add the auto-discovery. The decision is independent of the rest of this ADR.
