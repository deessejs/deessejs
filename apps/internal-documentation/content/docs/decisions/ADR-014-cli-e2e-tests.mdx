# ADR-014: CLI e2e tests

## Status

Accepted (2026-08). Non-negotiable.

## Context

`@deessejs/cli` is the only surface of the monorepo that users actually run. The unit tests (`apps/cli/test/contract/`, `apps/cli/test/unit/`) cover the internal logic: error mapping, output formatting, and a small set of git helpers. They do not cover the published artifact as a whole.

The verify workflow (ADR-013) catches publish-path regressions: `npx @deessejs/cli@latest --help` runs against the just-packed tarball. It catches broken installs and missing runtimes. It does not catch commands that run but return the wrong thing.

Three failure modes the unit tests and the verify job do not catch:

1. A command that returns the wrong templates. The mock-free path is `pnpm dev` + a hand-edited server. Beyond manual smoke testing, nothing.
2. A command that crashes on a specific input shape. `cli info <unknown-slug>` should print a `not_found` CliError, not a stack trace. The unit tests cover the mapping; they do not cover what happens when the oRPC procedure returns a typed error.
3. `cli init` cloning the wrong repository. The unit tests mock `cloneRepo`; the real `git clone` path is untested.

For the published `@deessejs/cli@2.0.1`, the verify job caught a broken install. It would not have caught a CLI that installs cleanly but returns garbage.

Three approaches were considered for the e2e suite. Each was rejected in turn before the current decision was reached.

#### Approach 1: a mock server in the test process (rejected)

The first attempt at this ADR designed a mock HTTP server that re-implemented the API contract. The implementation shipped as a draft PR (branch `chore/cli-e2e-spike`). The attempt failed: the mock's ORPC envelope was a best-guess at the real one, and the test could not be exercised end-to-end. A mock server is a second source of truth that has to stay in sync with the real API. When the API evolves, the mock drifts. When the test fails, it is not clear whether the failure is the CLI or the mock. A mock server is the right tool when the real API is unstable, slow, or has meaningful side effects. None of those apply to the DeesseJS API: it is stable, the read path is fast, and the templates endpoint has no side effects.

#### Approach 2: test against the production API (rejected)

The second attempt pivoted to running the suite against `https://deessejs.com`. The pivot was wrong on two counts.

First, the suite does not test the code of the PR being reviewed. It tests the code that is currently in production. A bug introduced by the PR is invisible to the test until the PR merges and a new release ships the CLI that depends on it. The whole point of running tests on a PR is to catch regressions before they reach users.

Second, the suite depends on the production API being available. If the production API is down, the suite fails. This is the correct failure mode for a synthetic-monitor workflow that runs against production. It is the wrong failure mode for a PR gate that should be hermetic.

#### Approach 3: build the server and the CLI from the same PR, run both in CI (this ADR)

The pattern is well established. Hookdeck, Trigger.dev, Mastra, and others run a CI job that builds the server in the same runner as the SDK or CLI under test. The runner starts the server on `localhost`, waits for a health check, then runs the e2e suite against `http://localhost:<port>`. Both processes run the same PR's code. The test surface is hermetic, fast, and faithful to the code being reviewed.

For DeesseJS, this means:

- The CI runner builds `packages/api` (the server) from the PR's source.
- The CI runner builds `@deessejs/cli` (the CLI) and packs the tarball.
- The runner starts the server on `localhost:<port>` in the background.
- The runner waits for `GET /healthz` to respond (or equivalent).
- The runner spawns the CLI tarball with `API_BASE_URL=http://localhost:<port>`.
- The runner asserts on the CLI's stdout, stderr, and exit code.

The CLI is exercised against the server it is designed to talk to. The server is exercised against the code the PR changes. The test surface is hermetic. No external service is required.

## Decision

The e2e suite lives in `apps/cli/test/e2e/`. It is one file per command (`list.test.ts`, `info.test.ts`, `init.test.ts`), plus a helpers folder for the CLI runner and the git fixture. There is no HTTP mock server in the suite.

The suite runs in CI on every PR touching `apps/cli/**` and in a deeper nightly run. The CI workflow starts a local server from the same PR, waits for the health check, then runs the e2e suite against the local server. The server is killed at the end of the job.

### One prerequisite: `API_BASE_URL` env var

The CLI hardcodes `API_RPC_PATH` and `API_BASE_PATH` as path constants and lets `globalThis.fetch` resolve them as relative URLs. A reproduction confirms that `fetch("/api/v1/rpc")` in Node fails with `TypeError: fetch failed` — there is no `window.location.origin` to resolve against in non-browser environments. The CLI cannot be pointed at a different server today.

This is what makes the e2e suite possible. Before any e2e test can run, the CLI must accept an `API_BASE_URL` environment variable that prefixes the path constants. The override is read at startup, fails loudly if the env var is malformed, and falls back to a production default when unset (so existing consumers are not affected).

#### What the modification is

The behavior change is small but not trivial. It has three parts.

**1. A new module exposes the resolved URL.** Today, `apps/cli/src/api/client.ts` and `apps/cli/src/version/check.ts` import `API_RPC_PATH` and `API_BASE_PATH` directly from `@workspace/api/base-path`. A new module — for example `apps/cli/src/api/runtime.ts` — exposes `getApiRpcUrl()` and `getApiVersionUrl()` instead. The functions read `API_BASE_URL` from the environment at call time and return a fully resolved URL. The CLI calls these functions where it currently uses the path constants.

**2. The fallback uses a production default.** When `API_BASE_URL` is unset, the resolver returns the production URL. The exact value is decided at implementation time; a reasonable candidate is `https://deessejs.com` (the marketing site, which also serves the API). This preserves current behavior for users who do not set the env var. Users who run the CLI against a self-hosted registry get to override the URL without rebuilding.

**3. Malformed values fail loudly.** If `API_BASE_URL` is set but not a valid URL (e.g., empty, missing scheme, trailing whitespace), the CLI exits with a non-zero code and a clear error message before making any request. The validation is cheap and prevents confusing failures deep in the network stack.

#### Naming

The current `@workspace/api/base-path` module exports two constants: `API_BASE_PATH` (the path prefix, e.g. `/api/v1`) and `API_RPC_PATH` (the RPC endpoint, e.g. `/api/v1/rpc`). Adding an `API_BASE_URL` env var to the CLI creates a naming collision with the existing `API_BASE_PATH` constant. The implementation will rename one of the two. The implementation PR resolves the naming before this ADR is implemented.

#### Files impacted

Three files in this repo:

- `apps/cli/src/api/client.ts` — replace `RPCLink({ url: API_RPC_PATH })` with a function call.
- `apps/cli/src/version/check.ts` — replace the template-literal URL with a function call.
- A new file under `apps/cli/src/api/` — the resolver module. The location and the exact name are decided at implementation time.

The change does not touch the `@workspace/api` package. The path constants stay where they are; the CLI gains a runtime resolver that lives in the CLI itself.

#### Behavior in each environment

| Environment | `API_BASE_URL` | Behavior |
|---|---|---|
| Production user (no env var) | unset | Resolver returns the production default. Same as today, modulo the runtime resolution. |
| Production user (sets env var) | `https://self-hosted.example.com` | Resolver returns the override. The CLI talks to the self-hosted registry. |
| Local dev (`pnpm dev`) | unset | Same as production user. The CLI talks to the production registry. |
| Local dev (overrides) | `http://localhost:4873` | Resolver returns the override. The CLI talks to a local mock. |
| E2E test | `http://localhost:<random-port>` | Resolver returns the override. The CLI talks to the in-process mock server. |
| E2E test (unset, broken) | unset | Resolver returns the production default. The CLI talks to the real API. The test fails with a clear network error. The test runner is responsible for setting the env var. |

This is the four-line change in concrete terms: one env var read, one validation, one fallback constant, one resolver function. The rest of the CLI calls the resolver instead of the hardcoded constants. The change is local to two CLI files and one new file. It does not change the public surface of the CLI.

### Code surface

The implementation lands the following additions. None of this is code yet — it is the public shape the implementation PR will produce.

#### New module: `apps/cli/src/api/runtime.ts`

Three exports. The module is the only place in the CLI that reads `process.env.API_BASE_URL`.

| Export | Type | Purpose |
|---|---|---|
| `getApiBaseUrl` | `() => string` | Returns the resolved base URL. Reads `API_BASE_URL` from the env, validates it, returns the production default if unset. Memoized after the first call. |
| `getApiRpcUrl` | `() => string` | Returns `${getApiBaseUrl()}/api/v1/rpc`. |
| `getApiVersionUrl` | `() => string` | Returns `${getApiBaseUrl()}/api/v1/version`. |

The memoization matters. The CLI calls `getApiRpcUrl` once at startup (in `client.ts`) and `getApiVersionUrl` once at startup (in `version/check.ts`). If the env var were read at every call, a test that wraps spawn in a way that mutates the env would have surprising behavior. The memoization makes the resolution deterministic.

#### Validation

The validation rules are tight enough to catch obvious mistakes but lenient enough to accept any well-formed URL. The format is `https://example.com` or `http://localhost:4873`. Empty strings, missing scheme, whitespace, and `null` are rejected. The CLI throws a `CliError` with code `internal_error` and a message that includes the offending value. The failure happens before any network call so it does not mask deeper issues.

The regex is small. It rejects anything that does not match `^https?://[^/\s]+(:\d+)?(/.*)?$`. URLs with credentials, query strings, and fragments are accepted; we do not need that surface area yet.

#### Call sites

Two call sites change. Both are local replacements of a constant with a function call.

`apps/cli/src/api/client.ts`:
```diff
- import { API_RPC_PATH } from "@workspace/api/base-path"
+ import { getApiRpcUrl } from "./runtime.js"
  ...
  const link = new RPCLink({
-   url: API_RPC_PATH,
+   url: getApiRpcUrl(),
    plugins: [...]
  })
```

`apps/cli/src/version/check.ts`:
```diff
- import { API_BASE_PATH } from "@workspace/api/base-path"
+ import { getApiVersionUrl } from "./runtime.js"
  ...
- const versionUrl = `${API_BASE_PATH}/version`
+ const versionUrl = getApiVersionUrl()
```

The `@workspace/api/base-path` imports stay in `@workspace/api`. The CLI still gets the path constants for places that need them (e.g., the Readme mentions the API path; the cli-self-version test exists; the version probe shape). Only the runtime URL resolution moves to the CLI.

#### Unit tests

The new module is small enough to test in isolation. The implementation PR adds a `runtime.test.ts` next to the module. The tests cover the five cases:

1. `API_BASE_URL` unset → returns the production default.
2. `API_BASE_URL` set to a valid URL → returns the URL.
3. `API_BASE_URL` set to an empty string → throws `CliError`.
4. `API_BASE_URL` set to a malformed value (no scheme, whitespace) → throws `CliError`.
5. `getApiRpcUrl` and `getApiVersionUrl` join paths correctly with the resolved base.

The tests do not spawn the CLI. They call the resolver functions directly. The integration with the CLI is verified by the e2e suite that this ADR mandates.

#### Changeset

The implementation ships with a patch changeset for `@deessejs/cli`. The body documents the new env var override, the fallback, and the validation. It does not document the e2e suite — that lands in a follow-up PR.

#### What does NOT change

Three things this ADR leaves out of scope:

- The `@workspace/api` package. The path constants stay. The CLI gains a runtime resolver; the API package does not gain a runtime counterpart.
- The constants `API_BASE_PATH` and `API_RPC_PATH` are still exported from `@workspace/api/base-path`. Web, app, and tests use them. The CLI gains a runtime resolver; the other consumers keep the constants.
- The error code for malformed `API_BASE_URL`. The current proposal is `internal_error`. The choice is decided at implementation time. `invalid_env` is a candidate if the team prefers a more specific code.

### The tests

Three commands, three suites. Each suite covers the happy path plus at least one error path. The suites live in `apps/cli/test/e2e/` as `list.test.ts`, `info.test.ts`, `init.test.ts`. Each suite is a `describe` block with at least one `it` per scenario.

The tests target a **local server** built from the same PR's source. The CI workflow starts the server on `localhost:<port>` before running the e2e job. The CLI's runtime module resolves `API_BASE_URL` to that local server when the env var is unset. The tests do not need to pass `API_BASE_URL` explicitly.

The convention is that every test follows the same shape: bootstrap the local server, run the CLI, assert on stdout, stderr, and exit code. The convention is enforced by the `run()` helper, which returns `{ stdout, stderr, exitCode, durationMs }` and exposes a `expect*` API for the common assertions.

#### `list` suite

Two tests. The CLI runs against the local server.

| Test | Assert on stdout | Assert on stderr | Assert on exit |
|---|---|---|---|
| `list happy path` | stdout contains the seeded template slug (`e2e-template`) and its name | empty | 0 |
| `list network error` | empty | stderr contains `network_error` code | 1 |

The happy-path test seeds the local server with a known template before invoking the CLI. The seed is an HTTP POST to the server's internal test endpoint. The server's normal `list` endpoint reads from the registry; the test endpoint writes a fixture. This is a single internal endpoint, not a parallel mock.

The network-error test stops the local server before invoking the CLI. The CLI is expected to fail fast with a `network_error` code. This is the only test in the suite that does not exercise the server.

The happy-path test asserts only on the presence of a known slug, not on the full shape. The unit tests in `apps/cli/test/unit/output.test.ts` already pin the column format. The e2e test confirms the wired-up commands work end-to-end against the local server.

#### `info` suite

Three tests. The CLI runs against the local server.

| Test | Setup | Assert on stdout | Assert on stderr | Assert on exit |
|---|---|---|---|---|
| `info happy path` | seed a template, then `info <slug>` | stdout contains the slug, name, description | empty | 0 |
| `info not found` | `info does-not-exist` (server returns 404) | empty | stderr contains `not_found` code | 1 |
| `info network error` | stop server, then `info <slug>` | empty | stderr contains `network_error` code | 1 |

The not-found test runs against the local server with a deliberately unknown slug. The server returns a 404 with the standard `not_found` code. The test confirms that the CLI's error mapping reads the server's 404 and surfaces the right CliError code. This is the most realistic test of the not-found path because it exercises the real server's 404 response, not a synthetic fixture.

The malformed-data test from the previous version of this ADR is removed. The unit tests in `apps/cli/test/contract/orpc-to-cli-error.test.ts` already pin that `parse_error` is the right code when the runtime parser is given bad data. The e2e suite does not duplicate that coverage. A regression in the malformed path is caught at the unit level, not the e2e level.

#### `init` suite

Three tests. The git fixture is the only mock in this suite. The CLI runs against the local server for the happy path. The local server's `list` endpoint returns a template whose `cloneUrl` points at the local bare repo.

| Test | CLI args | Assert on filesystem | Assert on stderr | Assert on exit |
|---|---|---|---|---|
| `init happy path` | `init e2e-template --no-install --dir <tmpdir>/dest` | `<tmpdir>/dest/<expected-file>` exists and matches the fixture's commit | empty | 0 |
| `init clone refused (existing dir)` | `init e2e-template --no-install` (target dir already exists) | nothing created | stderr contains `target_exists` code | 1 |
| `init network error` | stop server, then `init e2e-template --no-install` | nothing created | stderr contains `network_error` code | 1 |

The `--no-install` flag is the only path that skips the package-manager step. The unit tests in `apps/cli/test/unit/git.test.ts` already cover the spawn helper, so the e2e suite does not duplicate that. The `--no-install` path is the only one that completes in CI without a network round-trip to a package manager.

The happy-path test seeds the local server with a template whose `cloneUrl` is a `file://` URL pointing at the local bare repo. The seed is an HTTP POST to the server's internal test endpoint, identical to the seed used in the `list` suite.

The existing-dir test asserts that the CLI refuses to overwrite without `--force`. The current behavior is correct; the test pins it so a future regression is caught.

The network-error test pins that the CLI fails fast on the first request, before invoking `git clone`. A regression where the CLI clones first and reports the network error after would be caught here.

### The CLI runner

A `cli-runner.ts` helper in `apps/cli/test/e2e/helpers/`. The implementation is ~50 lines.

#### API

```ts
type RunOptions = {
  args: string[]
  env?: Record<string, string>
  timeoutMs?: number  // default 30_000
}

type RunResult = {
  stdout: string
  stderr: string
  exitCode: number
  durationMs: number
}

function run(options: RunOptions): Promise<RunResult>
```

Tests use it like:

```ts
const result = await run({
  args: ["list"],
  // env left unset — runner uses the default DEESSEJS_API_URL
})
expect(result.exitCode).toBe(0)
expect(result.stdout).toContain("saas-starter")
```

The runner returns a structured result rather than throwing on non-zero exit codes. The test asserts on the exit code rather than catching a thrown error. This makes the failure messages explicit: the test can print `result.stdout` and `result.stderr` in the assertion failure.

#### Tarball resolution

The runner reads the tarball path from the env var `DEESSEJS_CLI_TARBALL`. The verify workflow sets this env var before invoking the tests. If the env var is unset, the runner fails the test with a clear error message: `DEESSEJS_CLI_TARBALL is not set; the e2e suite requires the verify workflow to run first.` The runner does not invoke the source TypeScript directly; the e2e suite tests the published artifact, not the source.

The verify workflow produces the tarball at `apps/cli/dist/deessejs-cli-*.tgz`. The runner uses `glob` to find the file. If multiple tarballs exist (e.g., from a previous run that did not clean up), the runner uses the most recent one by `mtime`.

#### Stream handling

The runner captures stdout and stderr separately. This is what makes the test assertions on `Code:` lines in stderr work. The runner does not pipe them through a TTY; the CLI is invoked with a non-interactive stdin.

#### Cleanup

The runner kills the child process on timeout or on parent test failure. The cleanup uses `SIGTERM` first, then `SIGKILL` after a 5-second grace period. The runner does not leak child processes when a test fails.

### The git fixture

A `git-fixture.ts` helper in `apps/cli/test/e2e/helpers/`. The implementation is ~40 lines.

#### API

```ts
type GitFixture = {
  barePath: string       // absolute path to the bare repo
  fileUrl: string         // file:// URL for the bare repo
  content: { path: string, content: string }  // the single file in the main branch
}

function createBareRepo(tmpdir: string): Promise<GitFixture>
function cleanup(fixture: GitFixture): Promise<void>
```

Tests use it like:

```ts
const tmpdir = await fs.mkdtemp(path.join(os.tmpdir(), "cli-e2e-"))
const fixture = await createBareRepo(tmpdir)
try {
  // ... test
} finally {
  await cleanup(fixture)
}
```

The `try/finally` is the test's responsibility. The fixture does not auto-cleanup because the test might want to inspect the repo after failure.

#### What the fixture creates

A bare git repo at `<tmpdir>/repo.git`. The repo has a `main` branch with a single commit. The commit contains one file, `README.md`, with a fixed content. The `main` branch is the default branch because the CLI clones with `git clone --branch main` (the default).

The fixture does not create a working tree. The CLI clones the bare repo at clone time, so the working tree is the test's actual assertion target.

#### Cleanup

The cleanup removes the entire `tmpdir`. The cleanup runs on test failure too. The fixture does not leave orphan repos behind.

#### Why this is the only deliberate mock

The GitHub repo is the only externally-facing surface in the `init` flow that we cannot exercise against the production environment. Two reasons:

1. **Speed.** A `git clone` of the production `deessejs/saas-template` repo takes seconds and depends on GitHub availability. A local bare repo is milliseconds.
2. **Write isolation.** Cloning the production repo does not require writes, but the broader `init` flow (which includes a `pnpm install` step) would. The fixture stops the test at the clone step.

The fixture is a true local mock for a network-bound dependency. It is not a reimplementation of the API contract. The CLI does not know it is talking to a bare repo instead of a GitHub repo — `git clone file://<...>` is a real git transport.

### CI integration

Two workflows. The implementation is in `.github/workflows/`, named `cli-e2e.yml` and `cli-e2e-extended.yml`.

#### `cli-e2e.yml` (PR blocking)

The PR workflow is the gating one. It runs on every PR that touches `apps/cli/**`. It runs the three suites against a local server built from the same PR's source. Failures block merge.

The workflow has three jobs:

1. **`build-and-start-server`**: builds `packages/api` from the PR's source, starts the server on `localhost:<port>` in the background, waits for `GET /healthz` to respond, sets `E2E_SEED_ENABLED=1`. The server stays up for the duration of the e2e job.
2. **`pack-and-e2e`**: depends on the first job. Builds `@deessejs/cli` and packs the tarball. Sets `API_BASE_URL` to the local server's URL and `DEESSEJS_CLI_TARBALL` to the tarball path. Runs `pnpm --filter @deessejs/cli test:e2e`. The e2e suite talks to the local server.
3. **`teardown`**: depends on the second job. Kills the local server. The teardown is `if: always()` so a failure in the e2e job still cleans up.

The workflow uses `ubuntu-latest` and `node-version: 24` (matching the verify workflow). The total runtime is under 3 minutes for the PR suite: ~1m for the server build, ~30s for the CLI build, ~1m for the e2e suite.

The workflow has `permissions: contents: read` for the e2e job. No `id-token`, no `NPM_TOKEN`. The publish path is unchanged from the verify workflow.

#### `cli-e2e-extended.yml` (nightly non-blocking)

The nightly workflow is the deep one. It runs on a schedule (cron: `0 3 * * *`) and on manual dispatch. It runs an extended matrix that the PR workflow skips.

The matrix dimension is "scenario". Each scenario tests a different aspect of the CLI that is too slow or too flaky for PR gating:

| Scenario | What it covers | Why nightly-only |
|---|---|---|
| `large-registry` | Local server with 100 templates; CLI lists them. | Tests retry logic under load. Takes ~10s. |
| `slow-network` | Local server with a 2s delay on every response. | Tests timeouts. Too slow for PR. |
| `flaky-network` | Local server that returns 500 on the first request, 200 on the second. | Tests retry logic. Flaky in normal CI. |
| `real-pm` | Skips `--no-install` and runs the actual package manager against the cloned repo. | Slow; depends on pnpm in CI. |
| `unicode` | Local server with templates with unicode names. | Sanity check; not part of the PR contract. |

The slow-network and flaky-network scenarios wrap the local server with a small proxy that adds the delay or flakiness. The proxy is a few lines and is the only mock in this workflow. It exists because the slow/flaky behavior is not something we can engineer against the local server directly.

Failures in the nightly workflow post a GitHub issue with the captured output. The issue template is pre-populated with the workflow run URL, the scenario that failed, and the stdout/stderr of the failing test. The post is done via `peter-evans/create-or-update-comment` or a custom action; the choice is decided at implementation time.

#### Why two workflows

The split is cost. The PR workflow is the gate; it must run on every PR and stay fast. The nightly workflow is the deep check; it can run slowly and tolerate flakiness. Combining them would either slow PRs (extended matrix on every PR) or weaken the gate (PR workflow skips important tests). The split is the standard pattern for CI matrices that have a fast-slow split.

### Why the local server instead of a mock or the production API

Three patterns were considered. The first two are rejected; the third is the decision.

#### Mock server (rejected)

A mock server that re-implements the API contract has three failure modes:

1. **Drift.** The mock changes slower than the real API. A test that passes against the mock can fail against production. The mock is a contract to maintain, separately from the API it stands in for.
2. **Wrong contract.** The mock's contract is a best-guess at the real one. If the guess is wrong, the test fails for reasons that have nothing to do with the CLI. The first attempt at this suite (the spike on branch `chore/cli-e2e-spike`) failed for exactly this reason: the mock's ORPC envelope was a guess, and the test could not be exercised end-to-end.
3. **Double infrastructure.** The real server is one system to maintain. The mock is a second. Two systems that have to stay in sync is more maintenance than one.

The mock server pattern is right when the real API is unstable, slow, or has meaningful side effects. None of those apply here: the DeesseJS server is stable, the read path is fast, and the templates endpoint has no side effects.

#### Production API (rejected)

Running the suite against `https://deessejs.com` was the second attempt. The pivot was wrong on two counts.

First, the suite does not test the code of the PR being reviewed. It tests the code that is currently in production. A bug introduced by the PR is invisible to the test until the PR merges and a new release ships the CLI that depends on it. The whole point of running tests on a PR is to catch regressions before they reach users.

Second, the suite depends on the production API being available. If the production API is down, the suite fails. This is the correct failure mode for a synthetic-monitor workflow that runs against production. It is the wrong failure mode for a PR gate that should be hermetic.

#### Local server in CI (chosen)

This is the pattern used by Hookdeck, Trigger.dev, Mastra, and others. The runner builds the server from the same PR's source, starts it on `localhost`, and runs the e2e suite against it. Both the CLI under test and the server it talks to run the PR's code. The test surface is hermetic, fast, and faithful to the code being reviewed.

The implications for maintenance:

- **No mock code to update** when the API contract changes. The CLI is exercised against the real server. A breaking change in the API will surface as a CLI test failure, which is the desired signal.
- **No double infrastructure.** The server is the one being changed by the PR; the test runs it directly.
- **Real-world data.** The server runs the same code the PR is changing. Tests catch the bugs the PR introduces.
- **Latency.** The server is on `localhost`. No network round-trip. The full PR suite runs in under 3 minutes.
- **Hermetic.** The suite does not depend on any external service. It runs on a fork PR and on a private network. The only requirement is that the CI runner has `node` and `pnpm`.

The trade-off is that the suite must run the server, which means the server has to be buildable. The server already builds on the verify workflow's `Build` job, so the additional build cost is one job's worth.

### Cost

One developer-day for the local server fixture and the seed endpoint on the server. One developer-day for the three test suites. One developer-day for the CI workflows. The prerequisites (`API_BASE_URL` override, runtime module, runner) are already done.

The cost is bounded and the value compounds: every future change to the CLI is automatically tested against the server the PR is changing.

## Consequences

- Every PR that touches `apps/cli/**` runs the e2e suite against a local server built from the same PR's source. Bugs of the form "the CLI runs but returns the wrong thing" are caught at PR time, not at release time.
- A nightly run exercises a wider matrix. Bugs that are too slow or too flaky for PR gating surface in a GitHub issue, not as a CI failure.
- The CLI gains an `API_BASE_URL` env var override. This is a small ergonomic improvement for users who run the CLI against a self-hosted registry, and it is the prerequisite that makes the e2e suite possible.
- The verify job (ADR-013) and the e2e suite are complementary. The verify job catches broken publishes; the e2e suite catches broken behavior. A release is green only when both pass.
- The e2e suite is hermetic. It does not depend on any external service. It runs on fork PRs and on private networks.
- `pkg.pr.new` is a future option. It would let reviewers run the actual CLI from a PR preview URL. It is out of scope here; ADR-013 explains why.
- The earlier spike on branch `chore/cli-e2e-spike` retained a mock server design that this ADR supersedes. The spike's PR is a draft and will be closed once the local-server implementation lands.
