# ADR-020: Device authorization for the CLI auth surface

## Status

Accepted (2026-08). Non-negotiable.

## Context

`apps/cli/` is the only published package in the monorepo
(`@deessejs/cli`, per ADR-010). Today its public surface is
three commands (`init`, `list`, `info`) that talk to the
upstream server exclusively through the typed oRPC client and
never carry an identity. The server's public routes
(`/api/v1/rpc/*`, `/api/v1/auth/*`) are reachable anonymously
for everything the CLI does today: listing templates, fetching
template metadata, cloning a repo. The CLI has no notion of
"who is running this command", and the server has no notion of
"this is an authenticated CLI".

This changes with the next feature surface. Two consumers
need to know who the caller is:

- A user running `deesse auth login` on a fresh machine
  needs to obtain a session token without typing a password
  into a terminal.
- The server, when it eventually exposes authenticated
  procedures (per the broader roadmap), needs a wire
  format that identifies the caller.

The CLI cannot store a long-lived password. The server
cannot ask the CLI for a password either. The shape that
fits both is **device authorization** (RFC 8628): the CLI
requests a code, the user approves the code in a browser,
the CLI polls for a token, and the token is a Better Auth
session token. Better Auth ships this as a first-class
plugin (`better-auth/plugins/device-authorization`), already
present in `node_modules/better-auth@1.6.23`.

The temptation when wiring device auth is to build a custom
flow: a parallel REST endpoint that returns a token, a CLI
subcommand that posts credentials directly, a webhook the
server calls back to. Each custom flow fragments the auth
surface, doubles the wire-format surface, and forces every
consumer to learn a new path. The cost compounds: the
custom endpoint becomes a public surface that future
contributors must understand, the parallel CLI subcommand
becomes a second way to authenticate, the callback becomes
a second wire format the server must validate.

The Better Auth device-authorization plugin is the
load-bearing shape. We do not work around it. We do not
reimplement it. We do not add a second auth surface.

## Decision

The CLI auth surface is driven by the Better Auth
device-authorization plugin. The plugin is wired once, on
the server, and the CLI consumes it through the same
`/api/v1/auth/*` mount that already serves Better Auth's
session endpoints. No new HTTP surface is added. No new
wire format is introduced.

### Server-side wiring

`packages/auth/src/auth.ts` adds the plugin to the existing
plugin array:

```ts
import { deviceAuthorization } from "better-auth/plugins"

plugins: [
  deviceAuthorization({
    verificationUri: "/device",
  }),
  nextCookies(), // must remain last
]
```

The plugin adds five endpoints under the existing
`/api/v1/auth/*` mount:

| Endpoint | Method | Purpose |
|---|---|---|
| `/api/v1/auth/device/code` | POST | CLI requests a device + user code |
| `/api/v1/auth/device/token` | POST | CLI polls for the access token |
| `/api/v1/auth/device` | GET | Web UI claims a code for the calling session |
| `/api/v1/auth/device/approve` | POST | Authenticated user approves a code |
| `/api/v1/auth/device/deny` | POST | Authenticated user denies a code |

No new mount. No new base path. No new wire envelope. The
five endpoints sit alongside `/sign-in/email`,
`/sign-up/email`, `/get-session`, and the rest of the
Better Auth surface that already lives under
`/api/v1/auth/*`.

The plugin adds one table (`deviceCode`) to the Better Auth
schema. The table is regenerated by `pnpm auth:generate`
and lands in `packages/database/src/schema/auth.ts`. The
generation step is already wired as `packages/auth`'s
`auth:generate` script; the new table follows the same
review process as every other schema change.

### Client-side wiring

`apps/app/lib/auth-client.ts` adds the client plugin to the
existing client:

```ts
import { deviceAuthorizationClient } from "better-auth/client/plugins"

export const authClient: ReturnType<typeof createAuthClient> =
  createAuthClient({
    baseURL: clientEnv.NEXT_PUBLIC_APP_URL,
    basePath: API_AUTH_PATH,
    plugins: [deviceAuthorizationClient()],
  })
```

The client plugin adds five methods (`device.code`,
`device.token`, `device`, `device.approve`, `device.deny`)
that map one-to-one to the server endpoints. The wire
shape is whatever Better Auth publishes; the typed client
does not invent a parallel shape.

### CLI commands

`apps/cli/src/commands/auth/` holds three new commands,
each in its own file, following ADR-010's command-file
invariants:

| Command | File | Purpose |
|---|---|---|
| `deesse auth login` | `login.ts` | Request codes, open browser, poll, persist token |
| `deesse auth status` | `status.ts` | Read token from disk, hit `/get-session`, show user |
| `deesse auth logout` | `logout.ts` | Hit server-side sign-out, delete token file |

The three commands are registered in `apps/cli/src/index.ts`
under the `auth` parent:

```ts
const authCommand = new Command("auth").description(
  "Authenticate this machine against the DeesseJS server",
)
authCommand.addCommand(loginCommand)
authCommand.addCommand(statusCommand)
authCommand.addCommand(logoutCommand)
program.addCommand(authCommand)
```

The new subcommand tree is reviewed against ADR-010 §1
(commands are siblings, not nested features). The `auth`
parent is a sibling of `init`, `list`, `info`; the three
children are siblings of each other.

### Token storage

The session token returned by `/device/token` is persisted
on disk at `~/.deessejs/auth.json`. The file lives in the
same `~/.deessejs/` directory that already hosts the
templates cache (`apps/cli/src/cache/location.ts`). The
file format:

```jsonc
{
  "access_token": "<session.token>",
  "user": { "id": "...", "email": "...", "name": "..." },
  "fetchedAt": "2026-08-17T..."
}
```

The file is owned by a new module
`apps/cli/src/auth-store/index.ts` (one concept per folder,
per ADR-002). The module exposes `readAuth`, `writeAuth`,
`clearAuth`: three pure file-IO helpers. The token file
is **opaque** to consumers: a tool that reads
`~/.deessejs/auth.json` directly is reading the cache, not
the contract. The format may change between CLI minor
versions without bumping the major, on the same opacity
rule that ADR-010 §4 pins for the templates cache.

The token file is **not encrypted at rest** in V1. The
threat model is "someone with shell access to my machine",
not "someone who steals my laptop's encrypted home
directory". If the threat model widens, encryption at rest
ships as a separate ADR.

The token file is written with mode **`0600`** (read/write
for the owner only). The `writeAuth` helper calls
`fs.writeFile(path, body, { mode: 0o600 })` and explicitly
`fs.chmod(path, 0o600)` after the write. `writeFile`'s
mode is masked by the process umask, so the chmod is the
authoritative step. On Windows (which has no `0600`
equivalent), the helper falls back to `icacls` to grant
the current user only; the rule is "the file is readable
only by the user running the CLI", not "the bits are 0600".
The `readAuth` and `clearAuth` helpers do not change the
mode (the file's owner is set once, at write time).
A `writeAuth` call that fails the chmod check is treated
as a write failure: the CLI exits through `CliError`
with an internal error code, not a public code. The
permission hardening is not a user-facing concern.

### Wire format for the polling loop

The CLI does not invent a wire format for the polling
loop. The loop calls the typed Better Auth client method
`authClient.device.token({ grant_type, device_code,
client_id })` and decodes the response into the shape
Better Auth publishes. The error codes
(`authorization_pending`, `slow_down`, `expired_token`,
`access_denied`, `invalid_grant`, `invalid_client`)
are Better Auth's codes, not CLI codes. The CLI maps
them to behavior, not to user-facing labels.

The mapping table lives in
`apps/cli/src/commands/auth/polling-errors.ts` as a
pure function `mapPollingError(code: BetterAuthErrorCode): CliError`:
- `authorization_pending` → continue polling (no exit)
- `slow_down` → increase local interval by 5s, continue
- `expired_token` → `cliDeviceExpired(...)` with message
  "Device code expired before approval. Run `deesse auth login` again."
- `access_denied` → `cliDeviceDenied(...)` with message
  "Authorization was denied in the browser."
- `invalid_grant`, `invalid_client` → `cliDeviceExpired(...)`
  with a "code invalid or already used" message (the user
  has no way to recover without restarting the flow)

The `interval` returned by `/device/code` is the minimum
polling interval. Better Auth's default is `"5s"`; the
CLI respects whatever the server publishes. On `slow_down`,
the CLI increases its local interval by 5 seconds and
continues. On `expired_token`, `access_denied`,
`invalid_grant`, or `invalid_client`, the CLI exits
through the `mapPollingError` table above.

The polling loop also enforces a **total timeout** of
30 minutes (the upstream device-code TTL). On timeout, the
CLI exits with `cliDeviceExpired` and the message
"Device flow timed out after 30 minutes. Run `deesse auth login` again."
The timeout uses the same `sleep` helper as the polling
interval; no second timing mechanism.

### apps/app pages

The user-facing surface for the device flow lives in
`apps/app/`. The plugin's `verificationUri: "/device"`
points to a page that handles four states; the page is
reachable without a session, the session is established
on the fly when the user signs in. The CLI never sees
the page directly. The CLI's `deesse auth login`
command opens the browser to the `verification_uri_complete`
returned by `/device/code`, which already carries the
`user_code` in the query string.

#### Route layout

The verification page lives under the `(unprotected)`
route group, **inside the `(auth)` sub-group**, alongside
`login`, `signup`, `forgot-password`, `reset-password`,
and `verify-email`:

```
apps/app/app/(unprotected)/
└── (auth)/
    ├── login/page.tsx
    ├── signup/page.tsx
    ├── forgot-password/page.tsx
    ├── reset-password/page.tsx
    ├── verify-email/page.tsx
    ├── device/
    │   └── page.tsx
    └── layout.tsx
```

The page inherits the `(auth)/layout.tsx` layout. The
centered single-column panel (`max-w-md`) that
`login`, `signup`, and the rest of the form-based
flows already use. The form-based flow and the device
flow share the same panel shape (a heading, a caption,
one or two primary actions, a "go back" link); the
shared layout is the right fit. The
`(unprotected)/layout.tsx` is unchanged.

The page is **public**: `apps/app/proxy.ts` does not
gate it. The proxy's `AUTH_PREFIXES` allowlist is the
list of routes that bounce a signed-in user to `/home`;
the device page is added to this list so a user who is
already authenticated is forwarded to the approve/deny
view directly instead of being bounced to `/login`. The
allowlist gains `/device`; the rest of the proxy is
unchanged.

#### The page component

`apps/app/app/(unprotected)/device/page.tsx` is a
server component that reads `user_code` from the search
params, validates the shape (8 chars, charset
`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`), and renders the
matching state. The validation lives in a small Zod
schema (`userCodeSchema = z.string().regex(/^[A-HJ-NP-Z2-9]{8}$/)`)
imported from the auth components barrel; the page
calls `userCodeSchema.safeParse(searchParams.user_code)`
and renders the "Expired" panel on a parse failure
(invalid or missing `user_code` is the same as
expired. There is no point telling an unauthenticated
visitor why the URL was bad). The page types
`searchParams` as `Promise<{ user_code?: string | string[] }>`
(the Next.js 16 searchParams shape), narrows to
`{ user_code: string }` after the Zod check, and passes
the narrowed value down to `DeviceForm`. The four states:

| State | Condition | Render |
|---|---|---|
| Not signed in | `authClient.getSession()` returns null | "Sign in to continue" panel with a `next` param pointing back to `/device?user_code=...`; clicking the panel signs the user in, lands back on the device page, the session is now present and the page re-renders into the "claim" state |
| Claimed, pending | `authClient.device({ query: { user_code } })` returns `{ status: "pending" }` and the calling session is now bound to the code (the GET endpoint side-effects `userId` on first call) | "Approve" panel with two `Button` components (shadcn `Button` per the `use-shadcn` discipline), one for `authClient.device.approve({ userCode })`, one for `authClient.device.deny({ userCode })`. A short caption names the device (the `client_id` from the device-code record, when present) and the scopes (`scope`, when present). |
| Approved | the user clicked approve, the next `device()` poll returns `{ status: "approved" }` | "Done" panel: "You can close this tab and return to your terminal." with a `<Link>` back to `/home` (not a forced redirect; the user may want to keep the tab open). |
| Denied, expired, or invalid | the device-code record's `status` is `denied` / `expiresAt` is in the past / the record is missing | "Expired" panel: "This code has expired or is invalid. Run `deesse auth login` again." No retry button on this page; the CLI owns the retry loop. |

The component uses `@tanstack/react-query` for the
client-side state machine, not a server component with
revalidation and not raw `useEffect` + `useState`. The
read path (`authClient.device(...)`) goes through
`useQuery` with a stable `queryKey` keyed on `user_code`,
so concurrent polls are deduped and a `slow_down`-style
throttle can sit in `refetchInterval` if the server
exposes a next-poll hint. The mutations
(`authClient.device.approve(...)`, `authClient.device.deny(...)`)
go through `useMutation` so the in-flight state can
disable the buttons without a local boolean. The four
states are an interaction state, not a server state;
the server state is read on demand through the typed
Better Auth client.

The `apps/app` workspace pins `@tanstack/react-query` in
the catalogue (`pnpm-workspace.yaml`) and wires
`QueryClientProvider` at the root layout. The page is a
thin server component (reads `searchParams.user_code`,
runs the runtime validation, renders the
`DeviceForm`); the `DeviceForm` component owns the
state machine.

#### Components

The page composes a new component
`apps/app/components/auth/device-form.tsx` that owns
the four-state machine. The form follows the same
convention as `login-form.tsx`, `signup-form.tsx`,
`forgot-password-form.tsx`, and `reset-password-form.tsx`
(per the `use-shadcn` discipline. Button, Input,
Card, and friends from `@workspace/ui` only, no raw
`<input>` with shadcn classes copy-pasted). The
component is exported from `apps/app/components/auth/index.ts`
alongside the existing five forms; the page imports
it through the barrel, mirroring `login/page.tsx`'s
`import { AuthContainer, LoginForm } from "@/components/auth"`.

The `AuthContainer` layout is reused. The page is
inside the `(auth)` sub-group, so it inherits the
centered single-column panel from `(auth)/layout.tsx`
The same panel `login`, `signup`, and the rest of
the form-based flows already use. The device flow's
"what you're approving" caption and the
approve/deny buttons fit the `max-w-md` panel without
needing a wider container. If a future ADR adds a
device page that needs more horizontal space (a code
preview, a longer scopes list), the wider layout is a
new primitive registered through the design system,
not duplicated as ad-hoc Tailwind.

#### Wiring the typed client

`apps/app/lib/auth-client.ts` already exports the typed
`authClient`. The device page calls the four client
methods directly:

```ts
const { data } = await authClient.device({
  query: { user_code },
})
const { data } = await authClient.device.approve({
  userCode,
})
const { data } = await authClient.device.deny({
  userCode,
})
```

No wrapper. No bespoke fetch. The typed client is the
wire format, per ADR-001.

#### Email verification gate

The device page is reachable by an unverified user
(they may have just signed up to approve their CLI).
The page itself does not gate on `emailVerified`; the
flow is "sign in, approve". The existing
`apps/app/proxy.ts` gate (per
`docs/guides/better-auth/pitfalls.md` §3) redirects
unverified users on protected prefixes to
`/verify-email`. The device page is **not** a
protected prefix, so the gate does not apply; the
approve flow proceeds, and the CLI receives a session
token whose cookie is subject to the same verification
gate on its next visit to a protected route. A user who
signs in to approve a CLI without verifying their
email gets a token, but cannot use the web app until
they verify. This is the intended behavior: the device
flow is a wire-level approval, not an onboarding step.

#### Settings integration

The device flow does not add a new entry to the
settings home. The existing `/settings/sessions` page
already lists active sessions via the Better Auth
`session` table; the CLI session appears there like
any other session. A future ADR may add a "pending
device authorizations" panel; it does not belong in
this ADR.

## What this rule allows

- A new command under `apps/cli/src/commands/auth/`. Each
  command is a sibling file with its own flag list, output
  formatter, and exit-code mapping, per ADR-010 §1.
- A new module `apps/cli/src/auth-store/` with the three
  pure helpers (`readAuth`, `writeAuth`, `clearAuth`).
- Adding `deviceAuthorization(...)` to
  `packages/auth/src/auth.ts`'s plugin array. The plugin
  must sit before `nextCookies()` (which must remain
  last, per the Better Auth Next.js integration
  requirement).
- Adding `deviceAuthorizationClient()` to
  `apps/app/lib/auth-client.ts`'s plugin array.
- Regenerating `packages/database/src/schema/auth.ts` via
  `pnpm auth:generate` to add the `deviceCode` table.
- Reading the Better Auth docs and the plugin source to
  understand the polling protocol and the error codes.
  Reading is not bypassing.
- Mapping Better Auth's error codes to local CLI exit
  codes through the existing `CliError` machinery. The
  mapping is internal; the public error code list (per
  ADR-010 §2) does not gain new entries for the polling
  loop.
- The CLI opening the browser to the
  `verification_uri_complete` returned by `/device/code`,
  (not to `verification_uri` alone). The `_complete`
  variant already carries the `user_code` in the query
  string; navigating to `verification_uri` without the
  code sends the user to a bare sign-in page that does
  not know which device to claim. The CLI encodes the
  `user_code` in the URL it opens so the page hydrates
  the right state on first paint. The CLI uses the `open`
  package (catalogued in `pnpm-workspace.yaml`) to launch
  the OS-default browser on Linux/macOS/Windows; the
  cross-platform shim is one line (`open(url)`) and the
  package handles WSL detection and the
  `xdg-open`/`open`/`start` per-OS dispatch.
- A new page
  `apps/app/app/(unprotected)/(auth)/device/page.tsx`
  inside the existing `(auth)` sub-group, alongside
  `login`, `signup`, `forgot-password`,
  `reset-password`, and `verify-email`. The page
  inherits the centered `AuthContainer` layout from
  `(auth)/layout.tsx`.
- A new form component
  `apps/app/components/auth/device-form.tsx` exported
  from `components/auth/index.ts`. The component owns
  the four-state machine (not signed in / claimed
  pending / approved / expired) and uses the typed
  Better Auth client directly.
- Adding `/device` to the `AUTH_PREFIXES` allowlist in
  `apps/app/proxy.ts`. The proxy bounces a signed-in
  user to `/home`; an authenticated user landing on
  `/device` skips the bounce and goes straight to the
  approve/deny view.
- Composing the device page from `@workspace/ui`
  shadcn components (Button, Input, Card) per the
  `use-shadcn` discipline. No raw `<input>` with
  shadcn classes copy-pasted.

## What this rule forbids

- **A new HTTP route outside `/api/v1/auth/*` for the
  device flow.** The five endpoints live under the
  existing Better Auth mount. Adding
  `/api/v1/device/*`, `/api/v1/cli/*`, or any parallel
  mount is a regression.
- **A new wire envelope for the auth response.** The CLI
  decodes whatever Better Auth publishes; the CLI does
  not invent a parallel response shape.
- **A custom envelope alongside `ORPCError` for the
  polling loop.** ADR-001 forbids custom envelopes; this
  ADR reinforces the rule for the auth path. If a polling
  response cannot be decoded into the Better Auth shape,
  the error is a `network_error` or `parse_error` per
  ADR-010 §2, not a new code.
- **Storing the token outside `~/.deessejs/auth.json`.**
  The CLI does not read `~/.config/`, `~/.cache/`,
  environment variables, or the macOS Keychain for the
  session token in V1. The home-directory path is the
  contract.
- **Reading the session token from a non-CLI source.**
  The token is opaque; a tool that parses
  `~/.deessejs/auth.json` directly reads the cache at its
  own risk, on the same opacity rule as the templates
  cache (ADR-010 §4).
- **Storing the user's password on disk.** The device
  flow never sees the password; storing it would defeat
  the point of the flow.
- **Reimplementing the polling loop in the server.** The
  Better Auth plugin owns the polling protocol; the server
  exposes the five endpoints, the plugin enforces
  `interval` and `lastPolledAt` throttling, the CLI
  consumes them.
- **Adding `deviceAuthorization` to `packages/api/` or
  `packages/api/src/http/`.** The plugin lives in
  `packages/auth/`, which is the single source of truth
  per the better-auth guides (`docs/guides/better-auth/index.md`).
- **Bypassing `nextCookies()` to put `deviceAuthorization`
  last.** `nextCookies()` must be last in the plugin
  array; moving it is a Next.js integration regression.
- **Adding a settings page that duplicates the device
  verification page.** The verification page is the
  user-facing surface; `/settings/sessions` already
  covers device management.
- **Placing the device page outside the `(auth)`
  sub-group.** The page is part of the auth surface
  and inherits the `AuthContainer` layout; a sibling
  placement under `(unprotected)/device/` would
  duplicate the layout primitive for no gain.
- **Introducing a wider container primitive
  (`device-container.tsx` or a generic
  `WideAuthContainer`) for V1.** The `AuthContainer`
  `max-w-md` panel fits the approve/deny caption and
  the two buttons. A wider container is added only if
  a future ADR surfaces a layout that does not fit
  the existing panel, and it lands in the design
  system, not in `components/auth/`.
- **Bypassing `authClient` for the four device methods
  on the web side.** The page calls
  `authClient.device()`, `authClient.device.approve()`,
  `authClient.device.deny()` directly. A bespoke
  `fetch`, a wrapper that imitates the typed client, or
  a parallel envelope on the web side is forbidden by
  ADR-001.
- **Gating the device page on `emailVerified`.** The
  page is reachable by a user who has not yet verified
  their email; the flow is "sign in, approve". The
  verification gate that protects `/home` and
  `/settings` (per `docs/guides/better-auth/pitfalls.md`
  §3) is unchanged; the device page is not a protected
  prefix and the gate does not apply here.
- **Putting the device page under a protected route
  group.** The page is `(unprotected)`; a protected
  wrapper would block the very users the flow is
  designed to serve (a fresh CLI user who has never
  signed in to the web app).

## What this rule does not change

- **The single-tenant decision.** The
  device-authorization plugin does not introduce
  organization concepts; it adds a `deviceCode` table
  and five endpoints that operate on user identity, not
  on organization membership. The locked-in decisions in
  `docs/guides/better-auth/index.md` (no
  `organization(...)`, no `databaseHooks.session.create.before`,
  no `useActiveOrganization`) are unchanged.
- **The session cookie configuration.** The device flow
  creates a session with the existing
  `session.expiresIn: 7 days`, `updateAge: 1 day`
  configuration. The CLI token is a `session.token`;
  the cookie config is unrelated.
- **The CLI's public command set.** The three existing
  commands (`init`, `list`, `info`) and their flags are
  unchanged. The `auth` parent command is a new sibling,
  not a renamed or removed command.
- **The CLI's error code list.** The four codes
  (`network_error`, `parse_error`, `not_found`,
  `cli_outdated`) are unchanged, plus the two device-flow
  codes (`cli_device_denied`, `cli_device_expired`) added
  in lockstep by ADR-010 §2 (the public-list amendment
  this ADR required). The polling loop maps Better Auth
  error codes to these via the `CliError` machinery; no
  other new public code is added by this ADR.
- **The CLI's HTTP wire format.** The CLI still talks to
  the upstream through the Better Auth client for the
  auth endpoints. The typed oRPC client (per ADR-001)
  remains the wire format for business procedures.
- **The CLI's cache opacity rule.** The token file
  inherits the same opacity rule as the templates cache
  (ADR-010 §4): the format may change between CLI minor
  versions without bumping the major.
- **The `trustedOrigins` configuration.** The device
  verification page lives on the same origin as the rest
  of `apps/app/`; no new origin is added to the
  allowlist.
- **The `apps/cli/` folder structure.** The new
  `commands/auth/` and `auth-store/` folders follow the
  one-folder-per-concept rule (ADR-002); no new file at
  the `apps/cli/` root.
- **The OAuth-device path is not in scope here.** Better
  Auth ships a sibling plugin, `oauthDeviceAuthorization`,
  under the separate `@better-auth/oauth-provider`
  package. That plugin adds `POST /oauth2/token` for
  registered OAuth clients and is the right shape for
  machine-to-machine consumers (other CLIs, CI bots).
  This ADR covers only the user-in-the-browser flow
  driven by `deviceAuthorization`; the OAuth path
  ships in a separate change with its own ADR. The
  single-tenant decision, the `deviceCode` table, and
  the `verificationUri` page are shared, but the
  plumbing does not change here.

## Test strategy

The device-flow ships with **one test layer** in the
implementation PR: an integration test on the server,
extending `packages/api/tests/integration/system/auth.test.ts`
to cover the five Better Auth endpoints
(`/auth/device/code`, `/auth/device/token`, `/auth/device`,
`/auth/device/approve`, `/auth/device/deny`). The test
uses a real `http.createServer` plus a real database
fixture, per ADR-009 (test strategy) and the
Source-Side Client pattern (ADR-001 / rule 0008
test-mocking). The integration test runs on every PR
that touches the device-flow path, in the same CI
job as the other system-route tests.

The web side (`DeviceForm`, the `device` page, the
`QueryClientProvider` wiring) ships without a unit or
component test in the implementation PR. The page is a
thin shell that delegates the state machine to
`DeviceForm`; the only logic worth testing is the
`mapPollingError` table on the CLI side and the Zod
`userCodeSchema` runtime validation. The web side is
exercised manually against a local Better Auth
instance, then covered by the server integration test
indirectly (the same wire format is consumed).

The CLI commands (`auth login`, `auth status`,
`auth logout`) ship without a unit or integration test
in the implementation PR. The polling-loop logic is
the part with the most surface (timeout, backoff,
mapping table) and gains the most from a test, but
building the fixture (a fake Better Auth server that
returns `authorization_pending` then `approved` after
N polls) is a separate concern. The follow-up PR
"add device-auth CLI tests" lands alongside the
implementation PR but is not part of it.

A PR that adds a unit test for the web side or the
CLI side is **not rejected** by this ADR. The ADR
documents what the implementation PR ships, not what
follows it. The follow-up tests are the right shape;
the implementation PR is the right scope.

## Consequences

- A PR that adds a device-auth endpoint outside
  `/api/v1/auth/*` is rejected. The contributor moves the
  endpoint under the Better Auth mount.
- A PR that adds a CLI command without a sibling file in
  `commands/auth/` is rejected. The contributor splits
  the command into one file per command.
- A PR that adds `deviceAuthorization` after
  `nextCookies()` in the plugin array is rejected. The
  plugin must sit before `nextCookies()`.
- A PR that introduces a custom auth wire format is
  rejected. The wire format is whatever Better Auth
  publishes.
- A PR that stores the token outside
  `~/.deessejs/auth.json` is rejected. The home-directory
  path is the contract.
- A PR that adds a new public CLI error code for the
  polling loop is rejected per ADR-010 §2. The
  contributor maps Better Auth codes to existing CLI
  codes or escalates the public-list change to a new ADR.
- A PR that adds `organization(...)` or
  `useActiveOrganization` in the same change as
  `deviceAuthorization(...)` is rejected. The
  device-auth plugin does not require the org plugin;
  the contributor splits the change.
- A PR that regenerates `schema/auth.ts` without
  reviewing the diff is rejected. The generator may
  overwrite custom field names or indexes (per
  `docs/guides/better-auth/setup.md`).
- A PR that ships a CLI binary with the auth commands
  without a changeset is rejected by the
  `check-changeset` CI job (per ADR-010 §6).

## Where this rule came from

The CLI shipped V1 (`@deessejs/cli@1.x`) without an auth
surface. The three commands that exist today
(`init`, `list`, `info`) are anonymous on the wire: the
server does not know who is calling, and the CLI does not
carry identity. The first feature that requires identity
on the CLI side. A roadmap item that surfaces a
"personal registry" experience for authenticated users.
forces the question: how does the CLI authenticate?

Three options were considered:

1. **Username and password in the CLI.** The user types
   credentials on every command (or stores them in the
   shell). The approach fails the threat model: shell
   history, copy-paste, screen sharing. It also fails
   the email-verification gate (per
   `docs/guides/better-auth/email.md`): a CLI that
   requires verified email cannot verify a user who has
   not yet logged in to the web app.
2. **A long-lived API key issued from the web app.** The
   user creates a key in `/settings/connections`, pastes
   it into the CLI on first run, the CLI stores it. The
   approach works, but the key-management surface
   (`/settings/connections` + a CLI storage path) is a
   second wire format that the CLI must learn.
3. **Device authorization.** The CLI requests a code, the
   user approves in the browser, the CLI polls for a
   token. The wire format is Better Auth's wire format;
   the token is a session token that the existing
   `/get-session` endpoint already knows how to decode;
   the verification page is the user-facing surface;
   no new key-management UI is needed.

Option 3 wins on three counts:

- **No new wire format.** The five endpoints live under
  the existing Better Auth mount.
- **No new user-facing key-management UI.** The
  verification page is a one-page surface, not a CRUD.
- **No new CLI storage path.** The session token lives
  in the same `~/.deessejs/` directory as the templates
  cache.

The risk of option 3 is the polling protocol: a CLI that
polls too aggressively could DDoS the server. Better Auth's
plugin enforces this: the `pollingInterval` field and the
`slow_down` error code prevent abuse. The CLI respects
the protocol; the server enforces it.
