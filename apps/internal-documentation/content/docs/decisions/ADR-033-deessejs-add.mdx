# ADR-033: deessejs add `feature`

## Status

**The contract is accepted; the implementation lands in a follow-up change set.** Approved as part of the trio ([ADR-031](./ADR-031-deesse-json.mdx) + [ADR-032](./ADR-032-deesse-template.json.mdx) + ADR-033), tracked by [PR #137](https://github.com/deessejs/deessejs/pull/137). The spec-vs-implementation split is documented in [ADR-032 Open Question #1](./ADR-032-deesse-template.json.mdx): the file-shape change (`deesse.json` + `deesse-template.json` + the registry CDN at `registry.deessejs.dev`) ships first; `deessejs add feature` ships as a follow-up. This ADR documents the *contract* for `add` (commands, flags, install sequence, dry-run, error mapping) so the implementation can land later without re-litigating the shape.

## Context

The DeesseJS template registry exists to scaffold projects. shadcn's CLI ships two headline commands: `shadcn init` (clone a starter) and `shadcn add` (layer a single component, block, or feature onto an existing project). The DeesseJS CLI today ships only `init` (`apps/cli/src/commands/init.ts`), `list`, and `info` (per ADR-010 §1). A user who wants to add a `crud` feature or an `auth` block to an existing project has no command — they have to merge two cloned trees by hand, or copy-paste from a documentation page.

The open questions #1 of both [ADR-031](./ADR-031-deesse-json.mdx) and [ADR-032](./ADR-032-deesse-template.json.mdx) flagged this gap. The motivation for `add` got stronger once those two ADRs landed:

- [ADR-031](./ADR-031-deesse-json.mdx) gives the CLI a project-side config (`deesse.json#paths`, `aliases`, `database`) that an overlay command can read to know where to write. Without `deesse.json`, the overlay command has to guess the project's layout — same guess-fail pattern that motivates `deesse.json` in the first place.
- [ADR-032](./ADR-032-deesse-template.json.mdx) gives the CLI an item descriptor (`deesse-template.json#type = "template:package" | "template:cli" | ...`) that distinguishes a full project clone (`template:app`, today's `init`) from an overlay (`template:package` and the other five types). Without the `type` discriminator, an item is either a full clone or it has no install semantics at all.

Together the two ADRs create the conditions for `add` to exist; this ADR decides whether to ship it.

### Why the spec ships now, the implementation ships in a follow-up

Three reasons the **specification** lands in this ADR but the **implementation** lands in a follow-up change set:

1. **The shape is non-trivial; it deserves review on its own.** `add`'s contract — command surface, dry-run, type-discriminator enforcement, force semantics, dependency installation, hook ordering — touches enough edge cases that a reviewer benefits from reading the spec without the implementation PR. Landing the spec alongside [ADR-031](./ADR-031-deesse-json.mdx) and [ADR-032](./ADR-032-deesse-template.json.mdx) means the three ADRs that together define the registry ship together. The implementation PR for `add` lands later, after the registry CDN is operational.

2. **Bundling a new public command with two AD-shape changes is a bigger blast radius.** [ADR-031](./ADR-031-deesse-json.mdx) and [ADR-032](./ADR-032-deesse-template.json.mdx) are non-breaking at the CLI surface (no new public command, no new flag, no new error code). `add` is the first public command added under ADR-010 §1. Spreading the two changes — shape change now, new command in a follow-up — keeps each release's blast radius small and lets the shape change land and stabilise before `add` adds user-visible surface.

3. **Implementation is gated on the registry CDN.** The implementation needs `registry.deessejs.dev` to be live and `deesse-template.json` to be co-located in template repos. The CDN ships in the same change set as the file shape (per [ADR-032 Decision #4](./ADR-032-deesse-template.json.mdx)) and the co-location discipline takes time to propagate across `deessejs/*` template repos. The follow-up is the earliest point at which `add` can ship against a populated registry.

The implementation PR for `add` lands in a follow-up change set, not in this one. The spec documented in this ADR is the contract that PR must implement; deviations from the spec are themselves ADRs.

### Why this is breaking

[ADR-010 §1](./ADR-010-cli-public-surface.mdx) pins the CLI's public command surface as a closed list of three (`init`, `list`, `info`) plus the `auth` group. Adding `add` is **breaking** under that rule:

- A reviewer who has memorised the three commands now sees four.
- A script that does `case "$cmd" in init|list|info) ... ;; esac` must add a fourth branch.
- A documentation generator that lists CLI commands must regenerate.

The closed-list rule in ADR-010 §2 (closed `CliErrorCode`) does not apply here — no new error code ships with `add`. The `--offline` global flag, the `--json` per-command flag, the `engines.node` constraint, the cache location, the wire contract — all stay. Only the command list grows.

### What this command is not

Three patterns the team considered and explicitly rejected before drafting this ADR. They're called out here so a future reviewer doesn't re-propose them.

1. **`add` as an alias for `init`.** Non-breaking, but blurs the meaning. Today's `init saas-starter` clones an entire project; tomorrow's `add auth` would do something completely different (overlay files into an existing project). Same command name, two opposite semantics. Rejected: aliases for opposites break the CLI's mental model.
2. **`add` as a subcommand of `init`.** Reads as `deessejs init add auth`, which is awkward. Rejected because shadcn's precedent is the flat `add`, not the nested one.
3. **`add` exposed only behind a feature flag.** Rejected because a feature flag hides a public command from the docs, which is worse than breaking the docs once.

## Decision

### What this rule decides

Four concrete decisions. They ship together because shipping any one without the others leaves `add` half-working.

#### 1. `deessejs add <feature>` is the fourth public command

The CLI gains a fourth public command, registered alongside `list`, `info`, `init` in `apps/cli/src/commands/index.ts`. The command signature:

```
deessejs add <feature> [options]
```

Where `<feature>` is a registry item address: a slug (`auth-addon`), a namespaced slug (`@deessejs/auth-addon`, `@community/auth-addon`), a full URL (`https://example.com/r/auth-addon.json`), or a local file path (`./auth-addon.json`). The same resolver as `init` applies, with the namespace map read from `deesse.json#registries` (per [ADR-031](./ADR-031-deesse-json.mdx)).

Flags (initial set):

| Flag | Purpose | Default |
|---|---|---|
| `--yes` | Skip prompts, apply defaults | `false` |
| `--dry-run` | Show what would be written without writing | `false` |
| `--force` | Overwrite existing files (the per-file list lives in `deesse-template.json#files[]`, not in the command flag) | `false` |
| `--path <dir>` | Override the project root detection | cwd |
| `--json` | JSON output for scripting | `false` |

The flags follow the same per-command-flag invariant as `init` per ADR-010 §1. None of them changes the meaning of an existing flag on another command.

#### 2. The command is an overlay, not a clone

`add` and `init` diverge on the `template:type` discriminator from [ADR-032](./ADR-032-deesse-template.json.mdx):

| Command | Allowed `template:type` values | Behaviour |
|---|---|---|
| `init <slug>` | `template:app` only | Clones the template repo, applies transforms, runs install. Refuses any other type with `parse_error`. |
| `add <feature>` | `template:package`, `template:cli`, `template:mobile`, `template:desktop`, `template:agent`, `template:landing` | Fetches the item descriptor, applies the `files[]` overlay onto the current project (no clone), runs `hooks.postInit`. Refuses `template:app` with `parse_error`. |

The refusal is enforced at parse time on `TemplateV2#type`. A user who tries `deessejs add saas-starter` (a `template:app`) gets a clear error: *"saas-starter is a template:app; use `deessejs init saas-starter` instead."* A user who tries `deessejs init auth-addon` (a `template:package`) gets the inverse: *"auth-addon is a template:package; use `deessejs add auth-addon` instead."*

This split is load-bearing: it prevents `add` from accidentally cloning a full project into a sub-directory of an existing project (the most likely failure mode if the two commands were merged).

#### 3. The command reads `deesse.json` for paths, aliases, database

The command's sequence:

1. **Detect project root.** The CLI walks up from the current directory until it finds a `deesse.json`. If none is found, the CLI refuses with `parse_error`: *"deesse.json not found; run `deessejs init` first."* This is the same closed-list error code as a malformed `deesse.json`; no new public code ships.
2. **Load `deesse.json`.** Zod-validate the file through the `Project` schema in `@workspace/contracts` (per [ADR-031](./ADR-031-deesse-json.mdx)). Reject with `parse_error` on failure.
3. **Fetch the item descriptor.** Resolve `<feature>` through `deesse.json#registries` (or use the literal URL / local path). Fetch `deesse-template.json` from the registry host (`registry.deessejs.dev`) or the user's literal URL. Zod-validate through `TemplateV2`.
4. **Refuse on `template:app`.** Enforce the discriminator split from Decision #2. Refuse with `invalid_item_type` (internal error code).
5. **Resolve `templateDependencies` (topological, with cycle detection).** Same recursive logic as `init` (per [ADR-032 Decision #3](./ADR-032-deesse-template.json.mdx)). Each dependency is also a `template:package` (or other overlay type); the recursion terminates at items with no further dependencies.

   **Cycle detection**: the CLI runs a depth-first topological sort on the resolved dependency graph. If a cycle is detected (e.g. `auth` depends on `database-adapter` which depends on `auth`), the CLI refuses with `circular_dependency` (internal error code) and prints the cycle path: *"Circular dependency detected: auth → database-adapter → auth."*

   **Depth limit**: the dependency tree has a maximum depth of **5**. A dependency at depth 6 or more is rejected with `dependency_depth_exceeded` (internal error code). This prevents denial-of-service via deeply nested dependency trees and bounds the install flow to a predictable size. A template author who needs deeper composition must refactor.

   **No conflicting dependencies**: if template A requires `database: postgresql` and template B requires `database: sqlite`, the CLI **does not auto-resolve** the conflict. It surfaces both requirements to the user during the prompt aggregation (step 6) and asks them to pick one (or pass `--force` to override, with a loud warning).
6. **Run `prompts[]` (eagerly aggregated).** All `prompts[]` across the resolved dependency graph are collected **upfront** before any file acquisition or disk write. The CLI walks the topological order (per step 5) and presents prompts in declaration order; answers may mutate the overlay's resolved paths (a `database` prompt may pick a Prisma adapter that writes a different `schema.prisma`); the command respects that.

   **Lazy prompts across dependencies** (one prompt per item, interleaved with installs) are **explicitly forbidden**: interleaving breaks atomic rollback (the user cannot undo a partial install if a later prompt is rejected after earlier items' files are written). Eager aggregation is the only correct behaviour.

   **`when` evaluation context** (per [ADR-032 §"The `when` DSL"](./ADR-032-deesse-template.json.mdx)): each `when` expression is evaluated against a context with two scopes:
   ```ts
   type WhenContext = {
     answers: Record<string, unknown>;   // prior prompts[] in the same install
     project: DeesseProjectConfig;       // the loaded deesse.json
   };
   ```
   This allows `when: "project.database == 'postgresql'"` to skip the database adapter prompt for users who already configured `database` in `deesse.json`. Identifiers are scoped to `answers.<promptName>` and `project.<fieldName>`; bare identifiers in `when` are resolved against `answers` first, then `project`. Same gating, same `--yes` behaviour as `init` for prior prompts; `--yes` short-circuits the `when` gate and applies the documented `default`.
7. **Apply `files[]` transformations.** Walk the item's `files[]`, substitute `@components/`, `@lib/`, `@hooks/`, `@ui/`, `@apps/`, `@packages/` against `deesse.json#aliases` (per [ADR-031 Decision #2](./ADR-031-deesse-json.mdx)). Write each file at its resolved `target`. **Refuse to overwrite existing files** unless the user passes `--force`; the per-file allow-list is in `deesse-template.json#files[].overwrite`, not in the command flag.
8. **Run `hooks.postInit`.** Same closed-list verb whitelist as `init`.
9. **Update `deesse.json#templates["<feature>"]`.** Same resolved-state block as `init`.

Every step except step 1 (which is read-only) is idempotent. Re-running `add <feature>` on an already-installed feature updates `deesse.json#templates["<feature>"]` and re-applies `files[]` (overwriting where the user passed `--force`, leaving alone otherwise).

#### 4. The dry-run flag is a first-class concern

`--dry-run` is not optional. The command lists the files it would write, the dependencies it would install, the hooks it would run, and the `deesse.json` mutations it would apply, then exits 0 without writing anything. The output goes to stdout in human-readable form by default and to stdout in JSON form with `--json`.

Why this matters: the most common failure mode for an overlay command is "I ran it and it stomped on my code." The dry-run gives the user a way to inspect the diff before committing. The same flag is available on `init` for parity (it is not in the current CLI today; this ADR adds it to `init` as a side effect of the shared code path).

#### 5. File acquisition: how `add` reaches the overlay sources

Unlike `init`, which clones the entire template repo into the project root, `add` does **not** write a clone into the user's project. The user already has a project; the overlay is a thin layer of files plus metadata. The CLI must reach the source files from the registry descriptor (`deesse-template.json`) without polluting the project tree with a hidden `.deesse-cache/` directory.

The acquisition mechanism is **tarball-first, with `git clone` as fallback**, into the OS temp directory.

1. **Resolve the source ref.** From `deesse-template.json#source = { repo, ref, cloneUrl }` (per [ADR-032](./ADR-032-deesse-template.json.mdx)). The `repo` field is `owner/name`, the `ref` is a git tag/branch/SHA, and `cloneUrl` is the optional override.

2. **Try the CDN tarball first** (when `cloneUrl` is `github.com/<owner>/<repo>` and `registry.deessejs.dev` exposes a pre-built tarball). The CLI does `fetch('https://registry.deessejs.dev/t/<slug>-<version>.tar.gz')` (or `<owner>/<repo>/<ref>.tar.gz` from GitHub's `codeload` endpoint if the CDN tarball is not available). Tarball extraction is streamed via `tar-stream` (pure-JS, no `tar` binary dependency, portable on Windows).

3. **Fall back to shallow `git clone`** if the tarball fetch fails (404, network error, non-GitHub source). The CLI runs `git clone --depth 1 --branch <ref> <cloneUrl> <tmpdir>/deesse-add-<slug>-<hash>` where `<hash>` is `sha1(slug + ref)` truncated to 8 chars. The clone reuses `apps/cli/src/utils/git.ts` (already used by `init`); no new git plumbing ships. The depth-1 flag limits the clone to the ref's tip; the --branch flag pins the ref.

4. **Read the `files[]` entries** from the extracted tree (whether tarball or clone). The CLI walks `deesse-template.json#files[]` and reads each `path`. Each entry's `path` is relative to the template repo root (e.g. `apps/web/src/lib/auth.ts`); the CLI joins it with the extracted root. The content is read into memory; the temp tree is **never moved or copied into the project tree**.

   **Zip Slip guard (anti-path-traversal)**: every entry extracted from the tarball is validated against path traversal before being written to disk. The extraction logic (in `apps/cli/src/transforms/extract.ts`) computes the absolute target path for each entry as `path.resolve(destDir + path.sep + entry.name)` and asserts that the result starts with `path.resolve(destDir) + path.sep`. Any entry whose resolved path escapes `destDir` (e.g. `../../../etc/passwd`) triggers `security_violation` (internal error code) and the install aborts.

   **Symlink and hardlink guard**: hardlinks and symlinks are **rejected by default**. Only regular files and directories are extracted from the tarball. The extraction implementation reads the entry type byte from the tar header and aborts with `security_violation` on any non-regular entry. This closes the "symlink pointing outside the extraction root" attack vector (e.g. a symlink from `package.json` to `/etc/passwd`).

   **CDN-hosted tarballs**: the official `@deessejs/*` tarballs are pre-built and published by the publication CI in `packages/api` to `registry.deessejs.dev/t/<slug>-<version>.tar.gz`. The CLI does **not** rely on `codeload.github.com` for the official registry — that path is the fallback for third-party GitHub sources where the CDN tarball is not available.

5. **Clean up the temp tree.** The CLI `rm -rf`s the temp directory after the file reads complete (in a `finally` block, even if a downstream step throws). The cleanup is non-negotiable: a stale temp tree is a leak and a potential security surface (a malicious template could write `.bashrc` files into the user's home if the temp dir was reused).

6. **Cache the extracted tree, optionally.** For repeat `add <feature>` calls within the same release window, the CLI caches the extracted tree under `~/.deessejs/cache/overlays/<slug>-<hash>/` keyed by ref + a TTL (default 1h). The cache is invalidated on ETag mismatch against the registry CDN. The first `add` in a session pays the extraction cost; subsequent `add`s for the same ref hit the cache. `--offline` falls back to the cache when the network is unreachable.

**Why tarball-first, not git clone-first**: three reasons that compound.

- **No `git` dependency at runtime.** `git` is not always present on minimal CI containers, Lambda layers, or sandboxed dev environments. The CLI assumes a Node runtime; the tarball path requires nothing else.
- **One HTTP round-trip vs Git negotiation.** A tarball is a single `GET` returning the full source as a compressed stream. A `git clone` performs protocol-level handshake, fetch, pack negotiation, and checkout — each step is a network round-trip and a small-but-real failure surface.
- **Faster in practice.** The codeload tarball endpoint serves the source tree in O(content size); `git clone --depth 1` serves it in O(content size + protocol overhead) plus the cost of unpacking the Git object database. For a 100-file overlay, the tarball is typically 3-5x faster end-to-end on a warm cache.

**Why tarball-first, not inlining.** shadcn inlines file contents in the registry JSON (`files[].content`) because their registry items are small (a single component, a few hundred lines). The DeesseJS overlay model is heavier: a `template:package` may include a route, a Prisma adapter, a server-side handler, and a UI form — easily a thousand lines across multiple files. Inlining that into a registry JSON bloats the descriptor past what a CDN can comfortably serve and what an editor can read. The tarball-based approach keeps the descriptor small (paths + metadata) and lets the CLI stream the file contents from a separate URL.

**Why tarball with `git clone` fallback.** Some sources don't expose a CDN tarball (private mirrors, custom Git hosts, on-prem Gitea instances). The fallback is the same plumbing as today — no regression. For the official `@deessejs` registry, the publication CI builds pre-computed tarballs alongside the registry items, so the tarball path is the common case.

**Why `tar-stream` (pure-JS) instead of shelling out to `tar`.** The tar binary is not always present on Windows in a portable form (git-for-windows ships a `tar.exe`, but many CI images don't). `tar-stream` (npm, ~10kb, zero deps) handles gzip + plain tar in pure JS. It is slower than a native tar at extraction, but the portability win is worth it for a CLI that ships cross-platform.

#### 6. Install sequence (corrected)

The 9-step install sequence from Decision #3 is amended to include dependency installation and `hooks.postInstall`, plus a pre-flight dirty check and a staged-write rollback path. The corrected sequence is **13 steps**:

0. **Pre-flight dirty check.** The CLI runs `git status --porcelain` from the project root. If the output is non-empty (uncommitted changes), the CLI refuses with `parse_error`: *"Working directory has uncommitted changes. Commit, stash, or pass `--allow-dirty` to continue."* The `--allow-dirty` flag bypasses the check. For non-Git projects (no `.git/` directory, or `git` not installed), the check is skipped silently and the CLI prints a **one-time warning**: *"Not a Git repository: automatic rollback on install failure is unavailable. Review your changes manually."* The `--strict-git` flag (off by default) hard-crashes on non-Git projects. This avoids the failure mode where an `add` failure leaves the user's working tree in an inconsistent state with no record of what was modified.

   **Why this matters for rollback**: step 0 guarantees that every subsequent file write is either a new file or a tracked file at a known git baseline. When steps 9-11 fail, the rollback strategy is straightforward:
   - **Newly created files**: the CLI maintains a `Set<path>` of files it created in this install and `fs.unlink`s each on failure.
   - **Overwritten tracked files**: the user restores via `git checkout -- <files>` — the CLI prints the exact command in the rollback stderr message.
   - **Overwritten untracked files** (rare; only happens when the user has an untracked file that a template tries to overwrite): the user's only recovery path is their backup. The CLI cannot help.

   The `--allow-dirty` flag is therefore not a casual bypass — it opts the user out of the rollback safety net for steps 9-11. When `--allow-dirty` is set and an install fails, the CLI prints a louder warning: *"Cannot rollback: working directory was dirty at install time. Review your changes manually."*
1. **Detect project root.** The CLI walks up from the current directory until it finds a `deesse.json`. If none is found, the CLI refuses with `parse_error`: *"deesse.json not found; run `deessejs init` first."* This is the same closed-list error code as a malformed `deesse.json`; no new public code ships.

4. **Refuse on `template:app`.** Enforce the discriminator split from Decision #2. Refuse with `invalid_item_type` (internal error code).
5. **Resolve `templateDependencies` (topological, with cycle detection).** Same recursive logic as `init` (per [ADR-032 Decision #3](./ADR-032-deesse-template.json.mdx)). Each dependency is also a `template:package` (or other overlay type); the recursion terminates at items with no further dependencies.

Eager aggregation is the only correct behaviour.

   ```ts

   ```

Same gating, same `--yes` behaviour as `init` for prior prompts; `--yes` short-circuits the `when` gate and applies the documented `default`.
7. **Acquire the source tree.** Run Decision #5: tarball-first (CDN or GitHub `codeload`), git clone as fallback, read `files[]` entries into memory, delete the temp tree in a `finally` block.
8. **Apply `files[]` transformations.** Walk the item's `files[]`, substitute `@components/`, `@lib/`, `@hooks/`, `@ui/`, `@apps/`, `@packages/` against `deesse.json#aliases` (per [ADR-031 Decision #2](./ADR-031-deesse-json.mdx)). **Stage the writes in memory first**: the CLI builds a `Map<resolvedPath, content>` of the final file content for every `files[]` entry, then applies them atomically to disk at the end of step 8. If any single write fails (EACCES, ENOSPC, target is a directory, etc.), the CLI rolls back the staged writes that already succeeded, deletes the partial file, and returns `install_failed`. **`--force` is sovereign**: a `--force` flag on the user's command line overrides any per-file guard. The `overwrite: true` flag in `deesse-template.json#files[]` authorises **silent** overwrite (no `--force` needed) — see Decision #7 below.

   **`merge` transform scope**: the `merge` transform verb is **strictly limited** to three target types:
   - **JSON files** (`.json`): deep merge of objects, with arrays replaced wholesale (no element-level merge).
   - **Env files** (`.env`, `.env.local`): key/value line replacement; existing keys are overwritten, new keys are appended.
   - **Append-with-sentinel files** (e.g. `AGENTS.md`): lines appended after a sentinel marker (e.g. `# --- deessejs-managed ---`); the marker is added on first install and the section between markers is owned by the CLI on subsequent installs.

   **AST-level code merging** (TypeScript, Python, Rust, etc.) is **explicitly forbidden** in this contract. Code modification goes through overlay file placement (`files[]` with `transform: "rename"` or `transform: "interpolate"`) or `hooks.postInstall`. Attempting to `merge` a `.ts`, `.py`, `.rs`, or other AST-sensitive file aborts the install with `parse_error` and a clear error message.
9. **Install npm dependencies.** Run `{pm} add <dependencies>` followed by `{pm} add -D <devDependencies>` (substituted with the detected package manager from `deesse.json#packageManager`). The whitelist from [ADR-032](./ADR-032-deesse-template.json.mdx) applies: `{pm} add` is in the whitelist, so the runner invokes it via `shell: false` with tokenised argv (per the safety rule documented in ADR-032 Consequences). **If this step fails (peer-dependency conflict, network drop, registry unreachable)**, the CLI rolls back the staged files (step 8) and returns `install_failed`. The user's `deesse.lock#templates["<feature>"]` is NOT updated. If a literal `{{KEY}}` sentinel would be written into an output file (per [RFC-001 §"The `tokens{}` substitution map"](./RFC-001-deesse-json)), the CLI fails fast with `unresolved_token` (internal error code), listing the file path and the missing env var. (step 12 is the last step, not yet reached).
10. **Run `hooks.postInit`.** Same closed-list verb whitelist as `init`. May include `{pm} install` for projects that do not yet have node_modules (rare for `add` — the user already has a project — but possible if the project is freshly cloned and not yet installed). **If this step fails**, same rollback semantics as step 9.
11. **Run `hooks.postInstall`.** May include `{pm} generate` (Prisma), `{pm} db:push` (Prisma), `{pm} db:migrate` (Drizzle), etc. **If this step fails**, same rollback semantics as step 9.
12. **Update `deesse.lock#templates["<feature>"]`.** Record the installed `version`, `installedAt` (date-only `YYYY-MM-DD` UTC per [RFC-001 §"Implementation notes C"](./RFC-001-deesse-json)), and `source`. The CLI writes `deesse.lock` atomically (`fs.writeFile(tmp); fs.rename(tmp, real)`); `deesse.json` is **never** written to on `add` (per [RFC-001 §"Detailed Design"](./RFC-001-deesse-json)). This is the **commit point**: only reached when every preceding step succeeded.

The corrected sequence is 13 steps (was 9 in the original ADR-033, then 12 after the dependency-and-`postInstall` amendment). The original 9-step list omitted steps 9 and 11 (dependency install and `postInstall` hook). Those steps are present in [ADR-032 Decision #3](./ADR-032-deesse-template.json.mdx) for the `init` flow and must be present in the `add` flow too — `add` is not exempt from dependency management. The pre-flight dirty check (step 0) and the staged-write rollback path (steps 8-11) are new in this ADR.

**Rollback implementation note**: the rollback is best-effort. The CLI maintains a `Set<path>` of files it created in this install, and on any step failure, `fs.unlink`s each file in reverse order. If a file was overwritten (not created), the CLI does NOT restore the previous content — restoring requires the user to have committed before the install (which step 0 enforces). This is documented in the CLI's stderr output on failure: *"Rollback removed N files. Use `git status` and `git checkout` to restore any pre-existing files that were overwritten."*

#### 6b. Error taxonomy (add command)

| Condition | Error code | User fix |
|---|---|---|
| Malformed descriptor / placeholder / `when` grammar | `parse_error` | Edit the descriptor or file an issue |
| Target path exists, no `--force`, no `overwrite: true` | `file_collision` (internal) | Pass `--force` |
| Overlay transform fail / staged-write rollback | `install_failed` (internal) | Inspect stderr, retry |
| Registry unreachable | `network_error` | Retry or check network |
| Tarball / archive traversal attempt (Zip Slip, symlink escape) | `security_violation` (internal) | File an issue against the registry author; do not retry |
| `env:<VAR>` cannot be resolved | `unresolved_token` (internal) | Set the env var or update `.env.local` |
| `add <slug>` against an installed item without `--force`/`--upgrade` | `item_already_installed` (internal) | Pass `--force` or `--upgrade` |
| `add` against `template:app` (or `init` against non-`template:app`) | `invalid_item_type` (internal) | Use the other command |
| Cyclic dependencies in the resolved graph | `circular_dependency` (internal) | File an issue against the authors; do not retry |
| Dependency tree deeper than 5 | `dependency_depth_exceeded` (internal) | Refactor the dependency chain |
| Sentinel token left in a `files[]` output | `unresolved_token` (internal) | Set the env var |

All internal codes do not amend ADR-010 §2's closed list on **public** codes.

#### 7. `--force` is sovereign; `overwrite: true` authorises silent overwrite

The two-gate policy from the original Decision #3 is amended. The corrected policy:

- **`--force` (user-side, on the command line) is sovereign.** When the user passes `--force deessejs add auth`, the CLI overwrites any existing file at the resolved `target` path, regardless of whether `deesse-template.json#files[].overwrite` is set. This matches the shadcn CLI's behaviour and avoids the UX trap where a corrupted user file cannot be repaired because the template author forgot `overwrite: true`.
- **`overwrite: true` (template-side, in the descriptor) authorises silent overwrite.** When `deesse-template.json#files[].overwrite: true`, the CLI overwrites an existing file **without prompting and without requiring `--force`**. This is the right default for files that are fully template-owned (a generated route, a generated Prisma model) — the user is unlikely to want to keep a hand-edited copy, and re-running `add` should restore the template's intent.
- **Default (`overwrite: false` or absent, no `--force`)** : the CLI refuses to overwrite an existing file and surfaces a list of conflicts at install time. The user re-runs with `--force` to override, or hand-deletes the conflicting files first.

**Per-file matrix:**

| `overwrite` field | `--force` flag | Behaviour |
|---|---|---|
| `true` | absent | Silent overwrite (template-owned file). |
| `true` | present | Silent overwrite (no change). |
| `false` or absent | absent | Refuse with `parse_error`, list conflicting files in stderr. |
| `false` or absent | present | User-sovereign overwrite; warn on stderr but proceed. |

The `--force` warning is a one-line message (`"Overwriting <path> due to --force"`) printed to stderr per file. The warning is informational, not an error — the user explicitly opted in.

### What this rule allows

- A user runs `deessejs init saas-starter` in an empty directory. The CLI writes `deesse.json` (per [ADR-031](./ADR-031-deesse-json.mdx)) and clones the template (per [ADR-032](./ADR-032-deesse-template.json.mdx)).
- The same user then runs `deessejs add auth` in the resulting project. The CLI reads `deesse.json` (paths, aliases, database), fetches the `template:package` item, and applies the auth files into `paths.routes` and `paths.components`. The user's project gains an auth flow without a full re-clone.
- A user runs `deessejs add @community/stripe-billing` in a project that has `deesse.json#registries["@community"]` set to a community registry host. The CLI resolves the namespace through the user's own `registries{}` map and applies the community item.
- A user runs `deessejs add auth --dry-run` and inspects the diff before committing. The output lists every file the command would write, every dependency it would install, every hook it would run, and the diff to `deesse.json`.
- A user runs `deessejs add auth --yes` to skip prompts. The documented `default` answers apply; the `--yes` short-circuits `when` gates (per [ADR-032](./ADR-032-deesse-template.json.mdx)).
- A user re-runs `deessejs add auth` after the registry publishes a new version of the auth item. The CLI compares `deesse.json#templates["auth"].version` against the fetched `version` and surfaces the drift (without auto-applying — the user passes `--force` to re-write files).

### What this rule forbids

- `add` against a `template:app` item. Refused at parse time. The user must use `init` instead.
- `init` against a `template:package` (or any non-app) item. Refused at parse time. The user must use `add` instead. The inverse asymmetry from the previous point.
- `add` against a project without `deesse.json`. Refused at parse time. The user must run `init` first (or hand-write a `deesse.json` matching [ADR-031](./ADR-031-deesse-json.mdx)).
- `add` refusing to overwrite a file the user explicitly asked to overwrite via `--force`. The corrected policy (Decision #7) makes `--force` sovereign and removes the dual gate; this ADR no longer enforces a "both gates must clear" rule. A user who encounters a stale conflict after `--force` is failing should `git status` first — a hand-edited conflict is not what `--force` is for.
- A new public `CliErrorCode` for `add`-specific failures. The closed list per ADR-010 §2 stays closed. `add`'s failure modes map to `parse_error` (malformed item, missing `deesse.json`, wrong `type`), `install_failed` (overlay transform fail or staged-write rollback), `file_collision` (target path already exists and neither `overwrite: true` nor `--force` is set — distinct from `install_failed` because the user can resolve it by passing `--force`, not by retrying the install), or `network_error` (registry unreachable). `file_collision` is added to the **internal** error-code list (per ADR-010 §2, the closed list is on **public** codes; internal codes are not gated). No new public codes.
- A new public flag on `init` that overlaps with `add`'s flags. The flags are disjoint where they mean different things. `--force` on `init` means "overwrite the target directory"; `--force` on `add` means "overwrite individual files where the item allows". The two meanings are documented separately per ADR-010 §1's per-command flag rule.

### Why not the alternatives

Three patterns the team considered and rejected.

1. **Add `add` as a non-public command behind `DEESSEJS_EXPERIMENTAL=1`.** Avoids the breaking change by hiding the command from the help output and the docs. Rejected because hiding a public command behind an env var is worse than breaking the docs once: contributors who discover `add` write integration tests against it; users who enable the env var depend on undocumented behaviour. The proper path for "not ready for users" is a major version bump with a deprecation warning on the old commands — but there are no old commands to deprecate, so the bump is silent. Cleaner to break the docs once.

2. **Implement `add` as a subcommand of `init` (`deessejs init add <feature>`).** Rejected because shadcn's precedent is the flat `add`. A nested form breaks the muscle memory of every contributor who has used the shadcn CLI. The cost of breaking the flat form is one PR; the cost of keeping a non-standard nested form is permanent cognitive load.

3. **Skip `add` entirely.** Rejected because [ADR-031](./ADR-031-deesse-json.mdx) and [ADR-032](./ADR-032-deesse-template.json.mdx) create the conditions for `add` to exist; shipping them without `add` is shipping a registry with no overlay semantics. The CLI gains `loadDeesseJson` and the transform layer regardless; the marginal cost of `add` is small enough that deferring it is not a real saving.

### What this rule does not change

- The CLI's wire contract stays unchanged. `add` consumes the same `TemplateV2` shape (per [ADR-032](./ADR-032-deesse-template.json.mdx)) and the same `Project` shape (per [ADR-031](./ADR-031-deesse-json.mdx)). No new wire shape ships.
- The CLI's typed oRPC client at `apps/cli/src/api/client.ts` stays the only outbound transport per ADR-001. `add` reuses the client for `deesse-template.json` fetches that fall through to the oRPC source (the same source split as `init`, per [ADR-032 Decision #4](./ADR-032-deesse-template.json.mdx)).
- The cache directory (`~/.deessejs/`) and the cache file shape stay as documented by ADR-010 §4. `add` shares the `~/.deessejs/template-items/<slug>.json` cache that `init` already populates.
- The closed-list `CliErrorCode` per ADR-010 §2 stays closed. `add`'s failure modes map to existing codes (see "What this rule forbids" above).
- The `engines.node >= 20.0.0` floor at `apps/cli/package.json` stays. The CLI continues to publish as `@deessejs/cli` per ADR-010 §6.
- The `apps/cli/src/commands/init.ts` flags (`--pm`, `--dir`, `--ref`, `--no-install`, `--force`, `--json`) stay. `add` adds `--dry-run` (per Decision #4) and `--path` as new flags; the existing flags on `init` are not renamed.
- The `--offline` global flag (per ADR-010 §1) applies to `add` the same way it applies to `init` and `list`. Offline mode skips the `deesse-template.json` fetch if the cache hit is fresh.
- The registry host `registry.deessejs.dev` stays static-only (per [ADR-032 Decision #4](./ADR-032-deesse-template.json.mdx)). `add` is a read-only consumer of the host; no new endpoint ships.

## What changes at the CLI surface

This ADR is **the first breaking change to ADR-010 §1** since the ADR was accepted. The change is small (one new command) and localised (the command-list table), but it must be tracked.

- **The `ADR-010 §1` "Commands" table gains a fourth row.** The row: `deessejs add <feature>` with purpose "Layer an item onto an existing project", exit code `0` / `1`, output "diff summary to stdout in dry-run; install summary to stdout otherwise". The three existing rows stay unchanged.
- **The `ADR-010 §1` "What this rule forbids" bullet on "Adding a new command" is updated.** The bullet currently forbids adding a fourth command without a V-bump. This ADR is that V-bump. The next contributor who adds a fifth command still needs a new ADR; this ADR does not open a precedent.
- **The `apps/cli/src/commands/` folder gains one file.** `apps/cli/src/commands/add.ts` follows the same one-file-per-command invariant as `list.ts`, `info.ts`, `init.ts`. The folder structure (per ADR-010's "Folder and file structure") is unchanged: one folder per concept, no `.ts` at the package root except `index.ts`.
- **The CLI help output regenerates.** Every script that introspects `deessejs --help` sees the new command. This is the visible surface of the breaking change.

The changeset that ships `add` to npm carries a `minor` bump (per the release discipline in ADR-021). **SemVer justification:** adding a public command is an additive feature in the strict SemVer sense — existing scripts that do `case "$cmd" in init|list|info) ... ;; esac` fail with "unknown command" on `add`, but the existing three commands behave identically. This is a `minor` bump, not a `major`. The "breaking" language in [ADR-010 §1](./ADR-010-cli-public-surface.mdx) is about the closed-list governance rule (adding a fourth command requires an ADR), not about SemVer compatibility. The two notions are independent: the ADR sanctioned the surface change; the npm bump reflects the binary compatibility. The changelog entry names the new command and calls out the closed-list update for downstream consumers who introspect the help output: "four public commands where there were three; existing scripts that pattern-match on the command list must add a fourth branch."

## Consequences

- **`apps/cli/src/commands/add.ts` is a new file.** One file per command per ADR-010. The file follows the Commander.js inline pattern (`addCommand(new Command("add").description(...).argument(...).option(...).action(...))`) like its three siblings. The action delegates to a shared helper at `apps/cli/src/commands/_apply-item.ts` (new file, internal, not a public command) that both `init` and `add` call. The shared helper encapsulates the steps from Decision #3 minus the clone step (which `init` runs and `add` skips).
- **`apps/cli/src/transforms/` is the home of the four transform verbs.** Already mandated by [ADR-032 Consequences](./ADR-032-deesse-template.json.mdx). `add` consumes the same verbs as `init`; no new transform verbs ship.
- **`deesse-template.json#files[].overwrite` is a new optional field.** Co-shipped with this ADR (the field exists in the [ADR-032](./ADR-032-deesse-template.json.mdx) Zod schema but is documented here for the first time). Each `files[]` entry may carry `"overwrite": true` to opt into the `--force` overwrite behaviour. Default is `false`. The field is the per-file allow-list that backs the second `--force` gate in Decision #3.
- **`deesse-template.json#type` enforcement is a new code path in `apps/cli/src/commands/init.ts`.** The `init` command gains a check at parse time: if `TemplateV2#type` is not `template:app`, refuse with `parse_error`. The inverse check on `add` lives in `add.ts`. The two checks together enforce the [Decision #2](#2-the-command-is-an-overlay-not-a-clone) split.
- **A new CLI integration test lives in `apps/cli/test/integration/add.test.ts`.** Asserts (a) the `template:app` refusal on `add`, (b) the `template:package` refusal on `init`, (c) the missing `deesse.json` refusal on `add`, (d) the `--dry-run` exit-zero-no-write behaviour, (e) the `--force` overwrite gated by `deesse-template.json#files[].overwrite`. The test pool follows the test strategy in ADR-009 (forks pool, 30s timeout).
- **The CLI disk cache gains no new file.** `add` shares the `~/.deessejs/template-items/<slug>.json` cache that `init` populates (per [ADR-032 Consequences](./ADR-032-deesse-template.json.mdx)). The cache shape change is internal per ADR-010 §4.
- **`apps/cli/CHANGELOG.md` gains a `minor` entry under the next release.** The entry names the new command, the `--dry-run` flag, the `deesse-template.json#files[].overwrite` field, and the `template:type` enforcement on `init`. The entry calls out the closed-list surface update for consumers who introspect the help output.
- **`apps/cli/README.md` documents `add` alongside `init`, `list`, `info`.** The README gains a fourth section matching the four-command surface. Each section follows the same shape (purpose, syntax, flags, examples).
- **The CLI version probe at `apps/cli/src/version/check.ts` is unchanged.** `add` is a new command, not a new version requirement. The probe's "minimum supported version" stays where ADR-010 §3 pins it.
