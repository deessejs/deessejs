# ADR-021: Inter-app URL configuration

## Status

Draft (2026-08). Awaiting review.

## Context

The monorepo deploys three Next.js apps on three distinct Vercel
domains:

| App | Path | Domain | Catch-all API |
|---|---|---|---|
| `apps/web` (marketing) | `apps/web/src/app/` | `deessejs.com` | none — there is no `src/app/api/` directory under `apps/web` |
| `apps/app` (auth + UI) | `apps/app/app/` | `app.deessejs.com` | `apps/app/app/api/[[...route]]/route.ts` mounts Hono + oRPC |
| `apps/internal-documentation` | `apps/internal-documentation/app/` | `docs.deessejs.com` | none — no catch-all |

The Hono backend lives in `packages/api` and is mounted by the
catch-all in apps/app. The full backend URL is therefore
`https://app.deessejs.com/api/v1/...`; the marketing site at
`https://deessejs.com` has no backend mounted at all.

`packages/api/src/constants/base-path.ts` is the single source of
truth for the **path** part:

```ts
export const API_BASE_PATH = "/api/v1"
export const API_RPC_PATH  = `${API_BASE_PATH}/rpc`   // "/api/v1/rpc"
export const API_AUTH_PATH = `${API_BASE_PATH}/auth`  // "/api/v1/auth"
```

The path constants are correct. The URL construction in every
consumer is the problem. The pattern in use today:

| Consumer | URL form | Resolves to |
|---|---|---|
| `apps/app/lib/orpc.ts:20` | `url: API_RPC_PATH` (relative) | `https://app.deessejs.com/api/v1/rpc` ✓ |
| `apps/app/lib/auth-client.ts:22` | `baseURL: clientEnv.NEXT_PUBLIC_APP_URL` (full URL) | depends on env var |
| `apps/app/proxy.ts:57-60` | `new URL(path, request.url)` (relative-to-host) | `https://app.deessejs.com/api/v1/auth/get-session` ✓ |
| `apps/cli/src/api/client.ts:44` | `url: API_RPC_PATH` (relative) | **breaks** — the CLI runs from the user's working directory, not from a domain |
| `apps/web/src/lib/orpc.ts:103` | `url: API_RPC_PATH` (relative) | **breaks** — resolves against `deessejs.com`, where the backend is not mounted |

Two consumers construct the URL wrong:

1. **apps/web** fetches `/api/v1/rpc/templates/list` relative to
   `deessejs.com`. The domain returns a Next.js 404 for every
   `/api/v1/*` path (the catch-all exists only in apps/app). The
   oRPC client throws before the templates list can render. The
   `/templates` page has displayed the documented empty state since
   the apps split; `/templates/[slug]` returns a Next.js 500 because
   the fetch error escapes the segment `error.tsx` boundary.
2. **apps/cli** fetches `/api/v1/rpc/templates/list` relative to
   the user's working directory. The path resolves against the
   filesystem, where there is no HTTP server. Every published
   `deessejs list` invocation fails.

The URL surface in `packages/env/src/schema.ts` does not cover
either case:

```ts
// packages/env/src/schema.ts
NEXT_PUBLIC_APP_URL          z.string().url()  // client, default "http://localhost:3000"
BETTER_AUTH_URL              z.string().url()  // server, default "http://localhost:3000"
ALLOWED_ORIGINS              csv.default([])
```

Three load-bearing URLs are missing:

- `NEXT_PUBLIC_API_BASE_URL` — the URL of the backend API as seen
  by clients in the same browser (used by apps/web's RSC and
  client fetches).
- `API_BASE_URL` — the same URL, server-side, used by apps/cli and
  by the CLI's own runtime, and by apps/web's server components
  when the call runs on Node.
- `WEB_URL` — the canonical marketing URL, used by apps/app when
  it links back to the marketing site (e.g. for cross-app SSO
  redirects, post-signup landing, email links from better-auth).

`apps/web` today hard-codes ecosystem URLs (footer, header,
`ecosystem/page.tsx`) as full string literals — for example
`https://drpc.deessejs.com`, `https://errors.deessejs.com`. Those
are static and do not change per environment, so they can stay as
literals; this ADR scopes itself to the URLs that vary per
environment.

The foot-gun is the relative-path pattern in `apps/web/src/lib/orpc.ts`
and `apps/cli/src/api/client.ts`. The pattern works in one place
(`apps/app`) and breaks in two places (`apps/web`, `apps/cli`).
A contributor reading either of the two broken files will see a
"single source of truth" comment and trust it; the bug only
surfaces in the deployed environment.

## Decision

The inter-app URLs are first-class members of `@workspace/env`,
with one server variable and one client variable per app. Every
consumer builds its URL by concatenating the env constant with
the existing `packages/api` path constant. Relative-path
construction is removed.

### What this rule decides

Four concrete decisions.

**1. One env variable per app, with both a `NEXT_PUBLIC_*`
(client) and a server variant.**

| App | Server name | Client name | Default (dev) | Default (prod) |
|---|---|---|---|---|
| Marketing | `WEB_URL` | `NEXT_PUBLIC_WEB_URL` | `http://localhost:3000` | `https://deessejs.com` |
| Auth/UI | `APP_URL` | `NEXT_PUBLIC_APP_URL` | `http://localhost:3001` | `https://app.deessejs.com` |
| Docs | `DOCS_URL` | `NEXT_PUBLIC_DOCS_URL` | `http://localhost:3002` | `https://docs.deessejs.com` |
| API | `API_BASE_URL` | `NEXT_PUBLIC_API_BASE_URL` | `http://localhost:3001` (apps/app's port) | `https://app.deessejs.com` |

The client variants carry the `NEXT_PUBLIC_` prefix because they
are inlined into the browser bundle by Turbopack. The server
variants are read at runtime from `process.env`. The naming
mirrors the existing `NEXT_PUBLIC_APP_URL` / `BETTER_AUTH_URL`
split, extended to all four surfaces.

The "default per environment" column is what the env loader
itself resolves to. In dev the defaults are localhost ports; in
prod the defaults are the real Vercel domains. **The defaults
are encoded in the schema**, not in a separate config file.
Adding a new environment (e.g. a staging preview) means setting
the env vars on Vercel; the schema does not change.

**2. The client oRPC link in apps/web uses
`new URL(API_RPC_PATH, NEXT_PUBLIC_API_BASE_URL)`.**

```ts
// apps/web/src/lib/orpc.ts
import { API_RPC_PATH } from "@workspace/api/base-path"
import { clientEnv } from "@workspace/env/client"

const link = new RPCLink({
  url: new URL(API_RPC_PATH, clientEnv.NEXT_PUBLIC_API_BASE_URL).toString(),
  // …existing fetch hook with ISR directives
})
```

The relative `url: API_RPC_PATH` line is removed. The URL
construction uses `new URL(path, base).toString()` rather than
string concatenation. Three reasons:

1. **Trailing-slash safety.** `new URL("/api/v1/rpc", "https://app.deessejs.com/")`
   collapses to `"https://app.deessejs.com/api/v1/rpc"`. String
   concatenation would produce `"https://app.deessejs.com//api/v1/rpc"`,
   which breaks Hono path matching and confuses reverse proxies
   (Vercel's edge, CDNs). The leading-slash rule of `new URL`
   means a slash on either side is normalised at the call site.
2. **One normalisation surface.** A `.refine()` in the schema
   rejects trailing slashes at parse time (Decision #1), so the
   env value itself is canonical. `new URL` is the second
   layer of defence at the call site. The two together make
   any malformed deployment visible immediately rather than at
   the first HTTP failure.
3. **Same shape across consumers.** The same `new URL(path, base)`
   idiom is used in apps/cli (Decision #3) and apps/app's proxy
   (Decision #4). A contributor who has seen one example has
   seen all three.

The single-source-of-truth comment is updated to read:

> `API_RPC_PATH` is the path part of the URL. The host part is
> `clientEnv.NEXT_PUBLIC_API_BASE_URL` (declared in
> `@workspace/env`); together they form the full oRPC endpoint
> URL. Renaming the API prefix means editing
> `API_BASE_PATH_V*` and updating the env var on Vercel.

The same shape applies to apps/app (`NEXT_PUBLIC_API_BASE_URL`
on apps/app happens to equal `NEXT_PUBLIC_APP_URL`, so the
construction is identical) and to apps/cli (which reads the
server-side `API_BASE_URL`).

**3. The CLI reads `API_BASE_URL` from `process.env`
directly.**

```ts
// apps/cli/src/api/client.ts
import { API_BASE_PATH, API_RPC_PATH } from "@workspace/api/base-path"

const API_BASE_URL =
  process.env.API_BASE_URL?.replace(/\/$/, "") ??
  "https://app.deessejs.com"

const link = new RPCLink({
  url: new URL(API_RPC_PATH, API_BASE_URL).toString(),
  // …existing plugins
})
```

The CLI does **not** import `@workspace/env/server`. Two reasons:

1. **`@workspace/env` is private to the monorepo** (`private:
   true` in `packages/env/package.json`). The CLI is published on
   npm and cannot depend on it at runtime — the dependency would
   fail to resolve for any user who installs the tarball.
2. **The env loader pulls `node:fs`** via `loader.ts`. The CLI's
   tsup bundle avoids Node built-ins for size and startup cost.

The CLI's contract is the env var name (`API_BASE_URL`), not
the loader. The published tarball ships with the default
`https://app.deessejs.com`; users override via shell env
(`API_BASE_URL=https://my-staging.dev.example deessejs list`).

The same pattern applies to the system-level version probe at
`apps/cli/src/version/check.ts`, which hits `${API_BASE_PATH}/version`
(Hono-direct, not oRPC). That probe was silently broken by the
same relative-path bug (it resolved against the user's working
directory); it now uses `new URL(path, apiBaseUrl)` with the
same `process.env.API_BASE_URL` fallback.

The CLI is a published Node binary. It reads `API_BASE_URL` from
`process.env` at startup (the env loader exposes the server
schema). The published tarball ships with the default
`https://app.deessejs.com`; users override via shell env
(`API_BASE_URL=https://my-staging.dev.example deessejs list`).

This closes the latent CLI bug called out in ADR-014:44 —
"the fallback uses a production default … a reasonable candidate
is `https://deessejs.com`". The fallback is now `app.deessejs.com`
(the real backend domain) instead of the marketing site.

**4. The proxy in apps/app uses the same `API_BASE_URL`
constant.**

```ts
// apps/app/proxy.ts
import { API_BASE_PATH, API_AUTH_PATH } from "@workspace/api/base-path"
import { serverEnv } from "@workspace/env/server"

const getSessionUrl = new URL(
  `${API_AUTH_PATH}/get-session`,
  serverEnv.API_BASE_URL,
)
```

The current `new URL(path, request.url)` form is removed. The
proxy becomes a single explicit URL constructed via
`new URL(path, serverEnv.API_BASE_URL)` — the same idiom as
Decision #2 and Decision #3, with the same trailing-slash
safety. Two apps share `API_BASE_URL` so this expression is the
same on staging, prod, and dev. This removes the dependency on
the proxy running on the same domain as the backend — a future
split of apps/app and the API (e.g. an `api.deessejs.com`
deployment) is a one-line env var change.

### What this rule allows

- **`@workspace/env` declares four pairs of URL constants.** The
  pair that an app actually reads is the pair relevant to its
  surface (apps/web reads `NEXT_PUBLIC_API_BASE_URL`; apps/app
  reads `NEXT_PUBLIC_API_BASE_URL` and `WEB_URL`; apps/cli reads
  `API_BASE_URL`). Cross-reading is allowed when the use case
  demands it (apps/app's auth pages link back to marketing with
  `WEB_URL`).
- **A docstring on each env var explaining the per-environment
  default.** The convention already applies to `BETTER_AUTH_URL`
  and `NEXT_PUBLIC_APP_URL`; this ADR extends the convention to
  the four new pairs.
- **A Vercel env var on every deployment.** `WEB_URL`,
  `APP_URL`, `DOCS_URL`, `API_BASE_URL` are added to each
  Vercel project that reads them (apps/web, apps/app,
  apps/cli). Production values are the canonical domains;
  preview values are the Vercel-generated URLs of the same name.
- **A schema-level validation that the URL parses** and that the
  dev defaults are `localhost`-prefixed (catches a contributor
  accidentally committing a production URL as a default). Each
  new field carries a `.refine(url => !url.endsWith("/"), "URL
  must not end with a trailing slash — the call sites use new
  URL(path, base) which already normalises, but a slash in the
  default hides the bug from the reviewer who never runs the
  e2e suite"). The refine is a guard, not a transform: the env
  value is rejected at parse time with a clear message rather
  than silently mutated, so a contributor who copies a
  production URL with a trailing slash sees the failure on
  their machine before CI does.
- **`getApiBaseUrl()` and `getWebUrl()` ergonomic helpers in
  `@workspace/env`** that return the full URL for the most common
  cross-app links. The helpers are thin wrappers that read the
  server or client env and return a normalised string. They are
  not part of the wire surface — consumers can still read the
  raw env constant.

### What this rule forbids

- **Relative URLs in oRPC links.** `url: API_RPC_PATH` (without a
  host) is forbidden after this ADR lands. The pattern is the
  source of the apps/web and apps/cli bugs.
- **A separate "URL config" file or package.** The convention is
  `@workspace/env` for env vars; a parallel config layer
  duplicates the surface. New inter-app URLs go through
  `@workspace/env`.
- **Hardcoded `https://deessejs.com` strings in apps/app.** Any
  reference to the marketing URL in apps/app reads `WEB_URL`.
  The string literal is allowed only in `packages/env`'s schema
  default (the canonical default is the one place the literal
  lives) and in the documentation.
- **`process.env` reads outside `@workspace/env`.** The repo
  convention is to centralise env reads in `@workspace/env`.
  The CLI is the **explicit exception**: it reads
  `process.env.API_BASE_URL` directly (with a fallback) because
  the published tarball cannot depend on the private
  `@workspace/env` package, and the env loader's `node:fs`
  footprint would bloat the bundle. Every other consumer
  (apps/web, apps/app) reads through `@workspace/env`.

### Why not the alternatives

Four patterns were considered and rejected.

1. **A Vercel rewrite to proxy apps/web's `/api/v1/*` to
   apps/app.** The zero-code option (`apps/web/vercel.json`
   `rewrites: [{ source: "/api/v1/:path*", destination:
   "https://app.deessejs.com/api/v1/:path*" }]`) hides the bug
   instead of fixing it. It also only works in production — a
   `next dev` run still sees the 404 because Vercel rewrites do
   not apply to the local dev server. The CLI is unaffected by
   the rewrite (the CLI does not run on a Vercel domain). The
   ADR rejects the rewrite because it leaves the bug latent in
   dev and invisible in code review.

2. **A `packages/config/urls` package** that exports
   `getApiUrl()` / `getWebUrl()` etc. A new package for one
   concern (URLs) when `@workspace/env` already carries
   environment-derived values is unnecessary surface. The env
   loader already validates the URL shape via `z.string().url()`;
   adding a parallel package re-implements the validation.

3. **A separate per-app `.env.local` file convention.** Each app
   already reads its env through `@workspace/env`; per-app
   `.env.local` is the Vercel deployment shape, not a code shape.
   The ADR scopes itself to code; the deployment shape is
   documented in the runbook (see Consequences).

4. **Drop the `NEXT_PUBLIC_API_BASE_URL` (client) variant and
   have apps/web fetch through a Vercel rewrite or server-side
   proxy.** This conflates two concerns (client-side fetch URL
   vs. server-side rewrite) and removes the principle of least
   surprise: a RSC fetch from `apps/web` should be able to read
   the same URL the browser would. The two variants are kept
   because they answer different questions ("where the browser
   fetches" vs. "where the server fetches"), and they happen to
   share the same value in this codebase.

### What this rule does not change

- **The `packages/api` path constants.** `API_BASE_PATH`,
  `API_RPC_PATH`, `API_AUTH_PATH`, `API_HEALTH_PATH`,
  `API_READY_PATH` are unchanged. The path constants and the host
  constants live in different packages because they answer
  different questions (where the Hono mount lives vs. where the
  Vercel project lives); the ADR keeps the separation.
- **The `apps/app/app/api/[[...route]]/route.ts` catch-all.** The
  Hono mount in apps/app is the canonical home of the API; the
  ADR does not propose mounting a duplicate catch-all in
  apps/web. The marketing site reaches the API via cross-app
  fetch, not by hosting the backend.
- **The ecosystem page URLs in apps/web** (`errors.deessejs.com`,
  `drpc.deessejs.com`, etc.). Those are static, environment-
  independent literals. They are not inter-app URLs in the
  sense this ADR cares about (they do not vary per deployment).
  They stay hardcoded.
- **Better-auth's `baseURL` and `BETTER_AUTH_URL`.** They keep
  their existing meaning — `BETTER_AUTH_URL` is "the public URL
  of the better-auth instance" (apps/app's own domain). It is
  not the same as `APP_URL` in general (a future split of
  `app.deessejs.com` and `auth.deessejs.com` would make them
  diverge). The convention is: `BETTER_AUTH_URL` =
  `NEXT_PUBLIC_APP_URL` for now; the ADR documents the equality
  rather than refactoring it.

## Consequences

- **apps/web's `/templates` page renders the populated catalog.**
  The client oRPC link now points at `app.deessejs.com`'s
  `/api/v1/rpc`, where the handler is mounted and the
  `templates.list` procedure returns `{ templates: [...] }`. The
  empty state (`templates-empty` test-id) disappears; the
  populated grid (`templates-grid`, `templates-card`) renders.
  This is the immediate, user-visible consequence of the ADR.
- **apps/web's `/templates/[slug]` returns 200 instead of 500.**
  The Next.js 500 came from the same fetch failure escaping the
  segment `error.tsx` boundary. With the fetch reaching the
  backend, the page renders the documented detail UI.
- **The published CLI works out of the box.** `deessejs list`
  shipped to npm reads `API_BASE_URL=https://app.deessejs.com`
  by default; users override via shell env. The previous "fetch
  relative to working directory" failure mode is gone.
- **`packages/env`'s schema gains four new fields.** The schema
  validates each as a URL (`z.string().url()`) and assigns a
  default that matches the dev convention. Contributors adding
  a new URL constant follow the same convention; the existing
  README documents the pair.
- **A unit test pins the schema.** `packages/env/tests/unit/
  schema.test.ts` is extended with a case per new field that
  asserts the default parses, the production override parses,
  and an invalid value (a non-URL string) is rejected at parse
  time. The test prevents a typo from silently shipping.
- **Each Vercel project gets four new entries.** The runbook
  (delivered alongside the implementation PR) lists the four
  values per project (`apps/web`, `apps/app`, `apps/cli`) for
  production and for the default preview. The CI verifies job
  (ADR-013) does not change; Vercel env vars are not visible
  to the verify job because the CLI tarball is exercised
  against a mocked HTTP server, not the real Vercel deployment.
- **The marketing site's hardcoded ecosystem URLs stay.** They
  are not inter-app URLs in the sense of this ADR; they are
  third-party product URLs (deessejs-adjacent properties) that
  do not vary per environment. Future contributors are not
  encouraged to migrate them.
- **`BETTER_AUTH_URL` and `NEXT_PUBLIC_APP_URL` keep their
  current shape.** The ADR adds the four new pairs alongside,
  not in place of, the existing two. The JSDoc on each existing
  field is updated to reference this ADR so a future contributor
  understands why `BETTER_AUTH_URL` (auth) and `APP_URL` (app)
  happen to share a value today and where they would diverge if
  the deployment shape changed.

## Cross-origin considerations

The new URL configuration introduces a cross-origin fetch:
`apps/web` (`deessejs.com`) calls `app.deessejs.com` over HTTPS
from the browser. This is a browser-enforced cross-origin
boundary, not a same-origin request. Three sub-points follow.

**1. The `/templates` fetch is not credentialed.** The marketing
site's oRPC call to `templates.list` carries no cookies. There is
no better-auth session on `deessejs.com` (better-auth is mounted
on `app.deessejs.com`), and the templates procedure is a public
read. The browser sends a *cross-origin no-credentials request*,
which is governed by the CORS specification's simpler branch:
the server must respond with `Access-Control-Allow-Origin` set
to the requesting origin (or `*`) for the response body to be
readable.

**2. `ALLOWED_ORIGINS` must include `https://deessejs.com`.** The
Hono `cors({ origin: serverEnv.ALLOWED_ORIGINS })` middleware in
`packages/api/src/http/mount-rpc.ts` (cf. `apps/internal-
documentation/content/docs/knowledge-base/hono/middleware-
composition.mdx`) reads `ALLOWED_ORIGINS` from the schema. The
default today is `[]`; this ADR requires the deployment to set
`ALLOWED_ORIGINS=https://deessejs.com` (and the preview origins
of the marketing site). The CORS concern is operational
(Vercel env), not a code change to the schema: `ALLOWED_ORIGINS`
already exists, this ADR just specifies the value that must be
present.

**3. Credentialed cross-origin is not in scope.** better-auth's
session cookies live on `app.deessejs.com` and are scoped to that
origin. A future call site that needs to read those cookies from
a browser on `deessejs.com` would face a cross-origin
credentialed request, which requires `credentials: "include"`
on the fetch side AND `Access-Control-Allow-Credentials: true`
AND a non-wildcard `Access-Control-Allow-Origin` on the server
side. This ADR does not introduce that pattern. The marketing
site's surface (templates, knowledge-base, marketing copy) does
not need it. If a future feature requires it, that ADR adds the
mechanism explicitly; this ADR scopes itself to the no-
credentials case the visible bug actually exercises.

The cross-origin picture is therefore: same set of HTTP headers
that today answer same-origin fetches from `app.deessejs.com`,
plus one entry in `ALLOWED_ORIGINS` on the Vercel project. The
implementation PR for this ADR documents the value in the
runbook (companion file to `apps/web/tests/e2e/RUNBOOK.md`).

## Follow-ups

Two concerns surfaced during review and are intentionally
**out of scope** for this ADR. Both deserve their own ADR.

**1. ADR-022 (TBD): preview-deployment URL wiring.** On Vercel,
every PR generates a preview domain per project
(`<project>-git-<branch>-<scope>.vercel.app`). After this ADR
lands, a preview of `apps/web` will fetch the production
`API_BASE_URL` by default (the schema default). Three options
are visible today: (a) preview apps/web against production
(default, simple, but tests the PR against prod data), (b)
preview apps/web against a shared staging URL (a fixed
`staging.app.deessejs.com` deployment), (c) preview apps/web
against the corresponding preview of apps/app via a Vercel
project-link injection (the "preview" deployment runs against
the preview). None is trivial; none affects the code surface
this ADR changes. A future ADR picks one and adds the CI wiring.

**2. ADR-023 (TBD): hardcoded ecosystem URLs.** The marketing
site hardcodes `https://errors.deessejs.com`,
`https://drpc.deessejs.com`, `https://ui.deessejs.com`, etc.,
in the footer, header, and `ecosystem/page.tsx`. These are
third-party product URLs (deessejs-adjacent properties), not
inter-app URLs in the sense this ADR cares about (they do not
vary per environment). A future ADR that wants them dynamic
(e.g. for self-hosted deessejs deployments) belongs separately.

  URLs (`errors.deessejs.com`, `drpc.deessejs.com`, etc.).
  Those concerns are out of scope for this ADR; touching them
  belongs to a follow-up.
- **2026-08-21 (review)**: incorporated senior-review feedback
  on three points. (a) Replaced the `${host}${path}`
  concatenation at Decisions #2, #3, #4 with
  `new URL(path, host).toString()` and added a `.refine()` in
  the schema to reject trailing slashes at parse time. The two
  together make any malformed deployment visible immediately
  rather than at the first HTTP failure. (b) Acknowledged the
  Vercel preview-deployment URL wiring concern as
  `Follow-ups` §1 (a future ADR-022). (c) Added `Cross-origin
  considerations` to scope the CORS surface: the marketing
  fetch is a no-credentials cross-origin request, `ALLOWED_ORIGINS`
  must include `https://deessejs.com` (operational change, no
  schema change), and the credentialed cross-origin case is
  explicitly out of scope.
