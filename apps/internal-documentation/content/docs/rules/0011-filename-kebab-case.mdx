## Rule

Every file in this repository carries a name in **kebab-case**:
lowercase letters, digits, and hyphens. No spaces, no underscores,
no uppercase, no camel case, no Pascal case.

The rule applies to:

- Source files (`.ts`, `.tsx`, `.js`, `.mjs`).
- Test files.
- Configuration files (when the tool allows the name).
- Documentation files (`.md`, `.mdx`).
- Directory names.
- Asset filenames.

The rule applies to **filenames**. The contents of a file stay
free to use whatever convention the language requires: a `.ts`
file may export `PascalCaseComponent`, a `.tsx` file may declare
`PascalCaseComponents`. The boundary sits at the name on disk.

## Why

A consistent filename convention removes a category of decisions
that the contributor doesn't need to make. Every commit, every PR,
every grep, every file-listing in a tool reads the same way. The
casing of a file tells the reader nothing about its content, but
the **inconsistency** of casing tells the reader that someone
made a choice that didn't need to get made.

Kebab-case wins out because:

- It's the convention the broader JavaScript ecosystem uses for
  filesystem names (Next.js, a popular build tool, many build
  tools emit kebab-case routes by default).
- It survives cross-platform case-insensitive filesystems
  (macOS, Windows) without ambiguity. A file named
  `ErrorFactory.ts` and one named `errorFactory.ts` are the same
  file on a case-insensitive filesystem.
- It composes with the file-separation rule (0002) and the
  file-placement rule (0003): a concern folder reads as a list of
  kebab-case nouns, each describing what the file does.

## What the rule forbids

- **camel case**: `errorFactory.ts`, `errorHandler.ts`.
- **Pascal case**: `ErrorFactory.ts`, `ErrorHandler.ts`. Even
  when the file exports a `PascalCase` symbol, the filename stays
  kebab-case.
- **snake case**: `error_factory.ts`. Underscores fail the rule.
- **Mixed case in one file**: `Error-factory.ts` isn't
  kebab-case.
- **Uppercase abbreviations**: `URLParser.ts` becomes
  `url-parser.ts`.

## What the rule allows

- **Numbers** in the filename, between hyphens:
  `http2-server.ts`, `error-codes-1.ts`. Numbers are part of the
  name, not a separator.
- **Version-style numbers without hyphens**: `v2-handler.ts` is
  fine; `v2handler.ts` isn't.
- **Test files** that match the source file they test with a
  `.test.ts` suffix: `error-factory.ts` gets tested by
  `error-factory.test.ts`. The base name stays kebab-case.
- **Index files**: `index.ts` is the single exception. It's the
  convention every bundler, every import path, and every language
  module system recognises. The filename `index.ts` is a
  vocabulary word, not a casing choice.
- **Filesystem-mandated names**: `.gitignore`, `.npmrc`,
  `eslint.config.js`, `tsconfig.json`, `package.json`. These
  names get dictated by the tools that consume them, not by the
  project. They aren't subject to the rule.
- **Documentation files in this rules folder**: the rules
  themselves use `NNNN-kebab-case-slug.md` as filenames, including
  the digit prefix and the kebab-case slug. The rule applies to
  its own naming; the rule doesn't exempt itself.

## How to fix a wrong-cased filename

When you rename a file to fix its case, two things happen:

1. The file appears as a deletion and an addition in `git status`
   even though the content stays the same. This is correct: git
   tracks case-sensitive differences on case-insensitive
   filesystems.
2. Imports of the file (if any) must update in the same PR.
   Stale imports won't compile.

A rename PR lands as one commit that:

- Renames the file with `git mv` (or the like).
- Updates every import site in the same commit.
- Runs the test suite to confirm nothing breaks.

When the file gets renamed across the history, a `git log
--diff-filter=R` can surface the rename chain. The
current filename is what the rule cares about; history doesn't
get rewritten.

## What this looks like in violation

Three shapes that this rule exists to catch.

The first, common:

```
src/
├── errorFactory.ts       # camel case
├── ErrorHandler.ts       # Pascal case
└── error_factory.ts      # snake case
```

Three files, three conventions, all in the same directory. A
reader who greps for `error` sees hits in three different cases;
the mental model has to track which is which.

The second, mixed:

```
src/
├── apiClient.ts          # camel case
├── http-client.ts        # kebab-case
├── HttpServer.ts         # Pascal case
└── http_server.ts        # snake case
```

The same project, four files, four conventions. Each was
probably written by a different author at a different time. The
drift tells the reader that no one reads the existing names
before adding new ones.

The third, case-insensitive-filesystem trap:

A file `ErrorFactory.ts` gets created on macOS or Windows. The
next contributor, on Linux, creates `errorFactory.ts`. Git
tracks both. On macOS, the second contributor sees only one file
because the filesystem sees them as the same. The merge conflict
appears only when someone tries to checkout on Linux. The fix is
to enforce kebab-case at the rule level so the trap becomes
impossible to enter.

**Bad**, three folders, three conventions, same project:

```
src/
├── errorFactory/        # camel case
│   └── index.ts
├── ErrorHandler/        # Pascal case
│   └── index.ts
└── http_client/         # snake case
    └── index.ts
```

A grep for `error` returns hits in three different cases. A file
listing reads as three unrelated projects. The mental model has
to track which casing means which.

**Good**, one folder per concern, kebab-case throughout:

```
src/
├── error-factory/       # kebab-case
│   └── index.ts
├── error-handler/       # kebab-case
│   └── index.ts
└── http-client/         # kebab-case
    └── index.ts
```

A grep for `error` returns hits in one case. A file listing reads
as one project. The mental model stays uniform; the casing
doesn't need to get learned.

## Enforcement

- **Code review**. A reviewer who sees a non-kebab-case filename
  blocks the PR. The fix is `git mv`, not "fix it later."
- **CI lint** (existing). The existing lint workflows catch
  obvious casing inconsistencies in the diff. The rule is the
  review-time signal that those catches do real work.
- **Quarterly audit**. A standing review of "which files in this
  repo have non-kebab-case names?" surfaces the candidates that
  slipped through. Each becomes a one-commit rename PR.

## Exceptions

The exceptions are **vocabulary words, not casing choices**:

- `index.ts` in any directory.
- Tool-mandated names: `.gitignore`, `.npmrc`, `.editorconfig`,
  `.prettierignore`, `.eslintrc.*`, `.husky`, `.lintstagedrc.*`,
  `tsconfig*.json`, `vitest.config.ts`, `next.config.*`,
  `package.json`, `pnpm-*.yaml`, `.changeset/*.md` (changeset
  filenames get dictated by the changesets tool).
- Branded filenames that the tool requires (none today; revisit
  when one shows up).

The exceptions get listed because a reviewer should know what
isn't subject to the rule. They aren't loopholes; they're
constraints from tools the project depends on.

## Sources

This rule is a synthesis of the project's own working
experience. The casing choice (kebab-case) is the convention
the broader JavaScript ecosystem follows (Next.js, a popular
build tool, most build tools emit kebab-case routes by
default); the rule isn't anchored to a single external
reference because the convention is universal enough that
citing one would imply the others are wrong. The
case-insensitive-filesystem trap is a Git behaviour; the rule
documents the failure mode without attributing it.
