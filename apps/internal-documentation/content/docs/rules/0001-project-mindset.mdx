Every contribution to this repository must read **as if it
were the last commit before the project reached its largest
possible audience**. The standard asks, would the author be
comfortable explaining this line to a contributor joining
in two years, in front of a million users, with no
opportunity to revise it first?

No "good enough for now." No "fix it later." The work
done today is the work that ships at scale.

## The ten invariants

Every contribution must meet these. They're not
guidelines; they're the floor.

1. **No shortcuts.** A cast that bypasses the type system is a
   lie to the audience. Either the return type matches what
   you say it's, or it isn't, and the code reflects that
   directly.

2. **No conscious debt.** "Fix it later" is a promise to a
   future that may not exist. The only moment pays for doing
   something well is the moment of doing it. No later
   justifies a shortcut now.

3. **Understand before writing.** If the API called goes
   misunderstood in full, the code isn't ready to write.
   Reading the source, asking the maintainer, or waiting for
   an answer are all acceptable next steps. Guessing isn't.

4. **No speculative abstractions.** An abstraction added "in
   case" is a wall the next contributor will climb.
   Abstract only when three concrete cases exist (Rule of
   Three). Until then, the duplication costs less than the
   abstraction.

5. **No `any`.** `unknown` is the safe escape hatch. If a type
   lacks an expression, model it explicitly, through a
   schema, a discriminated union, or a generic, rather than
   closing the eyes.

6. **No silent failures.** A `try`/`catch` that swallows an
   error betrays the user. Either re-raise, transform
   with explicit context, or log through a structured channel.
   Never swallow.

7. **No compiler bypass.** `@ts-expect-error`, `as` casts,
   `// @ts-ignore`, dynamic `require`, and friends signal
   that the code has a problem. Address the problem; don't
   silence the alarm.

8. **No dependency without justification.** A new dependency is
   a long-term commitment. Before adding it, the contributor
   must answer, what's its license, its release cadence, its
   bus factor, and why this one and not its alternatives.
   If the answer is "it has stars," it isn't ready.

9. **Optimise for the reader.** The next maintainer is the
   audience. If a PR is harder to read than to write, it's
   the wrong PR. Comments explain _why_, not _what_. Names
   carry meaning; comments carry context that names can't.

10. **Excellence is silent.** No commit message that
    celebrates. No PR description that congratulates itself.
    The work is the artefact. If it needs explanation to
    earn recognition as good, the work falls short.

## The trust-the-type principle

The single sentence that puts the ten invariants into effect:

<Callout type="info" title="The trust-the-type principle">
  "If the type says it's not null, trust the type. If the
  type is wrong, fix the type. Don't add runtime null checks
  for values that can't be null."
</Callout>

. Miguel Pizza, _No Defensive Null Checks_, Maintainable
TypeScript doctrine.

Every invariant in this rule is a consequence of that
principle. The compiler is the first reviewer (invariant 9);
the compiler says "not null," the runtime says "I trust you,"
or, if the compiler is wrong, the fix is in the type, not
in the runtime. No conscious debt (invariant 2) means no
guard that papers over a type the codebase fears to fix. No
speculative abstractions (invariant 4) means no abstract
`defensive(...)` helper that catches everything on the
assumption that anything might happen.

The principle is the slogan of the project. A reader who
remembers only one sentence from this rule set should remember
this one.

## Enforcement

- **Code review** is the primary gate. A reviewer who sees
  any of the ten invariants violated blocks the
  PR, regardless of urgency or seniority of the author.
- **Welcome documentation** must include this rule verbatim.
  New contributors who arrive through a fast path
  (open-source contribution, AI-assisted PR) receive
  this link on their first interaction with the repo.
- **Self-removal**: contributors who consistently violate
  the invariants despite feedback exit the
  maintainer list. This isn't a punishment; it's a
  recognition that the project and the contributor have
  different standards, and the project's standard is the
  one that ships.

## Exceptions

<Callout type="warn" title="No exceptions">
  The invariants are absolute. A request for an exception is a
  signal that the request should be re-scoped until it no
  longer requires one.
</Callout>
