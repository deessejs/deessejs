## Rule

A class, type, or module name is **never** a bare job title. The
suffixes `Manager`, `Service`, `Handler`, `Controller`, `Helper`,
`Writer`, `Reader`, `Converter`, `Validator`, `Router`,
`Dispatcher`, `Observer`, `Listener`, `Sorter`, `Encoder`,
`Decoder`, and every other `-er` ending that names what the
thing **does for the caller** rather than what the thing **is**
get refused as standalone names.

The rule works against suffixes as **the only content of a name**
and against suffixes that survive qualification. A `Handler`
fails the rule because the name says only that something gets
handled; a `CancelOrderHandler` also fails, because the suffix
still describes the **role the thing plays in another file's
code**, not the thing itself. The qualifier doesn't change the
smell; it only makes the smell larger and harder to spot.

Two patterns, in increasing order of severity:

- **Suffix as name content** (`Manager`, `Service`, `Handler`,
  `CancelOrderHandler`, `UserCreationService`) fails the rule.
  The suffix is part of the name, with or without a qualifier.
  The name describes a role, not an entity.
- **Entity name** (`SortedApples`, `ValidatedPayload`,
  `CancellationRequest`) is the only accepted shape. The name
  describes what the thing **is**, not what it does for the
  caller.

The rule accepts the entity shape only. The suffix shape, with
or without a qualifier, is the smell this rule exists to catch.

## Why

A bare job title is a confession that the author couldn't name
the thing they built. The thing exists; the author wrote
it. Yet the name they gave it names the **role the thing plays
in code beyond the file**, not the thing itself. The author
outsourced the naming to the caller.

This is the same anti-pattern as a function called `doStuff`,
applied at the type level. The reader who meets the type for
the first time can't tell what it represents, only what it
does for the system that uses it. The reader has to read the
callers to recover the entity, when the name should have done
that work.

The deeper problem is **diffusion of responsibility**. A class
named `Manager` is a class to which any method can join
without breaking its name. A class named
`OrderCancellationService` is a class to which only
order-cancellation methods can join without breaking its name.
The first grows; the second stays focal. The smell isn't
aesthetic; it's a measurement of how much scope a class gets
to absorb.

## What this looks like in violation

The first shape, bare job title:

```ts
// Bad, what does this manage?
class UserManager {
  createUser(input: CreateUserInput): User {
    /* ... */
  }
  updateUser(id: string, input: UpdateUserInput): User {
    /* ... */
  }
  deleteUser(id: string): void {
    /* ... */
  }
  authenticateUser(credentials: Credentials): Session {
    /* ... */
  }
  sendPasswordResetEmail(email: string): void {
    /* ... */
  }
  generateUserReport(filters: ReportFilters): Report {
    /* ... */
  }
  /* ...and so on, indefinitely. */
}
```

Six unrelated responsibilities under one name. The next
contributor who adds a method asks "where does it go?" and the
answer is "UserManager." The class grows until it becomes
unmanageable.

The second shape, qualified job title, is the shape the rule
**refuses**. The shape gets mentioned here only because most
codebases reach for it as the "smaller" compromise:

```ts
// Refused, the suffix still describes a role, not an entity.
// The qualifier makes the smell larger, not smaller.
class OrderCancellationHandler {
  handle(command: CancelOrderCommand): CancellationResult {
    /* ... */
  }
}
```

The qualifier doesn't turn a role into an entity. The class
still carries its name for what it does for the caller
(`Handler`), not for what it represents. A reader who meets
`OrderCancellationHandler` learns that a handler exists; the
reader still has to read the body to discover that the handler
is the cancellation.

The right shape:

```ts
// The name describes what the thing is.
// The class stays internal; see rule 0014.
class OrderCancellation {
  cancel(command: CancelOrderCommand): CancellationResult {
    /* ... */
  }
}

// Or, more idiomatic in functional code:
type OrderCancellation = (command: CancelOrderCommand) => CancellationResult;
```

The class is the **thing**; the method is the **operation on
the thing**. The reader doesn't need to know who uses it. The
class above stays internal; rule 0014 forbids exporting it.
The public shape is a factory function
(`createOrderCancellation`) or, more often, a type alias and a
free function. The example here shows the naming pattern; rule
0014 shows the public-API pattern.

## When the rule doesn't apply

The rule applies to **shape names**, the name of a class, a
type, a module, a service handle. It doesn't apply to:

- **Variable names** that hold an instance for a moment. `const
  manager = new OrderCancellationHandler();` stays acceptable;
  the variable scopes to one expression and the type name carries
  the focal responsibility.
- **Test names**. `UserManagerTest` stays acceptable as a test
  class name when the type under test is `UserManager`; the test
  name mirrors the type name. Refusing the test name would
  create a useless indirection.
- **Build-time tooling**. Generated code, vendor bindings, and
  frameworks where the shape stays fixed by the other side.

## How to refactor a suffix-bearing name

When a contributor has written `Manager`, `Service`, `Handler`,
or any qualified version (`CancelOrderHandler`,
`UserCreationService`), the refactor has two steps, in order:

1. **Identify the entity.** The class does something for the
   caller. The thing it operates on, or the thing it **is**, is
   the entity. A `CancelOrderHandler` is the cancellation; the
   qualifier already names it. A `UserCreationService` is the
   user creation; the qualifier already names it. The entity is
   in the qualifier; the suffix is what gets removed.
2. **Rename to the entity, drop the suffix.**
   `CancelOrderHandler` → `OrderCancellation`.
   `UserCreationService` → `UserCreation`. The method on the
   entity is the action (`cancel`, `create`).

No "smallest change" path keeps the suffix. The suffix is the
smell; removing it makes the change. When the class runs too
small to deserve its own entity name, the qualifier gets
replaced by the action. `cancelOrder(command:
CancelOrderCommand)` lives as a function on the
`OrderCancellationService`. That function doesn't need a
wrapper class; it's a function.

The refactor in three steps when the class is large enough:

1. Split into one entity per focal responsibility.
2. Each entity exposes one operation (`cancel`, `create`,
   `validate`).
3. The suffix goes away with the wrapper class.

## What this looks like in violation, the focused case

A class that carries the right name but the wrong shape:

```ts
// Bad, the name says one thing, the methods do many.
class OrderCancellation {
  cancel(command: CancelOrderCommand): CancellationResult {
    /* ... */
  }
  refund(orderId: string, amount: Money): RefundResult {
    /* ... */
  }
  notifyCustomer(orderId: string): void {
    /* ... */
  }
  generateCancellationReport(filters: ReportFilters): Report {
    /* ... */
  }
}
```

The name promises one responsibility; the body delivers four.
The right move is to split. Each method becomes its own entity
or its own command. The class `OrderCancellation` then carries
only the `cancel` method; the others live in their own types.

## What senior practitioners say

> "Manager. Controller. Helper. Handler. Writer. Reader.
> Converter. data-validator. Router. Dispatcher. Observer.
> Listener. Sorter. Encoder. Decoder. This is the class names
> hall of shame. The reader has seen them in their code. In
> open source libraries. In pattern books. They all fail.
> What do they have in common? They all end in '-er.' And
> what's wrong with that? They aren't classes, and the objects
> they instantiate aren't objects. Instead, they read as
> collections of procedures pretending to be classes."
>
> . _Don't Create Objects That End With -ER_, a 2015 essay.

The author's diagnosis is the philosophical ground of the rule.
A bare job title is a class that has no entity to be; it's a
collection of procedures that the caller orchestrates. The
shape exists; the entity doesn't.

> "When a class only carries a single responsibility it becomes
> difficult to attach a Manager suffix to the class name."
>
> . _Manager Suffixes Are a Code Smell_, a 2008 essay.

The author's observation puts the previous point into practice.
The suffix serves as a proxy measurement for responsibility
count. When the suffix becomes necessary, the count runs high.

> "Six methods each with around five unit tests means 30 unit
> tests, probably all in the same file name
> 'CartServiceTest'. That becomes much harder to manage. […]
> Every class should be a noun and every method should be a
> verb."
>
> . _"Service" should be a banned word_, a 2019 essay.

The author quantifies the cost. A bare `Service` accumulates
methods faster than it accumulates tests. The total cost of the
class is the methods times the tests; the suffix makes the cost
invisible.

> "A command handler's job is to coordinate the execution of a
> command. The name comes from the command, not the entity. The
> handler takes the name `CancelOrderHandler`, not
> `OrderHandler`."
>
> . _Domain Command Patterns - Handlers_, a 2018 essay.

The author's position is the most permissive of the four
sources. The rule doesn't follow this position; the rule
follows the earlier essay's position. The qualifier-plus-suffix
shape the author recommends is, in this rule's reading, still a
role-naming convention: `CancelOrderHandler` tells the reader
what the thing does for the caller, not what the thing is.
The rule's stance is that a class described by what it does for
the caller should be a function on the entity it operates on,
not a wrapper class. The qualifier is the entity; the suffix
is the wrapper.

The four voices still converge on the **diagnosis**, the suffix
is a smell, even when they disagree on the **threshold**. The
rule picks the strictest threshold: no suffix, with or without
a qualifier. The other positions describe intermediate shapes
project contributors may reach for during a refactor; the rule
captures the shape the project is moving toward.

## Enforcement

- **Code review**. A reviewer who sees a bare `-er` suffix in a
  class or type name (`UserManager`, `PaymentService`,
  `EventHandler`) blocks the PR and asks for a qualifier, a
  split, or an entity rename.
- **Naming audit**. A standing review of "which classes in this
  codebase carry a bare `-er` suffix?" surfaces the candidates
  that slipped through. Each is a refactor candidate, not a
  backlog item.
- **Lint rule** (future). A custom ESLint rule can flag bare
  `-er` suffixes in class and type declarations. The rule's
  existence is the enforcement signal even before automation
  lands.

## Exceptions

A test class name (`UserManagerTest`) stays permitted because
it mirrors the type under test. The test class isn't the
entity; it's the verification of the entity. Renaming
`UserManagerTest` to `UserTest` while the type under test is
still `UserManager` would create a useless indirection; the
rename stays the responsibility of the type rename, not the
test rename.

A variable that holds an instance for a moment (`const
manager = ...`) stays permitted. The type name carries the
focal responsibility; the variable name is local. The rule
refuses type names, not variable names.

Build-time tooling, generated code, vendor bindings, and
frameworks where the shape stays fixed by the other side stay
permitted. The rule applies to code the project writes, not to
code the project consumes.

## See also

- **Rule 0002**, File Separation: a class with bare `-er`
  often mixes types and operations; the rule on file separation
  makes that mixing visible.
- **Rule 0007**, Top-Down Composition: the same principle at
  the function level. A function called `processData` is the
  function-level counterpart of a `DataManager` class. The
  principle stays the same: name the thing, not the job.
- **Rule 0011**, Filenames Are kebab-case: a class named
  `UserManager` often lives in a file named `user-manager.ts`,
  which carries the right casing. The rule's wrong shape is the
  class name, not the file name.
