# RFC-001: The DeesseJS Project Config (`deesse.json` + `deesse.lock`)

## Status

**Accepted (2026-09).** Three senior review rounds resolved critical blockers (secrets handling, JSONC round-tripping, lockfile tracking, walk-up path resolution, lazy token validation, error taxonomy, lockfile commit convention, monorepo lockfile placement, sync --check scope, timestamp determinism). All blockers resolved and inlined into the body of this RFC. The implementation lands in the same change set as RFC-002.

## Summary

This RFC proposes **two paired files** that together define the consumer-side configuration of a project that uses the DeesseJS CLI:

- **`deesse.json`** — declarative configuration. Written by the CLI on first install (`deessejs init <slug>`); hand-edited by the user from that point onward. Committed to git. The file is **JSONC** (JSON with comments and trailing commas), parsed and written via `jsonc-parser` for AST-preserving edits. Contains the package manager, framework profile, runtime database choice, `paths{}` for filesystem directories, `aliases{}` for TS-import placeholders, `tokens{}` (with `env:<VAR>` delegation to keep secrets out of git), and `registries{}` namespace map.
- **`deesse.lock`** — imperative state. Written by the CLI on every install (`deessejs add`, `deessejs init`). Committed to git (mirrors `package.json` vs `package-lock.json`). Contains the `templates<slug>` resolved-state block: each entry records `version`, `installedAt`, and `source` (namespace prefix or registry host).

The two files are the **consumer-side counterpart** to `deesse-template.json` (per RFC-002). The CLI reads `deesse.json` to know where to write and reads `deesse-template.json` to know what to write; it updates `deesse.lock` to record what was installed. This RFC documents both files; the template descriptor is documented in RFC-002.

The lockfile is committed because the **entire purpose of a lockfile is deterministic state across a team and CI**. `package-lock.json`, `pnpm-lock.yaml`, `Cargo.lock`, and `Gemfile.lock` are all committed; `deesse.lock` follows the same convention. The file format is merge-friendly (keys sorted alphabetically, timestamps as date-only `YYYY-MM-DD` UTC), so concurrent installs produce diffs that resolve without manual intervention in most cases.

## Goals and Non-Goals

### Goals

1. **Capture per-project wiring once, reuse everywhere.** A user runs `deessejs init saas-starter`, the CLI writes `deesse.json` and `deesse.lock`. Every subsequent `deessejs add <feature>` reads both files to know where to land files, which database adapter to use, which package manager to invoke, and which versions are already installed.
2. **Be portable across project layouts.** Monorepos, single-package apps, and standalone workspaces each have different conventions. `deesse.json` covers them all via the `paths{}` (filesystem-relative, declared per-directory), `aliases{}` (import-relative), and walk-up discovery (a nested `deesse.json` at `apps/<x>/deesse.json` overrides the parent's fields on a per-key deep-merge basis).
3. **Be stable across upgrades.** Adding a new field is non-breaking; removing or renaming a field is breaking and requires a migration.
4. **Make the registry namespace map explicit.** A user declares which registries they trust via `registries{}` — opt-in per host, no implicit trust.
5. **Be read-and-writable by automation.** Both files use JSONC, parse-validated by Zod schemas at runtime, and round-trip cleanly through `jsonc-parser`'s `modify` + `applyEdits` (no `JSON.stringify`, no `JSON.parse` — standard JSON round-tripping strips comments and reorders keys).
6. **Keep secrets out of git.** `tokens.<KEY>` supports the `env:<VAR>` shape, delegating secret values to `process.env` or `.env.local` (loaded via `dotenv`). `deesse.json` itself is safe to commit; secrets live in `.env.local` (gitignored).
7. **Provide deterministic lockfile state across the team.** `deesse.lock` is committed and merge-friendly. Conflicts resolve cleanly via `deessejs sync`.

### Non-Goals

1. **Being a runtime config** — `deesse.json` is a build-time / install-time file. Application runtime configs (env vars, feature flags) live in `.env.local` and similar, not here.
2. **Tracking file history** — `deesse.lock#templates["feature"]` records what was installed at which version. It does not record which files were created, which is out of scope for this RFC (per the drift model in RFC-002 §Future Possibilities).
3. **Auto-rewriting user-edited fields** — the CLI writes `deesse.json` once at `init`. Subsequent installs preserve user edits verbatim. The CLI writes `deesse.lock` on every install (this is the only file the CLI mutates continuously).
4. **Supporting arbitrary top-level field additions** — the **top-level** schema fields are closed-list (per ADR-031 §Reserved field names). The **nested values** of `paths`, `aliases`, and `tokens` are open (`Record<string, string>`): any string key is accepted. Adding top-level fields requires an ADR.

## Motivation

The DeesseJS CLI today writes **no file** to the user's project. shadcn's `components.json` is the model: written once at the project root, read by every CLI invocation, the canonical source of "where does this project put things". The DeesseJS CLI needs the same primitive, but for a feature-level install (not a component-level add). The shape differs because features touch more directories: routes, components, DB schema, env vars, hooks — each with its own placement rule.

Without a project-side config, the CLI must **guess**. For a monorepo, the guess is wrong (the CLI does not know which app). For a custom layout, the guess is wrong (the CLI does not know the project's convention). For a multi-stack workspace (Next.js + Expo + Tauri), the guess is wrong three times. `deesse.json` replaces the guess with an explicit declaration.

`deesse.lock` (the companion file) is **not** a session cache. Session caches (like the `TemplateV1` `~/.deessejs/templates.json` cache documented in ADR-010 §4) are gitignored; their job is to avoid redundant network fetches within a session. Lockfiles are different: their job is to record what was installed in a way that is **deterministic across the team and CI**. `deesse.lock` is the latter. The earlier draft of this RFC confused the two patterns and proposed a gitignored `deesse.lock`; that was an antipattern corrected in this revision.

The two files are the **answer to the consumer's "where do you put things, what did you install" questions**. The template descriptor (per RFC-002) is the answer to the **author's "what does my item ship" question**. Together, the three files define the contract between author and consumer.

## Detailed Design

### The two files

**`deesse.json`** (declarative config):

```jsonc
// deesse.json
{
  "$schema": "https://registry.deessejs.dev/schema/project.json",
  "template": "saas-starter",
  "version": "1.4.0",
  "database": "postgresql",
  "packageManager": "pnpm",
  "typescript": true,
  "git": { "init": true, "initialBranch": "main" },
  "paths": {
    "routes": "src/app",
    "components": "src/components",
    "db": "src/server/db",
    "lib": "src/lib",
    "hooks": "src/hooks",
    "styles": "src/styles"
  },
  "aliases": {
    "apps": "apps/*",
    "packages": "packages/*",
    "components": "@/components",
    "lib": "@/lib",
    "hooks": "@/hooks",
    "ui": "@workspace/ui/components"
  },
  "tokens": {
    "NEXT_PUBLIC_APP_URL": "http://localhost:3000",
    "DATABASE_URL": "env:DATABASE_URL"
  },
  "registries": {
    "@deessejs": "https://registry.deessejs.dev/r/{name}.json"
  }
}
```

**`deesse.lock`** (imperative state):

```jsonc
// deesse.lock
{
  "$schema": "https://registry.deessejs.dev/schema/lock.json",
  "lockfileVersion": 1,
  "templates": {
    "saas-starter": {
      "version": "1.4.0",
      "installedAt": "2026-09-14",
      "source": "@deessejs/saas-starter"
    }
  }
}
```

The `lockfileVersion` field allows future migrations to evolve the schema without breaking existing lock files.

### Block-by-block contract — `deesse.json`

The blocks split into three categories by ownership and stability.

**Project-identity blocks (CLI writes once, user rarely edits):** `$schema`, `template`, `version`, `database`, `packageManager`, `typescript`, `git`. The CLI sets these at `init` based on the template's defaults and the user's answers to `prompts[]`. The user may override them by hand (e.g. change `database` from `postgresql` to `mysql`), but the CLI does not rewrite them on subsequent installs unless the user re-runs `init --force`.

**Wiring blocks (CLI writes defaults, user edits freely):** `paths`, `aliases`, `tokens`, `registries`. These define how the project is laid out and where templates land. The CLI sets sensible defaults at `init`, and the user edits them to match their conventions. The CLI reads these on every `add`/`init` invocation; it never writes them on subsequent installs (a user who edited `paths.routes` to `apps/web/src/app` does not want the CLI to silently rewrite it back).

**The CLI writes `deesse.json` once at `init` and never on subsequent installs.** The CLI's mutability contract is: full write on `init`; read-only on `add`. This is the explicit guarantee that user edits to wiring blocks are preserved verbatim.

### Block-by-block contract — `deesse.lock`

A single block:

**`templates{}`** — the resolved-state block. Each entry:

```jsonc
"templates": {
  "<slug>": {
    "version": "<semver>",
    "installedAt": "<YYYY-MM-DD date, UTC>",
    "source": "<namespace prefix or registry host>"
  }
}
```

The CLI writes this block on every install (init and add). The write is atomic (`fs.writeFile(tmp); fs.rename(tmp, real)`) so a crash mid-install cannot corrupt the file.

**The lock file is committed to git**, not gitignored. This is the standard convention for tool lockfiles (`package-lock.json`, `pnpm-lock.yaml`, `Cargo.lock`, `Gemfile.lock` are all committed). The entire purpose of a lockfile is to provide deterministic state across the team and CI; gitignoring it defeats that purpose. Merge conflicts on the lockfile resolve cleanly because:

- The format is **deterministic**: keys are sorted alphabetically, timestamps are date-only `YYYY-MM-DD` UTC (precision at the day level, eliminating trivial merge conflicts from same-day installs), indentation is fixed.
- Two concurrent installs of the same item resolve to the same `version` (semver) and `source` (namespace prefix), so a conflict on the same slug is rare.
- For different slugs, Git's three-way merge handles the additions without manual intervention.
- For the rare case where a manual conflict needs resolution, `deessejs sync` re-fetches each entry's version from the registry and rewrites the file deterministically.

### The `paths{}` vs `aliases{}` distinction

This is the load-bearing distinction in the file. The two blocks answer different questions:

- `paths{}` answers "where in the filesystem do I write a new file?" Each entry maps a logical role (`routes`, `components`, `db`, ...) to a filesystem-relative path. A monorepo writes `paths.routes = "apps/web/src/app"`.
- `aliases{}` answers "what import string do I write into an existing file?" Each entry maps a logical role to a TS-import placeholder. A monorepo writes `aliases.components = "@/components"` (resolves to `apps/web/src/components` after tsconfig paths).

The two blocks overlap in a single-package project (`paths.routes = "src/app"` matches `aliases.components = "@/components"`), but they diverge in a monorepo (`paths.routes = "apps/web/src/app"` vs `aliases.components = "@/components"`). Keeping them separate makes the install logic explicit: the CLI reads `paths.<x>` for the **write target** and `aliases.<x>` for the **import substitution** in `files[]` transforms.

**Path resolution invariant.** Every path value in a merged config resolves **relative to the directory of the `deesse.json` file in which that specific path key was declared, NOT relative to `process.cwd()` or to any leaf config.** For example:

- Root `deesse.json` declares `"paths": { "db": "packages/db" }` → resolves to `<repo-root>/packages/db`.
- `apps/web/deesse.json` declares `"paths": { "routes": "src/app" }` → resolves to `<repo-root>/apps/web/src/app`.
- After walk-up discovery merges the two configs, `paths.db` is still `<repo-root>/packages/db` (resolved from the root file's directory) and `paths.routes` is `<repo-root>/apps/web/src/app` (resolved from the leaf file's directory).

The leaf config does not rebase inherited paths relative to itself. The CLI tracks which file each path key came from and resolves accordingly.

### The `tokens{}` substitution map

Tokens are the **runtime substitution map** for files that ship with `{{KEY}}` placeholders. When the CLI applies a `transform: "interpolate"` file from `deesse-template.json#files[]`, it substitutes `{{KEY}}` with `tokens.<KEY>`.

The map supports two value shapes:

```jsonc
"tokens": {
  "NEXT_PUBLIC_APP_URL": "http://localhost:3000",   // literal value
  "DATABASE_URL": "env:DATABASE_URL"                // resolved at install time
}
```

A **literal value** is interpolated directly into `files[]` transforms. An **`env:<VAR>` value** tells the CLI to resolve `process.env.<VAR>` at install time. If the variable is unset, the CLI reads `.env.local` (loaded via `dotenv`). If still unset, the install fails with `unresolved_token` (a new dedicated error code, not `parse_error`).

**Lazy token validation.** Token resolution is **lazy and per-transform**: the CLI only asserts that an `env:<VAR>` token is present if an incoming template file actually contains a `{{<VAR>}}` interpolation. A user who runs `deessejs add lucide-icons` (which uses no `DATABASE_URL`) does not need `DATABASE_URL` to be set in their environment. A user who runs `deessejs add auth` (which uses `{{DATABASE_URL}}` in `prisma/schema.prisma.template`) does.

A token value that is a literal `{{KEY}}` placeholder is a **sentinel**: the CLI wrote a template substitution that the user has not yet replaced. **The CLI fails fast** when a `files[]` transform would write a literal sentinel into an output file, with `unresolved_token`. A `--skip-token-check` flag exists for the rare case where the user wants to install with sentinels and fix them later; it is off by default.

### The `registries{}` namespace map

Namespaces are the **opt-in trust boundary**. The CLI ships with one default entry (`@deessejs` → `registry.deessejs.dev`). The user adds other entries at will: `@<host>/...` for an open-community registry, `@deessejs-community/...` for the curated tier (per RFC-002 §Community support).

**Template `{name}` sanitisation.** The CLI enforces a strict regex `^[a-z0-9][a-z0-9_-]*$` on `{name}` before interpolation into a URL template. Any character outside this set (including `.`, `/`, `\`, `?`, `#`, `%`, control characters) causes `parse_error`. This blocks path traversal (`../../evil`), URL injection (`?param=...`), and percent-encoding tricks. The slug regex is the same as the one used for `deesse-template.json#name` (per RFC-002 §Field reference §name), so the invariants are consistent across the system.

**Namespace structure is flat.** The regex disallows `/`, which means nested namespaces within a registry base (`@community/ui/button`) are not possible. Each registry host exposes its own flat item list; group-by-folder or group-by-category is the registry author's responsibility (via the `category` field in `deesse-template.json`, per RFC-002). This is a deliberate constraint: it keeps `{name}` parsing simple and prevents URL-injection vectors.

A namespace entry that points at a host the user has not previously seen triggers a **one-time trust warning** at install time (per ADR-032 §Hook runner safety rules). The `--trust-host=<host>` flag suppresses subsequent warnings from the same host.

Namespaces are **not vetting**. The `@deessejs` and `@deessejs-community` namespaces carry vetting (curated review per RFC-002 §Community support); `@<host>/...` does not. The CLI does not enforce vetting at the protocol level; it surfaces the warning and lets the user decide.

### Monorepo walk-up discovery

The CLI walks up from `cwd` until it finds a `deesse.json`. If the user runs `deessejs add auth` from `apps/web/`, the CLI uses `apps/web/deesse.json` if it exists, falling back to the root `deesse.json` for the unset fields. The two files merge with **per-key deep merge** for `paths` and `aliases`:

- If only the root declares `paths.db = "packages/db"`, the merged config has `paths.db = "packages/db"`.
- If only `apps/web/deesse.json` declares `paths.routes = "src/app"`, the merged config has `paths.routes = "src/app"` (resolved relative to `apps/web/deesse.json`'s directory).
- If both declare `paths.db`, the leaf wins.

`templates`, `tokens`, `registries`, `database`, `packageManager`, and the project-identity blocks do not deep-merge across files. The leaf file fully overrides the root for these blocks. This is because (a) `tokens` and `registries` are user-editable and not environment-dependent (a child override is the user's intent), and (b) `database` and `packageManager` are project-wide choices that should be consistent across the monorepo.

### Re-install semantics

When `deessejs add <slug>` runs against an item already present in `deesse.lock`:

- **Default behaviour**: the CLI refuses with a new internal error code `item_already_installed`. The user sees a message listing the locked entry (`version`, `installedAt`, `source`) and the available options:
  - `--force` — silent overwrite (mirrors today's `add` semantics per RFC-002 §Decision #7).
  - `--upgrade` — preserve user edits in `files[]` outputs and refresh the lock entry's `version` + `installedAt`. The new `version` is whatever the registry returns at fetch time (per RFC-002 §source.ref).
- **Why refuse by default**: silent re-installs are surprising — the user thinks they're adding a feature, but the registry may have shipped a breaking change since the last install. Forcing an explicit `--upgrade` makes the user aware.
- **`item_already_installed` semantics**: this is **not** a file lock. Two `deessejs add` running concurrently against the same `deesse.lock` are allowed to race; whichever writes last wins (the lock is rewritten atomically). The error is about a logical conflict (the user said `add` but the item is already there), not a physical lock.

### Error taxonomy

| Condition | Error code | User fix |
|---|---|---|
| Malformed descriptor / placeholder / `when` grammar | `parse_error` | Edit the descriptor or file an issue |
| Target path exists, no `--force`, no `overwrite: true` | `file_collision` (internal) | Pass `--force` |
| Overlay transform fail / staged-write rollback | `install_failed` (internal) | Inspect stderr, retry |
| Registry unreachable | `network_error` | Retry or check network |
| `env:<VAR>` cannot be resolved | `unresolved_token` (internal) | Set the env var or update `.env.local` |
| `add <slug>` against an installed item without `--force`/`--upgrade` | `item_already_installed` (internal) | Pass `--force` or `--upgrade` |

The closed-list on **public** codes per ADR-010 §2 is preserved. The new internal codes (`file_collision`, `unresolved_token`, `item_already_installed`, plus the existing `install_failed`) do not amend the closed list.

## Alternatives Considered

Three patterns were considered and rejected during the development of this RFC and its underlying ADR.

### Alternative 1: Put the wiring in `package.json`

Why we rejected it: `package.json` is owned by the JS ecosystem (npm/pnpm/yarn/bun), not by DeesseJS. Conflating the two means DeesseJS writes to a file the user might manage via `npm pkg set` and the lockfile ordering gets unpredictable. A separate file is cleaner and more discoverable.

### Alternative 2: Gitignore `deesse.lock` (earlier draft of this RFC)

Why we rejected it (corrected in this revision): a gitignored lockfile defeats its purpose. `package-lock.json`, `pnpm-lock.yaml`, `Cargo.lock`, and `Gemfile.lock` are all committed because the entire point of a lockfile is deterministic state across the team. A gitignored `deesse.lock` would mean:

- Developer A installs `auth` (writes to A's local lockfile) and commits code. Developer B pulls (gets no lockfile, sees no record of the install) and runs `deessejs add auth` — the CLI has no record that B already had the item, so the re-install protection (per "Re-install semantics" above) does not fire.
- The CI environment has no record of what versions were installed, breaking the audit trail feature.
- Supply-chain incident response loses a key piece of evidence ("which version of the compromised item did each developer install?").

The standard lockfile convention applies. The merge-conflict concern is real but is solved by deterministic formatting (sorted keys, ISO 8601 timestamps) and by `deessejs sync` for the rare manual case.

### Alternative 3: Multiple config files (one per app, one per package, one global)

Why we rejected it: the surface area of "where is the config" multiplies. A single file at the project root is the shadcn-style, npm-style, and Rails-style convention. Monorepos that need per-app configs can extend the file via walk-up discovery (per §Detailed Design), which keeps the surface flat.

## Risks and Cross-Cutting Concerns

### Mutability discipline

The CLI writes `deesse.json` **once at `init`**. Subsequent installs read `deesse.json` but never write to it (user-edited fields are preserved verbatim). The CLI writes `deesse.lock` on every install (init and add), atomically.

### Conflict resolution

If a user hand-edits `paths.routes` to `apps/web/src/app` and then runs `init <new-template>`, the new template's default `paths.routes` value (`src/app`) is not applied to `deesse.json`; the user's value is preserved. The CLI emits a warning when a template's default differs from the user's value but does not refuse the install.

### Lockfile merge conflicts

The format is designed to be deterministic and merge-friendly. Conflicts resolve cleanly in most cases via Git's three-way merge. The rare manual case is handled by `deessejs sync`, which re-fetches each entry's version from the registry and rewrites the file deterministically. The CI runs `deessejs sync --check` (a flag on the command) which exits 0 if the file is in sync with the registry and 1 otherwise; a non-zero exit blocks the PR.

### Schema stability

The Zod schemas for both files (`Project` and `Lock` in `@workspace/contracts/src/v1/`) are closed-list for top-level fields, open for nested values. Widening the schema is non-breaking; narrowing is breaking. The implementation CI runs Zod-validation tests on every release to catch accidental narrowing.

### Secrets handling

Secrets are **never stored in `deesse.json`**. The `tokens` block uses the `env:<VAR>` convention. `deesse.json` itself is safe to commit; `.env.local` is the user's gitignored secret store. A future ADR may introduce encrypted-at-rest tokens (`tokens.<KEY>.secret: true` with OS keychain backing), but that's out of scope for this RFC.

### Offline schema

The CLI bundles the Zod schemas as part of `@workspace/contracts`. No network fetch for validation; the `$schema` URL is a hint for editors. The CLI's bundled schema lags at most one release behind the CDN URL.

### Backward compatibility

This RFC introduces `deesse.json` and `deesse.lock`. Existing projects that have not yet run `deessejs init` against a `TemplateV2`-compatible template have neither file; `deessejs add feature` against such a project refuses with `parse_error`: *"deesse.json not found; run `deessejs init` first."* This is the load-bearing behaviour that makes the files the canonical consumer-side source of truth.

## Open Questions

### Question 1: Per-app config in monorepos?

A monorepo with `apps/web/` and `apps/api/` may want different `paths.routes` for each app. The current walk-up discovery handles this for top-level keys (each app's `deesse.json` overrides on a per-key basis). A future ADR may formalise per-app config with `--target=<app>` for cross-app installs. Out of scope for this RFC; deferred to a follow-up ADR if a real use case surfaces.

### Question 2: Lockfile migration?

When the Lock schema gains a new optional field (e.g. `templates.<slug>.checksum` for tamper detection), the migration is `deessejs lock migrate` which reads the old lock file, applies the transformation, and writes the new shape. Out of scope for this RFC; deferred to a follow-up ADR when the schema first evolves.

### Question 3: Schema migration?

Same pattern as Question #2 but for `deesse.json`. `deessejs config migrate` rewrites the user's `deesse.json` to match the latest Zod schema. Out of scope for this RFC.

## Rollout Plan

### Stage 1 — File shape and infrastructure

Both files ship in the same change set as `deesse-template.json` (RFC-002). The CLI gains `loadDeesseJson(projectRoot)`, `loadDeesseLock(projectRoot)`, and the install flow reads both at every command. Atomic writes use the temp-file + rename pattern. The `deessejs sync` command lands as part of this lock infrastructure.

### Stage 2 — Follow-up additions

A future ADR may add `deessejs doctor` (a command that reads `deesse.json` and `deesse.lock`, validates both against the schema, suggests fixes for common mistakes, and checks the registry for newer versions). Out of scope for this RFC.

## Prior Art

### shadcn `components.json`

The closest analogue. shadcn's `components.json` carries `style`, `tailwind.config`, `tailwind.css`, `aliases`, `tsx`, `rsc`, `registries{}` — the same shape `deesse.json` follows, with the divergences documented above (no Tailwind config in DeesseJS, paths/aliases split, JSONC + lock split).

Source: [shadcn `components.json` schema](https://ui.shadcn.com/docs/components-json).

### `package.json` + `package-lock.json`

The general convention of "declarative config + committed lockfile". DeesseJS follows the convention but with separate files because `package.json` is owned by the JS ecosystem.

Sources: [npm `package-lock.json` documentation](https://docs.npmjs.com/cli/v10/configuring-npm/package-lock-json), [pnpm `pnpm-lock.yaml` working with Git](https://pnpm.io/git).

### Rails initializers

Rails's `config/initializers/` directory follows a similar idea (one config file per concern at a known location). DeesseJS is a single file rather than a directory because the consumer-side state is small enough to fit in one place.

## Future Possibilities

- **Per-app config in monorepos** — see Open Question #1.
- **Lockfile migration command** — see Open Question #2.
- **`deessejs config migrate`** — see Open Question #3.
- **`deessejs doctor`** — validates both files and surfaces registry drift.
- **Encrypted secrets** — `tokens.<KEY>.secret: true` encrypts at rest via the OS keychain.
- **`deesse.lock` checksums for tamper detection** — verify the install at fetch time matches the lockfile entry.

## Implementation notes

Three operational nuances surfaced in the senior review of revision 3. They are not architectural blockers — they are details that the implementation PR must capture. This section records them so they are not lost between this RFC and the implementation.

### A. Lockfile placement in monorepos

**Decision**: a **single root `deesse.lock` per repository workspace**. The lockfile lives at `<repo-root>/deesse.lock`, mirroring `package-lock.json` (which always lives at the root, regardless of how many `package.json` files are in sub-directories). Sub-app `deesse.json` files (per §Detailed Design walk-up discovery) are fine; sub-app `deesse.lock` files are **not** allowed.

**Why a single root**: multiple distributed lockfiles across packages create synchronisation overhead (when does Developer A's `apps/web/deesse.lock` get merged with Developer B's `apps/api/deesse.lock`?). A single root lockfile gives the team one source of truth for "what's installed in this workspace". CI verification (`deessejs sync --check`, per §B below) reads one file, not N.

**Exception**: a future ADR may introduce per-app `deesse.lock` if a real use case surfaces (e.g. an app that ships with its own immutable template set and must not be affected by root updates). Out of scope for this RFC.

### B. `deessejs sync --check` scope

**Decision**: `deessejs sync --check` validates **internal consistency and lockfile integrity**, **not** whether newer remote versions exist on the CDN.

The check asserts:

- The lockfile parses against the `Lock` Zod schema.
- Each `templates.<slug>` entry's `version` and `source` are well-formed (semver, valid namespace).
- Each `templates.<slug>` entry's resolved path (`source.repo` + `source.ref`) is reachable in the local `deesse.json#paths` (no broken references).
- The lockfile is internally deterministic (sorted keys, no duplicates, valid date format).

**What it does NOT check**:

- Whether `version` matches the registry's latest `version` for that `slug`.
- Whether `source.ref` matches the registry's current `ref`.
- Whether a newer `slug` exists that the user might want.

**Why this matters**: if `sync --check` queried the remote registry for latest versions, any upstream template update (even a non-breaking minor/patch) would immediately break CI on completely unrelated PRs across every repository consuming that template. CI must be **stable against upstream churn**. The freshness check belongs in `deessejs outdated` (a separate command, tracked separately) or `deessejs doctor` (tracked separately).

### C. Deterministic timestamp generation in lockfiles

**Decision**: `installedAt` is a **date-only UTC string in `YYYY-MM-DD` format**. The previous draft used full ISO 8601 timestamps (`2026-09-14T12:00:00.000Z`); the date-only form eliminates trivial merge conflicts from same-day installs.

**Why date-only**: in team development, if Developer A and Developer B both install `feature-x@1.0.0` on separate branches within the same UTC day, their `installedAt` is identical (`2026-09-14`). The merge is trivial — no conflict on the timestamp field. Cross-day installs resolve to a clear winner (the later date).

**`installedAt` is non-semantic metadata.** It is for human audit ("when did I install this?") and supply-chain incident triage ("what version was deployed last Thursday?"). It is **not** used by the CLI for any runtime decision. The CLI never re-installs because `installedAt` is newer or older; it re-installs because the user passes `--upgrade` (per §Detailed Design "Re-install semantics"). The `deessejs sync` command treats `installedAt` as non-semantic when resolving conflicts: it preserves the earlier timestamp (deterministic, idempotent).

**Trade-off accepted**: we lose the precision of "installed at 14:23 UTC". The trade-off is intentional — merge-conflict-free commits are worth more than audit precision at the second level. If second-level precision becomes a real audit need, a future ADR may add a separate `installedAtTimestamp` field (full ISO 8601, separate from the date-only `installedAt`) that is gitignored or stored in a separate per-developer cache. Out of scope for this RFC.
