# RFC-004: The DeesseJS Author Tooling (`deessejs template <validate | new | explain>`)

## Status

**Accepted (2026-09).** This RFC is the **senior narrative** that motivates and consolidates the spec at [ADR-034](./ADR-034-template-namespace). The contract (three subcommands, JSDoc-on-Zod-schema contract, lint enforcement, JSON output) is pinned by ADR-034; this RFC explains *why* the namespace lives under `template` (not as a top-level command), *why* JSDoc is the single source of truth for field documentation, and *why* inference defaults are explicitly a "mode" computation (not a smarter clustering). Two senior review rounds resolved critical blockers: namespace placement (top-level vs `template` subcommand), JSON output default vs `--json` flag, lint enforcement (CI-side vs author-side), and inference quality (mode vs cluster). All blockers resolved and inlined into ADR-034.

## Summary

This RFC proposes **the author namespace** in the `@deessejs/cli` surface: `deessejs template validate | new | explain`. The three subcommands together form the **production line** that lets the internal team produce registry items at scale without bespoke scripts.

The motivation is operational, not architectural: the DeesseJS template registry is the project's identity surface (per the locked homepage copy and the registry-roadmap notes). The team plans to ship **hundreds of items** spanning packages, CLI tooling, SaaS starters, mobile scaffolds, desktop scaffolds, AI agent scaffolds, and landing pages. Hand-curating each item as a `deesse-template.json` file is the bottleneck.

The three subcommands remove the bottleneck by automating the three error-prone steps in the authoring loop:

| Subcommand | What it automates | Output |
|---|---|---|
| `deessejs template validate` | Schema validation (Zod) + semantic validation (forward `when` references, broken `templateDependencies`, missing files on disk) | Exit 0 (clean) / exit 1 (shape error) / exit 2 (`--strict` semantic error); human or JSON |
| `deessejs template new` | Scaffolding a new `deesse-template.json` from defaults inferred from the registry (mode computation across same-type items) | A scaffolded `templates/<slug>/` directory with a valid descriptor |
| `deessejs template explain <field-path>` | Rendering field documentation from the JSDoc on the Zod schema (`TemplateV2`) | A field description with examples, common mistakes, and an ADR cross-reference |

The subcommands live under a `template` namespace (not as top-level commands) because the load-bearing governance rule is **ADR-010 §1's closed-list invariant**, only `init`, `list`, `info`, and `add` may appear at the top level. The `auth subcommand` exception (sanctioned in ADR-010) is the precedent for a subcommand group; `template` is the second such exception, sanctioned by ADR-034.

The JSDoc-on-Zod-schema contract is the load-bearing single-source-of-truth: every closed-list field on `TemplateV2` carries a `.describe(...)` block that includes four sections (type, valid values, example, common mistake) and an ADR link. The lint rule in the `contracts` package enforces this on the Zod schema; `deessejs template explain` consumes it. A change to the contract automatically propagates to the field documentation without any manual sync.

## Goals and Non-Goals

### Goals

1. **Ship three subcommands that remove the three authoring bottlenecks.** Schema validation, scaffolding, and documentation are the three steps that scale linearly with item count and are the most error-prone. Each gets a dedicated subcommand.
2. **Validate fast.** `deessejs template validate` returns in under 1 second for any descriptor, including semantic checks (forward `when` references, broken `templateDependencies`, missing files on disk). CI gates depend on this, a slow validator blocks PRs.
3. **Scaffold from real data, not from a hardcoded template.** `deessejs template new auth-addon` infers defaults from the **median item of the same type** in the registry (mode computation across `category`, `license`, `labels`, etc.). A smarter clustering is a future ADR; the default is intentionally simple and explainable.
4. **Document fields from the schema, not from a hand-maintained reference.** The Zod schema's JSDoc is the source of truth. `deessejs template explain consumes[].target` parses the `.describe(...)` block on the `consumes[].target` Zod field and renders it. There is no `templates-reference.md` to keep in sync.
5. **Be namespace-consistent with `auth`.** The `auth subcommand` group (per ADR-010 §1) is the precedent for a subcommand namespace; `template` follows the same shape. Users learn one mental model ("top-level commands are public surface; subcommands are sub-namespaces").
6. **Be CI-friendly by default.** `deessejs template validate --json` emits a machine-readable payload on stdout and exits non-zero on any error. The command is designed for `pnpm exec deessejs template validate --json > result.json` patterns in CI scripts.

### Non-Goals

1. **Replacing `deessejs init` or `deessejs add`.** Author tooling produces descriptors; `init` and `add` consume them. The two workflows are distinct and have different surface invariants.
2. **Auto-fixing validation errors.** `deessejs template validate --fix` is **not** in this contract. Auto-fixing JSON files silently is the failure mode that motivated the explicit JSDoc contract. A future ADR may add `--fix` with a closed list of safe transforms (e.g. re-sorting keys alphabetically) but not general auto-fix.
3. **Visual editing of descriptors.** There is no TUI / GUI for editing `deesse-template.json`. The file is JSONC (comments and trailing commas allowed); the team uses an editor (VS Code with a JSONC schema extension) for hand-editing. Visual editing is a future ADR.
4. **Cross-registry discovery.** `deessejs template new` infers from the **current registry** (the one declared in `deesse.json#registries` or the official `@deessejs` registry). It does not crawl the public web for similar items. Cross-registry discovery is a future ADR.
5. **Versioning the registry items from this command.** `deessejs template new` scaffolds a descriptor at the `0.1.0` version. Bumping versions, opening release PRs, and publishing to the registry are separate workflows (handled by the registry publication CI per RFC-002 §"Publication CI").

## Motivation

The DeesseJS template registry is the project's **identity surface**. The locked homepage copy frames it as a registry spanning "packages, CLI, SaaS multi-tenant, mobile, desktop, AI agent, landing page", not a single-template repo. The team's ambition is hundreds of items, each addressable as `deessejs add @<namespace>/<slug>` from any consumer project.

Today, producing an item requires hand-authoring `deesse-template.json`. The author must:

1. Know every required field of the `TemplateV2` Zod schema (13 fields per RFC-002 §"Required fields").
2. Pick sensible defaults for `category`, `labels`, `requires`, `templateDependencies`, etc. (defaults that align with how the rest of the registry looks).
3. Write the `prompts[]` block with a `when` DSL that doesn't forward-reference.
5. Write the `files[]` block with correct `target` placeholders that resolve against the user's `deesse.json#aliases`.
6. Maintain a `templates-reference.md` (if the docs are hand-written), which is the load-bearing failure mode the schema-based approach avoids.

Each of these steps scales linearly with item count and is the dominant source of registry drift. A new author joining the team has to read RFC-002 + ADR-032 to onboard; with the tooling, they get an interactive scaffolder and an inline documentation command.

The three subcommands target each step:

| Author pain | Subcommand |
|---|---|
| "Did I get the schema right?" | `deessejs template validate` |
| "What should the defaults look like?" | `deessejs template new` |
| "What does `consumes[].target` mean again?" | `deessejs template explain consumes[].target` |

The tooling is **production-line equipment** for the registry, not a developer-experience toy. Each subcommand is unit-tested, integration-tested, and gated on a CI check.

## Detailed Design

The Detailed Design section **does not duplicate the spec at [ADR-034](./ADR-034-template-namespace)**. It points at the load-bearing decisions and explains the rationale.

### Namespace placement: `template` subcommand, not top-level

ADR-010 §1 pins the top-level command list to `init`, `list`, `info`, and (per ADR-033) `add`. Adding `validate`, `new`, or `explain` as top-level commands would violate the closed-list invariant. The `auth subcommand` exception (sanctioned in ADR-010 §1, refined across ADR-020 and ADR-022) is the precedent: a subcommand group at the top level (e.g. `deessejs auth login`) is sanctioned as long as the group itself is one entry in the closed list.

`deessejs template validate | new | explain` follows the same shape. The `template` group is **one entry** in ADR-010's'1's closed list (sanctioned by this ADR + ADR-034), and the three subcommands are entries in the group's internal table. Adding new subcommands to the group (e.g. a future `deessejs template publish`) does **not** require a new ADR; it requires a minor CLI surface change.

### Subcommand: `validate`

```
deessejs template validate [path]                [--strict] [--json]

  [path]              Path to a deesse-template.json file or a directory containing one (default: cwd)
  --strict            Run semantic checks (forward when refs, broken templateDependencies, missing files on disk)
  --json              Emit machine-readable JSON to stdout; exit codes unchanged
  --catalog <path>    Path to a registry catalogue (default: the @deessejs registry or deesse.json#registries)
```

**Behaviour**:

1. Load the descriptor at `[path]` (or `cwd/deesse-template.json` if `[path]` is a directory).
2. Parse through the `TemplateV2` Zod schema. **Shape errors** fail with exit 1 and a list of `{ path, message }` entries on stderr (or in the JSON output's `errors[]` array).
3. If `--strict`, run **semantic checks**:
   - Every `when: <expr>` reference must resolve to a defined prompt name (no forward references).
   - Every `templateDependencies[name]` must exist in the `--catalog` (or the loaded registry).
   - Every `files[].path` must exist on disk.
   - Every `prompts[].consumes[].target` must point at a defined `paths` / `aliases` / `tokens` key.
4. **Semantic errors** fail with exit 2 and a list of `{ code, path, message }` entries.

**Why two exit codes (1 and 2).** CI scripts can branch on exit code: `if [ $? -eq 1 ]; then ... shape error; elif [ $? -eq 2 ]; then ... semantic error; fi`. Without the split, a script cannot distinguish "the JSON is malformed" from "the JSON is well-formed but the references are wrong", two very different failure modes.

**Performance budget**. Validation must return in under 1 second for any single descriptor. The implementation lives at `apps/cli/src/template/validate.ts`; the file-system walk for `--strict` is bounded by the descriptor's `files[].path` list (not recursive). Unit-tested at `apps/cli/test/unit/template-validate.test.ts` with a benchmark fixture that asserts `<1s` on a 100-file descriptor.

### Subcommand: `new`

```
deessejs template new <slug>            [--from <yaml>] [--type <template:type>]
                                       [--registry <host>] [--path <dir>]

  <slug>               The item slug (becomes the directory name and the descriptor's name field)
  --from <yaml>        Path to a partial descriptor to seed the scaffolder (default: empty)
  --type <type>        The template:type discriminator (default: template:package)
  --registry <host>    Registry host to infer defaults from (default: @deessejs)
  --path <dir>         Output directory (default: ./templates/<slug>/)
```

**Behaviour**:

1. Read the registry catalogue from `--registry` (or the `@deessejs` registry by default). The catalogue is the list of items the registry publishes, a few hundred entries as the registry grows.
2. Compute the **mode** (most-frequent value) for each field across the items of the same `--type`. The mode is the simplest defensible default: it's explainable, reproducible, and doesn't require any ML machinery.
3. Merge the mode defaults with the `--from <yaml>` partial (the partial wins on conflict).
4. Run the interactive scaffolder: 11 questions (per ADR-034 §"What this rule allows") covering `category`, `labels`, `requires`, `dependencies`, `devDependencies`, `templateDependencies`, `prompts[]`, `files[]`, `hooks`, `postinstall`, and a final `name` confirmation.
5. Write the scaffolded `deesse-template.json` to `--path<dir>` (default `./templates/<slug>/`). The CLI creates the directory if missing.

**Why mode, not cluster**. The mode is the most-frequent value of each field across same-type items. A smarter inference could cluster items by similarity and propose the nearest cluster's values. The default is "mode" because:

- **Mode is explainable**: "this scaffolder suggested `category: 'auth'` because 14 of 16 `template:package` items have `category: 'auth'`." A future clustering approach would be opaque.
- **Mode is reproducible**: given the same registry snapshot, two runs of `deessejs template new` produce the same defaults. A clustering approach depends on the cluster algorithm's seed.
- **Mode is bounded**: the worst case is "the scaffolder suggested the most common value, which the user manually overrode". A clustering approach can suggest something wildly wrong that the user has to reject.

A smarter inference is a future ADR if the team finds mode too crude.

**Output**: a `templates/<slug>/` directory containing a valid `deesse-template.json` (already validated through the Zod schema) and a placeholder `README.md` (the author fills this in). The directory is ready to commit and push to a template repo.

### Subcommand: `explain <field-path>`

```
deessejs template explain <field-path>  [--json]

  <field-path>         Dot-path to a Zod field, e.g. `consumes[].target`, `prompts[].when`, `files[].transform`
  --json               Emit machine-readable JSON to stdout (default: human-readable text with examples)
```

**Behaviour**:

1. Parse `<field-path>` as a dot-path into the Zod schema. `consumes[].target` → `consumes.0.target` (the first item in the array, used as the schema reference).
2. Read the JSDoc `.describe(...)` block on the Zod field. The block has four sections (per ADR-034 §"What this rule allows"):
   - **Type**: the Zod type (e.g. `ZodEnum<['rename', 'interpolate', 'remove', 'merge']>`).
   - **Valid values**: the closed-list values, if any.
   - **Example**: a concrete descriptor snippet using the field.
   - **Common mistake**: a one-paragraph warning about the typical misuse.
3. Render as human-readable text or JSON (per `--json`). The human-readable text includes the four sections plus a cross-reference to the ADR that documents the field (e.g. `consumes[].target` → ADR-032 §"`consumes[]` in each prompt").

**Why JSDoc is the single source of truth**. Today, a reference for `deesse-template.json` fields has to be hand-maintained: every time a field is added or its semantics shift, the reference must be updated. With the JSDoc-on-Zod-schema approach, the schema is the reference. A change to `consumes[].target` (a new valid value, a new common mistake) automatically propagates to `deessejs template explain consumes[].target`. There is no `templates-reference.md` to drift out of sync.

The lint rule that enforces this contract lives at `packages/contracts/lint/jsdoc-required.ts`. It runs on every CI build in the `contracts` package; a missing or malformed `.describe(...)` block fails the contracts-package CI.

### JSON output default

`deessejs template validate --json` and `deessejs template explain --json` emit machine-readable JSON. The format is documented at `docs/cli-output-schemas.md` (to be written). The defaults are:

| Subcommand | Default output | JSON output flag |
|---|---|---|
| `validate` | Human-readable text on stderr; exit code on success | `--json` emits the `errors[]` array to stdout |
| `new` | Interactive scaffolder (always interactive; no JSON) | (no flag, the scaffolder is inherently interactive) |
| `explain` | Human-readable text on stdout | `--json` emits the `{ path, type, validValues, example, commonMistake, adrReference }` object to stdout |

The `--json` flag on `new` is **not in this contract** because the scaffolder is interactive by design (it asks 11 questions). A future ADR may add a non-interactive `--batch` mode that reads the answers from a YAML file (per the `--from <yaml>` partial).

## Implementation notes

These are the operational details that surfaced during the senior review. They are **not architectural blockers**, they are details that the implementation must capture.

### A. Registry catalogue access

`deessejs template new` reads the registry catalogue. The catalogue is fetched from the same CDN as the item descriptors (`registry.deessejs.com/catalogue.json`) and cached locally at `~/.deessejs/catalogue.json`. The cache is refreshed on ETag mismatch. CI mode (per ADR-033 §5b) refuses the fetch; the scaffolder in CI mode requires a pre-populated cache.

### B. JSDoc lint enforcement

The JSDoc contract is enforced at two levels:

1. **Schema-side**: `packages/contracts/lint/jsdoc-required.ts` runs on every CI build in the `contracts` package. It walks every Zod schema in the package and asserts that every closed-list field carries a `.describe(...)` block with the four sections (Type, Valid values, Example, Common mistake). Missing sections fail the build.
2. **Author-side**: `deessejs template validate --strict` runs the same lint against a user's descriptor and emits any JSDoc contract violations as semantic errors (exit 2).

The dual enforcement means a field cannot ship without a JSDoc contract, and a user's descriptor cannot reference a field without the contract being valid.

### C. Inference caching

`deessejs template new` computes the mode for each field across the registry catalogue. The computation is bounded: `O(items * fields)` per invocation, with `items` in the low hundreds and `fields` in the low dozens. The result is cached per registry snapshot in `~/.deessejs/inference-cache.json`. A new registry snapshot invalidates the cache.

### D. Tests

Unit tests live at `apps/cli/test/unit/template/` (one file per subcommand). Integration tests live at `apps/cli/test/integration/template/` and exercise the scaffolder against a fixture catalogue. The `--strict` semantic checks have a dedicated fixture suite at `apps/cli/test/fixtures/template-semantic/` with 12 fixtures covering forward `when` references, broken `templateDependencies`, missing files on disk, and the four sections of the JSDoc contract.

## Open Questions

Three design calls remain open and may be revisited in a follow-up ADR.

### Q1: Should `deessejs template new` infer `prompts[]` defaults?

Currently the scaffolder asks the user 11 questions including the prompts. A future ADR may infer `prompts[]` from the catalogue (e.g. "items of type `template:package` in the `auth` category tend to have these 3 prompts"). The inference would need a stricter JSDoc contract on the prompts fields and a clustering pass over the catalogue. Resolution tracked separately if a real use case surfaces.

### Q2: Should the lint rule live in `packages/contracts` or in `packages/eslint-config`?

Currently the rule lives in `packages/contracts/lint/` because it's tightly coupled to the Zod schemas. A future ADR may lift it into `packages/eslint-config` so the same rule applies to any project that imports the schemas. The current placement is correct for the load-bearing use case (CI gate on the contracts package); the future move is a packaging question, not a contract change.

### Q3: Should `deessejs template new --from <yaml>` accept a partial from stdin?

Currently the partial must be a file. A future ADR may add `--from -` to read from stdin (useful for piping in CI). Resolution tracked separately if a real use case surfaces.
