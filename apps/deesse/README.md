# deesse

Internal, compile-time framework prototype. This package is private and is not production-ready or publishable.

The prototype validates `DeesseConfig` and `DeesseInstance` inference, parsed Zod plugin arguments and inferred database/auth/API/extension contributions, readonly root-plugin tuples and `requires`, app and plugin oRPC router composition, Better Auth server-instance typing for application and Deesse-contributed plugins, the `deesse` and `deesse/react` public type surfaces, and a portable database capability contract that does not expose a provider client. Its type tests check exact router inputs/outputs, valid and invalid client calls, and that an empty API has no procedure keys.

`createDeesse()` currently returns a typed composition record only. It does not initialize services or serve requests; in particular, `auth` is a type-only placeholder and is not a constructed Better Auth instance. Its declared type is derived from Better Auth's `betterAuth<TOptions>` return type. The tests prove that an application-configured organization plugin and a Deesse-contributed username plugin both remain on the inferred server instance type. The React client bridge is a separate application-level module augmentation that lists the Better Auth client plugins, including `usernameClient()` and `inferAdditionalFields`; tests check the username endpoint input and result, the organization client's `checkRolePermission` input and result with invalid role rejection, and the inferred session user field. The prototype does not derive that client plugin list automatically from server contributions, and it does not merge plugins at runtime. Plugin factories parse registration arguments but do not initialize contributions. Source inference tests use local TypeScript path mappings for `deesse` and `deesse/react`; a separate consumer typecheck runs after declaration build with no such mappings and verifies both package exports resolve to their `dist/*.d.ts` targets. The client API member is a type placeholder, not a working transport client. The database fixture is a typed structural example, not a Drizzle adapter or a claim of Drizzle compatibility. The RFC's lifecycle, Hono dispatch, Next host adapter, database implementation, and runtime dependency validation remain out of scope for this slice.
