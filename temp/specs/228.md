## TL;DR

Add an opt-in `--verbose` flag that streams human-readable narration of each pipeline step to stderr, audit the real-create cancellation path to leave the filesystem in the same clean state the dry-run already guarantees, and confirm every failure path the user can recover from ships a `recovery` field in the JSON.

---

## Issue summary

The issue asks for two things: (1) an opt-in `--verbose` flag that never opens prompts and never changes exit semantics, with all progress and child-process diagnostics routed away from the structured JSON stdout; and (2) a closed, consistent result contract that covers generation (succeeded, skipped, failed), source SHA, manager, destination state, errors, and recovery — for every failure mode the user might encounter.

The dry-run + cancellation work in #241 already covers the dry-run side of (2). This PR extends the same shape to `--verbose`, the real-create cancellation path, and the remaining failure codes.

## Step-by-step implementation

### Step 1 — `--verbose` flag plumbing

#### 1.1. Add the option and thread `verbose` through `RunInput`

`apps/create-deesse-app/src/index.ts`:

- Add `.option("--verbose", "print human-readable progress to stderr (does not change JSON or exit semantics)")` to the commander program.
- Widen the inner `opts` type to `{ dir?: string; install: boolean; dryRun: boolean; verbose: boolean }`.
- Pass `verbose: opts.verbose` to `run(...)`.
- `apps/create-deesse-app/src/pipeline.ts`:
  - Add `verbose: boolean` to `RunInput`.
  - Construct a `Logger` once at the top of `run()` and pass it through the steps that narrate. The logger is built from `input.verbose`: `verbose: true` → `stderrLogger`, `verbose: false` → `nullLogger`.

The `Logger` is held in `RunState` (new `logger: Logger` field) so the steps can call it without each one re-deriving it.

#### 1.2. Pre-parse priority: `--version`/`-v` stay first

The pre-parse block at the top of `index.ts` (lines 22-26) short-circuits on `--version` and `-v` before Commander sees argv. `--verbose` is a separate flag with a different prefix; the pre-parse block is unaffected. No change here.

### Step 2 — Structured logger seam

#### 2.1. New `Logger` interface in `output/logger.ts`

The interface is intentionally tiny so the unit test can mock it with a single `vi.fn()`. Three methods cover everything the pipeline narrates:

```ts
export interface Logger {
  info(event: string, fields?: Record<string, string | number | boolean>): void
  warn(event: string, fields?: Record<string, string | number | boolean>): void
  error(event: string, fields?: Record<string, string | number | boolean>): void
}
```

The implementation writes one line per call to `process.stderr` with the `create-deesse-app:` prefix (dimmed when color is supported). Field rendering is `key=value` separated by spaces; values with spaces are wrapped in single quotes. `warn` adds a `(!)` marker after the prefix; `error` adds `(✗)`. This matches the style of `printInstallLog` and `warnInstallBootstrap` so the output is consistent.

#### 2.2. Two implementations: `nullLogger` and `stderrLogger`

`nullLogger` is the default; all three methods are no-ops. `stderrLogger` writes one line per call. Both are exported.

The dependency direction is correct: `pipeline.ts` imports from `output/logger.ts`; `output/logger.ts` imports from `picocolors` (already a project dep) only. `result.ts` is not touched.

### Step 3 — Pipeline narration events

#### 3.1. Where narration fires in `run()`

Each step gets a single `logger.info` call immediately before the work starts, and (where it adds value) a `logger.info` on success. The events are:

| Boundary | Event name | Notes |
|---|---|---|
| Before `guardInvocationAndArgs` | `validating arguments` | Always silent under `--verbose` (cheap) — only fired on failure via `logger.error`? No: guard is cheap and fast; skip the narration entirely. |
| Before `fetchSource` | `resolving source SHA` | Once at start |
| After `fetchSource` returns | `resolved source SHA` (with `sha` field) | Single info line |
| Before `validateAndStage` | `validating archive entries` | |
| After `validateEntries` succeeds | `validated N entries` (with `count` field) | |
| After extract + rename in `validateAndStage` | `staged template` (with `tempDir` field) | |
| For real-create path, after `publishProject` | `published project` (with `destination` field) | |
| Before `resolvePrereqs` (real-create only) | `probing install prereqs` | |
| After prereqs resolve | `install strategy: <strategy>` (with `strategy` field) | Reuses `warnInstallBootstrap` wording shape but does not write the bootstrap line (that's separate) |
| For `--dry-run`: after `buildDryRunResult` | `dry-run plan ready` | |
| For real-create `--no-install`: | `install skipped` (with `recovery` field) | |
| For real-create with install: | `running install` (with `cwd` field) | |
| For real-create, after `runInstall` returns ok: | `install completed` | |
| In the catch arm: | `error: <code>` (with `code`, `message` fields) | Single `logger.error` line |

The narration does NOT include the install child's stdout/stderr (that already lives in `printInstallLog` for the failure path; live install output is captured but not mirrored under `--verbose` because the user is running `pnpm install` and sees its output already).

#### 3.2. Wording per event

Wording is short, imperative, and free of timestamps (the user knows the time). The full per-event wording lives in the implementation; the README example shows the output shape.

### Step 4 — Real-create cancellation diagnostics

#### 4.1. What the catch arm does on a real-create abort

The dry-run + SIGINT plumbing in `pipeline.ts` (the `AbortController` at the top of `run`, the `state.tempDir` assignment BEFORE extract, the catch arm routing AbortError to a `CreateFailure` with `mode: state.input.dryRun ? "dry-run" : "create"`) was designed to be mode-agnostic. The real-create path was already covered by the same code; the only thing missing is the test.

This step adds the test (`pipeline-real-create-cancel.test.ts`) that asserts:

- The destination is NOT on disk.
- The staging tempdir `<dir>.staging.<uuid>` is NOT on disk.
- The JSON result is `ok: false, projectCreated: false, error.code: "aborted"`.
- The mode reflects `state.input.dryRun === false` → `mode: "create"`.

#### 4.2. Add `aborted` factory and `error.code: "aborted"` to the closed code set

`apps/create-deesse-app/src/errors/index.ts` and `apps/create-deesse-app/src/errors/abort.ts`:

- Add `"aborted"` to the `CreateAppErrorCode` union in `index.ts`. The reviewer in the #241 round called out that the JSON `error.code` was `string` (loose); the `CreateAppErrorCode` union is the canonical closed set. Adding `"aborted"` makes it a first-class code instead of a stringly-typed one.
- Replace the current `aborted()` import in `pipeline.ts` with a factory that uses the new code. The factory lives in `errors/abort.ts` already; the change is the `code` literal it returns.

### Step 5 — Recovery round-trip on every failure path

#### 5.1. Audit existing failure paths for `recovery` completeness

Walk every `CreateFailure` constructor in the codebase and confirm `recovery` is set whenever the user can re-attempt:

| Failure path | `recovery` today | After this PR |
|---|---|---|
| `destination_exists` (in `validateDestination`) | absent | Unchanged: the user must pick a different `--dir`; there is no command to retry. The hint is sufficient. |
| `invalid_name` | absent | Unchanged: pick a different name. |
| `unsafe_archive` | absent | Unchanged: the archive is malformed; retrying won't help. |
| `unsupported_manager` | absent | Unchanged: the user must change invocation. |
| `network_error` | absent | Unchanged: transient; the user retries the whole command. The whole command is its own recovery. |
| `source_failed` (missing `packageManager`) | absent for dry-run no-install; present for live no-install | Unchanged; the shape of `buildNoInstallResult`'s `recovery: null` branch on `source_failed` is correct: a malformed `packageManager` field gives the user no command to run, so the field is `null`. |
| `install_failed` (live path) | present | Unchanged. |
| `aborted` (new) | absent | Add a `recovery` value: the user can re-run the same command. The recovery is the exact CLI invocation. We compute it from `state.input.dir` and `state.input.projectName`: `cd '<dir>' && pnpm dlx create-deesse-app@latest <name>` (POSIX) / `cd /d "<dir>" && pnpm dlx create-deesse-app@latest <name>` (Windows). This is the same platform-aware quoting the install-recovery helpers use; we extract the platform branch into a tiny `recoveryCommandForReRun` helper to keep both call sites consistent. |
| `internal` (catch-all) | absent | Unchanged: a recovery is meaningless for an unexpected internal error. |

The `recoveryCommandForReRun` helper lives next to `recoveryCommand` in `install/recovery.ts`; it takes `{ cwd, name }` and emits the platform-shaped `cd` + `pnpm dlx create-deesse-app@latest <name>` line. The `@latest` is intentional: the user is re-running the same install flow, and the version of the CLI they got before is the one that got interrupted.

## Risks / edge cases

- **Logger is a process-wide singleton in stderr mode.** Concurrent invocations of `create-deesse-app` (e.g. parallel CI jobs piping to the same terminal) would interleave stderr lines. This is the same trade-off `printInstallLog` already accepts; it is the standard CLI behavior and not a regression.
- **`--verbose` and `--version` are independent flags.** A user who runs `-v` gets the version output and exits; a user who runs `--verbose` enters the pipeline. They cannot combine. The README spells this out.
- **The new `recoveryCommandForReRun` ships the literal `@latest` tag.** This pins the user to whatever npm serves at the time of the re-run, not the version they originally used. This is intentional: the original install was interrupted; re-running through `dlx` against the original tag is unlikely to be available, and the user can pin themselves if they need reproducibility.
- **The closed `CreateAppErrorCode` set widens with `"aborted"`.** Downstream tooling that pattern-matches on a known list must add `"aborted"`. This is acceptable: the JSON `error.code` has been loosely typed from the start, and the union is the canonical source of truth going forward.
