## TL;DR

Add a `--dry-run` flag to `create-deesse-app` that runs the same argument validation, source resolution, archive validation, and install-strategy planning as a real create, but never touches the destination, never runs install, never executes template code, and never initialises Git. The CLI exits 0 with one JSON object containing `mode: "dry-run"`, the actually-resolved `source.sha`, the planned entry list, the install command (or `skipped: true` under `--no-install`), and a documentation URL.

---

## Issue summary

Issue #227 is the planning-mode child of #225 and the natural complement of #226. The motivating need is CI-friendly and human-friendly previews: a developer or a script wants to know what `create-deesse-app my-project` will do *before* a project directory is materialised, what SHA of `deessejs/saas-template` would be used right now, what files would be created, and which install command would run. The contract the issue calls out: a dry-run must perform the same validation, the same SHA resolution, and the same prereq probing as a real create — printing the destination without retrieving and validating the source is explicitly rejected as not a meaningful preview. Conversely, the dry-run must not create files at the destination, run install subprocesses, init Git, or execute template code. Temporary staging outside the destination is allowed and must be cleaned on success, failure, and handled cancellation. The JSON mode changes from `"create"` to `"dry-run"` and `projectCreated` is always `false`. Saved-plan execution and revision pinning are explicitly out of scope.

## Step-by-step implementation

### Step 1 — Extend `RunInput` and result types with a `mode: "dry-run"` variant

`apps/create-deesse-app/src/result.ts`

The current union is `CreateResult = CreateSuccess | CreateInstallFailure | CreateFailure`, with `mode: "create"` on every variant. A dry-run is mutually exclusive with `projectCreated: true` (no project exists yet) and `installed: true` (no install ran). The cleanest discriminator is the `mode` field, which the current code already uses as a literal type.

#### 1.1 — `ResultMode` widens to `"create" | "dry-run"`

```ts
export type ResultMode = "create" | "dry-run"
```

`mode` stays a literal field on every variant. Scripts that read JSON can switch on it.

#### 1.2 — `CreateDryRunResult` discriminated union

```ts
export type PlannedEntry = {
  /** Normalized relative path inside the project, e.g. "src/index.ts". */
  path: string
  /** Size in bytes from the tarball entry header. */
  size: number
  /** Entry mode, decimal. */
  mode: number
}

export type DryRunInstall =
  | { skipped: false; strategy: InstallStrategy; command: InstallCommand; prereqs: { corepack: boolean; npm: boolean; pnpm: boolean } }
  | { skipped: true }

export type CreateDryRunResult = {
  ok: true
  mode: "dry-run"
  projectCreated: false
  installed: false
  source: ResultSource
  destination: string
  packageName: ResultPackageName
  packageManager: ResultPackageManager
  install: DryRunInstall
  plannedFiles: PlannedEntry[]
  documentation: string
  recovery: null
}
```

Three things to note:

- `install` is a discriminated union, not a flat optional. `skipped: true` carries no `strategy`/`command`/`prereqs`; the TypeScript narrowing prevents a script from reading them when they are absent.
- `projectCreated` and `installed` are *required and literal `false`*, matching the convention the install-failure variant established.
- `recovery` is `null` — there is no recovery to print because the dry-run did not attempt anything that could fail. (The error variants of dry-run — abort, source failure, archive failure — flow through the existing `CreateFailure` path; they do not need a recovery.)

`CreateResult` becomes:

```ts
export type CreateResult =
  | CreateSuccess
  | CreateInstallFailure
  | CreateDryRunResult
  | CreateFailure
```

The first three are mutually exclusive on `ok` and `mode`. `CreateFailure` is the catch-all for `ok: false` and remains the only variant that may carry `error`. Scripts read `result.mode` first, then narrow.

#### 1.3 — `RunInput.dryRun` flag

`apps/create-deesse-app/src/pipeline.ts`

```ts
export type RunInput = {
  projectName: string
  dir: string
  install: boolean
  dryRun: boolean
}
```

`dryRun` is independent of `install`. The CLI accepts all four combinations:
- `--dry-run` alone → probe install prereqs, plan, no run.
- `--dry-run --no-install` → skip prereqs, `install.skipped: true`.
- (no flag) → real create, with install.
- `--no-install` → real create, no install.

### Step 2 — `validateEntries` returns the entry list

`apps/create-deesse-app/src/extract/validate-entries.ts`

The current signature throws on malformed archives and otherwise returns `void`. The dry-run needs the *normalized* list of planned files: the same shape the real extraction would have written. We change the return type to keep the entry list.

#### 2.1 — Replace `Promise<void>` with `Promise<{ entries }>`

```ts
export type ValidateEntriesResult = {
  entries: PlannedEntry[]
}

export const validateEntries = async (
  args: ValidateEntriesArgs,
): Promise<ValidateEntriesResult> => { ... }
```

Implementation: same loop as today (rejects prefix deviation, path-traversal, normalized collisions, symlinks, special files, absolute paths). When `onentry` accepts an entry, push a `PlannedEntry` (with the path normalized post-strip) onto a local array. Return the array. No new IO — the entry list is collected during the read pass the function already performs.

The `unsafe_archive` throw path is unchanged. A malformed archive in a dry-run must produce the same `CreateFailure` with `error.code === "unsafe_archive"` that real execution produces; the dry-run does not get a different error code for the same defect.

#### 2.2 — Update callers in `pipeline.ts`

Two callers in `pipeline.ts`:
- `validateAndStage` (step 3) already calls `validateEntries`. Capture the return value into `state.validatedEntries`.
- A new `buildDryRunResult` step (step 4) reads `state.validatedEntries` to populate `plannedFiles`.

No test needs a JSON-equality update because the existing tests only check that `validateEntries` throws on bad input; they do not check the return value.

### Step 3 — AbortController plumbing

`apps/create-deesse-app/src/pipeline.ts`, `apps/create-deesse-app/src/source/resolve-sha.ts`, `apps/create-deesse-app/src/source/download-tarball.ts`, `apps/create-deesse-app/src/extract/extract.ts`

The issue requires the staging tempdir to be cleaned on *handled cancellation*, not just on completed function calls. A `SIGINT` mid-`extractTarball` is the canonical example.

#### 3.1 — `AbortSignal` threaded through `fetchSource` and `validateAndStage`

```ts
type RunState = {
  ...
  abortController: AbortController
}
```

`run()` constructs the `AbortController` at the top and threads `abortController.signal` into:

- `fetchSource(state)` → `resolveTemplateSha({ ..., signal })` and `downloadTarball({ ..., signal })`. The `fetch` in `downloadTarball` accepts `signal`; `resolveTemplateSha` calls `fetch` too, the same way.
- `validateAndStage(state)` → `extractTarball({ ..., signal })`. The `tar` package accepts `signal` from v7.0.0; we pin to that floor in `package.json` and add a `tar.t({ signal })` / `tar.x({ signal })` call.

When the signal aborts, the underlying `fetch` and `tar` calls reject with an `AbortError`. The pipeline's `try`/`catch` translates this to a new `CliError` with `code: "aborted"`, message "dry-run was cancelled before completion", and `hint: "re-run the command to retry"`. The catch arm at the top of `run` already routes `CliError` into `CreateFailure`; nothing else changes.

#### 3.2 — SIGINT handler in `run()`

```ts
const onSigint = () => abortController.abort()
process.once("SIGINT", onSigint)
try { ... } finally { process.off("SIGINT", onSigint) }
```

The handler is `process.once`, not `process.on`, so the second SIGINT (the user's "I really mean it") falls through to the default Node behavior — kill the process. That is the right default: the first SIGINT aborts the in-flight IO and triggers the cleanup path; the second SIGINT means "this is hung, terminate it now". The handler is removed in `finally` so it does not leak into other code paths.

`SIGTERM` is not handled — the create-deesse-app CLI is a one-shot command, not a long-running daemon, and the convention in this repo is to let SIGTERM kill the process.

### Step 4 — `buildDryRunResult` step in the pipeline

`apps/create-deesse-app/src/dry-run/build-dry-run-result.ts`

This is the only new step in the pipeline. It is a pure function over `RunState` plus the validated entry list.

#### 4.1 — Branch between step 3 (`validateAndStage`) and step 4 (`publishProject`)

```ts
// In pipeline.ts run():
await validateAndStage(state)
if (state.input.dryRun) {
  return buildDryRunResult(state)
}
await publishProject(state)
```

Two consequences of branching here:

- `publishProject` is not called → no `renameRootPackage`, no `publishOrRollback`, no `tempDir` ownership transfer. The destination does not exist on disk when `buildDryRunResult` returns.
- The `state.tempDir` cleanup is the dry-run's responsibility: `buildDryRunResult` calls `cleanupState` itself before returning, so a dry-run run never leaves a tempdir behind. The signal-driven abort path uses `cleanupState` too (it's already in the `catch` arm).

#### 4.2 — Prereq resolution parity with real execution

`buildDryRunResult` calls `readGeneratedPnpmVersion(state.tempDir)` (the version lives in the staging tempdir, not the destination — the destination does not exist). It then calls `probeInstallPrereqs()` and `pickInstallStrategy({ ... })` if and only if `state.input.install` is true. The exact same code paths as `resolvePrereqs`, called from a different step. We extract the prereq-resolution body into a helper so the real-create path and the dry-run path share it:

```ts
// In pipeline.ts:
const resolvePrereqs = (state: RunState, versionReader: (dir: string) => string): void => {
  if (!state.input.install) return
  state.prereqs = probeInstallPrereqs()
  state.pnpmVersion = versionReader(...)
  state.strategy = pickInstallStrategy({ ... })
  state.installCommand = pnpm.installCommand(state.strategy, state.pnpmVersion)
  warnInstallBootstrap(state.strategy)
}
```

The real-create path passes `state.input.dir` to `versionReader`; the dry-run passes `state.tempDir`. The probe, strategy, and warning are identical.

#### 4.3 — JSON shape

`buildDryRunResult` builds and returns a `CreateDryRunResult` literal. The fields and the rules that determine which are present:

| Field | Source | Notes |
|-------|--------|-------|
| `ok` | literal `true` | |
| `mode` | literal `"dry-run"` | |
| `projectCreated` | literal `false` | |
| `installed` | literal `false` | |
| `source` | `buildSource(state.sha)` | the *real* SHA, not a promise |
| `destination` | `state.input.dir` | the path the user passed, even though no directory is created there |
| `packageName` | `renameRootPackage({ tempDir: state.tempDir, newName: state.input.projectName })` — re-read from the staging tempdir's renamed `package.json`. Wait — we already rename the package in step 3 (`renameRootPackage` is called inside `validateAndStage`? No, it's called inside `publishProject`. Need to move it. See step 4.4.) |
| `packageManager` | literal `"pnpm"` | |
| `install` | the union, with `skipped: !state.input.install` | `strategy` and `command` are populated from the prereq path; `prereqs` from the probe |
| `plannedFiles` | `state.validatedEntries` | normalized paths, sizes, modes |
| `documentation` | `"https://docs.deessejs.com/getting-started"` | hardcoded for this increment |
| `recovery` | literal `null` | |

#### 4.4 — `renameRootPackage` runs in the staging step, not the publish step

`apps/create-deesse-app/src/pipeline.ts`, `apps/create-deesse-app/src/destination/rename-package.ts`

The current order is `validateAndStage` (extract to tempdir, no rename) → `publishProject` (rename `package.json` in tempdir, then atomic rename into destination). For the dry-run, we need the package rename to happen *before* the dry-run branch — because the planned `packageName` is "what the user's project would be named" and the staging tempdir has the template's original name. The clean fix is to move `renameRootPackage` from `publishProject` into `validateAndStage` (after extraction, before the dry-run branch). `publishProject` then becomes just the atomic rename. The behavior for the real-create path is unchanged: the package still has the right name at the moment the destination is populated, because the rename happened in tempdir.

This refactor is small and self-contained. The existing tests for `renameRootPackage` continue to pass (same call site, different module entry).

### Step 5 — CLI: `--dry-run` flag and option wiring

`apps/create-deesse-app/src/index.ts`

#### 5.1 — Add `.option("--dry-run", ...)` in `index.ts`

```ts
program
  .name("create-deesse-app")
  .description("Initialize a new DeesseJS project from the current main of deessejs/saas-template.")
  .version(readPackageVersion())
  .argument("<project-name>", "Name of the project to create")
  .option("--dir <path>", "Destination directory", defaultDir)
  .option("--no-install", "Skip the install step (the generated project is not run)")
  .option("--dry-run", "Plan the create without writing files, running install, or executing template code")
  .action(...)
```

`--dry-run` and `--no-install` are independent options. Commander 12 already supports this combination. `parsed.opts()` returns `{ install: boolean, dryRun: boolean, dir: string }`.

#### 5.2 — Conflict-free with `--no-install` and `--dir`

There is no conflict. `--dry-run --no-install` is a valid combination (the dry-run plan reports `install.skipped: true`). `--dry-run` is a no-op for `--dir` — `state.input.dir` is still the destination the plan reports, even though no directory is created there. The `printResult` step is identical to the real-create path: one JSON object on stdout, exit 0, no stderr chatter (the dry-run does not need install diagnostics because nothing ran).

### Step 6 — Tests of the dry-run boundary

The issue is explicit: tests must verify *actual filesystem / subprocess boundaries*, not just flag reflection. The same template as `pipeline-install-failure.test.ts` applies — mock the network, leave the filesystem and the extraction real.

#### 6.1 — `test/unit/dry-run-pipeline.test.ts`

Real-tarball fixture (same builder as `pipeline-install-failure.test.ts`). Mocks:

Assertions:

- `result.ok === true`
- `result.mode === "dry-run"`
- `result.projectCreated === false`, `result.installed === false`
- `result.source.sha === "abcdef…01"`
- `result.destination === <workRoot>/<name>`
- `result.install.skipped === false`, `result.install.strategy` is one of `"corepack" | "npm-exec" | "pnpm-direct"`
- `result.install.command` matches the same shape `manager.installCommand(...)` would produce for the same strategy and version
- `result.plannedFiles` is a non-empty array; each entry has `path`, `size`, `mode`; the first entry's path equals `"LICENSE"` or `"package.json"` (whichever the fixture puts first)
- `result.documentation === "https://docs.deessejs.com/getting-started"`
- `result.recovery === null`
- `vi.mocked(runInstall)` was never called
- The destination directory does *not* exist on disk
- The staging tempdir does *not* exist on disk (cleanup ran)
- `process.exitCode` is `undefined` (the dry-run exits 0 by default; the test does not call `process.exit`)

A second test asserts the *failure* path: a malicious tarball (a `../` entry, a symlink, a special file) is fed into `validateEntries`. The dry-run returns `result.ok === false` and `result.error.code === "unsafe_archive"`. The destination and the staging tempdir are both absent.

#### 6.2 — `test/unit/dry-run-cancel.test.ts`

This is the test the issue specifically calls out. It uses an `AbortController` and aborts mid-`validateAndStage` by mocking `extractTarball` to throw an `AbortError` after a microtask delay. The pipeline's catch arm translates the abort to a `CreateFailure` with `error.code === "aborted"`.

Assertions:

- `result.ok === false`, `result.error.code === "aborted"`
- The destination does not exist on disk
- The staging tempdir does not exist on disk (cleanup ran in the catch arm)
- `process.exitCode` is `1` (the abort path is a failure)

A complementary test injects a SIGINT by emitting the event on `process` directly:

```ts
process.emit("SIGINT")
await new Promise(setImmediate)
```

asserting the same outcome. This test is the bridge from `AbortController` to the user-visible SIGINT handler. (The mock must `vi.mock` the `process` event so the test is deterministic; otherwise the real handler kicks the runner.)

#### 6.3 — `test/unit/dry-run-no-install.test.ts`

`--dry-run --no-install`. Mocks:

- `probeInstallPrereqs` is *spied on* with `vi.fn()` and asserted to *not* be called.
- `pickInstallStrategy` is *spied on* and asserted to *not* be called.

Assertions:

- `result.install.skipped === true`
- The JSON has no `install.strategy`, no `install.command`, no `install.prereqs` (TypeScript's exactOptionalPropertyTypes already forbids them; the test confirms they are absent at runtime via `JSON.stringify(result).includes(...)`).

#### 6.4 — `test/unit/result-dry-run.test.ts` (JSON serialization)

Pure unit test on the `CreateDryRunResult` type. Builds a hand-rolled `RunState`, calls `buildDryRunResult`, asserts the result round-trips through `JSON.parse(JSON.stringify(result))` with the same field set. Verifies the field set the contract requires, byte for byte.

#### 6.5 — `test/e2e/smoke/native-smoke.test.ts` (CLI invocation)

A new `it("runs --dry-run, exits 0, returns mode dry-run, leaves no destination")`. The CLI is invoked as a child process (the existing pattern in the file). Assertions:

- `exitCode === 0`
- `stdout` parses as JSON, `result.mode === "dry-run"`, `result.ok === true`

These two tests run on every supported platform (Linux, macOS, Windows) per the existing `native-smoke` matrix. They are the only `e2e/` tests for the dry-run; the full e2e journey (Verdaccio, PostgreSQL, generated-app Playwright) is unnecessary because the dry-run has no real installation to test.

## Risks / edge cases

- **Drift between dry-run SHA and real-create SHA.** The issue explicitly accepts this risk: "a later invocation fetches the then-current main and may differ from the dry-run SHA." The README documents it in one sentence under "Dry-run". We do not pin revisions or save plans in this increment.
- **`renameRootPackage` moved into `validateAndStage`.** The current code renames in `publishProject`. The dry-run needs the renamed `package.json` to exist before the dry-run branch fires, so the rename has to happen in tempdir, before `publishProject`. The move is a 4-line refactor in `pipeline.ts`; the rename helper itself is unchanged. Risk: a regression in the real-create path if the rename has a side effect on the tempdir structure that the publish step depends on. The existing real-create tests (`pipeline-install-failure.test.ts`, `publish-or-rollback.test.ts`) cover this and must stay green.
- **AbortController + `tar` package version.** `tar` v7.0.0+ supports a `signal` option on `tar.t` and `tar.x`. We pin to that floor in `package.json` (the repo's `tar` is already at v7+ via the catalog; confirm in `apps/create-deesse-app/package.json`). If the catalog resolves to a version below 7, we either bump the floor or add a `try { ... } catch (err) { if (err.name === "AbortError") ... }` shim around the call.
- **SIGINT handler removal on `process.exitCode = 0` paths.** The `try { ... } finally { process.off("SIGINT", onSigint) }` shape is correct: the handler is removed whether the pipeline succeeded, failed, or aborted. Risk: a test that triggers SIGINT and does not return a Promise the test awaits could leak the handler. The cancel test waits on the abort.
- **Dry-run of a destination that already exists.** The current `validateDestination` rejects an existing destination with `destination_exists`. That rejection happens in step 1 (`guardInvocationAndArgs`), *before* any IO. The dry-run inherits this behavior: `create-deesse-app my-project --dry-run` against an existing `./my-project` returns `ok: false`, `error.code: "destination_exists"` — the user learns the destination is taken without us even resolving the SHA. This is the right call: a dry-run should not silently overwrite the user's intent, even in plan mode.
- **JSON schema is a contract.** Adding a `CreateDryRunResult` variant is an additive change to the union, which is a non-breaking change for any script that switches on `mode`. Scripts that read the JSON without checking `mode` and assume `projectCreated: true` will need to handle the dry-run case; that is a 1-line check and is documented in the README.
- **Dry-run does not validate the destination is writable.** The issue explicitly says: "Revalidate at actual creation." We do not pre-check writability in dry-run. Real execution revalidates.
- **Out of scope (deliberate, per the issue body):** human-readable rendering of the plan (separate "verbose output" issue, #228); persisted plans and replay tokens; revision pinning; dry-run of a pre-existing project directory (refactor preview).
