> **Scope correction (2026-10-17).** The original issue body asked the CLI to convert the saas-template to an npm project. After discussion with the developer, the scope is narrower: the CLI must be invokable via `npx create-deesse-app@latest`, but the generated project stays a pnpm project. There is no template conversion, no `--package-manager` flag, and no `npm` row in `PackageManagerId`. The issue body will be re-framed on the GitHub side; this spec reflects the new scope.
>
> **Strategy correction (2026-10-17, post-review).** The first draft used `corepack prepare pnpm@X --activate` and resolved the resulting shim from a private cache path. The second draft switched to `corepack pnpm install` when corepack is on `PATH`, falling back to `pnpm install` otherwise. The third draft, after the second review, accepts that **Node 25 unbundles corepack** ([Node.js Corepack documentation](https://nodejs.org/api/corepack.html)). A `pnpm install` fallback on Node 25 fails when pnpm is not on `PATH`, which contradicts the package's declared `engines.node: ">=20.0.0"`. The install bootstrap must therefore have a third path that does not depend on corepack: `npm exec -- pnpm@11.0.0 <args>`. npm ships with every Node ≥ 16, including Node 25, and `npm exec` runs a binary from npm's cache without modifying the user's `PATH`. This is the fallback chosen for this increment.

## TL;DR

`npx create-deesse-app@latest <name>` and `pnpm dlx create-deesse-app@latest <name>` both run the same pipeline and produce the same pnpm-managed project. The CLI no longer rejects npm-spawned invocations. The install command is chosen at runtime from three paths, in order:

1. **`corepack pnpm install`** when corepack is on `PATH` (Node 20–24 default).
2. **`npm exec -- pnpm@11.0.0 install`** when corepack is absent but npm is on `PATH` (Node 25 fallback).
3. **`pnpm install`** when pnpm is already on `PATH` (any Node, when the user pre-installed it).

A single warning line on stderr announces the chosen path. With `--no-install`, the install step is skipped entirely — no corepack, no npm, no pnpm is invoked.

---

## Issue summary

Today, the CLI throws `unsupported_manager` when invoked via `npx` or `npm exec`. The first working increment (#225) explicitly chose this trade-off. The new increment relaxes it: the CLI accepts any invoker, picks the best install bootstrap for the runtime, and runs the install. The generated project remains pnpm. The CLI also satisfies the package's declared `engines.node: ">=20.0.0"` on every supported Node, including Node 25 where corepack is unbundled.

## Step-by-step implementation

### Step 1 — Drop the npm-invocation guard

`apps/create-deesse-app/src/pm/detect-invoker.ts`, `apps/create-deesse-app/test/unit/detect-invoker.test.ts`, `apps/create-deesse-app/src/pipeline.ts`

- Delete `assertNotNpmInvocation` and its test file.
- Remove the import in `pipeline.ts:guardInvocationAndArgs`. The function now only validates `projectName` and `destination`.
- The `unsupported_manager` error code stays exported. No code path throws it in this increment; it is preserved as a closed enum value for future use.

Why this step first: it is a strict removal. CI turns green only on the suite, not on the install path. No semantic change yet — an `npx` user without pnpm or corepack will still fail at the spawn step with the existing ENOENT handler.

### Step 2 — Corepack probe and three-way install command

`apps/create-deesse-app/src/pm/install-strategy.ts` (new), `apps/create-deesse-app/src/pm/probe-paths.ts` (new), `apps/create-deesse-app/src/pm/manager.ts`, `apps/create-deesse-app/src/pm/pnpm.ts`, `apps/create-deesse-app/src/install/run.ts`, `apps/create-deesse-app/src/install/recovery.ts`, `apps/create-deesse-app/src/pipeline.ts`, `apps/create-deesse-app/test/unit/install-strategy.test.ts` (new), `apps/create-deesse-app/test/unit/probe-paths.test.ts` (new), `apps/create-deesse-app/test/unit/install-command.test.ts` (new), `apps/create-deesse-app/test/unit/recovery.test.ts`

- `apps/create-deesse-app/src/pm/install-strategy.ts` exports a single pure function:
  ```ts
  export type InstallStrategy = "corepack" | "npm-exec" | "pnpm-direct"

  export const pickInstallStrategy = (input: {
    corepackAvailable: boolean
    npmAvailable: boolean
    pnpmAvailable: boolean
    version: string
  }): InstallStrategy => {
    if (input.corepackAvailable) return "corepack"
    if (input.npmAvailable) return "npm-exec"
    if (input.pnpmAvailable) return "pnpm-direct"
    throw unsupportedManager("pnpm")
  }
  ```
  The order is documented in the function: corepack is preferred (no global pnpm install), then `npm exec` (no corepack needed, works on Node 25), then a direct `pnpm` invocation. The throw at the end produces the existing `unsupported_manager` error code with a hint that names three manual-install paths.
- `apps/create-deesse-app/src/pm/probe-paths.ts` exports:
  ```ts
  export type InstallPrereqs = { corepack: boolean; npm: boolean; pnpm: boolean }
  export const probeInstallPrereqs = (
    env: NodeJS.ProcessEnv = process.env,
    runner: SyncRunner = defaultRunner,
  ): InstallPrereqs
  ```
  The default runner is:
  ```ts
  const probe = (bin: string): boolean => {
    const which = process.platform === "win32" ? "where" : "which"
    const r = runner(which, [bin])
    return r.status === 0
  }
  ```
  Each probe uses `spawnSync` with a 5 s timeout and `stdio: "ignore"`. The function never throws — on any failure (binary missing, timeout, non-zero exit) the corresponding flag is `false`. On Windows, the `where` builtin reads `PATHEXT` correctly (so `where corepack` matches `corepack.cmd`); the test for the Windows branch is a docstring-documented expectation, not a CI-run unit test (CI runs Linux).
- `apps/create-deesse-app/src/pm/manager.ts` updates the `installCommand` signature:
  ```ts
  installCommand(strategy: InstallStrategy, version: string): InstallCommand
  ```
  The closed `PackageManagerId` enum stays `"pnpm"`. The stale `// #226 adds "npm"` comment is removed.
- `apps/create-deesse-app/src/pm/pnpm.ts`:
  ```ts
  export const pnpm: PackageManager = {
    id: "pnpm",
    installCommand: (strategy, version) => {
      switch (strategy) {
        case "corepack":
          return { bin: "corepack", args: ["pnpm", "install"] }
        case "npm-exec":
          // npm downloads pnpm@version into its cache and runs
          // the binary directly; no global install, no PATH
          // modification. Works on every npm ≥ 7 (Node 16+).
          return { bin: "npm", args: ["exec", "--", `pnpm@${version}`, "install"] }
        case "pnpm-direct":
          return { bin: "pnpm", args: ["install"] }
      }
    },
    lockfileName: "pnpm-lock.yaml",
    requiresCorepack: false,
  }
  ```
  The version (`11.0.0`) is a single source of truth in the repo. It is read from the same `packageManager` field of `apps/create-deesse-app/package.json` that the version banner uses, via a new `readPnpmVersion()` helper that mirrors the existing `readPackageVersion()`. The helper's env var is `CREATE_DEESSE_APP_PNPM_VERSION`; the drift-guard test in `package-version.test.ts` extends to cover it. (The previous draft argued for letting corepack read `packageManager` from the generated project at install time. That is still true, but the CLI's recovery command and the install command need a version string, so we read it here too. If the two ever disagree, that is a separate bug.)
- `apps/create-deesse-app/src/install/run.ts`: signature becomes `runInstall({ command: InstallCommand, cwd: string })`. The function spawns `command.bin` with `command.args`. The rest is unchanged.
- `apps/create-deesse-app/src/install/recovery.ts`: `recoveryCommand({ command: InstallCommand, cwd })` builds `<cd> <dir> && <bin> <args>...`. The output matches the install command that was actually used.
- `apps/create-deesse-app/src/pipeline.ts`:
  - The `corepackAvailable` probe is replaced by `probeInstallPrereqs()`, called **only when** `state.input.install === true`. The result is stashed on `RunState` as `prereqs: InstallPrereqs`.
  - `runInstallAndBuildResult` calls `pickInstallStrategy({ ...state.prereqs, version: readPnpmVersion() })` and passes the result to `pnpm.installCommand`. The recovery field uses the same command.
  - The `--no-install` path does not call `probeInstallPrereqs`, does not pick a strategy, and does not run the install. Its recovery field is a fixed literal (see Step 4).
- `apps/create-deesse-app/test/unit/install-strategy.test.ts`: eight cases covering every combination of the three boolean inputs and confirming the throw at the all-false case.
- `apps/create-deesse-app/test/unit/probe-paths.test.ts`: stub the runner; test each probe's success and failure path. The timeout case uses a runner that returns `{ status: null, signal: "SIGTERM" }` to simulate a 5 s timeout firing.
- `apps/create-deesse-app/test/unit/install-command.test.ts`: three cases, one per strategy. The version `11.0.0` is the only version tested; pinning it here catches accidental `pnpm@latest` regressions.
- `apps/create-deesse-app/test/unit/recovery.test.ts`: cover all three strategy forms in the recovery output. The `npm-exec` form must be `<cd> <dir> && npm exec -- pnpm@11.0.0 install` (verbatim, including the `--`).

Why this step second: the strategy is the load-bearing decision. Every later step uses the value this step produces. Validating the strategy in isolation (no I/O) keeps the tests fast.

### Step 3 — Honest warning text

`apps/create-deesse-app/src/install/warn-corepack.ts` (new), `apps/create-deesse-app/src/install/run.ts`, `apps/create-deesse-app/src/pipeline.ts`, `apps/create-deesse-app/test/unit/warn-corepack.test.ts` (new)

- `apps/create-deesse-app/src/install/warn-corepack.ts` exports:
  ```ts
  export type InstallBootstrap = "corepack" | "npm-exec" | "pnpm-direct"

  export const warnInstallBootstrap = (
    bootstrap: InstallBootstrap,
    writer: (s: string) => void = process.stderr.write.bind(process.stderr),
  ): void
  ```
  The function writes **one** of three lines, depending on the chosen bootstrap:
  - `corepack`: `create-deesse-app: installing dependencies via corepack (uses the generated project's packageManager field)\n`
  - `npm-exec`: `create-deesse-app: corepack not found; downloading pnpm through npm for this run only (no global install)\n`
  - `pnpm-direct`: `create-deesse-app: pnpm found on PATH; installing directly\n`
  The function does not probe anything; it only announces the choice the strategy function already made. The text never says "pnpm is not on PATH" because the code never verified that. (The `pnpm-direct` line is informational and may be skipped on `--silent` if we add that later; for this increment it always emits.)
  Lines honor `NO_COLOR` via picocolors: dim the `create-deesse-app:` prefix, leave the rest plain.
- `apps/create-deesse-app/src/install/run.ts` calls `warnInstallBootstrap(bootstrapFor(command))` at the top, before the spawn. The mapping is `corepack → "corepack"`, `{bin: "npm"} → "npm-exec"`, `{bin: "pnpm"} → "pnpm-direct"`.
- `apps/create-deesse-app/test/unit/warn-corepack.test.ts`: three cases, one per bootstrap, asserting the exact line text and that the writer is called exactly once.

Why this step third: the warning is a UX nicety on top of the strategy. Putting it in `run.ts` keeps the install path (warning + command + spawn) in one file.

### Step 4 — `--no-install` does not spawn anything

`apps/create-deesse-app/src/pipeline.ts`, `apps/create-deesse-app/src/install/recovery.ts`, `apps/create-deesse-app/test/unit/pipeline-install-failure.test.ts`

- `apps/create-deesse-app/src/pipeline.ts:run`:
  - The `probeInstallPrereqs` call moves inside the `if (input.install)` branch. The `--no-install` path does not probe, does not pick a strategy, and does not warn.
  - `buildNoInstallResult` returns a recovery field that is the fixed literal `pnpm install` (the bare command). The reasoning: on `--no-install`, the user has not committed to any install path. If they later want to install, the safest instruction is the most common one (`pnpm install`). If pnpm is not on their `PATH`, they will see the standard `command not found`, which is honest. We do not try to guess which bootstrap they would want on a future run.
- `apps/create-deesse-app/test/unit/pipeline-install-failure.test.ts`: a new sub-case for `--no-install: true` asserts the install spawn is **not** called, the warning is not emitted, the recovery field is exactly `cd <dir> && pnpm install`, and the result has `installed: false`. The test uses a runner stub for `probeInstallPrereqs` that asserts the runner is **never** called.

Why this step fourth: this is the constraint the reviewer called out twice. It is small and self-contained once Step 2 is in place.

### Step 5 — e2e smoke for real `npx` invocation

`apps/create-deesse-app/test/e2e/application-generation.test.ts`, `apps/create-deesse-app/test/e2e/support/consumer-stack.ts`

- `apps/create-deesse-app/test/e2e/support/consumer-stack.ts` adds:
  ```ts
  export const clearCorepackCache = async (consumer: StartedTestContainer): Promise<void> => {
    const r = await consumer.exec([
      "sh",
      "-c",
      "rm -rf ~/.cache/node/corepack ~/.local/share/node/corepack 2>/dev/null; true",
    ])
    // no-op: we accept any exit code; the goal is that the
    // next corepack invocation has to download, not that the
    // cleanup succeeded
    void r
  }
  ```
  The path covers Linux (`~/.cache/node/corepack`) and macOS (`~/Library/Caches/node/corepack`, not listed here for brevity but the function name is platform-aware in a follow-up). The test that uses it is Linux-only.
- `apps/create-deesse-app/test/e2e/application-generation.test.ts` adds a child case:
  1. Call `clearCorepackCache(consumer.container)`.
  2. Invoke the binary via the `npx` shim on the consumer image (a new `runViaNpx` helper in `consumer-stack.ts`, parallel to `runViaDlx`, dispatches through `sh -c`).
  3. Assert: exit code 0, JSON result parseable, `recovery` field contains `corepack pnpm install` (because the consumer image ships corepack), warning line lands on stderr with the `installing dependencies via corepack` text, and the generated project has a `pnpm-lock.yaml` (proves install actually used pnpm).
  4. The test does **not** assert that pnpm was downloaded fresh in the sense of "a network round trip happened." What it asserts is that the install succeeded with an empty corepack cache, which is the strongest practical signal: if `corepack pnpm install` had failed to download pnpm, the test would have failed at the install step. (A truly exact download assertion would require a network-level mock; that is out of scope.)
  5. The test does not need the PostgreSQL probe; that part of the existing test stays in the `pnpm dlx` test only.
- The test runs in the same `describe.skipIf(!dockerAvailable())` block and on the same `ubuntu-latest` consumer e2e job as the existing tests. No new runner, no self-hosted.
- The consumer image's npm version must be at least 7 for `npx --yes` to work. The e2e config asserts this once in `beforeAll` and skips the new test (with a clear `it.skip`) if npm is older. The skip path mirrors the existing `dockerAvailable` guard.

Why this step fifth: the e2e smoke is the only end-to-end check that the change actually works for a real `npx` user. The cache-clear step makes the test meaningful — without it, the test would pass even if the install path were broken, because pnpm would already be cached from the consumer's bootstrap.

## Risks / edge cases

- **Node 25 unbundles corepack.** The `npm exec -- pnpm@<version> install` fallback is the dedicated path for this case. The risk is that `npm exec` is itself deprecated or removed in some future npm major version. The fallback only depends on npm ≥ 7 (Node 16+), and npm has no announced deprecation of `npm exec` as of the spec's authoring. If it ever does, the next fallback is to shell out to `npx --yes pnpm@<version> <args>`, which is morally equivalent.
- **PATH ordering on Linux.** `corepack pnpm install` resolves the binary itself. The npm-exec and pnpm-direct branches use the absolute path through `sh -c`'s `PATH`. No private cache paths are ever read.
- **Windows shim extension.** `where corepack` on Windows uses `PATHEXT` correctly. `where npm` and `where pnpm` follow the same rule. The test for the Windows branch is a docstring-documented expectation, not a CI-run unit test (CI runs Linux). A follow-up issue can run the test on a Windows runner.
- **`packageManager` field in the generated project.** Today the saas-template ships `pnpm@11.0.0` at the root `package.json`. We do not need to set it; the field is already there. If the field is missing or malformed in a future template revision, the CLI's `readPnpmVersion()` still returns `11.0.0` (its fallback), and corepack falls back to its own pinned default. The two are decoupled by design.
- **`npm exec` requires npm ≥ 7.** npm 7+ ships with Node 16+. The package's `engines.node: ">=20.0.0"` covers every supported Node, and every supported Node has npm ≥ 9. The fallback is safe.
- **E2e cost.** The new test runs the full install (60–120 s). It is on the same `ubuntu-latest` job as the existing e2e tests, and the job's `timeout-minutes: 45` is the budget. The four existing tests already fit; one more with the same shape fits too.
- **Cache-clear side effects.** `clearCorepackCache` deletes the corepack cache for the consumer container, which is fine — the consumer is ephemeral. The clear happens only in the new test's `beforeAll`, not in the existing `pnpm dlx` test. The two tests are isolated: the pnpm-dlx test bootstraps pnpm once at consumer startup and does not clear it, so its behavior is unchanged.
- **`unsupported_manager` still throws if all three prereqs are missing.** The recovery hint names three manual-install paths. This is acceptable for the rare case (a user with a stripped Node install and no global package manager). The unit test in `install-strategy.test.ts` covers this branch.

## Out of scope (explicit)

- Converting the saas-template to an npm project.
- A `--package-manager npm|pnpm` flag.
- A `npm` row in the `PackageManager` enum.
- Changes to the generated `package.json` or `pnpm-lock.yaml`.
- A `bun add` or `yarn add` install path.
- A `Bun` or `Yarn` invoker detection. The CLI does not need to know how it was launched; the install path is decided by the prereq probes alone.
- An `invokedVia` field in the result JSON. The install path is reported via the `recovery` field, which is what tools and humans need.
- A self-hosted runner. The e2e runs on `ubuntu-latest`, the same runner the existing consumer e2e uses.
- Running the e2e on a Windows runner. The Windows probe is documented in the code; CI validates the Linux path.
