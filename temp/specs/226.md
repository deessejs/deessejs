> **Scope correction (2026-10-17).** The original issue body asked the CLI to convert the saas-template to an npm project. After discussion with the developer, the scope is narrower: the CLI must be invokable via `npx create-deesse-app@latest`, but the generated project stays a pnpm project. There is no template conversion, no `--package-manager` flag, and no `npm` row in `PackageManagerId`. The issue body will be re-framed on the GitHub side; this spec reflects the new scope.
>
> **Strategy correction (2026-10-17, post-review).** The first draft of this spec used `corepack prepare pnpm@X --activate` and resolved the resulting shim from a private cache path. The reviewer flagged this as fragile: the cache path is not stable, `corepack enable` is the operation that places shims on the PATH (and can fail if the cache is read-only), and reading a private cache path ties the implementation to one corepack version's layout. The spec now uses **`corepack pnpm install`** as the install command when corepack is available: corepack reads the generated project's `packageManager` field, downloads the matching pnpm, and runs the install. No shim resolution, no cache path lookup.

## TL;DR

`npx create-deesse-app@latest <name>` and `pnpm dlx create-deesse-app@latest <name>` both run the same pipeline and produce the same pnpm-managed project. The CLI no longer rejects npm-spawned invocations. The install command becomes `corepack pnpm install` when corepack is on `PATH` and the resolved install command is `pnpm install` otherwise. A single warning line on stderr announces which path was taken. With `--no-install`, the install step is skipped entirely — no pnpm or corepack is invoked.

---

## Issue summary

Today, the CLI throws `unsupported_manager` when invoked via `npx` or `npm exec`. The user-facing workaround documented in the error hint is to use `pnpm dlx create-deesse-app@latest <name>` instead. The first working increment (#225) explicitly chose this trade-off. The new increment relaxes it: the CLI accepts any invoker, prefers corepack for the install (so pnpm does not need to be on `PATH` for `npx` users), and falls back to a bare `pnpm install` when corepack is absent. The generated project remains pnpm.

## Step-by-step implementation

### Step 1 — Drop the npm-invocation guard

`apps/create-deesse-app/src/pm/detect-invoker.ts`, `apps/create-deesse-app/test/unit/detect-invoker.test.ts`, `apps/create-deesse-app/src/pipeline.ts`

- Delete the call to `assertNotNpmInvocation` in `pipeline.ts:guardInvocationAndArgs`. The function now only validates `projectName` and `destination`.
- Delete `assertNotNpmInvocation` and its tests. The file `detect-invoker.ts` is removed entirely.
- The `unsupported_manager` error code stays exported (Step 5 may reuse it for the corepack-missing path; even if Step 5 is deferred, removing the code is a breaking change for the public surface and is out of scope for this increment).
- The `pm/detect-invoker.ts` import in `pipeline.ts` is removed.
- The unit test file is removed.

Why this step first: it is a strict removal. CI turns green only on the suite, not on the install path. No semantic change yet — the install still requires pnpm, and an `npx` user without pnpm will fail at the spawn step with the existing ENOENT handler.

### Step 2 — Corepack-aware install command

`apps/create-deesse-app/src/pm/manager.ts`, `apps/create-deesse-app/src/pm/pnpm.ts`, `apps/create-deesse-app/src/install/run.ts`, `apps/create-deesse-app/src/install/recovery.ts`, `apps/create-deesse-app/src/install/probe-corepack.ts` (new), `apps/create-deesse-app/src/pipeline.ts`, `apps/create-deesse-app/test/unit/install-command.test.ts` (new), `apps/create-deesse-app/test/unit/probe-corepack.test.ts` (new), `apps/create-deesse-app/test/unit/recovery.test.ts`

- `apps/create-deesse-app/src/install/probe-corepack.ts` exports:
  ```ts
  export const probeCorepackAvailable = (
    env: NodeJS.ProcessEnv = process.env,
    runner: CommandRunner = defaultRunner,
  ): boolean
  ```
  The default runner uses `child_process.spawnSync("corepack", ["--version"], { stdio: "ignore", timeout: 5_000 })`. The result is `true` only when the exit code is `0`. The function never throws; on any failure (binary missing, timeout, non-zero exit) it returns `false`. Tests inject a fake runner.
- `apps/create-deesse-app/src/pm/manager.ts` updates the `installCommand` signature:
  ```ts
  installCommand(opts: { corepackAvailable: boolean }): InstallCommand
  ```
  The closed `PackageManagerId` enum stays `"pnpm"`. The stale `// #226 adds "npm"` comment is removed and replaced with `// #226 keeps pnpm as the only install target; npm/yarn/bun refer to invokers, not installs.`
- `apps/create-deesse-app/src/pm/pnpm.ts`:
  ```ts
  export const pnpm: PackageManager = {
    id: "pnpm",
    installCommand: ({ corepackAvailable }) =>
      corepackAvailable
        ? { bin: "corepack", args: ["pnpm", "install"] }
        : { bin: "pnpm", args: ["install"] },
    lockfileName: "pnpm-lock.yaml",
    requiresCorepack: false, // metadata; the install command itself decides
  }
  ```
  When corepack is available, the install command is **`corepack pnpm install`**. Corepack reads the generated project's `packageManager` field (which is `pnpm@11.0.0`), downloads the matching pnpm if needed, and runs `pnpm install`. **No shim resolution, no cache path lookup.** When corepack is not available, the install command is `pnpm install`; if pnpm is also not on `PATH`, the existing `child.on("error")` ENOENT path runs.
- `apps/create-deesse-app/src/install/run.ts`: signature becomes `runInstall({ command: InstallCommand, cwd: string })`. The function spawns `command.bin` with `command.args`. The rest is unchanged.
- `apps/create-create-deesse-app/src/install/recovery.ts`: `recoveryCommand({ command: InstallCommand, cwd })` builds `<cd> <dir> && <bin> <args>...`. The output must match the install command that was actually used.
- `apps/create-deesse-app/src/pipeline.ts`:
  - `RunState` gains `corepackAvailable: boolean`, populated by a single call to `probeCorepackAvailable()` at the start of `run`.
  - `runInstallAndBuildResult` calls `pnpm.installCommand({ corepackAvailable: state.corepackAvailable })` and passes the result to `runInstall`.
  - `buildNoInstallResult` does the same for the recovery field (it does not run the install, but the recovery must match what would have run if the user removes `--no-install`).
  - The `recoveryCommand` call everywhere uses the same `command` value.
- `apps/create-deesse-app/test/unit/install-command.test.ts`: two cases. The factory is pure (no I/O), so the test takes `corepackAvailable: true` and `corepackAvailable: false` and asserts the exact command form.
- `apps/create-deesse-app/test/unit/probe-corepack.test.ts`: three cases. The runner is stubbed.
- `apps/create-deesse-app/test/unit/recovery.test.ts`: a new case asserts `recoveryCommand({ command: pnpm.installCommand({ corepackAvailable: true }), cwd })` produces the `corepack pnpm install` form, and the existing case uses `corepackAvailable: false`.

Why this step second: the install command is the load-bearing change. Every later step uses the value this step produces. Validating the factory in isolation (no I/O) keeps the tests fast and the failures specific.

### Step 3 — Warn before the install runs

`apps/create-deesse-app/src/install/warn-corepack.ts` (new), `apps/create-deesse-app/src/install/run.ts`, `apps/create-deesse-app/src/pipeline.ts`, `apps/create-deesse-app/test/unit/warn-corepack.test.ts` (new)

- `apps/create-deesse-app/src/install/warn-corepack.ts` exports:
  ```ts
  export const warnCorepackDownload = (writer: (s: string) => void = process.stderr.write.bind(process.stderr)): void
  ```
  Writes one line:
  ```
  create-deesse-app: pnpm not found on PATH; running via corepack (uses the project's packageManager field)
  ```
  Honored `NO_COLOR` via picocolors: dim the prefix, leave the rest plain. The line ends with a single `\n`. The function is pure (it does not probe anything) and is the same regardless of the project's pnpm version — corepack reads `packageManager` at runtime.
- `apps/create-deesse-app/src/install/run.ts` calls `warnCorepackDownload` once at the top, **only when** the `command.bin === "corepack"`. The warning is not emitted when the install runs `pnpm install` directly.
- `apps/create-deesse-app/src/pipeline.ts` does not need to change: the warning is colocated with the install spawn. The pipeline's responsibility is to pass the right command.
- `apps/create-deesse-app/test/unit/warn-corepack.test.ts`: a single case asserting the message contents and that the writer is called exactly once with the expected line. The writer is stubbed to capture the output.

Why this step third: the warning is a UX nicety on top of the install command. Putting it in `run.ts` keeps the install path (command + warning + spawn) in one file.

### Step 4 — `--no-install` does not download pnpm

`apps/create-deesse-app/src/pipeline.ts`, `apps/create-deesse-app/src/install/run.ts`, `apps/create-deesse-app/src/install/recovery.ts`, `apps/create-deesse-app/test/unit/pipeline-install-failure.test.ts`

- `apps/create-deesse-app/src/pipeline.ts:runInstallAndBuildResult` is renamed `runInstallAndBuildResult` (no rename, but its body shrinks) — the function now only runs when `state.input.install` is true. The `corepackAvailable` probe happens unconditionally so the recovery field is correct in both branches.
- The `--no-install` branch (`buildNoInstallResult`) does **not** call `runInstall`, does **not** call `warnCorepackDownload`, and does **not** require pnpm to be on `PATH`. Its recovery field still names the exact install command that would have run (`corepack pnpm install` or `pnpm install`), so a user who later removes `--no-install` and runs the recovery command gets the same outcome.
- The `corepackAvailable` probe is the only thing the no-install path needs from the env. It is a single `spawnSync` with a 5 s timeout; it does not block the no-install path on a missing binary (the probe returns `false` immediately).
- `apps/create-deesse-app/test/unit/pipeline-install-failure.test.ts`: add a sub-case for `--no-install: true` that asserts the install spawn is **not** called, the recovery field is the correct `corepack pnpm install` form when corepack is available, and the result has `installed: false`. Use a runner stub for the corepack probe.

Why this step fourth: this is the constraint the reviewer specifically called out ("Don't bootstrap pnpm with --no-install"). It is small and self-contained once Step 2 is in place.

### Step 5 — e2e smoke for real `npx` invocation

`apps/create-deesse-app/test/e2e/application-generation.test.ts`, `apps/create-deesse-app/test/e2e/support/consumer-stack.ts`

- `apps/create-deesse-app/test/e2e/support/consumer-stack.ts` adds a new helper, parallel to `runViaDlx`:
  ```ts
  runViaNpx: (
    packageName: string,
    version: string,
    args: readonly string[],
    timeoutMs: number,
  ) => Promise<CommandResult>
  ```
  It dispatches through `sh -c` with the same `workingDir: installDir, user: "root"` as `runViaDlx`. The shell command is `npx --yes <name>@<version> <args>`. The `corepackAvailable` flag is **not** set by the test; corepack is already installed on the consumer image (`node:24-alpine` ships with corepack). The test asserts the install runs and the recovery field carries the corepack form.
- The consumer image's npm version must be at least 7 for `npx --yes` to work. The e2e config asserts this once in `beforeAll` and skips the new test (with a clear `it.skip`) if npm is older. The skip path mirrors the existing `dockerAvailable` guard, so the test does not produce false failures on a future image bump.
- The new test sets `npm_config_user_agent=npm/<v> node/<v> ...` on the consumer **before** invoking, **and** uses the `npx` shim path so the env is real (not just env-injected). The test asserts:
  1. The exit code is 0.
  2. The JSON result is parseable.
  3. The JSON's `recovery` field contains the `corepack pnpm install` form (or `pnpm install` if the future image ships without corepack).
  4. The warning line landed on stderr (captured by `consumer.container.exec` and read back).
  5. The generated project at `state.input.dir` has a `pnpm-lock.yaml` (proves the install actually used pnpm).
- The new test is added to the same `describe.skipIf(!dockerAvailable())` block in `application-generation.test.ts`. It runs on the existing `ubuntu-latest` consumer e2e job — no new runner, no self-hosted.
- The new test does not need the PostgreSQL probe; that part of the existing test stays in the `pnpm dlx` test only.

Why this step fifth: the e2e smoke is the only end-to-end check that the change actually works for a real `npx` user. Pushing it last means the unit and integration tests already prove the building blocks before we ask CI to assemble them.

## Risks / edge cases

- **Corepack absent on Node 25+.** The [Node.js 25 release](https://nodejs.org/api/corepack.html) flags corepack as being unbundled. A user on Node 25+ with no pnpm pre-installed will hit the existing `child.on("error")` ENOENT path: the `pnpm install` fallback fails because pnpm is not there. The recovery command in the JSON result is the actionable guidance: install pnpm or corepack manually, then re-run. This is acceptable for this increment: the goal is `npx` works on the supported Node versions (20, 22, 24), and Node 25 is allowed to fail loudly. A follow-up issue can add a non-corepack bootstrap (the reviewer's `npm exec` suggestion) if the user base moves to Node 25 in volume.
- **Corepack `prepare` prompt.** Some setups show a confirmation prompt the first time corepack runs. `corepack pnpm install` is the documented "do what I mean" entry point and does not prompt; it goes through corepack's prepared-binary path. The `corepack prepare` we no longer call has no prompt either. Verified empirically.
- **PATH ordering.** `corepack pnpm install` resolves the binary itself; we never resolve a private cache path. The install command, the recovery command, and the user's manual retry all use the same shell-resolved form. No path drift possible.
- **Windows shim extension.** `corepack pnpm install` on Windows uses `corepack.cmd` if needed. We do not special-case extensions; `sh -c` is the only path the install runs through, and that handles the resolution.
- **`packageManager` field in the generated project.** Today the saas-template ships `pnpm@11.0.0` at the root `package.json`. We do not need to set it; the field is already there. If the field is missing or malformed in a future template revision, corepack falls back to a default (its own pinned version), which may be older than what the user expects. We do not check or repair the field in this increment; that is a separate concern (template hygiene, not CLI hygiene).
- **`npx --yes` on the consumer image.** The consumer image is `node:24-alpine`, which ships npm 10.x. `npx --yes` is stable in npm 7+, so this is safe. The version is asserted in `beforeAll` and the test skips on older npm rather than failing.
- **E2e cost.** The new test runs the full install (which can take 60-120 s). It is on the same `ubuntu-latest` job as the existing e2e tests, so the job's `timeout-minutes: 45` is the budget. The four existing tests already fit, and one more with the same shape fits too. If the install grows past the budget, we can split into a new job in a follow-up.

## Out of scope (explicit)

- Converting the saas-template to an npm project.
- A `--package-manager npm|pnpm` flag.
- A `npm` row in the `PackageManager` enum.
- Changes to the generated `package.json` or `pnpm-lock.yaml`.
- A `bun add` or `yarn add` install path.
- A `Bun` or `Yarn` invoker detection. The CLI does not need to know how it was launched; the install command is decided by the `corepackAvailable` probe alone.
- An `invokedVia` field in the result JSON. The install path is reported via the `recovery` field, which is what tools and humans need.
- A non-corepack bootstrap for Node 25. A follow-up issue can pick up the reviewer's `npm exec` suggestion if Node 25 adoption makes it necessary.
- A self-hosted runner. The e2e runs on `ubuntu-latest`, the same runner the existing consumer e2e uses.
- Detecting pnpm, yarn, or bun versions from inside the CLI. We only need to know whether corepack is on `PATH`.
