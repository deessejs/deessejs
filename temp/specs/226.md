## TL;DR

`npx create-deesse-app@latest <name>` and `pnpm dlx create-deesse-app@latest <name>` both run the same pipeline and produce the same pnpm-managed project. The CLI detects the invoker, reports it in the JSON result, and obtains pnpm on demand via corepack if pnpm is not on `PATH`. There is no template conversion and no manager switch.

---

## Issue summary

Today, the CLI throws `unsupported_manager` when invoked via `npx` or `npm exec`. The user-facing workaround documented in the error hint is to use `pnpm dlx create-deesse-app@latest <name>` instead. The first working increment (#225) explicitly chose this trade-off. The new increment relaxes it: the CLI accepts any invoker, ensures pnpm is available, and runs the install with pnpm. The generated project remains pnpm.

## Step-by-step implementation

### Step 1 — Detection helper rewrite

`apps/create-deesse-app/src/pm/detect-invoker.ts`, `apps/create-deesse-app/test/unit/detect-invoker.test.ts`

- Rename `assertNotNpmInvocation` to `detectInvokedVia(env: NodeJS.ProcessEnv = process.env): InvokedVia`.
- The return type is a new union: `"npm" | "pnpm" | "bun" | "yarn" | "direct"`.
- Order of precedence (most specific first):
  1. `env.npm_config_user_agent` starts with `npm/` → `"npm"`.
  2. `env.npm_lifecycle_event` is set and non-empty → `"npm"` (catches `npm run`).
  3. `env.npm_node_execpath` is set and non-empty → `"npm"` (catches `npm exec`).
  4. `env.npm_config_user_agent` starts with `pnpm/` → `"pnpm"`.
  5. `env.pnpm_config_store_dir` or `env.pnpm_config_registry` set → `"pnpm"` (catches `pnpm dlx` which does not set `npm_config_user_agent`).
  6. `env.npm_config_user_agent` starts with `yarn/` or `env.YARN_REGISTRY` is set → `"yarn"`.
  7. `env.BUN_INSTALL` or `env.BUN_LOCKFILE_VERSION` set → `"bun"`.
  8. Otherwise → `"direct"`.
- The function **never throws**. The old `assertNotNpmInvocation` and the `unsupported_manager` factory remain exported for backward compatibility, but no caller in the codebase invokes them after this step. They are removed at the end of Step 4 once the pipeline no longer references them.
- Test rewrite: every case that previously expected a throw now asserts a return value. Add a `direct` case (empty env) and a `pnpm dlx` case (no npm markers but pnpm markers).

Why this step first: the rest of the pipeline consumes `InvokedVia`. Establishing the contract and the unit-test surface before plumbing it through `pipeline.ts` and `result.ts` keeps each step diffable.

### Step 2 — Add `invokedVia` to the result JSON

`apps/create-deesse-app/src/result.ts`, `apps/create-deesse-app/src/pipeline.ts`

- Add a new exported type:
  ```ts
  export type InvokedVia = "npm" | "pnpm" | "bun" | "yarn" | "direct"
  ```
  Mirroring the type from Step 1. (Both files import the same type from a single source — `pm/detect-invoker.ts` exports it, `result.ts` re-imports.)
- Add `invokedVia: InvokedVia` to `CreateSuccess`, `CreateInstallFailure`, and `CreateFailure`. The three variants must carry the value uniformly so downstream tooling can pattern-match.
- `pipeline.ts:run` calls `detectInvokedVia()` once at the top, stashes the value in `RunState`, and threads it into every result builder. The stash is the single source of truth for the value across the three result variants.
- A dedicated unit test (`pipeline-install-failure.test.ts`) extends the existing failure-case coverage with three sub-cases: `invokedVia: "npm"` (the new path), `invokedVia: "pnpm"` (the existing path), and `invokedVia: "direct"` (the local-dev path).

Why this step second: the schema is the contract for downstream tooling. Adding the field now lets every subsequent step's test assert on the field without refactoring the assertion surface later.

### Step 3 — pnpm-on-demand resolver via corepack

`apps/create-deesse-app/src/pm/ensure-pnpm.ts` (new), `apps/create-deesse-app/src/utils/package-version.ts`, `apps/create-deesse-app/tsup.config.ts`, `apps/create-deesse-app/test/unit/ensure-pnpm.test.ts`

- `apps/create-deesse-app/src/utils/package-version.ts` adds a second function:
  ```ts
  declare const process: {
    env: { CREATE_DEESSE_APP_VERSION?: string; CREATE_DEESSE_APP_PNPM_VERSION?: string }
  }
  const PNPM_FALLBACK = "11.0.0"
  export const readPnpmVersion = (): string =>
    process.env.CREATE_DEESSE_APP_PNPM_VERSION ?? PNPM_FALLBACK
  ```
  Drift-guard test (`package-version.test.ts`) extended to cover the new function.
- `apps/create-deesse-app/tsup.config.ts` adds a new entry to its `define`:
  ```ts
  "process.env.CREATE_DEESSE_APP_PNPM_VERSION": JSON.stringify(pkg.packageManager),
  ```
  Reading `packageManager` from `apps/create-deesse-app/package.json` (a single source of truth, currently `pnpm@11.0.0`) keeps the dev environment and a `npx` user in lock-step.
- `apps/create-deesse-app/src/pm/ensure-pnpm.ts` exports:
  ```ts
  export type PnpmSource = { bin: string; source: "path" | "corepack" }
  export const ensurePnpmAvailable(args: { version: string }): Promise<PnpmSource>
  ```
  Steps inside the function:
  1. Probe `which pnpm` (or `where pnpm` on Windows). If found, return `{ bin: resolvedPath, source: "path" }`.
  2. Probe `which corepack`. If absent, throw `unsupportedManager("corepack")` with a hint that lists three manual install paths (see Step 5).
  3. Emit the warning on stderr *now*:
     ```
     create-deesse-app: pnpm <version> not found on PATH; downloading via corepack (this can take a minute the first time)...
     ```
     Plain text. Honors `NO_COLOR` via `picocolors`. No newline at the end of this line; `corepack prepare` will print its own progress on stderr after, which makes the two outputs visually adjacent.
  4. Spawn `corepack prepare pnpm@<version> --activate` with a hard 30 s timeout. The `--activate` flag is critical: it creates a shim without modifying the user's PATH globally.
  5. Resolve the shim path. On Linux/macOS: `~/.cache/node/corepack/v1/pnpm/<version>/bin/pnpm` (the exact path follows corepack's cache layout; the function reads it from `corepack prepare --help` output or probes `<corepack-cache>/pnpm/<version>/{bin,bin.cmd}`). On Windows: `<corepack-cache>/pnpm/<version>/bin/pnpm.cmd`.
  6. Return `{ bin: resolvedShimPath, source: "corepack" }`.
- `apps/create-deesse-app/test/unit/ensure-pnpm.test.ts` covers three branches:
  1. `which pnpm` returns `/usr/local/bin/pnpm` → `bin === "/usr/local/bin/pnpm"`, `source === "path"`, no spawn, no stderr.
  2. `which pnpm` returns null, `which corepack` returns `/usr/local/bin/corepack`, spawn succeeds and the shim resolves → `source === "corepack"`, stderr contains the warning.
  3. `which pnpm` returns null, `which corepack` returns null → throws `unsupportedManager("corepack")` with a hint that includes the strings `npm i -g pnpm@`, `npm i -g corepack`, and the standalone installer URL.
- The tests stub the `which` probe (and the `corepack prepare` spawn) via a thin `probeBin` seam the function takes as an optional dependency. Production calls `probeBin` with no argument and gets the real implementation.

Why this step third: the resolver is self-contained. Step 4 wires it into the pipeline, but the resolver's behavior can be validated in isolation first.

### Step 5 — Corepack-missing error path

`apps/create-create-deesse-app/src/errors/index.ts`, `apps/create-deesse-app/test/unit/ensure-pnpm.test.ts`

- `unsupportedManager` is overloaded with a new optional second argument:
  ```ts
  export const unsupportedManager = (invoker: "npm" | "corepack"): CliError => {
    if (invoker === "corepack") {
      return new CliError(
        "unsupported_manager",
        "could not find pnpm on PATH and corepack is not available",
        "install pnpm with one of: \`npm i -g pnpm@<version>\`, \`npm i -g corepack\` then retry, or the standalone installer at https://pnpm.io/installation",
      )
    }
    // existing npm branch
  }
  ```
- The `unsupported_manager` error code stays. The `CreateFailure` result shape stays. Only the message and hint change.
- A new test case in `ensure-pnpm.test.ts` asserts that with `which pnpm` and `which corepack` both null, the function throws a `CliError` whose `code === "unsupported_manager"`, whose message includes `corepack`, and whose hint includes all three recovery paths.
- A new test case in `pipeline-install-failure.test.ts` stubs `ensurePnpmAvailable` to throw the new error and asserts the resulting `CreateFailure` has `code: "unsupported_manager"` and the new hint.

Why this step last: the failure path is the only test surface that does not depend on any of the previous four steps' wiring. It is small (one factory branch, two test cases) and can land independently. Pushing it to the end keeps the previous four steps clean — they prove the happy path works before the failure path is shaped.

## Risks / edge cases

- **Corepack absent on Node 25+.** The [Node.js 25 announcement](https://nodejs.org/api/corepack.html) flags corepack as being unbundled. A user on Node 25+ with no pnpm pre-installed will hit the Step 5 error. The hint names three recovery paths; the test in Step 5 locks in the hint contents.
- **Corepack `prepare` prompt.** Some setups show a confirmation prompt the first time. We use a hard 30 s timeout; if the prompt blocks, the spawn exits non-zero and we fall through to the Step 5 error. Verified by the Step 3 test for the spawn-failure branch (added as a fourth case in `ensure-pnpm.test.ts`).
- **PATH ordering.** The shim created by `corepack prepare --activate` lives in the corepack cache, which is not on the current process's `PATH`. The function returns the absolute path so the install spawn and the recovery command both use it, not a bare `pnpm` lookup.
- **Windows shim extension.** On Windows, the shim is `pnpm.cmd`, not `pnpm`. The resolver probes both extensions and prefers `.cmd` when present. The test in Step 3 does not exercise Windows directly (the unit test runs on Linux CI) but the implementation handles the conditional.
- **`pnpm dlx` not setting `npm_config_user_agent`.** pnpm sets its own vars; the detector reads them. If we cannot prove pnpm, we return `"direct"`, not `"pnpm"`. Honest over optimistic. The unit test covers this branch.
- **Generated project's `packageManager: "pnpm@11.0.0"`.** Today this is what the generated `package.json` carries. The end user's *first* `pnpm install` triggers a corepack download of pnpm 11.0.0; the resolver we ship for the CLI does not affect that. This is fine: the user-facing experience is identical between pnpm-installed and npx-installed pnpm, because both go through corepack.
- **Corepack cache migration.** If the user already has a different pnpm version cached, `corepack prepare pnpm@11.0.0 --activate` adds the new version without disturbing the old one. The shim-resolution step reads the freshly prepared path, not the old cached one.
