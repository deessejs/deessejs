> **Scope correction (2026-10-17).** The original issue body asked the CLI to convert the saas-template to an npm project. After discussion with the developer, the scope is narrower: the CLI must be invokable via `npx create-deesse-app@latest`, but the generated project stays a pnpm project. There is no template conversion, no `--package-manager` flag, and no `npm` row in `PackageManagerId`. **The issue title on GitHub will be re-framed to "Accept npx invocation; pick pnpm install bootstrap; keep pnpm project"** to drop the "npm project generation" promise that the new scope no longer makes. This spec reflects the new scope.
>
> **Strategy correction (2026-10-17, post-review).** The first draft used `corepack prepare pnpm@X --activate` and resolved the resulting shim from a private cache path. The second draft switched to `corepack pnpm install` when corepack is on `PATH`, falling back to `pnpm install` otherwise. The third draft, after the second review, accepts that **Node 25 unbundles corepack** ([Node.js Corepack documentation](https://nodejs.org/api/corepack.html)). A `pnpm install` fallback on Node 25 fails when pnpm is not on `PATH`. The install bootstrap must therefore have a third path that does not depend on corepack: `npm exec --yes -- pnpm@<version> <args>`. npm ships with every Node ≥ 16, including Node 25, and `npm exec` runs a binary from npm's cache without modifying the user's `PATH` (it adds the binary to the child process's `PATH` for the duration of the exec, which is what `--` and the trailing `install` rely on). This is the fallback chosen for this increment.
>
> **Engines correction (2026-10-17, post-review).** pnpm 11 does not support Node 20, and the [pnpm 11.0.0 release](https://github.com/pnpm/pnpm/commit/1a7c088e4d288ec053b1e1bdcd0e19375bc02a32) further requires `>=22.13.0`. The major-version matrix page masks this distinction; the runtime check in `pnpm11/pnpm/bin/pnpm.mjs` rejects earlier 22.x minors. Keeping `engines.node: ">=20.0.0"` while requiring pnpm 11 is therefore a double contradiction. The package's `engines.node` is bumped to `">=22.13.0"` and `assertSupportedNode()` compares against that floor. Node 22.12 is rejected with the same `unsupported_node` error code as Node 20, so the boundary is consistent.
>
> **Pnpm version source correction (2026-10-17, post-review).** The previous draft proposed a `readPnpmVersion()` helper reading `apps/create-deesse-app/package.json`. That file does not carry a `packageManager` field, and the CLI does not own the template. The version comes from the **generated project's** `packageManager` field, which is set by the saas-template (e.g. `"packageManager": "pnpm@11.0.0"`). The CLI does not need to know the version statically; it passes the value to corepack and `npm exec` as an argument. For the recovery command and the `--no-install` recovery field, the CLI reads the generated project's `packageManager` from the destination directory after extraction. That is the source of truth.

## TL;DR

`npx create-deesse-app@latest <name>` and `pnpm dlx create-deesse-app@latest <name>` both run the same pipeline and produce the same pnpm-managed project. The CLI no longer rejects npm-spawned invocations. The install command is chosen at runtime from three paths, in order:

1. **`corepack pnpm install`** when corepack is on `PATH` (Node 22–24 default).
2. **`npm exec --yes -- pnpm@<version> install`** when corepack is absent but npm is on `PATH` (Node 25 fallback). The `<version>` is read from the generated project's `packageManager` field.
3. **`pnpm install`** when neither corepack nor npm is on `PATH` but pnpm is (rare).

The order is **not** "use pnpm-direct if pnpm is on `PATH`"; pnpm-direct is the last-resort fallback when both corepack and npm are missing. The intent is to keep the install command version-controlled through the generated project's `packageManager` field, not through whatever pnpm happens to be on the user's `PATH`.

A single warning line on stderr announces the chosen path. With `--no-install`, the install step is skipped entirely — no corepack, no npm, no pnpm is invoked.

The package's `engines.node` is bumped to `">=22.13.0"` because pnpm 11 does not support Node 20 and rejects earlier 22.x minors.

## Issue summary

Today, the CLI throws `unsupported_manager` when invoked via `npx` or `npm exec`. The first working increment (#225) explicitly chose this trade-off. The new increment relaxes it: the CLI accepts any invoker, picks the best install bootstrap for the runtime, and runs the install. The generated project remains pnpm. The CLI satisfies the package's `engines.node: ">=22.13.0"` on every supported Node, including Node 25 where corepack is unbundled. **A Node 20 user (or a Node 22.0–22.12 user) who installs the package despite the engines field will see a clear error at startup, not a silent install failure later** (see Step 1.5 below).

### Step 1 — Drop the npm-invocation guard

### Step 1.5 — Reject Node 20 at startup

`apps/create-deesse-app/src/check-node.ts` (new), `apps/create-deesse-app/src/pipeline.ts`, `apps/create-deesse-app/test/unit/check-node.test.ts` (new)

- A new `assertSupportedNode()` function reads `process.version` (the Node runtime's `process.versions.node` is the same value). If the major version is less than 22, it throws a new error code `unsupported_node` with a hint that names the pnpm 11 / Node 22+ compatibility matrix link and the supported version.
- The check runs at the very top of `pipeline.ts:run`, before `guardInvocationAndArgs`. The error is fatal: the CLI exits 1 with a single JSON object on stdout and the new error code on stderr.
- The check does **not** depend on `engines.node` from `package.json`. `engines` produces an `EBADENGINE` warning that npm emits on install — it is not a guarantee at runtime. The check is a runtime contract.
- The new error code `unsupported_node` is added to `CreateAppErrorCode` in `errors/index.ts` (the closed list, which is a public surface — adding an entry is a breaking change for tooling that pattern-matches on the set, but the only consumer in this repo is the JSON parsing in the e2e tests, and the set already has 8 entries; one more does not break the contract). The factory is:
  ```ts
  export const unsupportedNode = (version: string, required: string): CliError =>
    new CliError(
      "unsupported_node",
      `Node ${version} is not supported; create-deesse-app requires Node ${required} or later (pnpm 11 does not support earlier majors)`,
      `install Node ${required} LTS or later from https://nodejs.org and re-run`,
    )
  ```
- `apps/create-deesse-app/test/unit/check-node.test.ts` covers: `v20.0.0` throws, `v20.99.99` throws, `v22.0.0` throws, **`v22.12.99` throws**, **`v22.13.0` returns**, `v24.0.0` returns, `v25.0.0` returns, `v18.19.1` throws. The `process.version` setter is stubbed for the test by passing the version explicitly to `assertSupportedNode(version: string)` so the test does not depend on a runtime trick.

Why this step second: the `engines.node` field is informational and easy to bypass; a runtime check is the only way to honor the contract. The check is small (one new module, ~20 lines), independent of every later step, and prevents a class of bug where a Node 20 or Node 22.0–22.12 user installs pnpm 11 and the install fails with a confusing pnpm error rather than a clear CLI error. The `>=22.13.0` floor is the actual pnpm 11 requirement, lifted from the pnpm 11.0.0 source; documenting it as `>=22.0.0` would be a regression in the contract.

### Step 2 — Corepack probe and three-way install command

`apps/create-deesse-app/src/pm/install-strategy.ts` (new), `apps/create-deesse-app/src/pm/probe-paths.ts` (new), `apps/create-deesse-app/src/pm/manager.ts`, `apps/create-deesse-app/src/pm/pnpm.ts`, `apps/create-deesse-app/src/install/run.ts`, `apps/create-deesse-app/src/install/recovery.ts`, `apps/create-deesse-app/src/pipeline.ts`, `apps/create-deesse-app/test/unit/install-strategy.test.ts` (new), `apps/create-deesse-app/test/unit/probe-paths.test.ts` (new), `apps/create-deesse-app/test/unit/install-command.test.ts` (new), `apps/create-deesse-app/test/unit/recovery.test.ts`

- `apps/create-deesse-app/src/pm/install-strategy.ts` exports a single pure function:
  ```ts
  export type InstallStrategy = "corepack" | "npm-exec" | "pnpm-direct"

  export const pickInstallStrategy = (input: {
    corepackAvailable: boolean
    npmAvailable: boolean
    pnpmAvailable: boolean
  }): InstallStrategy => {
    if (input.corepackAvailable) return "corepack"
    if (input.npmAvailable) return "npm-exec"
    if (input.pnpmAvailable) return "pnpm-direct"
    throw unsupportedManager("pnpm")
  }
  ```
  The `version` is not part of the decision — the function only picks the bootstrap, and the bootstrap's command factory injects the version later. Keeping the strategy pure of `version` lets the unit test exhaustively cover the eight input combinations without faking version strings. The throw at the end produces the existing `unsupported_manager` error code with a hint that names three manual-install paths. The order is documented in the function and on the test cases: the function does not consider pnpm-direct until **both** corepack and npm are missing, because the goal is to use the version pinned by the generated project's `packageManager` field, not whatever pnpm happens to be on the user's `PATH`.
- `apps/create-deesse-app/src/pm/probe-paths.ts` exports:
  ```ts
  export type InstallPrereqs = { corepack: boolean; npm: boolean; pnpm: boolean }
  export const probeInstallPrereqs = (
    env: NodeJS.ProcessEnv = process.env,
    runner: SyncRunner = defaultRunner,
  ): InstallPrereqs
  ```
  The default runner is:
  ```ts
  const probe = (bin: string): boolean => {
    const which = process.platform === "win32" ? "where" : "which"
    const r = runner(which, [bin])
    return r.status === 0
  }
  ```
  Each probe uses `spawnSync` with a 5 s timeout and `stdio: "ignore"`. The function never throws — on any failure (binary missing, timeout, non-zero exit) the corresponding flag is `false`. On Windows, the `where` builtin reads `PATHEXT` correctly (so `where corepack` matches `corepack.cmd`); the test for the Windows branch is a docstring-documented expectation, not a CI-run unit test (CI runs Linux).
- `apps/create-deesse-app/src/pm/manager.ts` updates the `installCommand` signature:
  ```ts
  installCommand(strategy: InstallStrategy, version: string): InstallCommand
  ```
  The closed `PackageManagerId` enum stays `"pnpm"`. The stale `// #226 adds "npm"` comment is removed.
- `apps/create-deesse-app/src/pm/pnpm.ts`:
  ```ts
  export const pnpm: PackageManager = {
    id: "pnpm",
    installCommand: (strategy, version) => {
      switch (strategy) {
        case "corepack":
          // Corepack reads the generated project's
          // packageManager field and resolves pnpm@version.
          return { bin: "corepack", args: ["pnpm", "install"] }
        case "npm-exec":
          // npm exec downloads pnpm@version into npm's cache
          // and runs the binary directly; no global install,
          // no PATH modification. --yes suppresses the
          // confirmation prompt npm may issue in interactive
          // shells; in non-TTY contexts npm's default is to
          // install silently, but --yes is the documented
          // way to make the behavior explicit and consistent.
          return { bin: "npm", args: ["exec", "--yes", "--", `pnpm@${version}`, "install"] }
        case "pnpm-direct":
          return { bin: "pnpm", args: ["install"] }
      }
    },
    lockfileName: "pnpm-lock.yaml",
    requiresCorepack: false,
  }
  ```
  The `version` argument comes from the **generated project's** `packageManager` field, not from `apps/create-deesse-app/package.json`. The CLI reads the field from `<destination>/package.json` after extraction (the field is part of the public template contract and is present today). A new helper `readGeneratedPnpmVersion(destinationDir: string): string` parses the field with a small regex and returns the version. If the field is missing or malformed, the helper throws `source_failed` (the same error code the template-extraction step throws for a missing `package.json`), with a hint that names the expected field. There is no fallback to a hardcoded version.
- `apps/create-deesse-app/src/install/run.ts`: signature becomes `runInstall({ command: InstallCommand, cwd: string })`. The function spawns `command.bin` with `command.args`. The rest is unchanged.
- `apps/create-deesse-app/src/install/recovery.ts`: `recoveryCommand({ command: InstallCommand, cwd })` builds `<cd> <dir> && <bin> <args>...`. The output matches the install command that was actually used.
- `apps/create-deesse-app/src/pipeline.ts`:
  - The `corepackAvailable` probe is replaced by `probeInstallPrereqs()`, called **only when** `state.input.install === true`. The result is stashed on `RunState` as `prereqs: InstallPrereqs`.
  - `runInstallAndBuildResult` calls `pickInstallStrategy({ corepackAvailable: state.prereqs.corepack, npmAvailable: state.prereqs.npm, pnpmAvailable: state.prereqs.pnpm })` and passes the result together with `readGeneratedPnpmVersion(state.input.dir)` to `pnpm.installCommand`. The recovery field uses the same command.
  - The `--no-install` path does not call `probeInstallPrereqs`, does not pick a strategy, and does not run the install. Its recovery field is a fixed literal (see Step 4).
- `apps/create-deesse-app/test/unit/install-strategy.test.ts`: eight cases covering every combination of the three boolean inputs and confirming the throw at the all-false case.
- `apps/create-deesse-app/test/unit/probe-paths.test.ts`: stub the runner; test each probe's success and failure path. The timeout case uses a runner that returns `{ status: null, signal: "SIGTERM" }` to simulate a 5 s timeout firing.
- `apps/create-deesse-app/test/unit/install-command.test.ts`: three cases, one per strategy. The version `11.0.0` is the only version tested; pinning it here catches accidental `pnpm@latest` regressions.
- `apps/create-deesse-app/test/unit/recovery.test.ts`: cover all three strategy forms in the recovery output. The `npm-exec` form must be `cd "<dir>" && npm exec --yes -- pnpm@<version> install` (verbatim, including `--yes`, the `--`, and the version). The test also covers a path containing spaces, single quotes, and a `$` (a realistic test directory: `/tmp/cda recov'ery $1/foo`). The quoting reuses the existing `quoteForShell()` helper that already lives in `install/run.ts`; the test asserts both that the helper exists with that exact name and that the recovery command round-trips through `sh -c "cd ... && <rest>"` without losing any character.

Why this step second: the strategy is the load-bearing decision. Every later step uses the value this step produces. Validating the strategy in isolation (no I/O) keeps the tests fast.

### Step 3 — Honest warning text

`apps/create-deesse-app/src/install/warn-install-bootstrap.ts` (new), `apps/create-deesse-app/src/install/run.ts`, `apps/create-deesse-app/src/pipeline.ts`, `apps/create-deesse-app/test/unit/warn-install-bootstrap.test.ts` (new)

- `apps/create-deesse-app/src/install/warn-install-bootstrap.ts` exports:
  ```ts
  export type InstallBootstrap = "corepack" | "npm-exec" | "pnpm-direct"

  export const warnInstallBootstrap = (
    bootstrap: InstallBootstrap,
    writer: (s: string) => void = process.stderr.write.bind(process.stderr),
  ): void
  ```
  The function writes **one** of three lines, depending on the chosen bootstrap:
  - `corepack`: `create-deesse-app: installing dependencies via corepack (uses the generated project's packageManager field)\n`
  - `npm-exec`: `create-deesse-app: corepack not found; running pnpm through npm (may be downloaded into npm's cache, no global install)\n`
  - `pnpm-direct`: `create-deesse-app: corepack and npm not found on PATH; using pnpm from PATH (version is not guaranteed to match the project)\n`
  The function does not probe anything; it only announces the choice the strategy function already made. The npm-exec text says "may be downloaded" because pnpm@version may already be in npm's cache from a previous run, in which case the command is effectively instant. The pnpm-direct text does not claim the version matches the project, because the function cannot know that.
  Lines honor `NO_COLOR` via picocolors: dim the `create-deesse-app:` prefix, leave the rest plain.
- `apps/create-deesse-app/src/install/run.ts` calls `warnInstallBootstrap(bootstrapFor(command))` at the top, before the spawn. The mapping is `corepack → "corepack"`, `{bin: "npm"} → "npm-exec"`, `{bin: "pnpm"} → "pnpm-direct"`.
- `apps/create-deesse-app/test/unit/warn-install-bootstrap.test.ts`: three cases, one per bootstrap, asserting the exact line text and that the writer is called exactly once.

Why this step third: the warning is a UX nicety on top of the strategy. Putting it in `run.ts` keeps the install path (warning + command + spawn) in one file.

### Step 4 — `--no-install` does not spawn anything

`apps/create-deesse-app/src/pipeline.ts`, `apps/create-deesse-app/src/install/recovery.ts`, `apps/create-deesse-app/test/unit/pipeline-install-failure.test.ts`

- `apps/create-deesse-app/src/pipeline.ts:run`:
  - The `probeInstallPrereqs` call moves inside the `if (input.install)` branch. The `--no-install` path does **no** probe, **no** strategy selection, and **no** warning. The recovery field is a fixed literal, not a result of probing.
  - `buildNoInstallResult` returns a recovery field built by `recoveryCommandForNoInstall({ version, cwd: state.input.dir })`. The function is deterministic and offline:
    ```ts
    export const recoveryCommandForNoInstall = (
      { version, cwd }: { version: string; cwd: string }
    ): string => `cd "${cwd}" && npm exec --yes -- pnpm@${version} install`
    ```
    The choice is fixed: **`npm exec --yes -- pnpm@<version> install`**. The reasoning is that the supported runtime is Node 22+, which always has corepack *or* npm; `npm exec` is the one bootstrap that works on every supported Node without probing, without requiring corepack, and without depending on whatever pnpm happens to be on the user's `PATH`. The `version` is read from the generated project's `packageManager` field by `readGeneratedPnpmVersion(state.input.dir)` (the same call the live install path makes). If the field is missing or malformed, the recovery command is `<install command unavailable: see JSON error>` and the `recovery: null` field is set. We do not try to use `corepack pnpm install` or `pnpm install` in the recovery, because the no-install path is offline and cannot tell which bootstrap is on the user's `PATH`.
- `apps/create-deesse-app/test/unit/pipeline-install-failure.test.ts`: a new sub-case for `--no-install: true` asserts the install spawn is **not** called, the warning is not emitted, the recovery field is exactly `cd "<dir>" && npm exec --yes -- pnpm@<version> install` (with the version from the generated project's `packageManager` field), and the result has `installed: false`. The test uses a runner stub for `probeInstallPrereqs` that asserts the runner is **never** called. A second sub-case covers a generated project with no `packageManager` field and asserts `recovery: null`.

Why this step fourth: this is the constraint the reviewer called out twice. It is small and self-contained once Step 2 is in place.

### Step 5 — e2e smoke for real `npx` invocation

`apps/create-deesse-app/test/e2e/application-generation.test.ts`, `apps/create-deesse-app/test/e2e/support/consumer-stack.ts`

- `apps/create-deesse-app/test/e2e/support/consumer-stack.ts` adds:
  ```ts
  export const withFreshCorepackHome = (
    consumer: StartedTestContainer,
    body: (env: { COREPACK_HOME: string }) => Promise<void>,

  ```
  Instead of trying to find and clear corepack's cache path (which is platform-dependent and version-dependent), the helper sets `COREPACK_HOME` to a fresh empty directory under `/tmp/cda-corepack-<random>/` for the duration of `body`, then deletes the directory. - `apps/create-deesse-app/test/e2e/application-generation.test.ts` adds a child case:
  1. Run the test inside `withFreshCorepackHome(consumer.container, ...)` so corepack's cache is empty for the test.
  2. Invoke the binary via the `npx` shim on the consumer image (a new `runViaNpx` helper in `consumer-stack.ts`, parallel to `runViaDlx`, dispatches through `sh -c`).
  3. Assert: exit code 0, JSON result parseable, `recovery` field contains `corepack pnpm install` (because the consumer image ships corepack), warning line lands on stderr with the `installing dependencies via corepack` text, and the **install** of the generated project succeeds (asserted via `installed: true` in the JSON, **not** via the presence of `pnpm-lock.yaml`, which the template ships before install — the earlier draft used the lockfile as a proxy and was wrong). ## Risks / edge cases

- **Node 25 unbundles corepack.** The `npm exec -- pnpm@<version> install` fallback is the dedicated path for this case. The risk is that `npm exec` is itself deprecated or removed in some future npm major version. The fallback only depends on npm ≥ 7 (Node 16+), and npm has no announced deprecation of `npm exec` as of the spec's authoring. If it ever does, the next fallback is to shell out to `npx --yes pnpm@<version> <args>`, which is morally equivalent.
- **No corepack and no npm on `PATH` (extreme edge case).** A user on a stripped Node install where both `corepack` and `npm` are missing is a rare configuration. The recovery field on `--no-install` is `npm exec --yes -- pnpm@<version> install`, which depends on npm. If the user has no npm, the recovery command will fail with the standard `command not found` for npm itself; the error message is clear enough to point the user at installing npm first. The unit test for `pickInstallStrategy` covers the all-false case and throws `unsupported_manager` with a hint that names three manual-install paths.

- **Corepack removed from Node 25+.** The npm-exec fallback is the dedicated path for this case. The risk is that `npm exec` is itself deprecated or removed in some future npm major version. The fallback only depends on npm ≥ 7 (Node 16+), and npm has no announced deprecation of `npm exec` as of the spec's authoring. If it ever does, the next fallback is to shell out to `npx --yes pnpm@<version> <args>`, which is morally equivalent.

- **PATH ordering on Linux.** `corepack pnpm install` resolves the binary itself. The npm-exec and pnpm-direct branches use the absolute path through `sh -c`'s `PATH`. No private cache paths are ever read.
- **Windows shim extension.** `where corepack` on Windows uses `PATHEXT` correctly. `where npm` and `where pnpm` follow the same rule. The test for the Windows branch is a docstring-documented expectation, not a CI-run unit test (CI runs Linux). A follow-up issue can run the test on a Windows runner.
- **`packageManager` field in the generated project.** Today the saas-template ships `pnpm@11.0.0` at the root `package.json`. We do not need to set it; the field is already there. If the field is missing or malformed in a future template revision, `readGeneratedPnpmVersion` throws `source_failed` (the same error code the template-extraction step throws for a missing `package.json`), and the install does not run. The recovery field is `null` in that case; the user is told to add a `packageManager` field to the template. There is no silent fallback to a hardcoded version.
- **`npm exec` requires npm ≥ 7.** npm 7+ ships with Node 16+. The package's `engines.node: ">=22.13.0"` covers every supported Node, and every supported Node has npm ≥ 9. The fallback is safe.
- **E2e cost.** The new tests run the full install (60–120 s each). The total e2e time on the consumer e2e job is bounded by the existing `timeout-minutes: 45` budget. The four existing tests plus the two new ones fit; if the budget becomes tight, a follow-up issue can split the consumer e2e job into a corepack and a no-corepack variant.
- **Cache-isolation side effects.** `withFreshCorepackHome` redirects `COREPACK_HOME` to a fresh empty directory under `/tmp` for the duration of `body`, then deletes the directory. The consumer is ephemeral, so the redirect and the deletion are safe. The redirect happens only inside the new corepack-path e2e test's `beforeAll`, not in the existing `pnpm dlx` test. The two tests are isolated: the existing pnpm-dlx test bootstraps pnpm once at consumer startup and does not redirect `COREPACK_HOME`, so its behavior is unchanged.
- **`unsupported_manager` still throws if all three prereqs are missing.** The recovery hint names three manual-install paths. This is acceptable for the rare case (a user with a stripped Node install and no global package manager). The unit test in `install-strategy.test.ts` covers this branch.

## Out of scope (explicit)

- Converting the saas-template to an npm project.
- A `--package-manager npm|pnpm` flag.
- A `npm` row in the `PackageManager` enum.
- Changes to the generated `package.json` or `pnpm-lock.yaml`.
- A `bun add` or `yarn add` install path.
- A `Bun` or `Yarn` invoker detection. The CLI does not need to know how it was launched; the install path is decided by the prereq probes alone.
- An `invokedVia` field in the result JSON. The install path is reported via the `recovery` field, which is what tools and humans need.
- A self-hosted runner. The e2e runs on `ubuntu-latest`, the same runner the existing consumer e2e uses.
- Running the e2e on a Windows runner. The Windows probe is documented in the code; CI validates the Linux path.
