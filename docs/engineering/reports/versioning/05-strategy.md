# 5. Senior release pattern (revised)

[← Index](README.md) · **Prev: [04-prereleases.md](04-prereleases.md)** · **Next: [06-implementation-specs.md](06-implementation-specs.md)**

## 5.1 The rule

**Contributors add a changeset if (and only if) their PR changes `@deessejs/cli`'s public surface.** That's the entire maintainer-facing rule. Everything else flows from there.

## 5.2 Architecture overview

**One source of truth, one workflow, one mental model.**

- **Source of truth**: changesets (`.changeset/<feature>.md` files in PRs touching `apps/cli/**`)
- **Workflow**: `.github/workflows/release.yml` (a rewrite of the existing one)
- **Versioned artifact**: only `@deessejs/cli`. No root version. No `template/v*` tags.
- **Publish mechanism**: npm trusted publisher (OIDC) + provenance
- **Output**: `@deessejs/cli@x.y.z` on npm + `release/v{x.y.z}` git tag + GitHub Release

Why this is the senior pattern:

- **One thing to remember** (changeset if you change the CLI). Compare with the dual-flow draft where the maintainer also had to know about root VERSION bumps, separate workflows, and cross-coupled commit-message filters.
- **One place to look** (the single workflow file). No "Flow A vs Flow B" mental model.
- **Edge cases reuse the same primitives.** A hotfix is a PR with a `patch` changeset (same path as any release). A yank uses `npm unpublish` or `npm deprecate` (manual because it requires judgment).

## 5.3 What this pattern deliberately does NOT do

- **No root versioning.** Root has no `version`, no `VERSION` file, no `template/v*` tag, no root `CHANGELOG.md`. Repo-level metadata for Vercel/deploy/tracking uses git commit hashes.
- **No dual workflow.** No separate `release.yml` + `publish-cli.yml`. One workflow does bump + publish + tag.
- **No `.changeset` filter cascading.** The `.changeset` substring in the commit message is the one and only filter; it's the convention for "this commit consumed changesets."
- **No manual intermediate steps.** After the staging → main promotion (per AGENTS.md), the workflow fires automatically.

## 5.4 Three layers (unchanged from earlier analysis)

### Layer 1: Internal only (`packages/*`)

- Every `packages/*` is already `"private": true` (verified). No change needed.
- Optionally set `privatePackages: { version: false, tag: false }` in `.changeset/config.json` to suppress the version bump changesets applies by default to private packages. Cosmetic.
- Versions remain arbitrary 0.0.x / 0.1.x. Hand-bumped when needed.

### Layer 2: Public npm (`@deessejs/cli`)

- `private: false` (currently `true`).
- `publishConfig: { access: "public", provenance: true }`.
- `license` (`MIT`, matches upstream saas-template).
- `repository`, `keywords`, `module`, `types` entrypoints.
- Real SemVer via changesets: every PR that changes the CLI adds a `.changeset/<feature>.md`.
- `apps/cli/CHANGELOG.md` auto-generated by changesets on every release.
- npm provenance (triple belt: `publishConfig.provenance`, `--provenance` flag, `NPM_CONFIG_PROVENANCE=true` env var).
- Trusted publisher configured on npmjs.com (one-time setup).

### Layer 3: Apps (`apps/app`, `apps/web`, `apps/docs`)

- Already `private: true`. No change.
- Versions are arbitrary. Hand-bumped if/when needed.

## 5.5 The single workflow (high level)

`release.yml` runs on push to `main`:

1. Gate on commit message containing `.changeset` OR `workflow_dispatch`.
2. `pnpm install --frozen-lockfile`.
3. `pnpm changeset version` → bumps `apps/cli/package.json#version`, regenerates `apps/cli/CHANGELOG.md`, commits the version bump.
4. `pnpm changeset publish --provenance --access public` → publishes the bumped `@deessejs/cli` to npm via OIDC.
5. `git tag -f release/v{VERSION}` based on `apps/cli/package.json#version`.
6. `gh release create release/v{VERSION} --generate-notes` for the GitHub Release.

Concrete YAML in [06-implementation-specs.md §6.3](06-implementation-specs.md#63-release-workflow-proposed).

## 5.6 Why drop root versioning?

Three reasons:

1. **No consumer cares.** Vercel deploy metadata, divergence tracking with upstream, GitHub Release notes: none of these need a stamped version number on the repository itself. Git commit hashes + the `release/v*` tag history cover what they need.
2. **It was the wart.** In the dual-flow draft, root needed to bump separately because changesets ignores `private` packages by default. That meant either a manual bump on the first release or a custom config: both complexity the senior pattern doesn't pay for.
3. **It was an artifact.** Root versioning existed because the upstream `deessejs/saas-template` has it (and that template publishes itself). We're a fork, not the upstream; we don't need to inherit every ritual.

## 5.7 What about the GitHub Release notes?

The senior pattern creates one GitHub Release per `@deessejs/cli` release. The release body is auto-generated from commits (`gh release create --generate-notes`). For consumers wanting more detail, `apps/cli/CHANGELOG.md` (auto-generated by `@changesets/changelog-git`) has the curated list of changes per version, same content as before, just under `apps/cli/` where it belongs.

## 5.8 Edge cases

### Hotfix

A critical CLI bug → PR with a changeset using `"@deessejs/cli": patch`. Fast-track the staging → main promotion. The same workflow runs and publishes the patch.

### Yanking a version

`npm unpublish @deessejs/cli@x.y.z` within 72 hours of publish (npm policy). `npm deprecate @deessejs/cli@x.y.z "..."` after 72 hours. Records the yank in the next release notes. **Manual because it requires judgment.**

### Workflow broken

`pnpm --filter @deessejs/cli build && pnpm --filter @deessejs/cli publish --provenance --access public --no-git-checks` from a maintainer's machine. Provenance will fail outside GitHub Actions, expected. Document the failed workflow run as an issue to fix.

### Adding a new template

Server-side change. Touches `packages/api/src/templates.ts` (or a future DB table). **No CLI change, no changeset, no release.** See [11-templates-not-cli.md](11-templates-not-cli.md).

## 5.9 What the maintainer has to remember (post-implementation)

Exactly one thing:

> *"My PR changes the CLI's public surface (new command, new flag, behavior change, breaking change)? Add a `.changeset/<name>.md` with the bump type. CI verifies; the rest is automatic."*

That's the senior pattern. Anything else the maintainer encounters (a hotfix, a yank, a broken CI run) is a special case handled by the same primitives, not a separate discipline.

## 5.10 What gets deleted compared to the dual-flow draft

| Before (dual flow) | After (senior pattern) |
|---|---|
| `release.yml` handles root VERSION bumps | Root versioning dropped |
| `publish-cli.yml` separate workflow | Subsumed into `release.yml` |
| Filter A: `.changeset` (Flow A) + Filter B: `template/v` (Flow B) | One filter: `.changeset` |
| Tag prefix `template/v*` | Tag prefix `release/v*` |
| Manual root VERSION bump on first release | No root to bump |
| Two workflows to maintain | One workflow to maintain |
| Two CHANGELOG.md (root + apps/cli) | One CHANGELOG.md (apps/cli) |
| Cross-coupled staging-first dance | Same staging-first (per AGENTS.md), but downstream is one workflow |
